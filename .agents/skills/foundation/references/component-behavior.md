# 컴포넌트 구축: 동작 조달

컴포넌트는 두 단면으로 이루어진다: **동작(behavior)** 과 **표현(presentation)**.
이 파일은 *동작*을 바퀴 재발명 없이 어디서 가져올지를 다룬다(표현은 토큰을
그 위에 입히는 일이다). 동작 조달은 두 granularity로 나뉘며 — 둘은 별개 단계가
아니라 *같은 일의 두 단위*다:

- **파트 A — 위젯 단위: 헤드리스 UI 프리미티브.** Dialog / Combobox / Menu /
  DatePicker 같은 *하나의 위젯* 전체.
- **파트 B — 조각 단위: 헤드리스 유틸리티 (CDK 대응).** 여러 위젯에 걸쳐 재사용되는
  로직 전용 역량(포지셔닝, 가상화, 드래그, 포커스 트랩, 날짜 연산).

> **추천하기 전에 검증하세요.** 아래 라이브러리 이름들은 출발점 지도이지, 기억에서
> 반복할 순위가 아닙니다. 프론트엔드 생태계는 월 단위로 바뀝니다 — 추천을 확정하기
> 전에 후보의 최신 릴리스 날짜, 오픈 이슈/PR 건강도, 프레임워크 버전 호환성을 웹
> 검색하세요.

운영 전제 (장황한 설명 대신 짧게):

- **헤드리스 = 스타일이 없다는 뜻이지 동작/UI가 없다는 뜻이 아니다.** 위젯
  프리미티브는 상태·포커스·키보드·ARIA를 이미 품고, **스타일 없는 맨 박스**를
  그린다. 표현(모양)은 별개 — 토큰을 그 위에 입히는 일이며, shadcn 경로를
  고르면 그 표현이 딸려 와 *우리 토큰으로 다시 칠하기만* 하면 된다.
- **위젯이냐, 위젯의 재료냐가 파트 A/B를 가른다.** 위젯 단위(파트 A)는 하나의
  인터랙션 패턴을 모델링하고, 조각 단위(파트 B)는 여러 위젯이 공유하는 횡단 역량이다.
  중복하지 마라: 채택한 위젯 프리미티브가 이미 포커스 트랩/scroll-lock/포지셔닝을
  포함하면 같은 일을 하는 조각 라이브러리를 또 더하지 마라.

## 목차

**파트 A — 위젯 단위**
1. 두 가지 소비 모델 (설치형 vs. 복사형)
2. 크로스 프레임워크 옵션
3. 프레임워크별 매트릭스 (React, Vue, Svelte, Angular, Solid, Web Components)
4. 구축 vs. 채택 결정
5. shadcn 스타일: 실제로 무엇인가
6. 의견 키트는 기본 경로에서 제외 (Material / daisyUI / PrimeNG …)

**파트 B — 조각 단위**
7. Angular은 다르다: CDK가 이미 대부분을 번들한다
8. 역량 → 라이브러리 매핑 (비-Angular)
9. 조각 단위를 사용하는 방법
10. 커스텀이 정당화되는 경우

# 파트 A — 위젯 단위: 헤드리스 UI 프리미티브

목표: 접근성 있고 인터랙티브한 컴포넌트 *로직*(Dialog, Combobox, Menu, Select,
Tabs, Tooltip, DatePicker 등)을 위젯 단위로 어떻게 확보할지 결정하는 것 —
유지보수되는 헤드리스 라이브러리를 채택하거나, 그 위에 스타일이 입혀진 "shadcn
스타일" 계층을 채택하거나, 프리미티브를 직접 구축하는 것 중에서.

> 단위는 "하나의 위젯"이다. 마크업까지 그려주는 것(Radix, Ark UI, Reka UI, Bits
> UI)과 동작/훅만 주는 것(React Aria 훅, Downshift, Melt UI builder)의 차이는 이
> 단위 안의 세부일 뿐 — 둘 다 위젯 단위 조달이다.

## 1. 두 가지 소비 모델

- **설치형 프리미티브 패키지** — 헤드리스 라이브러리를 `npm install`하고 그
  스타일이 없는 컴포넌트를 조합합니다; 업그레이드는 패키지를 통해 도착합니다.
  유지보수를 대신 처리받고 싶을 때 최선입니다.
- **복사형 / "당신이 코드를 소유한다"** (shadcn 모델) — CLI가 스타일이 입혀진
  컴포넌트 *소스*를 당신의 저장소에 복사하며, 이는 하부의 프리미티브 패키지 위에
  구축됩니다. 완전한 제어와 무거운 커스터마이징을 원하고, 복사된 파일의 유지보수를
  소유하는 것을 수용할 때 최선입니다.

이 둘은 상호 배타적이지 않습니다: 복사형 계층도 여전히 `node_modules` 안에 그 하부의
헤드리스 프리미티브 패키지를 가집니다.

## 2. 크로스 프레임워크 옵션 (하나의 로직 코어, 여러 프레임워크)

조직이 **여러 프레임워크**를 운영하고 *동일한* 컴포넌트 동작을 어디서나 원한다면,
두드러지는 것은 **Zag.js** 상태 머신 위에 구축된 **Ark UI**입니다. 이는 하나의
유한 상태 머신 코어로부터 React, Vue, Solid, Svelte에 걸쳐 동일한 컴포넌트 API를
제공하며, ~40개 이상의 스타일 없는 접근성 컴포넌트를 갖추고 있습니다. **Park UI**는
Ark UI 위에 스타일이 입혀진 (shadcn 같은) 계층입니다. "스택 간 일관된 동작"이
"프레임워크별 가장 관용적인 API"보다 우선할 때 이것을 선택하세요.

컴포넌트 래퍼 없는 순수 로직만의 상태 머신을 원한다면, **Zag.js** 그 자체가 더
저수준 프리미티브입니다.

## 3. 프레임워크별 매트릭스

### React / Next.js / Remix
- **Base UI** — 활발히 유지보수되는 프리미티브 계층 (MUI 팀 제작); Radix의 인수
  이후 속도가 둔화되면서 사실상의 표준이 되었습니다. 설치형 프리미티브를 원하는
  새 React 프로젝트의 좋은 기본값.
- **React Aria (Components)** — Adobe의 접근성 우선 프리미티브; 컴포넌트당 더 많은
  코드를 대가로 가장 깊은 a11y와 i18n 스토리를 제공합니다. 접근성/국제화가 강한
  요구사항일 때 최선.
- **Radix UI** — 여전히 극도로 널리 사용됨 (특히 shadcn/ui의 하부 계층으로),
  하지만 새 작업을 여기에 걸기 전에 현재 유지보수 상태를 확인하세요.
- **Headless UI** (Tailwind Labs) — 작음 (~10개 컴포넌트), Tailwind 우선,
  초보자 친화적; 단순한 요구에는 괜찮으나 복잡한 것에는 제한적.
- **shadcn/ui** — 지배적인 *복사형 스타일* 계층; 기본적으로 Radix 위에 구축되며,
  최근 버전에서는 Base UI를 프리미티브 계층으로 선택할 수 있습니다.

### Vue / Nuxt
- **Reka UI** — Vue를 위한 활발히 유지보수되는 프리미티브 라이브러리 (구 Radix
  Vue의 진화형); 표준 헤드리스 선택지.
- **shadcn-vue** — Reka UI 위에 구축된 Vue용 복사형 스타일 계층.
- **Headless UI (Vue)** — Tailwind Labs의 작은 세트, Vue 빌드.
- **Ark UI (Vue)** — 스택 간 일관성이 중요할 때의 크로스 프레임워크 옵션.

### Svelte / SvelteKit
- **Bits UI** — 인체공학적 컴포넌트 API를 가진 헤드리스 컴포넌트 프리미티브
  (Radix 같은); Svelte 5의 강력한 기본값.
- **Melt UI** — 더 저수준 "builder" API (요소에 펼쳐 넣는 속성을 반환하는 함수);
  최대한의 제어, 더 많은 의례. Svelte 5 / runes 마이그레이션 상태에 유의하세요 —
  확정 전에 검증하세요.
- **shadcn-svelte** — Svelte용 복사형 스타일 계층.
- **Ark UI (Svelte)** — 크로스 프레임워크 옵션.

### Angular
Angular의 스토리는 독특한데, **CDK**(파트 B 참고)가 이미 어려운 인터랙션/a11y 배관
작업의 상당 부분을 제공하기 때문입니다:
- **Angular CDK** (`@angular/cdk`) — 공식적이고 실전에서 검증된 동작들(overlay,
  a11y, portal, drag-drop 등)을 당신의 컴포넌트에 조합합니다. 이것이 Angular의
  네이티브 "헤드리스 유틸리티" 계층입니다.
- **Spartan (`spartan/ui`)** — 사실상의 "Angular용 shadcn." **brain**(CDK 위에
  구축된 스타일 없는 접근성 프리미티브)과 **helm**(복사해 넣는 Tailwind 스타일)로
  나뉩니다. shadcn 워크플로에 가장 가깝습니다.
- **Radix NG (Radix Angular Primitives)** — Radix 프리미티브의 Angular 포팅.
- **Angular Aria** — Angular의 더 새로운 공식 ARIA 프리미티브 노력; 사용 시점의
  성숙도/커버리지를 확인하세요.
- 더 새로운 진입자들(예: Semantic Components, Zard)이 존재합니다 — 채택 전
  유지보수를 평가하세요.
- 더 무거운 스타일 입혀진 **의견 키트**(Angular Material, PrimeNG, ng-zorro)는
  아래 §6 "의견 키트는 기본 경로에서 제외"를 보세요 — 자체 디자인 언어를 소유하려는
  이 워크플로와 충돌합니다.

### Solid / SolidStart
- **Kobalte** — Solid를 위한 확립된 헤드리스 프리미티브 라이브러리.
- **Ark UI (Solid)** — 크로스 프레임워크 옵션.

### 프레임워크 비종속 / Web Components
- **Zag.js**(로직)와 Web-Component 기반 라이브러리는 프리미티브가 어디서나
  작동하게 합니다. 여러 앱 프레임워크를 지원해야 하는 디자인 시스템에 유용합니다.

## 4. 구축 vs. 채택 결정

기본적으로 유지보수되는 라이브러리를 채택하세요. 다음의 경우에만 커스텀을
구축하세요:
- 요구사항이 진정으로 비범하고 적합한 유지보수 프리미티브가 없을 때, **또는**
- "컴포넌트"가 사소하고 실제로는 프리미티브가 아닐 때 (스타일이 입혀진 button,
  badge, card는 상태 머신이 아니라 토큰 + 마크업이 필요함), **또는**
- 강한 제약(번들, 라이선싱, 무의존성 정책)이 있을 때.

만약 프리미티브를 직접 구축한다면, 그래도 접근성을 처음부터 손수 만들기보다는
어려운 부분 — 포지셔닝, 포커스 트래핑, 리스트 키보드 네비게이션 — 에는 **조각 단위
유틸리티**(파트 B)에 기대세요.

유용한 리트머스 시험: *"여기서 키보드 인터랙션, 포커스 순서, ARIA를 올바르게
만드는 데 반나절 이상 걸릴까?"* 그렇다면 채택하세요; 다시 만들지 마세요.

## 5. shadcn 스타일: 실제로 무엇인가

shadcn/ui(그리고 그 포팅: shadcn-vue, shadcn-svelte, Angular용 Spartan, Ark용
Park UI)는 **컴포넌트 의존성이 아닙니다.** 이것은 CLI + 하부의 헤드리스 프리미티브
위에 구축된 스타일이 입혀진 소스 파일 세트로, 당신이 소유하고 커스터마이징하도록
저장소에 복사됩니다. 이는 Tailwind + CSS variables를 가정하며, 이는
`design-tokens.md`의 토큰 파이프라인과 맞물립니다(복사된 컴포넌트가 당신의 semantic
토큰을 읽습니다). 팀이 shadcn의 미학 *그리고* 완전한 제어를 원할 때 추천하세요;
컴포넌트 소스를 소유하고 싶지 않다면 설치형 프리미티브를 추천하세요.

## 6. 의견 키트는 기본 경로에서 제외

**의견 있는 키트**(Angular Material, PrimeNG, ng-zorro, MUI, daisyUI, Bootstrap
등)는 동작 + 표현 + *그들의 디자인 의견*을 한 번에 가져옵니다. 헤드리스/shadcn
경로가 동작만(또는 동작 + 다시 칠할 수 있는 표현) 가져오는 것과 달리, 의견 키트는
색·타이포·반경·밀도에 대한 자기 결정을 함께 들고 와 **설계한 자체 토큰과
브랜드를 상당 부분 덮어씁니다.** 자체 디자인 언어를 정밀하게 소유하려는 이 워크플로의
목적과 정면으로 충돌합니다.

따라서 **기본 경로에서 제외하되, 조용히 빼지 마세요.** 사용자가 "왜 Material을 안
쓰나"라고 물을 수 있으니, 기각 사유를 ADR에 명시하세요(빠른 출시를 위해 브랜드
정밀도와 커스터마이징 자유를 포기하는 팀에는 합리적일 수 있으나 — 그 트레이드오프를
의식적으로 골라야 합니다). 의견 키트가 *이미* 도입된 기존 프로젝트라면, 그 위에 자체
토큰을 강제하느라 싸우기보다 키트의 테마 시스템을 따르는 편이 나을 수 있다는 점도
함께 기록하세요.

# 파트 B — 조각 단위: 헤드리스 유틸리티 (CDK 대응)

이들은 자체 UI가 없는 **로직만의** 라이브러리입니다: 포지셔닝, 가상 스크롤링,
드래그 앤 드롭, 포커스 관리, 날짜/숫자 i18n, 옵저버, 클립보드. 위젯 단위
프리미티브(파트 A)가 여러 위젯에 걸쳐 재사용하는 **조각 단위 역량**이다. Angular
사용자는 이 카테고리를 **CDK**(Component Dev Kit)라고 부르고, 일반적인 이름은
**헤드리스 유틸리티** 또는 **인터랙션 프리미티브**입니다. 지침 규칙: 이 문제들은
미묘하고 보안/접근성에 민감합니다 — **유지보수되는 오픈소스를 채택하고, 손수 만들지
마세요.**

## 7. Angular은 다릅니다: CDK가 이미 대부분을 번들합니다

`@angular/cdk`는 다른 프레임워크들이 별개의 라이브러리들로 조립하는 것 대부분을
하나의 유지보수되는 패키지로 제공합니다: **Overlay**(포지셔닝된 플로팅 패널),
**A11y**(focus trap, focus monitor, live announcer, list key-manager),
**Portal**, **Drag and Drop**, **Scrolling**(virtual scroll), **Layout**
(breakpoint observer), **Clipboard**, **Stepper**, **Table**, **Text-field
autosize**. Angular 프로젝트에서는 CDK를 먼저 손에 잡고, 그것이 결여한 것에
대해서만 외부 라이브러리를 추가하세요. Spartan의 "brain" 프리미티브는 CDK 위에
구축되므로, 위젯 단위(파트 A)와 깔끔하게 조합됩니다.

다른 모든 프레임워크에서는 아래의 역량별 라이브러리를 조합하세요.

## 8. 역량 → 라이브러리 매핑 (비-Angular)

이들 대부분은 **프레임워크 비종속 코어**(순수 JS/DOM)와 얇은 프레임워크 바인딩을
가지며, 이것이 이상적입니다: 그 지식이 프로젝트 간에 전이됩니다.

| 역량 | 프레임워크 비종속 코어 | 비고 / 바인딩 |
| --- | --- | --- |
| **Overlay 포지셔닝** (툴팁, 팝오버, 메뉴, 드롭다운: anchor, flip, shift, collision) | **Floating UI** | 코어는 바닐라; React는 `@floating-ui/react`를 통해, 추가로 Vue/Svelte 바인딩. 포지셔닝의 표준. |
| **가상화** (거대한 리스트/그리드에서 보이는 행만 렌더링) | **TanStack Virtual** | 하나의 헤드리스 코어, 공식 React/Vue/Svelte/Solid 어댑터. |
| **드래그 앤 드롭** (정렬 가능한 리스트, 칸반, 재정렬) | **Pragmatic drag-and-drop** (Atlassian)은 프레임워크 비종속; **dnd-kit**은 React 중심 | 크로스 스택은 비종속 코어를; React 인체공학은 dnd-kit을 선택. |
| **포커스 트랩** (포커스를 모달 안에 유지) | **focus-trap** | 바닐라 코어; 유지보수되는 Dialog 프리미티브를 사용하면 보통 이미 처리됨. |
| **캐러셀 / 슬라이더** | **Embla Carousel** | React/Vue/Svelte/Solid 래퍼를 가진 프레임워크 비종속 코어. |
| **날짜 / 시간 / 숫자 i18n & 연산** | **@internationalized/date** (+ Intl API) | 로케일에 맞는 날짜 로직; date-picker 프리미티브와 짝을 이룸. |
| **커맨드 팔레트 / 퍼지 검색** | **cmdk** (React) / 퍼지는 **Fuse.js**를 통해 (비종속) | list/combobox 프리미티브와 결합. |
| **옵저버** (resize, intersection, mutation) | 네이티브 `ResizeObserver` / `IntersectionObserver` | 얇은 프레임워크 훅; 라이브러리가 거의 필요 없음. |
| **클립보드, focus-visible, scroll-lock** | 작은 단일 목적 라이브러리 또는 네이티브 | 많은 프리미티브 라이브러리가 이미 Dialog와 함께 scroll-lock을 포함함. |

## 9. 조각 단위를 사용하는 방법

1. 위젯 목록(파트 A)에서 *로직만의* 필요를 도출하세요.
   (Select는 포지셔닝이 필요하고; 긴 결과 리스트는 가상화가 필요하며; 정렬 가능한
   설정 리스트는 드래그 앤 드롭이 필요하고; bottom sheet는 포커스 트랩 + scroll
   lock이 필요합니다.)
2. Angular는 CDK를 먼저 확인하고; 그 외에는 각 필요를 위의 유지보수되는
   라이브러리에 매핑하세요.
3. 동일한 멘탈 모델이 조직의 스택들에 걸쳐 이어지도록 **프레임워크 비종속 코어**를
   선호하세요.
4. 중복하지 마세요: 선택한 위젯 프리미티브(파트 A)가 그 Dialog/Popover에 대해
   이미 포지셔닝/포커스 트랩/scroll-lock을 포함한다면, 같은 작업을 위한 경쟁
   라이브러리를 추가로 더하지 마세요.
5. 각 추가를 사용자와 확인한 다음, 그 세트를 ADR로 기록하세요.

## 10. 커스텀이 정당화되는 경우

동작 유틸리티를 직접 구축하는 것은 그것이 진정으로 사소할 때(예: `matchMedia`를
감싸는 얇은 `useMediaQuery`/breakpoint 훅)나 실제 제약에 대해 유지보수되는 옵션이
없을 때만 하세요. 포커스 순서, ARIA, 또는 포인터/키보드 엣지 케이스를 건드리는
무엇이든 유지보수되는 라이브러리에서 와야 합니다 — 그것들을 틀리게 만드는 것은
스타일 흠집이 아니라 접근성 퇴행입니다.

의견 키트 기각 사유, 그리고 그 이유)을 ADR로 기록하세요.
