# 라우팅 의사결정 가이드 (정체성 vs 표현)

> **이 문서의 위치**
> `responsive-app` SKILL 1장(결정 프레임)의 전문 근거다. SKILL 본문은 두 축과 결정 절차만 응축해
> 담고, 라우티드 모달·멀티스텝 흐름·모핑 판단 같은 패턴별 상세는 여기서 본다.
> "어떤 UI를 모달·시트·페이지·드롭다운 중 무엇으로 띄울 것인가", "URL(라우트)을 줄 것인가",
> "데스크탑과 모바일에서 어떻게 다르게 표현할 것인가"를 결정하기 위한 프레임워크다.
> 특정 프레임워크에 종속되지 않는 **원칙**을 먼저 제시하고, 필요한 곳에만 프레임워크별 구현 예시를 붙인다.

---

## 0. TL;DR — 한 문장 규칙

> **먼저 묻는다: "이 화면이 주소창(URL)에 남아야 하는가?"**
> - **Yes** → 표현(모달이든 페이지든)과 무관하게 **실제 라우트를 준다.**
> - **No** → 콘텐츠 무게에 맞는 **오버레이**를 고르고, 표현은 플랫폼 관용을 따르되 **공유되는 것은 UI 껍데기가 아니라 로직·데이터·동작이다.**

---

## 1. 관통 원칙: 두 개의 독립된 축

의사결정에서 가장 흔한 실수는 아래 두 가지를 하나로 묶어 판단하는 것이다. **이 둘은 직교(independent)한다.**

| 축 | 질문 | 값의 예 |
|---|---|---|
| **정체성 (Identity)** | 이것은 *무엇*인가? | 목적지(destination) ↔ 일시적 오버레이(transient overlay) |
| **표현 (Presentation)** | 이것을 *어떻게* 보여주는가? | 인라인 · 팝오버 · 액션시트 · 바텀시트 · 풀스크린 다이얼로그 · 페이지 |

**핵심 규칙: 표현이 정체성을 결정하게 두지 마라.**
"모달이니까 URL이 없어도 된다"거나 "모바일이니까 페이지여야 한다"는 판단은 이 두 축을 혼동한 것이다. URL 유무는 오직 **정체성 축**이 결정하고, 모달/페이지 여부는 **표현 축**의 문제다. 같은 정체성을 플랫폼·화면 크기에 따라 다른 표현으로 렌더할 수 있다.

---

## 2. 핵심 멘탈 모델 3가지

### 2.1. 판단 축은 "모바일 vs 데스크탑"이 아니라 "목적지 vs 일시적 오버레이"다

**목적지(destination)의 판별 조건 — 하나라도 Yes면 목적지다:**
- 이 화면에 **직접 링크로 진입**(공유 URL, 새 탭, 북마크)하는 것이 의미 있는가?
- **새로고침**해도 이 화면이 유지되어야 하는가?
- **뒤로가기**로 이 화면을 빠져나가는 것이 사용자에게 자연스러운가?

→ 목적지라면 **모든 브레이크포인트에서 URL(라우트)을 부여**한다. 데스크탑이라고 URL이 불필요한 것이 아니다.

**일시적 오버레이(transient overlay):**
- 선행 화면에 **종속적**이고, 잠깐 떴다 사라지는 임시 액션(확인 다이얼로그, 선택 메뉴, 값 선택 등).
- URL 불필요. 모바일에서 풀스크린/바텀시트로 키우더라도 여전히 오버레이다.

### 2.2. 이분법이 아니라 "무게의 스펙트럼"이다

콘텐츠의 무게와 플랫폼 관용에 따라 왼쪽(가벼움) → 오른쪽(무거움)으로 이동한다:

```
인라인 → 팝오버 → 액션시트 → 바텀시트(시트 모달) → 풀스크린 다이얼로그 → 라우티드 페이지
 가벼움 ─────────────────────────────────────────────────────────────► 무거움
                                                          (오른쪽 끝만 URL 보유)
```

- 데스크탑은 대체로 스펙트럼의 왼쪽(팝오버/다이얼로그)을 선호.
- 모바일은 같은 콘텐츠라도 한 칸 오른쪽(바텀시트/풀스크린)이 관용적인 경우가 많음.
- **URL 경계선은 "라우티드 페이지"에서 그어지지만, 라우티드 모달(4.3)처럼 오버레이 표현에 URL을 결합하는 하이브리드도 있다.**

### 2.3. 공유하는 것은 UI 껍데기가 아니라 로직·데이터·동작이다

플랫폼별로 표현이 갈릴 때, **단일 소스(single source of truth)로 유지해야 하는 것**:
- 선택지/항목 **정의**(예: 액션 목록)
- **액션 핸들러**(선택 시 무슨 일이 일어나는가)
- 컴포넌트의 **동작·상태·접근성 로직**

→ 이 원칙의 구현형이 **헤드리스 코어(headless core) + 표현 레이어(presentation layer)** 구조다(6장 참조). 표현은 플랫폼마다 갈아끼우되, 그 안의 동작과 데이터는 한 곳에서 온다.

## 3. 의사결정 절차 (에이전트가 그대로 적용 가능)

```
[1] 이 화면이 목적지인가? (2.1의 3가지 조건 중 하나라도 Yes)
      │
      ├─ Yes → 라우트(URL)를 부여한다.
      │         └─ 표현을 반응형으로: 데스크탑=다이얼로그/모달, 모바일=풀스크린.
      │            └─ 목록에서 진입 시 모달, 직접 진입 시 풀페이지가 필요하면 → "라우티드 모달"(4.3)
      │
      └─ No → 일시적 오버레이. URL 없음.
                └─ 콘텐츠 무게로 표현 결정:
                     - 단순 텍스트 액션 목록(≤6, 단일) → 액션시트(모바일)/팝오버·다이얼로그(데스크탑)
                     - 아이콘·설명·리치 레이아웃 → 바텀시트(모바일)/모달·팝오버(데스크탑)
                     - 옵션 많음/검색 필요/다중선택 → 풀스크린 피커 또는 모달
                └─ 진입점이 플랫폼마다 다르면(버튼 위치·종류가 다름) → 억지로 한 컴포넌트로 모핑하지 말 것.
                     별개 트리거 + 공유 로직(2.3)으로 구성.
```

## 4. 패턴별 플레이북

각 패턴은 **언제 / 왜 / 어떻게 / 함정** 순으로 정리한다.

### 4.1. 목적지의 반응형 표현 (모달 ↔ 풀페이지)

- **언제:** 상세 화면 등 목적지 성격의 콘텐츠를 데스크탑에선 모달로, 모바일에선 페이지처럼 보여주고 싶을 때.
- **왜:** "모바일=페이지, 데스크탑=모달"이라는 직감은 방향은 맞지만 기준이 어긋나 있다. 진짜 기준은 화면 크기가 아니라 **목적지 여부**다. 목적지면 데스크탑 모달조차 URL을 가져야 공유·뒤로가기·새로고침이 일관된다.
- **어떻게:** 목적지에 **정식 URL을 하나 부여**하고, *표현만* 반응형으로 분기한다(데스크탑=가운데 다이얼로그, 모바일=풀스크린). 대표 사례: 인스타그램/트위터의 사진 상세 — 데스크탑에선 모달이지만 자체 URL을 가지며, 직접 접속하면 풀페이지로 열린다.
- **함정:** 모달이라는 이유로 URL을 생략하면 목적지의 3조건이 전부 깨진다. 모달은 "보여주는 방식"일 뿐 URL 유무의 결정 요인이 아니다.

### 4.2. 일시적 오버레이의 반응형 표현

- **언제:** 확인 다이얼로그, 임시 편집, 종속적 액션 등 URL이 불필요한 화면.
- **왜:** 가벼운 오버레이를 모바일에서 풀스크린/바텀시트로 키우는 것은 변칙이 아니라 정석이다(모바일 화면 폭 제약 + 터치 도달성). Material Design도 모바일의 복잡한 폼/작업에는 **풀스크린 다이얼로그**를 명시적으로 권장한다.
- **어떻게:** 데스크탑=다이얼로그/팝오버, 모바일=풀스크린 또는 바텀시트. URL은 부여하지 않는다.
- **함정:** 반대로 일시적 액션에 굳이 라우팅을 붙이면 히스토리가 오염된다. 종속적·임시 화면은 오버레이로 둔다.

### 4.3. 라우티드 모달 (Routed Modal) / 인터셉팅 라우트

- **언제:** 목적지를 목록 위 모달로 띄우면서, 동시에 직접 진입 시 풀페이지가 되어야 할 때(4.1의 완성형).
- **왜:** URL은 하나여야 하지만, 도달 경로에 따라 표현이 달라져야 한다.
- **어떻게:**
  - 상세 화면에 정식 URL(`/photos/123`)을 둔다.
  - **목록에서 클릭 진입** → URL은 바뀌되 뒤 목록을 살려둔 채 그 위에 모달로 렌더.
  - **직접 진입(공유·새로고침·새 탭)** → 같은 URL을 풀페이지로 렌더.
- **필수 디테일:**
  - **배경 위치/상태 보존:** 모달을 띄울 때 뒤 목록의 스크롤·상태를 유지하고, 닫으면 정확히 그 자리로 복귀. (라우터 상태에 "background location"을 들고 다니는 패턴)
  - **뒤로가기 = 모달 닫기:** URL이 바뀌었으므로 뒤로가기 시 목록 URL로 돌아가며 모달이 닫혀야 한다.
  - **닫기 경로 수렴:** X 버튼 · 백드롭 클릭 · Esc · 뒤로가기 — 네 가지가 모두 "목록 URL로 복귀"라는 동일 결과로 수렴해야 꼬이지 않는다.
  - **직접 진입 fallback:** 뒤에 깔 목록이 없을 때는 모달이 아니라 풀페이지로 렌더하거나, 닫았을 때 갈 곳(예: 목록)을 정의해 둔다.
- **프레임워크 예시:** Next.js는 이를 **Parallel Routes + Intercepting Routes** 전용 기능으로 지원한다. 다른 프레임워크는 라우터 상태에 background location을 수동으로 얹어 구현한다.

### 4.4. 멀티스텝 흐름 (위저드/체크아웃/온보딩)

- **언제:** 여러 단계를 거치는 흐름(회원가입, 체크아웃, 온보딩).
- **왜(중요 — 흔한 오해 교정):** 각 스텝에 URL(정확히는 히스토리 엔트리)을 주는 이유는 "각 스텝이 공유용 목적지라서"가 **아니다.** 스텝은 보통 선행 단계에 종속적이라 독립 목적지가 아니며, 콜드 진입도 대개 무의미하다. 진짜 이유는:
  - **뒤로가기:** 흐름 전체가 URL 하나면 뒤로가기 시 흐름 밖으로 통째로 튕겨 나가고 입력이 날아간다. 스텝을 히스토리에 쌓으면 뒤로가기가 "이전 스텝"으로 동작한다.
  - **새로고침 복구:** 현재 스텝이 URL에 담겨 있어야 복구 처리가 가능하다.
  - **퍼널 분석:** 단계별 이탈률을 URL 단위로 추적.
- **어떻게(정확한 표현):** "각 스텝 = 독립 URL"이 아니라 **"흐름은 하나의 라우트, 스텝은 그 안의 하위 상태로서 히스토리에 기록된다."**
  - 구현: 하위 라우트(`/signup/step/2`) 또는 쿼리 파라미터(`/signup?step=2`). 쿼리 파라미터가 "한 페이지의 하위 상태"라는 의미를 잘 드러내 무난한 경우가 많다.
  - **콜드 진입 가드 필수:** 선행 상태 없이 3단계 URL로 진입하면 1단계로 리다이렉트.
- **함정:**
  - **pushState vs replaceState 구분:** 모든 전환을 무지성으로 push하면 뒤로가기가 꼬인다.
  - **완료 후 처리:** 흐름을 완료한 뒤에는 뒤로가기로 완료된 흐름에 다시 들어오지 않도록 다른 곳으로 navigate + 히스토리 정리.
  - **규모 판단:** 길고 이탈·복구가 중요한 흐름이면 스텝 URL은 사실상 표준. 반대로 "옵션 고르고 확인" 수준의 2단계짜리면 컴포넌트 로컬 상태로 충분하며 URL은 오버킬.

### 4.5. 진입점이 다른 트리거 (예: 등록 버튼 vs FAB)

- **상황:** 데스크탑은 상단 "등록" 버튼 클릭 시 모달로 카드 목록(연차신청·연장근무신청 등), 모바일은 FAB 클릭 시 액션시트로 동일 항목.
- **판단:** 이것은 **하나의 컴포넌트가 반응형으로 변신하는 케이스가 아니다.** 진입점(버튼 위치·종류)도 다르고 표현(모달 vs 액션시트)도 다르므로, 사실상 **별개의 두 컴포넌트**다. 억지로 브레이크포인트로 모핑시키면 과설계.
- **본질:** 이 화면은 "선택지를 보여주는 메뉴"(액션으로의 분기점)일 뿐 콘텐츠 목적지가 아니다 → URL 불필요, 일시적 오버레이.
- **어떻게:**
  - 데스크탑·모바일 각각 **가장 관용적인 표현**을 쓴다(데스크탑=모달/팝오버, 모바일=액션시트).
  - **공유할 것은 UI가 아니라 "선택지 정의 + 액션 핸들러"** — 단일 소스로 두어 항목 추가·변경 시 양쪽이 자동 일관되게.
- **표현 경계:** 액션시트는 항목 5~6개 이하의 단순 텍스트 액션에 적합. 각 항목에 설명·아이콘·부가정보가 붙어 시각적으로 무거워지면 액션시트 대신 **바텀시트**로.
- **후속:** 각 항목(예: 연차신청)을 눌렀을 때 열리는 *그* 화면은 다시 "목적지 vs 오버레이" 판단을 적용할 지점 — 신청 폼이 길고 이탈·복구가 중요하면 URL 페이지(또는 라우티드 모달), 간단하면 모달.

### 4.6. 셀렉트/피커의 표현 모핑 (데스크탑 드롭다운 ↔ 모바일 오버레이)

- **판단:** 이것은 **정당한 "반응형 모핑" 케이스**다. 4.5와 정반대로, **진입점이 같고(셀렉트 필드를 누른다) 책임도 하나(목록에서 값 하나 고르기)**이며 바뀌는 것은 옵션을 펼치는 표현뿐이다. 한 컴포넌트가 플랫폼별로 표현만 바꾸는 교과서적 사례.
- **오해 교정 — "모바일=액션시트"는 부정확:** 모바일 셀렉트의 관용 표현이 꼭 액션시트는 아니다. 네이티브 `<select>`는 OS 기본 피커(iOS 휠, Android 다이얼로그)를 띄우고, 라이브러리에선 다이얼로그(라디오)·팝오버·바텀시트도 쓰인다. 액션시트는 하나의 선택지이며 제약이 있다:
  - **다중 선택 미지원.**
  - **옵션이 많으면 부적합**(예: Ionic `ion-select`는 옵션이 6개를 초과하면 action-sheet를 지정해도 alert 인터페이스로 대체).
  - 즉 액션시트는 **단일 선택 + 소수 옵션**에 한정.
- **데이터 형태로 모바일 표현 결정:**
  - 단일 선택 + 옵션 적음(~6) → 액션시트 / 팝오버 / 네이티브 피커.
  - 옵션 많음 → 검색 가능한 풀스크린 피커(모달/페이지). 사실상 셀렉트가 작은 "하위 화면"이 됨.
  - 다중 선택 → 체크박스 다이얼로그/모달.
- **기본 원칙:** 디자인 시스템이 없다면 이 모핑은 **직접 만들지 말고** 네이티브 `<select>`나 검증된 셀렉트 컴포넌트에 맡긴다. 직접 커스텀은 검색·리치 옵션·복잡한 다중선택 등 기본이 감당 못 할 때로 한정. **단, 디자인 시스템을 보유한 경우는 예외 → 5장 참조.**

## 5. 디자인 시스템을 보유한 경우 (네이티브 위임의 예외)

- **원칙:** 디자인 시스템(브랜드 토큰: 색·타이포·간격·모션)을 갖고 있다는 것 자체가 "네이티브에 맡겨라"의 **예외 조건**이다. 네이티브 피커는 브랜드 토큰을 따르지 않고, OS마다 생김새가 갈리며, 커스터마이즈가 거의 막혀 있다 — 일관된 시스템에는 받아들일 수 없는 비용.
- **중요한 구분:** "직접 만든다"가 "플랫폼별 표현 분기를 포기한다"는 뜻은 **아니다.** 4.6의 결론(셀렉트는 표현만 모핑하는 것이 정당)은 그대로 유효하다. 바뀌는 것은 "그 표현을 OS가 주느냐, 디자인 시스템이 주느냐"뿐이다.
- **만들어야 할 구조:**
  > **하나의 컴포넌트(공개 API·동작·접근성·상태는 단일) + 디자인 시스템 토큰을 입힌 자체 표현 레이어(데스크탑 팝오버 / 모바일 바텀시트 등)를 플랫폼별로 렌더.**
  > 네이티브 피커가 하던 "플랫폼에 맞는 표현 선택" 역할을 디자인 시스템 컴포넌트가 대신 떠안는 구조.
- **직접 만들 때 따라오는 책임 (네이티브에서 공짜로 받던 것들 — 빠뜨리기 쉬움):**
  - **접근성/키보드:** 포커스 트랩, 화살표 키 이동, 타입어헤드(글자 입력으로 항목 점프), 스크린리더 역할(`role="listbox"`/`option`, `aria-activedescendant`), Esc 닫기. 여기서 무너지면 디자인 시스템 컴포넌트로서 실격.
  - **헤드리스 + 스타일 분리:** 동작·상태·접근성을 담은 **헤드리스 코어**를 한 번 만들고, 그 위에 토큰을 입힌 표현(팝오버/바텀시트)을 얹는다. 표현이 플랫폼마다 달라도 동작은 단일 소스로 유지.
  - **모바일 입력 디테일:** iOS 줌 방지(트리거 폰트 16px 이상), 가상 키보드와 바텀시트 겹침 처리, 스크롤 잠금/포커스 복원.
  - **바퀴 재발명 최소화:** 0부터 짜지 말고, 동작·접근성만 제공하고 스타일은 100% 자체 토큰으로 입히는 **헤드리스(언스타일드 프리미티브) 라이브러리**를 코어로 깔면, 외관 통제권은 지키면서 접근성 지뢰밭을 상당히 피할 수 있다.

## 6. 헤드리스 코어 + 표현 레이어 (반복되는 구조적 결론)

2.3, 4.5, 5장에서 같은 원리가 반복된다. 일반화하면:

```
┌─────────────────────────────────────────────┐
│  Headless Core (단일 소스)                    │
│   - 상태/동작 로직                             │
│   - 접근성(ARIA, 키보드, 포커스 관리)          │
│   - 데이터/선택지 정의, 액션 핸들러             │
└───────────────┬─────────────────────────────┘
                │  같은 코어를 소비
     ┌──────────┴───────────┐
     ▼                      ▼
┌──────────────┐    ┌──────────────────┐
│ 데스크탑 표현  │    │ 모바일 표현        │
│ (팝오버/모달/  │    │ (바텀시트/액션시트/ │
│  드롭다운)     │    │  풀스크린)         │
│  + 토큰        │    │  + 토큰            │
└──────────────┘    └──────────────────┘
```

이 구조가 셀렉트·메뉴·다이얼로그 등 "표현은 플랫폼별, 정체성·동작은 단일"인 모든 컴포넌트의 공통 해법이다.

## 7. 프레임워크별 참고 (버전 확인 필요)

> 아래는 예시이며, 세부 동작·기본값은 버전에 따라 달라질 수 있으니 사용 중인 버전의 공식 문서로 검증할 것.

- **Ionic**
  - 스택 기반 내비게이션(이전 페이지를 DOM에 살려두고 전환 애니메이션). 히스토리 방향(direction)으로 전환 방향 결정.
  - **안드로이드 하드웨어 백 버튼**은 Capacitor/Cordova **네이티브 빌드에서만** 동작. 모바일 웹(PWA 포함)에서는 발생하지 않으며, 브라우저 뒤로가기(`popstate`)에 의존.
  - `ion-modal`은 앱 루트에 오버레이로 표시(전역 스타일 필요). 표현 방식: 풀스크린 / iOS 카드 / 바텀시트(`breakpoints` + `initialBreakpoint`). 모달은 Esc·하드웨어 백 버튼에 닫힘 반응.
  - `ion-select`의 `interface` 속성: `alert`(기본값) / `action-sheet` / `popover` / `modal`. action-sheet는 단일 선택 전용이며 옵션 6개 초과 시 alert로 대체.
- **Next.js (App Router)**
  - 라우티드 모달(4.3)을 **Parallel Routes + Intercepting Routes**로 1급 지원.
- **일반 SPA 라우터(React Router 등)**
  - 라우티드 모달은 라우터 상태에 `background location`을 수동으로 얹어 구현.

## 8. 커스텀 오버레이/컨트롤 접근성·플랫폼 체크리스트

네이티브 컨트롤을 직접 대체할 때(5장) 최소한 아래를 충족해야 한다:

- [ ] 포커스 트랩 (오버레이 열림 동안 포커스가 밖으로 새지 않음)
- [ ] Esc로 닫기 / 백드롭 클릭으로 닫기 (닫기 경로 일관성)
- [ ] 화살표 키 항목 이동, Home/End, 타입어헤드
- [ ] 올바른 ARIA 역할 (`listbox`/`option`, `dialog`, `aria-expanded`, `aria-activedescendant` 등)
- [ ] 열기 전 포커스 요소로 **포커스 복원**(닫을 때)
- [ ] iOS 입력 줌 방지 (트리거 폰트 ≥ 16px)
- [ ] 가상 키보드와 바텀시트/오버레이 겹침 처리
- [ ] 배경 스크롤 잠금(scroll lock)
- [ ] 라우티드 모달이라면: 뒤로가기=닫기, 배경 위치 보존, 직접 진입 fallback

## 9. 안티패턴 (냄새 목록)

- ❌ 모달이라는 이유로 목적지에 URL을 주지 않음 → 공유·뒤로가기·새로고침 붕괴.
- ❌ "모바일이니까 페이지, 데스크탑이니까 모달"을 화면 크기만으로 결정 → 정체성 축을 무시.
- ❌ 진입점이 다른 두 UI를 억지로 하나의 반응형 컴포넌트로 모핑 → 과설계(4.5).
- ❌ 멀티스텝 흐름 전체를 URL 하나로 두어 뒤로가기 시 흐름이 통째로 날아감(4.4).
- ❌ 콜드 진입 가드 없이 스텝/상세에 딥링크 허용 → 깨진 상태로 렌더.
- ❌ 디자인 시스템이 있는데 네이티브 피커를 그대로 사용 → 브랜드 불일치.
- ❌ 커스텀 오버레이를 만들면서 접근성·키보드를 생략 → 디자인 시스템 컴포넌트로서 실격.
- ❌ 옵션이 많거나 다중선택인데 액션시트를 강행(4.6).
- ❌ 플랫폼별 표현마다 선택지/핸들러를 중복 정의 → 단일 소스 원칙 위반.

## 10. 빠른 참조 치트시트

| 상황 | 결론 | 핵심 이유 |
|---|---|---|
| 목적지 콘텐츠 | 모든 브레이크포인트에서 **URL 부여**, 표현만 반응형 | 공유·북마크·새로고침·뒤로가기 |
| 목적지를 모달로 | URL은 그대로 바뀜 → **라우티드 모달** | 모달은 표현일 뿐, URL 결정 요인 아님 |
| 일시적 오버레이 | URL 없음, 무게에 맞는 오버레이 | 종속적·임시 액션 |
| 멀티스텝 | 흐름=1 라우트, **스텝=히스토리 엔트리** + 콜드 진입 가드 | 뒤로가기·새로고침 복구(공유 아님) |
| 진입점이 다른 트리거 | **별개 컴포넌트**, 로직만 공유 | 억지 모핑은 과설계 |
| 셀렉트/피커 | **정당한 모핑**, 데이터 형태로 표현 결정 | 진입점·책임이 하나 |
| 모바일 셀렉트 표현 | 액션시트는 단일+소수옵션 한정 | 다중·다수옵션은 시트/풀스크린 |
| 디자인 시스템 보유 | 네이티브 위임 예외 → **헤드리스 코어 + 토큰 표현** | 브랜드 일관성 + 접근성 자체 책임 |

---

*문서 끝. 새로운 컴포넌트 케이스(날짜 피커, 탭, 토스트/스낵바 등)도 1~3장의 프레임을 그대로 적용해 판단하면 된다.*
