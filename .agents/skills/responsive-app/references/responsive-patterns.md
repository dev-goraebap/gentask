# 반응형 적응 패턴

반응형 웹 앱은 부가 기능이 아니라 기본 전제입니다. 유동형 레이아웃은 쉬운
부분입니다. 어려운 부분은 **동일한 사용자 의도가 데스크톱과 모바일에서 서로 다른
컴포넌트를 필요로 한다**는 점이며, 잘못된 모바일 형태를 선택하는 것이 앱을 축소판
데스크톱 사이트처럼 느껴지게 만드는 원인입니다. 이 가이드는 그러한 매핑을 위한
의사결정 프레임워크입니다.

## 목차
1. 기본 원칙 (레이아웃만이 아니라 컴포넌트가 바뀌는 이유)
2. 브레이크포인트 전략
3. 핵심 매핑 (선택 규칙 포함)
4. responsive-dialog 패턴 (하나의 API, 두 가지 표현)
5. 자주 놓치는 함정 (뒤로가기 / safe-area / 스크롤 복원)
6. 컴포넌트별 반응형 체크리스트
7. 접근성 및 입력 모드 규칙

---

## 1. 기본 원칙

데스크톱과 모바일의 세 가지 차이가 모든 매핑을 좌우합니다:

- **터치에는 hover가 없다.** hover에 의존하는 모든 것(메뉴, 툴팁, hover로 드러나는
  액션)은 모바일에서 탭 기반의 명시적 대응물이 필요합니다.
- **엄지 도달 범위와 인체공학.** 모바일에서 주요 액션과 닫기 동작은 아래쪽의
  편안한 영역에 있어야 하며, 작은 타깃이나 상단 모서리 컨트롤은 실패합니다.
- **화면 공간과 집중도.** 넓은 캔버스 위에 중앙 정렬된 모달은 데스크톱에서는
  괜찮습니다. 하지만 휴대폰에서는 동일한 콘텐츠가 화면 전체를 차지하거나(전체 페이지)
  엄지가 닿는 아래에서 떠오르기를(바텀 시트) 원합니다.

따라서 질문은 결코 "이것을 어떻게 축소할까?"가 아닙니다. "이 의도에 대해 이 화면
크기와 입력 모드에서 올바른 *컴포넌트*는 무엇인가?"입니다.

## 2. 브레이크포인트 전략

- 브레이크포인트는 매직 넘버가 아니라 디자인 시스템의 **토큰**에서 도출하여
  어디서나 일관되게 합니다. 프로젝트에 토큰이 있으면 그대로 쓰고, 없으면 최소값을 정해
  값 옆에 `(임시)`로 표시합니다.
- 컴포넌트 수준의 적응에는 **컨테이너 쿼리**(카드가 뷰포트가 아니라 *자신의* 너비에
  따라 동작)를, 페이지 수준 레이아웃과 입력 모드 전환에는 **미디어 쿼리**를
  선호합니다.
- 너비만이 아니라 **입력 능력**을 감지하세요. 너비 브레이크포인트를
  `(hover: none) and (pointer: coarse)`와 결합하여 터치 동작인지 포인터 동작인지
  결정합니다. 작은 노트북 창은 휴대폰이 아니며, 마우스가 달린 태블릿은 터치
  휴대폰이 아닙니다.
- 명명된 작은 브레이크포인트 집합(예: `sm/md/lg/xl`)과, 컴포넌트 *형태*가 전환되는
  단일 "모바일 경계"(흔히 ~768px)를 정하고 일관되게 적용하세요.

## 3. 핵심 매핑 (선택 규칙 포함)

### 모달 / 다이얼로그 → 바텀 시트 *또는* 전체 페이지
가장 영향력이 큰 매핑입니다. 모바일에서 중앙 정렬 다이얼로그는 대개 잘못된
선택입니다. 작업에 따라 모바일 형태를 선택하세요:

- **바텀 시트** — 빠른 액션, 짧은 폼, 확인, 옵션/메뉴, 또는 컨텍스트(뒤쪽 페이지)를
  유지하는 것이 가치 있는 모든 경우. 아래에서 떠오르고, 엄지 친화적이며, 스와이프나
  백드롭으로 닫을 수 있습니다.
- **전체 페이지 / 전체 화면** — 복잡한 다단계 흐름, 콘텐츠가 많은 뷰, 긴 폼, 또는
  자체 백 스택 항목(과 뒤로 가기 버튼으로 닫기)을 가질 만한 것. 화면 전체를
  차지하며, 컨텍스트를 엿볼 수 없습니다.
- 경험칙: *사용자가 뒤쪽 페이지를 흘끗 보고 이득을 얻을 수 있는가?* → 시트.
  *작업이 완전한 집중이나 여러 단계를 요구하는가?* → 전체 페이지.

### hover 메뉴 / 팝오버 / 툴팁 → 탭 시트 / 드로어 / 인라인
터치에는 hover가 존재하지 않습니다. 모바일에서는:
- 드롭다운 메뉴 → 옵션의 **바텀 시트 / 액션 시트**.
- hover 툴팁 → 탭으로 드러내기, 또는 인라인 도움말 텍스트(터치에서는 필수 정보를
  hover 뒤에 숨기지 마세요).
- hover로 드러나는 행 액션 → 보이는 어포던스 또는 스와이프 액션.

### 밀집된 데이터 테이블 → 쌓인 카드 / 리스트
다중 컬럼 테이블은 좁은 화면에 맞지 않습니다. 모바일에서는:
- 각 행을 **카드**(라벨-값 쌍)로 접거나, 상세 뷰가 있는 요약 리스트로 만들거나,
  핵심 1~2개 컬럼을 우선하고 나머지는 탭 뒤에 둡니다.
- 주요 데이터에 대한 가로 스크롤은 피하고, 진정으로 표 형식이며 비교가 많은
  경우에만 사용하세요.

### 사이드바 내비게이션 → 드로어 / 하단 탭 바
- 상시 표시 사이드바(데스크톱) → 모바일에서 **오프캔버스 드로어**(햄버거) 그리고/또는
  상위 목적지를 위한 **하단 탭 바**.
- 가장 자주 사용하는 목적지는 하단 바(엄지 영역)에, 보조 항목은 드로어에 두세요.

### 다중 컬럼 레이아웃 → 단일 컬럼 스택
- 나란히 놓인 패널을 수직 스택으로 재배치하고, 주 패널을 승격하며, 보조 패널은
  강등하거나 미루세요(예: 탭이나 시트 뒤로).

### 날짜/숫자 입력, 셀렉트, 콤보박스
- 모바일에서 더 나은 경우 네이티브 입력 어포던스를 사용하고(네이티브 날짜 선택기,
  `inputmode`를 통한 숫자 키패드), 커스텀 UX가 명확히 유리한 경우에만 커스텀
  선택기를 사용하세요.

## 4. responsive-dialog 패턴 (하나의 API, 두 가지 표현)

정석적인 구현: **하나의 컴포넌트 API**(`<ResponsiveDialog>` 또는 그에 준하는 것)를
노출하여 입력 모드/너비 브레이크포인트에 따라 **데스크톱에서는 중앙 정렬
다이얼로그**, **모바일에서는 바텀 시트**를 렌더링하도록 전환합니다. 호출부는
분기하지 않고 컴포넌트가 처리합니다. 이렇게 하면 계약을 이식 가능하게 유지하고
호출 코드를 깔끔하게 유지할 수 있습니다.

프레임워크별 구현 노트(헤드리스 다이얼로그 + 시트/제스처 라이브러리와 짝을 이룸):
- **React**: 데스크톱에서는 Dialog 프리미티브(Base UI / Radix), 모바일에서는
  드로어/시트(예: vaul)를 `useMediaQuery` 스타일 훅으로 선택합니다.
- **Vue**: Reka UI 다이얼로그 + vaul에 준하는 시트(예: Ark/Reka 기반 바텀 시트)를
  하나의 래퍼 뒤에 둡니다.
- **Svelte**: Bits UI 다이얼로그 + vaul-svelte.
- **Angular**: 두 개의 첨부 템플릿을 가진 CDK Overlay/Dialog, 또는 Spartan의
  다이얼로그 + 시트를 `BreakpointObserver`로 전환합니다.

두 형태 모두에서 **포커스 관리, 라벨링, escape/뒤로 가기 동작**을 올바르게
유지하세요. 표현은 바뀌어도 접근성 계약은 바뀌지 않습니다.

## 5. 자주 놓치는 함정 (반응형 웹의 모바일 현실)

데스크톱 사고방식으로 짠 반응형 앱이 실제 휴대폰에서 무너지는 지점들입니다. 명세
단계에서 미리 챙기세요 — 나중에 버그로 발견하면 비쌉니다.

- **안드로이드/iOS 하드웨어·제스처 뒤로가기.** 모바일에서 시트·드로어·전체 페이지
  모달은 사용자가 본능적으로 **뒤로가기(안드로이드 시스템 버튼, iOS 가장자리
  스와이프)로 닫으려** 합니다. 이를 `history.pushState`로 받아서, 오버레이가 열릴 때
  히스토리 항목을 하나 쌓고 `popstate`에서 닫으세요. 그러지 않으면 뒤로가기가 시트를
  닫는 대신 **이전 페이지로 이탈**해 버립니다. 반대로, 닫기 버튼으로 닫을 때 쌓아둔
  히스토리 항목을 정리해 뒤로가기가 한 번 헛도는 일도 막으세요. 전체 페이지 형태는
  아예 자체 라우트(back-stack 항목)를 갖는 것이 가장 자연스럽습니다.
- **iOS Safari 뷰포트와 safe-area.** `100vh`는 iOS에서 주소창을 포함해 계산되어
  콘텐츠가 잘립니다 — `100dvh`(동적 뷰포트)를 쓰세요. 노치/홈 인디케이터를 피하려면
  `viewport-fit=cover` + `env(safe-area-inset-*)`로 하단 고정 바와 시트 핸들에 여백을
  주세요. 키보드가 올라올 때 고정 요소가 가려지는 문제도 `dvh`/`interactiveWidget`로
  점검하세요.
- **스크롤 위치 복원.** 오버레이를 열 때 배경 스크롤을 잠그되(보통 `position: fixed`
  + `top` 오프셋), 닫을 때 **원래 스크롤 위치를 정확히 복원**하세요. 단순히
  `overflow: hidden`만 토글하면 닫는 순간 맨 위로 점프합니다. 라우트 전환(전체 페이지
  형태)에서는 뒤로 돌아왔을 때의 스크롤 복원 정책도 정하세요.
- **`100%` 높이 사슬과 주소창 리사이즈.** 주소창이 접히고 펴질 때 뷰포트 높이가
  바뀌어 레이아웃이 튑니다. 높이에 의존하는 시트 스냅 포인트는 `dvh` 기준으로
  계산하고, 리사이즈에 재계산이 필요한지 확인하세요.

이 함정들은 대부분 *접근성/뒤로가기 동작*과 얽혀 있으므로, 위젯 프리미티브가 이미
일부를 처리하는지(예: scroll-lock) 확인하고 중복하지 마세요.

## 6. 컴포넌트별 반응형 체크리스트

상호작용 컴포넌트를 명세할 때 다음에 답하세요:
- 그것의 **데스크톱** 형태와 **모바일** 형태는 무엇인가?
- 어떤 **브레이크포인트 + 입력 모드**가 전환을 유발하는가?
- 각 형태에서 어떻게 **닫히는가**(백드롭, escape, 스와이프, 뒤로 가기 버튼)?
- 모바일에서 **주요 액션**은 어디에 위치하는가(엄지 영역)?
- **제스처**(→ `references/gestures-motion.md`)가 필요한가, 아니면 탭/키보드로 충분한가?
- 각 형태에서 **키보드** 경로는 무엇인가?

이것들을 컴포넌트 명세와 반응형 ADR(`assets/adr.template.md`)에 기록하여 반응형
동작이 나중에 떠올리는 것이 아니라 명세의 일부가 되도록 하세요.

## 7. 접근성 및 입력 모드 규칙 (항상)

- 모든 제스처/hover 상호작용에는 **제스처가 아니고 hover가 아닌 대응물**(보이는
  버튼, 키보드 경로)이 있어야 합니다.
- 모달과 시트 형태 모두에서 오버레이의 **포커스 트랩 + 복원**을 유지하세요.
- **`prefers-reduced-motion`**을 존중하세요. 이를 요청하는 사용자에게는 시트/전환
  모션을 줄이거나 제거합니다.
- 모바일에서 **타깃 크기**가 터치 최소치(~44px)를 충족하도록 하세요.
- 바텀 시트와 드로어는 반드시 배경 스크롤을 잠그고, 접근 가능한 이름과 닫기
  컨트롤을 노출해야 합니다.

반응형 전략(브레이크포인트 + 컴포넌트별 매핑 접근법)을 ADR로 기록하세요.
