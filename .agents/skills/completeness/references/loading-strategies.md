# 1.1 전문 — 로딩 전략: fetch-then-render vs fetch-on-render

## 두 전략의 전제 차이

| | fetch-on-render | fetch-then-render |
|---|---|---|
| 컴포넌트 마운트 시점 | 데이터 없이 먼저 마운트 | 데이터가 준비된 뒤 마운트 |
| 로딩 상태를 아는 주체 | 컴포넌트 자신 | 라우터 (컴포넌트는 모른다) |
| 필요한 UI | 스켈레톤/진행바/스피너 | 임계 시간 오버레이 (선택적) |
| 레이아웃 시프트 원인 | 빈 상태 → 채워진 상태 전환 구간 | 전환 구간 자체가 페이지 안에 없음 |

fetch-on-render는 컴포넌트가 마운트된 뒤 `useEffect` 등으로 데이터를 가져오는 방식이다. 데이터가
없는 첫 렌더가 반드시 존재하므로 로딩 상태를 그릴 수단(스켈레톤/진행바/스피너)이 필요하고,
로딩→완료 전환에서 콘텐츠 치수가 바뀌면 레이아웃 시프트가 난다.

fetch-then-render는 라우트가 활성화되기 *전에* 데이터를 확보한다. 컴포넌트는 완성된 데이터를
가지고 마운트되므로 로딩 분기 자체가 필요 없다. 대신 "얼마나 기다렸는지"는 라우터가 판단해
전환 오버레이로 표시한다.

## 결정 절차

**1. 라우터가 리졸버/로더를 지원하는가?**

| 라우터/프레임워크 | 리졸버·로더 |
|---|---|
| Angular Router | `ResolveFn` |
| React Router (v6.4+, data router) | `loader` |
| Remix | `loader` |
| SvelteKit | `+page.ts`/`+page.server.ts`의 `load` |
| TanStack Router | `loader` |
| Next.js App Router | 서버 컴포넌트가 사실상 동일한 효과(컴포넌트 자체가 fetch 종료 후 렌더) |
| Vue Router | 내장 리졸버 없음 — 네비게이션 가드 + Pinia 스토어로 직접 구현 |

지원하지 않거나(예: 순수 클라이언트 라우팅만 쓰는 구조) 팀이 이 구조로 전환할 여력이 없으면
fetch-on-render로 진행한다. 이 경우 갈래 자체를 언급하지 않고 조용히 fetch-on-render로
좁혀 들어간다 — 사용자에게 "네 라우터는 이걸 못 한다"는 식의 논평을 하지 않는다.

**2. 지원하면 팀이 선호하는지 확인한다.** fetch-then-render는 스켈레톤/스피너의 레이아웃
흔들림을 피하고 싶을 때 정당한 선택이다. 모범사례 여부의 문제가 아니라 전제가 다른 두 방식 중
하나를 고르는 문제로 다룬다.

## fetch-then-render 구현 패턴

### 전환 오버레이 (임계 시간 게이트)

라우트 전환 시작(`NavigationStart` 계열 이벤트) 직후 타이머를 건다. 임계 시간(150~500ms
권장 — 빠를수록 민감하게 보여주지만 캐시 hit 같은 즉시 완료 전환에서도 깜빡일 위험이 커진다)
안에 전환이 끝나면(`NavigationEnd`/취소/에러) 타이머를 취소해 오버레이를 아예 띄우지 않는다.
느린 전환만 오버레이가 보인다.

```
전환 시작 → 타이머 시작(예: 150ms)
  ├─ 타이머 만료 전 전환 종료 → 오버레이 표시 안 함
  └─ 타이머 만료 → 오버레이 표시 → 전환 종료 시 즉시 해제
```

참고 사례: Hotwire/Turbo의 `Turbo.setProgressBarDelay`(기본 500ms)가 동일한 원리로 진행바
표시를 지연시킨다.

### 루트/전역 캐시 (stale-while-revalidate)

리졸버/로더가 매번 네트워크를 치지 않고 전역 캐시(스토어)를 먼저 확인한다. 캐시가 있으면
즉시 반환(오버레이 안 뜸), 없으면 fetch 후 채운다. 재방문 시 콜드 로드가 없어져 오버레이가
사실상 최초 진입에만 보인다. 백그라운드 갱신이 필요하면(SWR) 오버레이가 아니라 1.4의 얇은
갱신 표시를 쓴다 — 이미 화면에 데이터가 있는 상태에서 콘텐츠 영역을 다시 비우지 않는다.

### 에러 처리

리졸버/로더의 에러를 라우터 자체의 네비게이션 에러로 전파하면 전환이 취소되고 이전 화면에
머무른다. 대신 에러를 캐치해 스토어/상태에 담고 네비게이션은 정상 진행시켜, 새 페이지가
마운트된 뒤 자체 에러 상태(1.2)를 그리게 하는 편이 사용자 경로를 덜 끊는다.

## 적용 범위의 한계

fetch-then-render는 **라우트 전환**에만 건다. 이미 마운트된 화면 안에서 발생하는 fetch(모달을
열 때, 버튼 클릭으로 추가 데이터를 가져올 때 등)는 라우터 이벤트에 걸 수 없으므로 이 전략의
적용 대상이 아니다. 이런 경우엔 fetch-on-render 갈래의 로컬 로딩 UI(스피너 등)가 그대로
필요하다.
