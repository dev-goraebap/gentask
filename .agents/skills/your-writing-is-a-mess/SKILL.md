# your-writing-is-a-mess

기술 문서, 소프트웨어 아키텍처 결정 기록(ADR), 요구사항 명세서, 코드 주석 등을 작성하거나 검토할 때 LLM(특히 Claude) 특유의 부자연스럽고 왜곡된 한국어 문체를 찾아내어 명확하고 자연스러운 공학적 표현으로 교정하고, 불필요한 과잉 부연을 과감히 덜어내는(삭제하는) 기준을 제공하는 스킬입니다.

---

## 1. 왜 클로드의 문장은 엉망이 되는가? (핵심 문제 의식)

LLM은 기술 문서를 작성할 때 다음과 같은 구조적 결함과 과잉 서술에 빠지기 쉽습니다.

1. **영어 직역 번역투**: 영어 SVO 구조를 그대로 흉내 내어 `~에 의해 ~된다`, `~을 가진다`, `~을 수행한다`, `이는 ~을 의미한다`와 같은 무생물 주어와 피동형을 남발합니다.
2. **어색한 순우리말 고유어 강박 (유사 미니멀리즘 문체)**: 번역투를 피하겠다는 의도로 전문 기술 용어(생성, 등록, 정의, 연결, 연동, 제거, 해제, 삭제, 발급, 반환, 위치, 화면, 엔드포인트) 대신 뜻이 모호한 일상 고유어(`세우다`, `잇다`, `걷다`, `거두다`, `내다`, `매다`, `자리`, `떠 있는 자리`, `두 층`)를 억지로 끼워 넣습니다.
3. **인격화와 형식적 리듬 맞추기**: 문서나 코드, 도구에 소유(`갖는다`)나 발화(`말한다`, `떠받친다`) 동사를 붙이고, 운율을 맞추기 위해 긍정/부정을 짝짓는 억지 대구(`~에 두고 ~에 두지 않는다`, `어느 층에 무엇을 두고 무엇을 두지 않는가가 여기 있다`)를 만듭니다.
4. **인과 관계의 후치 도치**: 결론을 먼저 던지고 뒤에 `~합니다. ~하기 때문입니다`로 꼬리를 붙여 문장의 자립성을 파괴합니다.
5. **과잉 부연과 방어적 사족 (Over-explanation)**: 자명한 상식, 코드가 이미 설명하는 동작, 모델 스스로의 사고 과정을 변명하듯 덧붙여 문장의 정보 밀도를 떨어뜨립니다. 이런 문장은 문체를 다듬는 것으로 해결되지 않으며 **문장 자체를 완전히 삭제**해야 합니다.

## 2. 핵심 서술 규격 및 올바른 표현 원칙

### 2.1 다의어 고유어 동사 금지 및 표준 공학 용어 사용
한자어와 외래어 기술 용어를 억지로 순우리말로 바꾼다고 해서 문장이 쉬워지지 않습니다. 고유어 동사는 다의어(다양한 의미를 지닌 단어)이므로 문장의 정밀도만 떨어뜨립니다. 문맥에 맞는 확정적 공학 용어를 사용합니다.

- `세우다` 금지 -> 문맥에 따라 **`작성한다`**, **`생성한다`**, **`정의한다`**, **`초기화한다`**
- `잇다` 금지 -> **`연결한다`**, **`연동한다`**, **`매핑한다`**
- `걷다` 금지 -> **`제거한다`**, **`해제한다`**, **`폐기한다`**
- `거두다` 금지 -> **`삭제한다`**, **`회수한다`**, **`만료 처리한다`**
- `내다` 금지 -> **`발급한다`**, **`반환한다`**, **`출력한다`**
- `매다 / 붙이다` 금지 -> **`연결한다`**, **`귀속시킨다`**, **`바인딩한다`**
- `자리` 금지 -> **`위치`**, **`계층`**, **`모듈`**, **`엔드포인트`**, **`화면`** (대상 이름을 직접 기술)
- `두 층 / 두 겹` 금지 -> **`2단계 계층`**, **`2중 구조`**
- `껍데기` 금지 -> **`래퍼(Wrapper)`**, **`레이아웃(Layout)`**, **`어댑터(Adapter)`**
- `보다` 금지 -> **`조회한다`**, **`판정한다`**, **`참조한다`**

### 2.2 무생물 대상의 소유·발화 의인화 배제
문서, 테스트, 모듈, 도구는 사람이나 생명체가 아닙니다. 소유(`갖는다`)와 발화(`말한다`, `떠받친다`)의 동사를 붙이지 않습니다.

- [금지] "이 결정의 근거는 아키텍처 결정-001이 갖습니다."
  - [권장] **"이 결정의 근거는 아키텍처 결정-001에 기술되어 있습니다."**
- [금지] "테스트는 지금의 명세를 말하고, 어느 항목의 일이었는지는 커밋의 트레일러가 갖습니다."
  - [권장] **"테스트는 현재 명세를 기술하며, 관련 작업 항목 식별자는 커밋 트레일러에 기록합니다."**
- [금지] "이 제약조건이 아키텍처 결정들을 떠받칩니다."
  - [권장] **"이 제약조건은 주요 아키텍처 결정의 전제 기반이 됩니다."**

### 2.3 인과 관계의 전치 배열 (후치 도치 `~하기 때문입니다` 금지)
`~합니다. ~하기 때문입니다` 구조는 앞 문장 없이는 성립하지 않는 종속문을 양산합니다. 근거와 배경을 앞에 먼저 서술하면 결론이 자연스럽게 도출되어 군더더기 연결어가 필요하지 않습니다.

- [금지] "추적 검사는 배포 절차에서 제거했습니다. 검사 비용이 검출 이득을 넘어섰기 때문입니다."
  - [권장] **"검사 실행 비용이 결함 검출 이득을 초과하므로, 배포 절차에서 추적 검사를 제외합니다."**
- [금지] "상태 변경 응답에는 본문을 싣지 않습니다. 화면에서 읽지 않는 응답이 남으면 유지보수 비용이 늘어나기 때문입니다."
  - [권장] **"클라이언트가 변경 후 재조회를 수행하므로 상태 변경 응답 본문은 생략하여 유지보수 부하를 방지합니다."**

### 2.4 형식적 운율과 억지 대구(對句) 제거
긍정과 부정을 짝지어 운율을 억지로 맞추면, 짝의 한쪽은 의미 있는 정보를 담지 못하고 자리만 채우게 됩니다. 실질적인 대상과 규칙을 직접 진술합니다.

- [금지] "어느 층에 무엇을 두고 무엇을 두지 않는가가 여기 있습니다."
  - [권장] **"계층별 테스트 배치 기준과 검증 대상을 규정합니다."**
- [금지] "접두어는 이름에 쓰고 주소에는 쓰지 않습니다."
  - [권장] **"접두어는 작업 항목의 명칭에만 사용하며 URL 주소에는 식별자를 사용합니다."**

### 2.5 능동적 긍정 서술 (수행하지 않는 동작으로 가치 포장 금지)
시스템이 수행하지 않는 동작을 장황하게 나열하여 가치를 설명하지 않습니다. 읽는 사람이 실제 동작을 알 수 없습니다.

- [금지] "화면을 열지 않고도 할 일을 남기고 고친다."
  - [권장] **"CLI를 통해 작업 항목을 직접 조회, 등록, 수정한다."**
- [금지] "서버에 직접 들어가지 않고 운영에 필요한 사실을 확인한다."
  - [권장] **"관리자 웹 콘솔에서 사용자 통계 및 운영 지표를 조회한다."**

### 2.6 영어 직역투 및 번역투 패턴 척결
- **수동태 연속 제거**: `~에 의해 ~된다`, `~되고 있다` -> 능동형 `~이 ~한다`
- **영어 SVO 1:1 매핑 동사 교체**:
  - `~을 가진다 (have)` -> `~이 있다`
  - `~을 수행한다 (perform)` -> `~을 한다 / 처리한다`
  - `이는 ~을 의미한다 (this means)` -> `즉 ~이다` 또는 문맥 생략
  - `~에 기여한다 (contribute to)` -> `~에 도움이 된다`
  - `~을 보장한다 (ensure)` -> `~이 어긋나지 않게 한다 / 방지한다`
- **추상명사 주어 풀어쓰기**: `X의 활용은 Y의 증가를 초래한다` -> `X를 사용하면 Y가 늘어난다`

## 3. 과잉 부연 현상 정의와 문장 덜어내기(완전 삭제) 판정 기준

### 3.1 과잉 부연(방어적 사족)이란 무엇인가?
LLM이 작성하는 기술 문서에서 가장 빈번하게 발견되는 또 다른 결함은 **'굳이 쓰지 않아도 되는 자명한 내용이나 자신의 사고 과정을 변명하듯 늘어놓는 사족'**입니다.

이러한 문장은 어휘를 표준어로 고치거나 문체(~합니다체/~한다체)를 아무리 우아하게 다듬어도 근본적으로 어색합니다. **애초에 텍스트로 존재할 이유가 없는 문장이기 때문입니다.**

따라서 문장 교정 작업 시 무조건 문장을 고쳐 쓰려 하지 말고, **과감히 덜어내는(완전 삭제하는) 분기**를 반드시 거쳐야 합니다.

### 3.2 완전 삭제(덜어내기)의 5대 판정 기준

다음 5가지 기준 중 하나라도 해당하면, 문장을 개선하지 말고 **완전히 삭제**합니다.

1. **코드 반향 주석 (Code Echo / 동작 재서술)**
   - 코드를 한 줄 읽으면 1초 만에 알 수 있는 자명한 동작을 그대로 한국어로 옮겨 적은 주석.
   - [삭제 대상] `// id가 null이면 에러를 던진다`, `// 값이 들어오면 상태를 갱신한다`
   - [원칙] 코드가 이미 말하고 있는 동작은 주석을 달지 않습니다. 주석은 '무엇을 하는가'가 아니라 '왜 이 비직관적인 제약이 필요한가'만 남깁니다.

2. **자명한 상식 및 동어반복 (Stating the Truisms / Tautology)**
   - 상식적으로 당연한 사실이거나, 한 단어의 정의 안에 이미 포함된 내용을 굳이 다시 설명하는 문장.
   - [삭제 대상] `외부 인용문은 원문 그대로 옮기며 문체를 고치지 않습니다.` ('원문 그대로'에 이미 문체를 안 고친다는 뜻이 포함됨 -> 후반부 삭제)
   - [삭제 대상] `삭제하면 데이터가 사라집니다. 복구할 수 없기 때문입니다.` (삭제 시 데이터가 사라지는 것은 도메인의 자명한 전제 -> 삭제)

3. **사고 과정 중계 및 자기 변명 (Narrating Thought Process)**
   - LLM이 의사결정을 내릴 때 거친 내면의 추론 과정, 혼잣말, 또는 방어적 변명을 본문에 기록한 문장.
   - [삭제 대상] `이것이 이 명령이 존재하는 이유입니다.`
   - [삭제 대상] `우리가 이렇게 한 것은 대안 A를 쓰면 복잡해지기 때문입니다.` (수치나 아키텍처 제약이 없는 감정적 변명은 삭제)

4. **행동을 유발하지 않는 무가치한 소음 (Non-Actionable Noise)**
   - 이 문장을 읽은 개발자나 사용자가 '해야 할 행동'이나 '피해야 할 제약'에 아무런 변화를 주지 못하는 문장.
   - [삭제 대상] `나중에 필요해지면 그때 가서 다시 판단할 수 있습니다.` (모든 결정은 나중에 재판단할 수 있으므로 무의미 -> 삭제)
   - [삭제 대상] `이 작업은 매우 중요하며 시스템의 핵심입니다.` (주관적 강조 표현 -> 삭제)

5. **미발생 상황에 대한 막연한 가정과 불안 (Premature Speculation)**
   - 현재 구현 범위가 아니거나 아직 일어나지 않은 먼 미래의 가상 시나리오에 대해 변명하듯 둘러댄 문장.
   - [삭제 대상] `지금은 항목이 적지만 나중에 수천 개로 늘어나면 어떻게 될지 모르므로 일단 이렇게 둡니다.` (실제 요구가 발생했을 때 작성 -> 삭제)

### 3.3 황금 질문 (The Golden Question)

문장을 고치기 전에 스스로에게 다음 질문을 던집니다.

> **"이 문장을 통째로 지워버렸을 때, 시스템의 요구 규격이나 작업자의 엔지니어링 판단에 단 1%의 결손이라도 발생하는가?"**
>
> - **아니다 (지워도 시스템 이해나 코드 작성에 아무 지장이 없다)** -> **개선하지 말고 즉시 삭제합니다.**
> - **그렇다 (지우면 필수적인 제약이나 규칙 정보가 유실된다)** -> **군더더기를 쳐내고 핵심 사실만 1문장으로 압축합니다.**

## 4. 종결 어미의 유연성과 2가지 표현 스타일

본 스킬은 문장을 보존하고 정제할 때 문맥과 요구사항에 맞추어 선택할 수 있도록 **[자연스러운 스타일 가이드 표현]**과 **[간결한 서술형]**의 두 가지 층위를 `~합니다체`와 `~한다체`로 유연하게 제공합니다.

| 스타일 구분 | 종결 어미 (~합니다체) | 종결 어미 (~한다체) | 특성 및 스타일 성격 |
| :--- | :--- | :--- | :--- |
| **자연스러운 스타일 가이드 표현** | `~합니다` | `~한다` | 표준 공학 용어, 논리적 인과 관계, 명확한 제약과 조건이 완결된 문장으로 서술된 완성형 문체 |
| **간결한 서술형** | `~합니다` | `~한다` | 군더더기 한정어, 접속사, 중복 수식어를 완전히 제거하고 1문장 1아이디어 원칙으로 핵심 사실만 전달하는 컴팩트 문체 |

### 종결 어미 적용의 유연성 원칙 (비강제)

**종결 어미는 특정 대상에 기계적으로 강제되지 않습니다.** 

프로젝트의 성격, 조직의 컨벤션, 사용자의 선호에 따라 얼마든지 달라질 수 있으므로, 아래의 분류는 일반적인 참고용 권장 예시일 뿐 강제 규칙이 아닙니다. 사용자가 원하는 형식이 있다면 어느 문서나 위치든 그에 맞추어 유연하게 적용합니다.

- **참고용 일반적 권장 예시**:
  - 공식 문서, 가이드, 대외용 README: 일반적으로 정중한 `~합니다체`를 권장합니다.
  - 소스 코드 주석, 테스트 명세, 커밋 메시지 제목, 작업 절차 흐름: 직관적이고 간결한 `~한다체(평서문)`를 권장합니다.
- **가장 중요한 기준**: 
  1. 형식을 기계적으로 강제하지 않고 **사용자나 프로젝트의 컨벤션을 최우선으로 존중**합니다.
  2. 한 문서나 동일한 작업 범위 안에서는 **선택한 어조의 일관성을 유지**합니다.

## 5. 자체 점검 체크리스트 (Self-Critique)

문서나 주석을 작성하거나 교정할 때 다음 항목을 점검합니다.

- [ ] **[덜어내기 검사]** 이 문장을 지워도 시스템 스펙과 작업자 판단에 아무 영향이 없는가? (해당 시 즉시 삭제)
- [ ] **[어휘 검사]** 2.1의 금지 단어(`세우다`, `잇다`, `걷다`, `거두다`, `내다`, `매다`, `자리`, `두 층`)가 포함되어 있는가?
- [ ] **[의인화 검사]** 문서나 코드 객체를 주어로 삼아 `갖는다`, `말한다`, `떠받친다`로 인격화하지 않았는가?
- [ ] **[인과문 검사]** `~합니다. ~하기 때문입니다` 구조로 이유를 문장 뒤에 달지 않았는가?
- [ ] **[대구 검사]** `~에 두고 ~에 두지 않는다` 식의 리듬용 억지 대구가 들어있지 않은가?
- [ ] **[부정문 검사]** `~하지 않고도` 식의 부정문으로 시스템의 가치를 설명하려 하지 않았는가?
- [ ] **[번역투 검사]** 영어 직역투(`~에 의해 처리된다`, `~을 가진다`, `이는 ~을 의미한다`)가 남아있지 않은가?
- [ ] **[문장 완결성]** 1문장 1아이디어를 지키고 단문 위주로 명료하게 끊었는가?
- [ ] **[일관성 검사]** 선택한 종결 어미(`~합니다체` 또는 `~한다체`)가 해당 문서 맥락 내에서 일관되게 유지되는가? (사용자 선호 최우선)
