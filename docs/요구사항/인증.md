# 요구사항 — 인증

상태 정의: `제안`(초안) → `확정`(사람 승인, 구현 착수 가능) → `구현됨`(DoD 충족) / `폐기`

| ID | 요구사항 | 상태 |
|---|---|---|
| AUTH-01 | 이메일/비밀번호로 회원가입·로그인할 수 있다 | 확정 |
| AUTH-02 | 구글 계정으로 로그인할 수 있다 | 확정 |
| AUTH-03 | 카카오 계정으로 로그인할 수 있다 | 확정 |
| AUTH-04 | 네이버 계정으로 로그인할 수 있다 | 확정 |
| AUTH-05 | 동일 이메일이면 인증 수단이 달라도 하나의 계정으로 통합된다 | 확정 |
| AUTH-06 | 인증 데이터는 user / session / account / verification 4테이블 구조로 관리된다 | 확정 |

세션 방식은 [결정-0014](../결정기록/결정-0014-세션-방식.md), 스키마는 [설계/데이터베이스.md](../설계/데이터베이스.md)를 따른다.

## AUTH-01 이메일/비밀번호 인증

- [ ] 이메일과 비밀번호로 가입할 수 있고, **가입 즉시 로그인 상태가 된다**
- [ ] 가입 시 이메일 검증 메일이 발송된다 (MAIL-01 의존)
- [ ] 검증 링크를 열면 해당 이메일이 검증됨으로 표시된다
- [ ] **이메일은 계정 전체에서 유일하다**
- [ ] 비밀번호는 bcrypt로 해시되어 저장되며, 원문은 로그·응답 어디에도 남지 않는다
- [ ] 로그인·로그아웃할 수 있고, 로그아웃 시 해당 세션이 **즉시** 무효화된다
- [ ] 로그인 실패 응답이 "이메일이 없음"과 "비밀번호가 틀림"을 구분해 노출하지 않는다

이메일 검증 정책: **가입 즉시 사용 가능하되, 미검증 상태는 계정 연동(AUTH-05)에서 제한**한다.
검증을 가입 필수 조건으로 두지 않는 이유는 이탈률과 파생 프로젝트의 정책 조정 여지 때문이다.

## AUTH-02 ~ AUTH-04 소셜 로그인

- [ ] 각 제공자의 OAuth 2.0 인가 코드 흐름(PKCE 포함)으로 로그인할 수 있다
- [ ] `state` 검증과 리다이렉트 URI 검증이 이루어진다
- [ ] 최초 로그인 시 `user`와 `account` 레코드가 생성된다
- [ ] 제공자가 알려주는 **이메일 검증 여부를 저장한다** — AUTH-05의 판단 근거가 된다
- [ ] 제공자가 발급한 액세스·리프레시 토큰은 `account`에 저장되며 클라이언트로 반환되지 않는다

구현은 Spring Security OAuth2 Client를 사용한다 — `state`·PKCE·리다이렉트 검증을 직접 책임지지 않기 위함이다.

미결(설계 단계에서 확인): 제공자별 이메일 검증 정보 제공 방식. 카카오는 OIDC를 지원해 ID 토큰으로
받을 수 있으나, **네이버는 확인이 필요하다.** 확인 결과에 따라 AUTH-05의 동작이 제공자별로 갈린다.

## AUTH-05 이메일 키 통합

- [ ] 제공자가 **이메일을 검증했음이 확인되면** 같은 이메일의 기존 계정에 자동 연결된다
- [ ] 검증 여부를 확인할 수 없으면 **자동 연결하지 않고**, 로그인 후 명시적으로 연동하도록 안내한다
- [ ] 다음 시나리오가 모두 의도대로 동작한다
  - 로컬 가입 → 같은 이메일로 소셜 로그인
  - 소셜 가입 → 같은 이메일로 로컬 가입 시도
  - 소셜 A 가입 → 같은 이메일로 소셜 B 로그인
- [ ] 자동 연결이 거부된 경우 사용자가 이유를 알 수 있는 안내가 제공된다

**막으려는 공격**: 공격자가 피해자의 이메일로 (검증을 요구하지 않는) 제공자에 계정을 만들고,
그 계정으로 로그인해 피해자의 기존 계정에 연결되는 계정 탈취. 그래서 "이메일이 같다"만으로는
연결하지 않는다.

## AUTH-06 4테이블 구조

- [ ] `user` / `session` / `account` / `verification` 스키마가 [설계/데이터베이스.md](../설계/데이터베이스.md)와 일치한다
- [ ] **비밀번호는 `user`가 아니라 `account`에 저장된다** — 로컬 인증도 하나의 제공자(`credential`)로 다룬다
- [ ] 세션은 DB에 저장되어 **즉시 무효화**할 수 있다
- [ ] 세션 토큰은 웹에서는 `HttpOnly` 쿠키로, 모바일·외부 클라이언트에서는 `Authorization: Bearer`로 전달된다
- [ ] 한 사용자의 활성 세션 목록을 조회할 수 있고, 개별 세션을 무효화할 수 있다
- [ ] 검증 토큰(`verification`)은 충분한 엔트로피를 가지며 만료되고 1회만 사용된다
