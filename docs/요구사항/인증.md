# 요구사항 — 인증

상태 정의: `제안`(초안) → `확정`(사람 승인, 구현 착수 가능) → `구현됨`(DoD 충족) / `폐기`

| ID | 요구사항 | 상태 |
|---|---|---|
| AUTH-01 | 이메일/비밀번호로 회원가입·로그인할 수 있다 | 구현됨 |
| AUTH-02 | 구글 계정으로 로그인할 수 있다 | 구현됨 |
| AUTH-03 | 카카오 계정으로 로그인할 수 있다 | 구현됨 |
| AUTH-04 | 네이버 계정으로 로그인할 수 있다 | 폐기 |
| AUTH-05 | 동일 이메일이면 인증 수단이 달라도 하나의 계정으로 통합된다 | 구현됨 |
| AUTH-06 | 인증 데이터는 user / session / account / verification 4테이블 구조로 관리된다 | 구현됨 |
| AUTH-07 | 비밀번호를 재설정할 수 있다 | 구현됨 |
| AUTH-08 | 인증 수단 접근을 잃은 경우 이메일로 계정을 복구할 수 있다 | 구현됨 |

세션 방식은 [결정-0014](../결정기록/결정-0014-세션-방식.md), 이메일 소유 증명은
[결정-0015](../결정기록/결정-0015-이메일-소유-증명.md), 스키마는 [설계/데이터베이스.md](../설계/데이터베이스.md)를 따른다.

## 공통 규칙

모든 흐름에 적용된다.

- **이메일 소유는 자체 OTP로 증명한다.** 소유 증명 없이는 계정이 생기지 않으며, 소셜 제공자가 준
  이메일은 신뢰하지 않는다. 근거와 파라미터는 결정-0015.
- **이메일 동일성 판정**: 소문자화 + 앞뒤 공백 제거만 한다. 점 제거·플러스 태그 제거는 하지 않는다.
- **계정 존재 여부를 화면으로 노출하지 않는다.** 가입·복구 요청의 응답은 성공/실패에 관계없이
  동일하며("입력하신 주소로 안내 메일을 보냈습니다"), 실제 분기는 메일 내용으로 가른다.
- **비밀번호·토큰·OTP 원문은 로그·응답 어디에도 남지 않는다.**

## AUTH-01 이메일/비밀번호 인증

- [x] 이메일을 입력하면 그 주소로 OTP가 발송되고, **OTP를 통과한 뒤에 계정이 생성된다**
- [x] OTP를 통과하지 못하면 `user` 행이 생기지 않는다 — 미검증 계정이 존재할 수 없다
- [x] 계정 생성과 동시에 로그인 상태가 되며, 이때 **세션 토큰을 새로 발급한다**
- [x] **이메일은 계정 전체에서 유일하다**
- [x] 비밀번호는 bcrypt로 해시되어 저장되며, 원문은 로그·응답 어디에도 남지 않는다
- [x] 로그인·로그아웃할 수 있고, 로그아웃 시 해당 세션이 **즉시** 무효화된다
- [x] 로그인 실패 응답이 "이메일이 없음"과 "비밀번호가 틀림"을 구분해 노출하지 않는다

**이메일 검증 정책이 바뀌었다.** 이전 판은 "가입 즉시 사용 가능하되 검증은 나중에"였고 근거는
이탈률이었다. OTP는 사용자가 같은 화면에 머문 채 코드를 입력하는 흐름이라 링크 방식이 회피하려던
비용을 애초에 지불하지 않는다. 또한 미검증 계정을 남기지 않는 것이 pre-hijacking 계열 공격의 전제를
없애는 유일한 방법이다(결정-0015).

## AUTH-02 · AUTH-03 소셜 로그인

- [x] 각 제공자의 OAuth 2.0 인가 코드 흐름(PKCE 포함)으로 로그인할 수 있다 — PKCE는 설정이 아니라
      `OAuth2AuthorizationRequestResolver` 빈으로 켠다(`SecurityConfig`). 설정 프로퍼티로는 켤 수 없다
- [x] `state` 검증과 리다이렉트 URI 검증이 이루어진다
- [x] 제공자 인증과 이메일 입력을 잇는 중간 표는 URL이 아니라 `HttpOnly` 쿠키로 전달되고,
      한 번 쓰면 지워진다
- [x] **이메일 scope를 요구하지 않는다.** 제공자가 이메일을 주더라도 입력칸 기본값(편의) 이상으로
      쓰지 않는다
- [x] 최초 로그인은 **2단계**다 — 제공자 인증 → 이메일 입력 + OTP → `user`·`account` 생성
- [x] 대기 중인 제공자 신원은 `user` 없이 `account`에 저장되지 않는다 (대기 레코드가 함께 보관한다)
- [x] `account`는 `(provider, providerAccountId)`로 식별되며 유니크하다 — 이메일을 제공자 식별
      키로 쓰지 않는다
- [x] 제공자가 발급한 액세스·리프레시 토큰은 **저장하지 않는다** — 담을 칸도 두지 않는다(아래 참조)

구현은 Spring Security OAuth2 Client를 사용한다 — `state`·PKCE·리다이렉트 검증을 직접 책임지지 않기
위함이다.

**단, PKCE는 라이브러리를 붙이는 것만으로 켜지지 않는다(보안 검토 F2에서 발견).** 기본 리졸버는
클라이언트 인증 방식이 `none`이거나 `ClientSettings.requireProofKey`가 참일 때만 PKCE를 붙이는데,
구글·카카오는 시크릿을 쓰는 기밀 클라이언트라 첫 조건에 해당하지 않고, Spring Boot 4.1의 OAuth2
클라이언트 프로퍼티에는 `client-settings` 바인딩이 없어 두 번째 조건을 설정으로 켤 방법이 없다.
그래서 리졸버 빈을 직접 등록한다. **이 인수조건은 한동안 문서에만 있고 코드에는 없었다** — 라이브러리에
맡긴 방어는 켜졌는지 확인해야 한다는 사례로 남긴다.

**제공자 토큰을 보관하지 않기로 했다(2026-07-29).** 원래 인수조건은 `account`에 저장하는 것이었으나,
구현하며 두 가지를 확인했다.

1. **쓸 데가 없다.** 이메일 scope조차 요구하지 않으므로(결정-0015) 제공자 API를 호출할 계획이 없다.
   토큰을 저장하는 목적은 "나중에 그 제공자의 API를 부르기 위해"인데, 그 나중이 아직 없다.
2. **쓰지 않을 자격증명을 들고 있으면 유출 시 피해만 커진다.** 우리 DB가 털렸을 때 남의 서비스
   접근 권한까지 함께 넘어간다.

**칸도 함께 없앴다(2026-07-29, 결정-0022).** 처음에는 "채우면 되니 자리는 두자"며 스키마에 남겼으나,
그 결과 `null` 세 개가 핸들러 → 신원 타입 → 도메인 → 저장소를 지나 빈 칸에 도달하는 경로가 생겼다.
승인자가 "이 값이 왜 필요한가"를 묻는 지점이 됐다는 것이 근거다. 빈 칸은 언젠가 채워지고, 그때
평문 저장이 되면 우리 DB 유출이 남의 서비스 침해로 번진다. **없는 칸은 잘못 채워질 수 없다.**
제공자 API가 필요해지는 시점(PROF-04 소셜 연동 관리 등)에 마이그레이션과 암호화 저장을 함께 정한다.

**미결이었던 제공자별 이메일 검증 방식은 해소됐다.** 구글과 카카오는 검증 신호를 주지만 네이버는
주지 않는다. 제공자 이메일을 쓰지 않기로 했으므로 이 차이가 우리 동작에 영향을 주지 않으며,
파생 프로젝트가 제공자를 추가할 때도 인증 로직을 재검토할 필요가 없다(결정-0015).

## AUTH-04 네이버 로그인 — 폐기 (2026-07-29)

**키트는 제공자 둘로 충분하다고 판단해 폐기했다.** 기능을 포기한 것이 아니라 **키트의 책임 범위에서
덜어낸 것**이다.

결정-0015가 자체 OTP를 택하면서 얻은 가장 큰 이득이 "제공자를 추가해도 인증 로직을 재검토할
필요가 없다"였다. 그 말이 참이라면 제공자 셋을 다 구현하는 것은 **같은 패턴을 한 번 더 반복하는
일**일 뿐이다. 구글(OIDC 표준)과 카카오(비표준 응답 형식) 둘이면 파생 프로젝트가 마주칠 두 갈래를
모두 보여준다 — 세 번째를 붙이는 일은 설정 파일 몇 줄이다.

되살리려면 이 항목을 지우지 말고 새 ID로 요구사항을 추가한다. 폐기 기록이 남아 있어야 "왜 없는가"에
답할 수 있다.

## AUTH-05 이메일 키 통합

통합 키는 **우리가 OTP로 검증한 이메일**이다. 제공자가 주장하는 이메일이 아니다.

- [x] 이메일 입력 단계에서 **기존 계정이 발견되면 OTP를 보내지 않고**, 기존 인증 수단으로 로그인한 뒤
      연동하도록 안내한다 (연동 경로에 OTP가 개입하지 않는다)
- [x] 신규 이메일이면 OTP를 통과한 뒤 계정이 생성되고, 그 이메일은 그 계정의 것이 된다
- [x] 다음 시나리오가 모두 의도대로 동작한다
  - 로컬 가입 → 같은 이메일로 소셜 로그인 → "로그인 후 연동" 안내
  - 소셜 가입 → 같은 이메일로 로컬 가입 시도 → "로그인 후 비밀번호 설정" 안내
  - 소셜 A 가입 → 같은 이메일로 소셜 B 로그인 → "소셜 A로 로그인 후 연동" 안내
- [x] 안내 문구가 계정 존재 여부를 화면에서 단정하지 않는다 (공통 규칙)

**세 시나리오는 같은 코드가 처리한다** — "그 이메일에 계정이 있으면 코드를 보내지 않고 안내한다"
하나면 셋이 모두 덮인다. 다만 안내 문구는 **어느 수단으로 가입했는지 알려주지 않는다.**
"소셜 A로 로그인하세요"라고 하면 그것만으로 그 사람이 소셜 A를 쓴다는 사실이 새기 때문이다.
대신 "기존에 쓰던 로그인 방법으로"라고만 안내한다 — 공통 규칙이 시나리오별 친절함보다 앞선다.

**막으려는 공격**: 공격자가 피해자의 이메일로 (검증을 요구하지 않는) 제공자에 계정을 만들고,
그 계정으로 로그인해 피해자의 기존 계정에 연결되는 계정 탈취. OTP 선행이 이 전제를 없애고,
"로그인 후 연동" 규칙이 기존 계정에 대한 현재 접근 권한을 증명하게 한다.

> **미완: 안내가 가리키는 연동 경로가 아직 없다 (보안 검토 F9).**
> 이 요구사항은 "로그인한 뒤 연동하라"고 안내하지만, **연동 기능 자체는 [PROF-04](프로필.md)이며
> 아직 `제안` 상태다.** 지금 상태에서 안내를 따라간 사용자는 로그인까지는 되지만 소셜 계정을 붙일
> 수단이 없다 — 막다른 길이다. 보안 결함은 아니다(안전한 쪽으로 막힌다). 다만 **AUTH-05가 `구현됨`인
> 것에 비해 사용자가 겪는 실질은 절반이므로**, PROF-04가 구현될 때까지 화면은 이 안내를 최종 상태로
> 취급하지 않아야 한다. AUTH-05는 PROF-04에 의존한다.

## AUTH-06 4테이블 구조

- [x] `user` / `session` / `account` / `verification` 스키마가 [설계/데이터베이스.md](../설계/데이터베이스.md)와 일치한다
- [x] **비밀번호는 `user`가 아니라 `account`에 저장된다** — 로컬 인증도 하나의 제공자(`credential`)로 다룬다
- [x] 세션은 DB에 저장되어 **즉시 무효화**할 수 있다
- [x] 세션 토큰은 웹에서는 `HttpOnly` 쿠키로, 모바일·외부 클라이언트에서는 `Authorization: Bearer`로 전달된다
- [x] 한 사용자의 활성 세션 목록을 조회할 수 있고, 개별 세션을 무효화할 수 있다
- [x] `verification`은 다목적이며 **용도(`purpose`) 컬럼으로 구분되고 조회에서 항상 필터된다** —
      한 용도로 발급된 코드가 다른 용도에 통과하지 않는다
- [x] OTP는 앱 시크릿을 키로 하는 HMAC으로 저장되며, 만료·시도 횟수 제한·1회 사용이 강제된다
- [x] 대기 중인 가입 시도는 이메일을 예약하지 않는다 — 유일성 제약은 `user`에만 있다
- [x] OTP 검증은 대기 레코드 식별자로 조회한다 — `(이메일, 코드)`만으로 찾지 않는다

## AUTH-07 비밀번호 재설정

로그인할 수 없는 상태의 복구 흐름이다. 로그인된 상태의 변경은 PROF-03이 담당한다.

- [x] 이메일로 OTP를 받아 새 비밀번호를 설정할 수 있다
- [x] **재설정 성공 시 그 사용자의 모든 세션이 무효화된다** (재설정을 요청한 세션 포함)
- [x] **대기 중인 이메일 변경 요청이 함께 취소된다** — 취소 대상을 만드는 PROF-05는 M2 소관이라
      아직 없지만, 연결을 먼저 넣어 두었다. 나중에 이 연결을 빠뜨리면 그 자체가 탈취 경로가 된다
- [x] 재설정용 OTP는 다른 용도의 코드로 사용할 수 없고, 그 반대도 성립한다
- [x] 요청 응답이 계정 존재 여부를 노출하지 않는다 — 계정이 없거나 비밀번호가 없는 소셜 전용
      계정이어도 같은 형태로 응답하고, 메일 제목까지 동일하게 두어 메일함에서도 구분되지 않게 했다.
      **코드를 보내지 않는 경우에도 아무도 맞힐 수 없는 대기 레코드를 남긴다** — 남기지 않으면
      코드를 다섯 번 틀려보는 것만으로 "시도 횟수 초과"가 나오는 쪽이 실재 계정임이 드러난다

전 세션 무효화와 대기 중 변경 취소는 pre-hijacking 변종 2·4번(재설정이 기존 세션을 남기거나,
미완료 이메일 변경이 재설정 후에 완료되는 경우)에 대한 방어다.

## AUTH-08 이메일 복구

- [x] 소셜 전용 계정(비밀번호 없음)이 제공자 접근을 잃은 경우, 검증된 이메일로 OTP를 받아 로그인할 수 있다
- [x] 복구 로그인 후 인증 수단을 추가·교체할 수 있도록 안내된다 — 응답의 `shouldSetPassword`가
      비밀번호 없는 계정임을 알리고, 메일 본문도 같은 안내를 담는다
- [x] 복구 로그인이 일어나면 본인에게 알림 메일이 간다 — 이 경로는 비밀번호 없이 세션을 내주면서
      기존 세션을 끊지 않으므로, 메일함 접근을 얻은 사람이 조용히 들어올 수 있다. 알림이 유일한 신호다

- [x] 복구용 OTP는 다른 용도의 코드로 사용할 수 없다
- [x] 복구 로그인 시 세션 토큰을 새로 발급한다

**복구는 비밀번호가 있는 계정에도 열려 있다.** 인수조건 첫 줄은 소셜 전용 계정을 상정하지만,
"비밀번호가 있으면 복구 불가"로 좁히면 그 거절 자체가 비밀번호 유무를 알려주는 신호가 된다
(위 열거 오라클과 같은 문제). 대신 알림 메일로 사후 감지를 보장한다.

이 요구사항으로 **이메일 메일함이 계정의 최상위 신뢰 근원**이 된다. 비밀번호 재설정이 있는 거의 모든
서비스가 이미 그런 구조이지만, 민감한 도메인의 파생 프로젝트는 여기에 2단계 인증을 얹어야 한다는
신호로 삼는다(결정-0015).
