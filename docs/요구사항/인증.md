# 요구사항 — 인증

상태 정의: `제안`(초안) → `확정`(사람 승인, 구현 착수 가능) → `구현됨`(DoD 충족) / `폐기`

| ID | 요구사항 | 상태 |
|---|---|---|
| AUTH-01 | 이메일/비밀번호로 회원가입·로그인할 수 있다 | 제안 |
| AUTH-02 | 구글 계정으로 로그인할 수 있다 | 제안 |
| AUTH-03 | 카카오 계정으로 로그인할 수 있다 | 제안 |
| AUTH-04 | 네이버 계정으로 로그인할 수 있다 | 제안 |
| AUTH-05 | 동일 이메일이면 인증 수단이 달라도 하나의 계정으로 통합된다 | 제안 |
| AUTH-06 | 인증 데이터는 user / session / account / verification 4테이블 구조로 관리된다 (Better Auth 방식) | 제안 |

## AUTH-01 이메일/비밀번호 인증

인수조건 (확정 단계에서 상세화):
- [ ] 이메일과 비밀번호로 가입할 수 있고, 가입 시 이메일 검증 절차를 거친다 (MAIL-01 의존)
- [ ] 가입한 계정으로 로그인·로그아웃할 수 있다
- [ ] 비밀번호는 안전하게 해시되어 저장된다

## AUTH-02 ~ 04 소셜 로그인

인수조건 (확정 단계에서 상세화):
- [ ] 각 공급자의 OAuth 흐름으로 로그인할 수 있다
- [ ] 최초 로그인 시 계정이 생성된다

외부 의존성: 구글·카카오·네이버 개발자 콘솔의 앱 등록 및 정책.

## AUTH-05 이메일 키 통합

인수조건 (확정 단계에서 상세화):
- [ ] 같은 이메일의 소셜/로컬 인증은 같은 user에 연결된다
- [ ] 통합 시나리오(로컬 가입 후 소셜 로그인, 그 역순)가 모두 동작한다

## AUTH-06 4테이블 구조

인수조건 (확정 단계에서 상세화):
- [ ] user / session / account / verification 스키마가 `docs/설계/데이터베이스.md`와 일치한다
- [ ] 세션 관리(생성·만료·무효화)가 session 테이블 기반으로 동작한다
