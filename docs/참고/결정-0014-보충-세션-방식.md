# 인증 세션 방식 — DB 세션 + 이중 전달의 근거

## 0. 요약

우리는 **DB에 저장한 불투명 세션 토큰**을 쓰고, 웹에는 `HttpOnly` 쿠키로, 모바일·외부 클라이언트에는
`Authorization: Bearer`로 **같은 토큰을 다른 경로로** 전달한다.

비교 대상인 "JWT 액세스 토큰 + 불투명 리프레시 토큰" 구성(이하 **JWT 액세스 안**)과의
**구조적 차이는 하나다**. 두 방식 모두 DB에 불투명 토큰 행을 둔다. JWT 액세스 안은 그 위에
**JWT 액세스 레이어를 한 겹 더 얹는다.** 따라서 실제 검토 질문은 "세션이냐 토큰이냐"가 아니라 이것이다:

> **그 한 겹이 우리에게 무엇을 주고, 무엇을 가져가는가?**

- **주는 것**: 액세스 토큰 수명 동안 세션 조회를 아낀다.
- **가져가는 것**: 즉시 무효화(만료 전 폐기). 그리고 클라이언트에 토큰 2개·재발급 흐름·경합 방지 코드.

우리 요구사항에는 **즉시 무효화가 필요한 항목이 이미 넷** 있고(로그아웃 AUTH-01, 비밀번호 재설정
AUTH-07, 비밀번호 변경 PROF-03, 기기 관리 AUTH-06), **액세스 레이어가 값을 발휘하는 조건**(다중
리소스 서버 · 제3자 API 개방 · 교차 도메인 · 조회가 측정된 병목인 트래픽)은 현재 **하나도 해당되지
않는다** (§6).

AUTH-07(비밀번호 재설정)은 결정-0014 이후 [결정-0015](../결정기록/결정-0015-이메일-소유-증명.md)
검토 과정에서 추가된 요구사항이며, **전 세션 무효화를 인수조건으로 명시**한다 — pre-hijacking
변종 2번(재설정이 기존 세션을 남기는 경우)에 대한 방어다. 즉시 무효화 요구는 시간이 지나며
줄지 않고 늘었다.

이 방향은 현행 표준 권고와도 일치한다 (§4).

## 1. 용어 정리

이 주제의 비교가 어긋나는 흔한 원인은 서로 다른 것을 같은 단어로 부르는 데 있다. 세 가지를 분리한다.

### 1.1 "세션 방식" ≠ 인메모리 `HttpSession`

"세션은 확장이 안 된다 / sticky session이 필요하다"는 지적은 **서버 메모리에 세션을 두는 방식**에
대한 것이다. 우리 방식은 그것이 아니다.

| | 인메모리 `HttpSession` | 우리 방식 (DB 세션) |
|---|---|---|
| 세션이 사는 곳 | 각 앱 서버의 힙 | `session` 테이블 (공용 DB) |
| sticky session | 필요 | **불필요** |
| 앱 서버 수평 확장 | 제약됨 | **제약 없음** |
| 인스턴스 재시작 | 세션 소실 | 무관 |

**앱 서버는 우리 방식에서도 무상태다.** 상태는 DB에 있고, DB는 어차피 모든 요청이 쓴다.

### 1.2 저장 방식과 전달 방식은 직교한다

| | **쿠키로 전달** | **`Authorization: Bearer`로 전달** |
|---|---|---|
| **불투명 토큰** (DB 조회로 검증) | 우리 웹 경로 | **우리 모바일 경로** |
| **JWT** (서명으로 자체 검증) | JWT를 쿠키에 넣은 구성 | 일반적 SPA 구성 |

모바일이 요구하는 것은 **Bearer 전달**이지 **JWT 형식**이 아니다. 우리는 Bearer 경로를 지원하며,
그 Bearer가 실어 나르는 것이 불투명 난수일 뿐이다.

### 1.3 두 안의 실제 차이는 "한 겹"

```
JWT 액세스 안:  [클라이언트] --JWT 액세스(15분)--> [API]  ...만료...  --리프레시--> [DB의 토큰 행]
우리 안:        [클라이언트] --불투명 세션 토큰----> [API] -----------------------> [DB의 토큰 행]
```

**둘 다 DB에 불투명 토큰 행을 둔다.** JWT 액세스 안에서 그 행의 이름이 "리프레시 토큰"일 뿐이다.
차이는 그 앞의 JWT 액세스 레이어 하나이며, 비교는 그 레이어의 가치라는 단일 쟁점으로 좁혀진다.

## 2. 비용: 요청마다 세션 조회 1회

### 2.1 사실이며, 감수 사항으로 명시했다

불투명 토큰은 자체 검증되지 않으므로 요청마다 `session` 테이블을 한 번 조회한다.

> "감수하는 것: 요청마다 세션 조회 1회. 액세스 토큰 레이어가 아끼는 몫을 포기한다" — 결정-0014 §결과

이 비용은 몰라서가 아니라 **알고 지불하기로 한 것이다.**

### 2.2 다만 비교 기준은 "조회 0회"가 아니다

JWT 액세스 안에서도 다음 지점에서 상태 조회가 발생한다.

1. **만료 전 무효화를 지원하려면 검증 시 상태 확인이 필요하다.** denylist(또는 allowlist) 조회가
   표준적 방법이다. 공정하게 말하면, denylist는 폐기된 토큰만 담는 작은 집합이어서 인메모리 캐시나
   전파형 캐시로 세션 테이블 조회보다 싸게 구현할 수 있고, "전체 무효화"만 필요하다면 전역
   not-before 값 하나로도 가능하다. 그러나 **특정 세션(특정 기기) 단위의 즉시 무효화**에는 결국
   토큰별 상태가 필요하고, 같은 캐시 전략은 세션 조회 앞에도 동일하게 둘 수 있다. 즉 캐시를
   허용하는 순간 양쪽의 조회 비용은 다시 가까워지고, 복잡도 차이(레이어 한 겹)만 남는다.
2. **사용자 상태·권한의 최신값이 필요하면 조회한다.** 역할 변경, 계정 정지, 테넌트 전환을 토큰에
   구워 두면 만료까지 낡은 값이 유효하다. 낡으면 안 되는 값이 하나라도 있으면 조회가 돌아온다.
3. **리프레시 자체가 DB 왕복이다.** 액세스 토큰 만료마다 조회 1회 + 회전 시 쓰기 1회.
   액세스 TTL을 줄일수록 이 비용이 커지며 우리 방식의 비용 구조로 수렴한다.
4. **대부분의 API는 이미 도메인 쿼리를 여러 번 돌린다.** 목록 조회 하나가 3~10 쿼리인 API에서
   인증 조회 1회가 병목이라는 판단은 측정을 근거로 해야 한다.

### 2.3 정량 비교

사용자 1명, 10분간 API 100회 호출, 액세스 토큰 TTL 15분 가정.

| | 우리 안 | JWT 액세스 안 (만료 전 무효화 없음) | JWT 액세스 안 (기기 단위 즉시 무효화) |
|---|---|---|---|
| 세션/토큰 상태 조회 | 100회 | 0~1회 | 100회 (denylist, 캐시로 절감 가능) |
| 서명 검증 | 0회 | 100회 | 100회 |
| 재발급 왕복 | 0회 | 0~1회 | 0~1회 |
| **무효화 반영** | **즉시** | **최대 15분 지연** | 즉시 |
| 클라이언트 토큰 개수 | 1 | 2 | 2 |

서명 검증(HMAC·ECDSA)이 DB 조회보다 싼 것은 사실이다 — 마이크로초 대 밀리초 단위다.
쟁점은 어느 쪽이 싼가가 아니라 **그 차이가 우리 규모에서 유의미한가, 그리고 그 대가로 무효화
지연(또는 denylist 레이어 추가)을 받을 만한가**다.

우리 규모에서 세션 조회는 **PK/유니크 인덱스 단일행 조회**다. 행 수는 활성 세션 수에 비례하고
(전체 사용자 수가 아니다), 워킹셋이 작아 대체로 메모리에 상주한다. 정확한 수치는 우리 환경에서
측정할 값이며, 결정-0014의 재검토 조건이 그것이다 — "세션 조회가 실제 병목으로 측정되면 캐시를
앞에 두고, 그래도 부족하면 전환을 검토한다." 캐시를 두면 캐시 전파 지연이라는 새 변수가 생기지만,
그 지연을 **도입할지 말지 선택할 수 있다**는 점이 구조에 지연이 내장된 방식과 다르다.

### 2.4 표준도 "요청마다 조회"를 정상 동작으로 취급한다

OAuth 2.0에서 액세스 토큰의 **기본형은 불투명 토큰**이며, 리소스 서버의 표준 검증 수단은
[RFC 7662 Token Introspection](https://www.rfc-editor.org/rfc/rfc7662) — **요청마다 인가 서버로
보내는 HTTP 왕복**이다. 우리의 로컬 DB 조회보다 비싼 방식이 표준에서 정상으로 취급된다.

JWT 액세스 토큰은 이후 [RFC 9068](https://www.rfc-editor.org/info/rfc9068/)(2021)로 **별도
프로파일**이 됐고, 해당 RFC는 도입 배경을 인가 서버와 리소스 서버가 **함께 있지 않거나 서로 다른
주체가 운영하는 토폴로지**로 설명한다. 우리는 그 조건에 해당하지 않는다.

## 3. 클라이언트·렌더링 모드별 영향

### 3.1 현재 구조

[결정-0011](../결정기록/결정-0011-렌더링-모드-경계.md)에 따라 렌더링 경계가 인증 경계와 일치한다.

| 영역 | 렌더링 | 인증 |
|---|---|---|
| `/`, `/login`, `/signup` | Prerender | 불필요 |
| `app/**` (인증 후) | **CSR** | 필요 |

또한 [설계/인프라.md](../설계/인프라.md) §2에 따라 **same-origin 배포가 기본 전제**다 —
리버스 프록시 뒤에 web·server를 한 오리진으로 노출한다.

### 3.2 CSR 웹

브라우저가 앱 셸을 받고 JS가 API를 호출한다. 두 방식 다 동작하며, 차이는 XSS 노출면과
클라이언트 코드량이다.

| | 쿠키 세션 (우리) | JWT (localStorage / 메모리) |
|---|---|---|
| 토큰을 JS가 만지는가 | **아니다** (`HttpOnly`) | 그렇다 |
| XSS 스크립트가 토큰을 읽을 수 있는가 | **없다** | 있다 |
| XSS 시 세션 남용(요청 대행) | 가능 (→ §5) | 가능 |
| 필요한 추가 방어 | CSRF | XSS 전량 차단 (달성 곤란한 목표) |
| 클라이언트 코드 | 없음 (브라우저가 자동 첨부) | 401 인터셉터·재발급·중복 갱신 방지 |

### 3.3 SSR 웹

인증된 화면을 서버에서 렌더링하려면 **문서 요청(HTML을 받는 그 요청)이 이미 인증되어 있어야 한다.**

- **쿠키**: 브라우저가 문서 요청에 자동으로 붙인다. SSR 서버가 그 쿠키를 읽어 API 호출에 전달하면
  첫 렌더부터 사용자 컨텍스트를 갖는다.
- **localStorage의 JWT**: 문서 요청에 전송되지 않는다. localStorage는 브라우저 안에만 있고 서버는
  접근할 수 없으므로, SSR 서버는 첫 렌더에서 사용자가 누구인지 알 수 없다.

이 지점의 일반적 해법은 셋이다: (1) 인증 후 화면을 CSR로 유지 — 결정-0011로 이미 택한 방안,
(2) 서버는 껍데기만 렌더하고 클라이언트가 재조회 — SSR 이점 상실, (3) **JWT를 쿠키로 옮김** —
전달 방식이 쿠키로 수렴. 3번을 택하는 순간 두 안의 차이는 "쿠키에 담긴 것이 불투명 토큰이냐
JWT냐"로 줄어들고, 그 축에서 만료 전 폐기는 불투명 토큰 쪽에 있다. 이는 전달 방식이 아니라 자체
검증 토큰의 본질에서 오는 차이다(결정-0014 §검토한 대안).

덧붙이면 SSR + 쿠키도 공짜는 아니다. Angular SSR 서버가 수신한 쿠키를 자기 HTTP 호출에
전달해 줘야 한다(`REQUEST` 토큰 주입 / 인터셉터). 비용은 있으나 **가능**하며, localStorage 방식은
이 지점이 가능/불가능의 문제가 된다.

결정-0014의 재검토 조건에도 이 문장이 있다 — "인증 후 화면을 SSR로 전환하려는 경우 — 쿠키
방식은 그대로 동작하므로 이 결정이 제약이 되지 않는다."

### 3.4 "메모리 액세스 토큰 + HttpOnly 리프레시 쿠키" 하이브리드

액세스 토큰을 메모리에만 두고 리프레시 토큰을 `HttpOnly` 쿠키에 두는 구성은 localStorage 방식의
XSS 노출을 크게 줄이는 좋은 구성이다. 구조를 정확히 보면:

- 리프레시 쿠키는 **장기 자격증명을 담은 HttpOnly 쿠키**로, 위험 프로필이 우리 세션 쿠키와 같다.
- 즉 이 구성은 **"HttpOnly 쿠키 세션 + 그 위의 JWT 액세스 레이어"**다 — §1.3의 그 한 겹이다.
- 새로고침·새 탭마다 리프레시 왕복(DB 조회 1회)이 발생한다. 요청당 조회보다는 훨씬 적지만,
  "상태 조회 0회" 구성은 아니다.

따라서 이 하이브리드와 우리 안의 비교도 결국 같은 질문으로 돌아온다 — 그 한 겹이 값을 하는가.

### 3.5 모바일 앱

- 쿠키 자동 첨부 메커니즘이 없으므로 Bearer 전달이 필요하며, 우리는 이미 지원한다
  ([설계/서버.md](../설계/서버.md) §1.5). 세션 테이블은 하나이고 전달 방식만 다르다.
- 토큰은 OS 보안 저장소(Keychain / Keystore)에 둔다. JWT든 불투명 난수든 동일하다.
- 즉시 무효화는 모바일에서 오히려 더 중요하다 — 기기 분실 시 "이 기기 로그아웃"(AUTH-06)이
  즉시 반영되어야 한다.

### 3.6 종합

| 클라이언트 | 우리 안 | JWT 액세스 안 |
|---|---|---|
| CSR 웹 | 쿠키 (JS가 토큰을 안 만짐) | 동작, XSS 노출면과 재발급 코드 추가 |
| SSR 웹 | 쿠키로 그대로 동작 | localStorage면 불가 → 쿠키 전환 필요 |
| 모바일·외부 | Bearer (같은 세션 테이블) | Bearer |

## 4. 표준 현황

### 4.1 IETF — OAuth 2.0 for Browser-Based Applications

[draft-ietf-oauth-browser-based-apps](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-browser-based-apps-26)
(2026-07 현재 draft-26, RFC 편집자 큐, 의도 상태 Best Current Practice)

- 브라우저 앱의 세 아키텍처 중 **BFF(Backend For Frontend)를 가장 강한 보안 패턴으로 제시**한다
  (§6.1). 토큰은 백엔드가 들고, 브라우저에는 **쿠키 기반 세션만** 내려준다.
- BFF 세션 쿠키에 `Secure`·`HttpOnly`를 필수로, `SameSite=Strict`를 권고로 규정하고(§6.1.3.2)
  CSRF 대응을 요구한다(§6.1.3.3). 결정-0014 §결정 2~3과 같은 내용이다.
- §1.3과 §7.1: 프런트엔드와 API가 **같은 도메인에 있는 웹 애플리케이션은 OAuth 2.0에 의존하지
  않는 아키텍처가 가능**하며, §7.1 "Single-Domain Browser-Based Applications (not using OAuth)"로
  분류되어 **이 명세의 범위 밖**임을 명시한다. 인증 후에는 애플리케이션이 사용자 인증 상태를 직접
  유지한다고 쓴다. 우리가 정확히 그 경우다 — same-origin 배포, 자체 프런트가 자체 백엔드를 호출.

### 4.2 OWASP

- 인증 토큰·세션 ID·JWT·리프레시 토큰을 `localStorage`/`sessionStorage`에 두지 말 것을 권고한다.
  같은 오리진의 모든 JS가 접근 가능하므로 XSS 하나로 전부 노출된다.
- 권고: `HttpOnly`·`Secure`·`SameSite` 쿠키, 또는 BFF 패턴.
  ([Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html))

### 4.3 OAuth 2.0의 설계 의도와 우리의 적용 범위

- OAuth 2.0은 **제3자 위임** 프로토콜로, 클라이언트·리소스 소유자·리소스 서버·인가 서버가 서로
  다른 주체일 수 있는 상황을 전제한다.
- [RFC 9700 Best Current Practice for OAuth 2.0 Security](https://datatracker.ietf.org/doc/rfc9700/)
  (2025-01)가 현행 보안 BCP다. 우리는 이를 따른다 — 소셜 로그인(AUTH-02~04)에서 인가 코드 +
  PKCE를 그대로 적용한다(요구사항/인증.md).
- 정리하면: **표준이 적용되는 자리(소셜 로그인)에는 표준을 쓰고, 표준이 스스로 범위 밖이라고
  말하는 자리(자체 앱의 로그인 세션)에는 그에 맞는 세션 관리를 쓴다.**

## 5. 보안 특성 — 정확한 범위

`HttpOnly` 쿠키가 주는 보호를 정확히 기술하면 다음과 같다.

**XSS 발생 시:**

| | 쿠키 세션 (우리) | localStorage JWT |
|---|---|---|
| 스크립트가 토큰 값을 읽어 외부로 보낸다 | **불가** (`HttpOnly`가 JS 읽기를 차단) | 가능 |
| 피해자 브라우저 안에서 요청을 대신 보낸다(남용) | 가능 | 가능 |
| 피해 지속 범위 | 페이지가 열려 있는 동안, 해당 오리진 안 | 만료까지 어디서든, 공격자 인프라에서 |
| 남용 차단 수단 | **즉시 세션 무효화** | 만료 대기 또는 denylist |

즉 `HttpOnly`가 주는 것은 "XSS 자체의 무력화"가 아니라 **"XSS를 통한 토큰 유출(exfiltration)
차단"**이다. 이 차이는 실질적이다 — 유출된 토큰은 다수 피해자로부터 수집되어 브라우저 밖에서,
피해자가 창을 닫은 뒤에도 만료까지 재사용된다. 남용(session riding)은 그렇지 않으며, 남용을 끊는
수단이 곧 즉시 무효화다.

**XSS 이외의 탈취 경로에 대해서도 정직하게 적어 둔다.** 멀웨어(인포스틸러), 단말 침해, 잘못
구성된 프록시·로그 등으로는 `HttpOnly` 쿠키도 불투명 토큰도 JWT도 모두 탈취될 수 있다. 이 경로에서
두 안의 차이는 **탈취 이후**에 나타난다:

- **폐기**: 탈취가 의심되면 우리는 해당 세션 행을 삭제해 즉시 차단한다. 자체 검증 JWT는 만료까지
  유효하며, denylist가 미리 준비되어 있어야 차단할 수 있다.
- **감지**: 리프레시 토큰 회전 + 재사용 감지는 이 경로의 탈취를 능동적으로 감지하는 유효한
  기법이며, 이는 JWT 고유 기능이 아니라 **불투명 토큰에도 동일하게 적용 가능한 패턴**이다(주기적
  세션 토큰 재발급 + 구 토큰 재사용 감지). 현재는 IP·User-Agent 기록과 기기 관리(AUTH-06)로
  시작하고, 위협 모델이 요구하면 세션 토큰 회전을 같은 테이블 위에 추가한다.

사고 대응 관점에서, "전 사용자 세션 즉시 만료"는 우리 안에서 `DELETE` 한 번이다. JWT 안에서도
전역 not-before 값으로 가능하지만, **세션·기기 단위의 선택적 즉시 폐기**는 결국 토큰별 상태를
요구한다 — 우리 안에는 그 상태가 처음부터 있다.

## 6. 자주 나오는 질문

**Q. 세션은 매 요청 DB를 조회하지 않나?**
맞다. 감수 사항으로 명시했다(§2.1). 다만 JWT 안도 기기 단위 즉시 무효화를 지원하려면 토큰별
상태 확인이 필요해 조회가 돌아오고(§2.2), 캐시 전략은 양쪽에 동일하게 적용 가능하다. 실제 절감분은
"액세스 토큰 수명 동안의 인덱스 단일행 조회"이며, 병목 여부는 측정으로 판단한다(재검토 조건).

**Q. stateless라서 확장에 유리하지 않나?**
우리 앱 서버도 무상태다. 상태는 공용 DB에 있고 sticky session이 필요 없다(§1.1). 확장 제약은
인메모리 세션의 문제다.

**Q. JWT+리프레시가 표준 아닌가?**
OAuth는 제3자 위임 표준이다. IETF BCP 초안 §7.1은 same-domain 프런트+API 앱을 "OAuth를 쓰지
않는" 범주로 범위 밖 처리하며, 우리가 그 범주다(§4.1). 2015~2020년 SPA 관행에는 당시의 이유
(도메인 분리, 모바일 쿠키의 어려움)가 있었고, 2023~2026년 권고(IETF·OWASP)는 쿠키·BFF 방향이다.

**Q. 모바일은 쿠키가 어렵지 않나?**
맞다. 그래서 모바일은 Bearer로 전달한다(§3.5). 모바일이 요구하는 것은 Bearer 전달이지 JWT
형식이 아니며, 세션 테이블은 하나다.

**Q. 액세스 토큰 TTL을 짧게 잡으면 무효화 문제가 사라지지 않나?**
15분 창은 "비밀번호 변경 시 다른 기기 로그아웃"(PROF-03)에 부적합하다. 1분 수준으로 줄이면
분당 재발급 왕복이 생겨 비용 구조가 우리 안으로 수렴하고, 레이어 복잡도만 남는다.

**Q. 리프레시 토큰 회전이 탈취 감지에 유리하지 않나?**
회전 + 재사용 감지는 유효한 기법이고, XSS 외 경로의 탈취에도 작동한다. 다만 불투명 토큰에도
동일하게 적용 가능한 패턴이므로 JWT 채택의 근거가 되지는 않는다. 필요해지는 시점에 세션 토큰
회전으로 같은 테이블 위에 추가한다(§5).

**Q. 마이크로서비스로 분리하면?**
그 시점에 세션 테이블 **위에** JWT 액세스 레이어를 얹는다. 기존 세션 토큰이 리프레시 토큰 역할을
그대로 수행하므로 서버 측은 재작성이 아니라 추가다(§7).

**Q. SSR로 전환하면?**
쿠키는 문서 요청에 자동으로 붙으므로 그대로 동작한다. localStorage JWT는 서버로 전송되지 않아
이 경우 쿠키 전환이 필요하다(§3.3).

**Q. 쿠키는 CSRF가 있지 않나?**
맞다. 결정-0014 §결정 3에 CSRF 방어를 명시했고, IETF 초안 §6.1.3.3도 같은 요구를 한다. 알려진
문제에 알려진 대응이 있는 경우다.

**Q. JWT는 서명되어 있어 안전하지 않나?**
서명은 무결성(위조 방지)을 준다. 기밀성도 폐기 가능성도 주지 않는다. 유출된 유효 JWT는 서명이
멀쩡한 채로 만료까지 사용 가능하다.

## 7. 이 결정이 바뀌어야 하는 조건, 그리고 전환 경로

**JWT 액세스 레이어가 실제로 옳은 상황이 있다.** 다음 중 하나라도 해당되면 이 결정은 재검토된다.

1. **리소스 서버가 여러 개**이고 각자 독립적으로 검증해야 할 때 — 중앙 세션 조회가 단일 장애점·병목이 된다.
2. **제3자 개발자에게 API를 개방**할 때 — 위임 범위(scope)·동의·클라이언트 신뢰 경계가 필요하며,
   그것이 OAuth의 목적이다.
3. **인가 서버와 리소스 서버가 다른 주체이거나 물리적으로 분리**될 때 — RFC 9068이 드는 조건.
4. **세션 조회가 측정된 병목**일 때 — 추정이 아니라 측정.
5. **프런트와 API가 다른 오리진**에 있고 교차 사이트 쿠키를 신뢰하기 어려울 때.

현재 우리는 다섯 중 어디에도 해당하지 않는다 — 모듈러 모놀리스, 자체 프런트 전용, same-origin,
트래픽 미측정 단계.

**우리가 감수하는 비용**도 다시 명시한다:

- 요청마다 세션 조회 1회. 캐시를 도입하는 날에는 캐시 무효화 설계가 숙제로 생긴다.
- 모든 요청의 인증 가용성이 DB 가용성에 결합된다. (캐시된 JWT 검증은 DB 장애를 일부 견딘다.
  현 단계에서는 어차피 도메인 로직도 같은 DB에 의존하므로 실질 차이는 작지만, DB를 분리·복제하는
  시점에는 세션 조회의 복제 지연 처리가 설계 항목이 된다.)

**전환 경로의 비용 구조:**

```
우리 안 → JWT 액세스 안 :  서버 — session 테이블 유지, 위에 JWT 발급·검증 추가.
                           기존 세션 토큰이 리프레시 토큰 역할 수행. → 추가 작업
                           클라이언트 — 토큰 2개 관리·401 인터셉터·재발급 경합 처리를
                           그 시점에 구현. 배포된 모바일 앱은 전환 기간 병행 지원. → 이연된 작업

JWT 액세스 안 → 우리 안 :  클라이언트의 재발급 코드를 걷어내고 쿠키 전달·CSRF를 새로 넣는다.
                           → 양방향 재작업
```

서버 측 전환은 비대칭적으로 우리 안이 유리하다(추가 vs 재작업). 클라이언트 측 재발급 복잡도는
전환 시 어차피 지불해야 하므로 "면제"가 아니라 **"필요가 확인될 때까지의 이연"**이다 — 그리고
지금 필요하지 않은 레이어를 나중에 얹을 수 있다면, 지금 얹지 않는 쪽이 낮은 위험이다.
