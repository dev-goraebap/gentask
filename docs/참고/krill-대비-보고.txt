Krill 디자인 시스템 — 대비 검증 보고
====================================

보고일   : 2026-08-03
검증 대상: krill.css (skills-lock 해시 878f39a58ca61724d972985271c264f869c079f59988b06ac33a3cedf185e168)
검증 주체: webapp-devkit 저장소의 web/src/app/styles/contrast.spec.ts
연락 맥락: webapp-devkit이 Krill을 프런트엔드 디자인 시스템으로 채택하며(결정-0024)
           팔레트 대비를 자동 검증하도록 테스트를 붙였고, 그 과정에서 나온 결과다.

이 문서는 Krill 쪽에 전달하기 위한 것이다. 발견 1건은 수정이 필요해 보이고,
1건은 문서상 용도 표기를 좁히는 것으로 충분해 보인다.


------------------------------------------------------------------------
요약
------------------------------------------------------------------------

  [수정 권고] 다크 모드 --color-border-control 이 WCAG 1.4.11(3:1) 미달
              라이트 3.02 / 3.24  →  통과
              다크  2.67 / 2.71  →  미달

  [표기 조정] --color-fg-faint 가 라이트에서 AA(4.5:1) 미달
              라이트 3.20 / 3.44  →  본문·캡션에 쓰면 미달
              다크  4.44 / 4.10  →  통과

  그 외 검증한 조합 54건은 모두 통과했다. 특히 시그널 색이 "표면 위 텍스트"와
  "soft 배경 위 칩" 두 조건을 동시에 4.5:1로 만든다는 krill.css의 주석은
  라이트·다크 양쪽에서 실제로 성립함을 확인했다.


------------------------------------------------------------------------
발견 1 — 다크 모드 border-control 이 3:1에 못 미친다  [수정 권고]
------------------------------------------------------------------------

현재 값
  라이트 : --color-border-control: oklch(0.645 0.012 110);
  다크   : --color-border-control: oklch(1 0 0 / 0.3);

측정된 대비 (반투명 값은 뒤에 깔린 면 위에 합성한 뒤 계산)

  모드     조합                                대비    기준   판정
  ------   ---------------------------------   -----   ----   ----
  라이트   border-control / background          3.02   3:1    통과
  라이트   border-control / surface             3.24   3:1    통과
  다크     border-control / background          2.67   3:1    미달
  다크     border-control / surface             2.71   3:1    미달

왜 이것이 면제 대상이 아닌가

  krill.css 주석은 장식선(border, border-strong)에 1.4.11을 적용하지 않는
  근거를 이렇게 밝힌다 — "이 선들이 사라져도 컴포넌트를 식별하지 못하게
  되지는 않기 때문". 이 판단에는 동의한다.

  같은 주석이 border-control 은 다르다고 말한다 — "폼 컨트롤의 테두리는
  '여기가 입력란'임을 알리는 유일한 시각 정보라 1.4.11 대상이다. 그래서 3:1을
  만족하는 별도 토큰을 둔다." 즉 이 토큰의 존재 이유 자체가 3:1이다.

  라이트가 3.02로 기준을 아슬하게 넘도록 조정된 흔적이 보이는 것으로 미루어,
  다크는 같은 계산을 거치지 않은 것으로 짐작한다.

제안하는 값

  --color-border-control: oklch(1 0 0 / 0.34);

  결과: background 위 3.09, surface 위 3.12

  0.30에서 0.34로 0.04만 올리면 기준을 넘는다. 0.34는 두 조건을 모두
  만족시키는 최소값이라, "은은한 톤이 정체성"이라는 설계 의도를 거의
  그대로 둔 채 기준만 넘긴다. 육안으로 구분하기 어려운 차이다.

webapp-devkit 쪽 임시 조치

  krill.css 는 손대지 않고 프로젝트 진입점(web/src/styles.css)에서 이 토큰
  하나만 덮어썼다. 업스트림에 반영되면 그 블록을 지운다.

    .dark {
      --color-border-control: oklch(1 0 0 / 0.34);
    }


------------------------------------------------------------------------
발견 2 — fg-faint 가 라이트에서 AA에 못 미친다  [표기 조정 제안]
------------------------------------------------------------------------

현재 값
  라이트 : --color-fg-faint: oklch(0.63 0.02 110);   /* 플레이스홀더·캡션 */
  다크   : --color-fg-faint: oklch(0.58 0.02 110);

측정된 대비

  모드     조합                          대비    AA 기준   판정
  ------   ---------------------------   -----   -------   ----
  라이트   fg-faint / surface             3.44   4.5:1     미달
  라이트   fg-faint / background          3.20   4.5:1     미달
  다크     fg-faint / surface             4.10   4.5:1     미달
  다크     fg-faint / background          4.44   4.5:1     경계

논점

  토큰 설명이 "플레이스홀더·캡션"이다. 이 둘은 접근성 기준이 다르다.

  - 플레이스홀더: 값의 예시를 보여주는 보조 정보이고, 라벨이 따로 있으면
    유일한 정보원이 아니다. 낮은 대비를 두는 관행이 있다.
  - 캡션: 읽어야 하는 본문 텍스트다. 1.4.3의 예외가 아니므로 4.5:1이 필요하다.

  값을 올리면 "옅은 회색"이라는 이 토큰의 쓸모가 사라지므로, 값을 바꾸기보다
  용도 표기를 좁히는 편이 맞다고 본다.

제안

  (a) 토큰 설명에서 "캡션"을 뺀다 — 플레이스홀더 전용으로 표기한다.
  (b) 캡션·보조 본문에는 fg-muted 를 쓰도록 문서에 한 줄 남긴다.
      (fg-muted 는 라이트 표면 위 6.0:1 수준으로 여유가 있다)
  (c) 값 자체를 바꾸는 것은 권하지 않는다 — 3단 전경 스케일의 폭이 좁아진다.

webapp-devkit 쪽 조치

  fg-faint 를 플레이스홀더 전용으로 못박고, 대비 테스트에서 3:1로 고정했다.
  본문·캡션에는 fg-muted 를 쓴다.

계산 절차

  1. krill.css 의 @theme 블록에서 라이트 토큰을, .dark 블록에서 다크 토큰을
     정규식으로 뽑는다. 값을 하드코딩하지 않으므로 krill.css 를 갈아끼우면
     그 값으로 다시 검증된다.
  2. OKLCH → OKLab → LMS → 선형 sRGB → 감마 인코딩 sRGB 로 변환한다.
     색역을 벗어난 값은 브라우저와 같이 [0,1]로 자른다.
  3. 알파가 있는 값(다크의 보더들)은 뒤에 깔린 면 위에 감마 공간에서
     합성한 뒤 계산한다 — 브라우저의 합성 방식과 맞춘다.
  4. WCAG 2.x 상대휘도 공식으로 대비비를 낸다.

검산

  oklch(1 0 0) 대 oklch(0 0 0) = 21.00 (이론값 21:1)

검증한 조합

  텍스트 (AA 4.5:1)
    fg / background · surface · elevated · chrome
    fg-muted / background · surface · muted
    primary / background · surface · primary-soft
    primary-fg / primary · primary-hover
    fg-inverse / danger
    success · warning · info · danger / surface
    success · warning · info · danger / 각자의 -soft

  비텍스트 (1.4.11 3:1)
    border-control / background · surface
    primary / background
    danger / background
    fg-faint / background · surface   (본문 금지 토큰으로 취급)

  의도적으로 검증하지 않은 것
    border, border-strong — krill.css 가 밝힌 면제 근거를 그대로 받아들였다.
    장식선을 진하게 만들어 미감을 깨는 대신 필요한 곳에만 진한 선을 두는
    판단은 1.4.11의 취지에 어긋나지 않는다.


------------------------------------------------------------------------
참고 — Krill 채택 과정에서 좋았던 점
------------------------------------------------------------------------

수정 요청만 담으면 균형이 맞지 않아 함께 적는다.

  - 타이포 토큰이 크기·굵기·자간·행간을 한 세트로 묶어 두어, 이전 시스템에서
    쓰던 역할 기반 이름(text-headline-lg 등)이 그대로 맞물렸다. 교체 비용이
    예상보다 훨씬 작았던 가장 큰 이유다.
  - 장식선과 폼 컨트롤 테두리를 나눈 판단이 이전 시스템보다 정교하다.
    이전에는 모든 경계선에 3:1을 요구해 톤이 탁해졌다.
  - 시그널 색을 "표면 위 텍스트"와 "soft 배경 위 칩" 두 조건으로 동시에 푼
    것이 실제로 성립함을 확인했다. 칩을 만들 때 색을 다시 고르지 않아도 된다.
  - 간격 토큰을 만들지 않고 Tailwind 기본 스케일을 쓰는 결정이 이전 시스템과
    같아, 그 부분은 아예 손댈 것이 없었다.
