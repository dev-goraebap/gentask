# 유스케이스 작성 지침

본 지침은 이바 야콥슨(Ivar Jacobson), 이언 스펜스(Ian Spence), 키스 데 멘돈카(Keith de Mendonca)의 **Use-Case 3.0**(*The Guide to Succeeding with Use Cases – Refreshed*, May 2024, 79쪽)을 기준으로 합니다. 쪽수는 같은 폴더의 [Use-Case_3.0_2024.pdf](./Use-Case_3.0_2024.pdf)를 따릅니다.

- 원문 eBook: [Ivar Jacobson International](https://www.ivarjacobson.com/publications/books/use-case-30-ebook)
- 실무 요약 해설: Simon Martinelli의 [Use-Case 3.0 해설](https://martinelli.ch/use-case-3-0-the-refreshed-guide-to-driving-development-with-use-cases/)

Use-Case 3.0에서 직접 다루지 않는 유스케이스 판별 및 세부 문장 규칙은 앨리스터 코번(Alistair Cockburn)의 **《Writing Effective Use Cases》**를 따르며, 이는 하단의 [3. 유스케이스 판별 및 문장 규칙 (Cockburn)](#3-유스케이스-판별-및-문장-규칙--cockburn) 절에서 다룹니다.

### 기본 용어

- **기본 흐름 (Basic Flow)**: 목표 가치에 도달하는 가장 대표적인 정상 경로입니다. (주요 성공 시나리오, 해피 패스) (p.9)
- **대체 흐름 (Alternate Flows)**: 특수 사례, 대안 경로, 선택적 단계, 오류 처리 등 기본 흐름에서 벗어나는 모든 경로를 한 목록에서 다룹니다. (p.9)

## 1. 유스케이스 식별 원칙

유스케이스 하나는 **주 액터의 단일 목표(Goal)**를 나타냅니다.

> "A use case is all the ways of using a system to achieve a goal of a particular user." (p.4, p.6)

유스케이스는 단순한 한 갈래의 실행 경로가 아니라, **목표를 달성하기 위한 모든 경로(성공·난관·실패)**를 포괄합니다. (p.6)

### 필수 3요소

유스케이스를 식별할 때는 다음 세 가지 요소가 명확히 정의되어야 합니다.

| 요소 | 정의 및 역할 |
| :--- | :--- |
| **관심 시스템 (System of Interest)** | 시스템의 경계 (무엇이 시스템 내부이고 무엇이 외부인지) (p.6) |
| **주 액터 (Primary Actor)** | 목표를 가지고 유스케이스를 능동적으로 개시하는 역할 (직무명이 아닌 역할) (p.6) |
| **목표 (Goal)** | 유스케이스가 성공했을 때 주 액터가 얻는 실질적 가치 (p.6) |

- **주 액터와 지원 액터**: 유스케이스를 시작하는 쪽이 주 액터이며, 시스템이 호출하거나 협력하는 외부 주체는 **지원 액터(Supporting Actor)**입니다. (p.6)
- **역할 기반 추상화**: 액터는 구체적인 직책이나 인물이 아닌 '역할'로 묶습니다. 예를 들어 악기점 시스템에서 기타리스트, 학부모, 밴드 매니저를 각각 두지 않고 **구매자**라는 하나의 역할로 추상화합니다. 상품마다 유스케이스를 나누지 않으며, 상호작용 방식과 목표가 같다면 하나의 유스케이스로 다룹니다. (p.7)
- **유스케이스가 아닌 것**: 동일한 목표에 이르는 다른 경로는 별도 유스케이스가 아니라 **대체 흐름**으로 다룹니다. (p.9, p.17) 화면이나 CRUD 단위로 쪼개는 안티패턴은 [3절](#3-유스케이스-판별-및-문장-규칙--cockburn)에서 다룹니다.
- **슬라이스와의 구분**:
  - **유스케이스**: 목표를 달성하는 모든 경로의 집합입니다. (p.6)
  - **유스케이스 슬라이스**: 특정 시점에 구현하고 검증할 수 있도록 종단간(End-to-End)을 관통하는 한 조각이며, 명시적인 테스트 케이스를 동반합니다. (p.6, p.27) 본 저장소에서는 슬라이스 하나가 백로그의 Story 하나이며 서술서에는 적지 않습니다.
- **점진적 발견**: 시작 시점에 모든 유스케이스를 완벽히 찾아낼 필요는 없습니다. 당장 가치를 제공하는 핵심 유스케이스부터 식별하고, 개발을 진행하며 점진적으로 확장합니다. (p.37)

## 2. 서술서 작성법

서술서의 핵심은 **구조적 명확성**입니다. 기본 흐름과 대체 흐름을 명확히 가려 두면, 시스템 사용 방식을 안내하는 훌륭한 지도가 됩니다. (p.9)

처음부터 길고 상세하게 작성할 필요는 없으며, **정확하고 가벼운 개요(Bullet points)**로 시작한 뒤 필요한 시점에 점진적으로 구체화합니다. 중요한 것은 정확성이지 상세량의 많고 적음이 아닙니다. (p.9, p.17)
- 초안 작성 예시: [작성초안 예제](./예제/작성초안%20예제.md)

### 최소 작성 양식 (초안)

```text
# [ID] [유스케이스 이름]

- 목표: 성공했을 때 액터가 얻는 실질적 가치
- 주 액터: 개시하는 역할 (단수형)
- 지원 액터: 호출되는 외부 시스템/역할 (없으면 '없음')
- 트리거: 유스케이스가 시작되는 계기/조건

## 기본 흐름 (Basic Flow)
1. 액터가 …한다.
2. 시스템이 …한다.

## 대체 흐름 (Alternate Flows)
- [조건/상황 이름]
- [조건/상황 이름]
```

- **목표 작성**: 유스케이스 이름을 동사형으로 단순 반복하지 않습니다. 예를 들어 `작업 추가`의 목표를 `작업을 적어둔다`로 쓰지 않고, `떠오른 일을 목록에 남겨, 기억에 의존하지 않는다`처럼 **사용하는 이유와 성공 시 얻는 가치**를 명시합니다. (p.6)
- **트리거 작성**: 트리거는 단계 번호를 매기는 상호작용 단계가 아니라 유스케이스가 시작되는 계기나 조건입니다. 원문 그림 5는 번호 앞에 *"The use case starts when …"* 을 둡니다. (p.10) `할 일이 떠올랐다`는 시작 조건(트리거)이며, 1단계 번호는 액터가 시스템과 첫 상호작용을 개시하는 행위부터 시작합니다.

### 기본 흐름 (Basic Flow)

- 목표를 달성하는 가장 단순하고 대표적인 성공 경로 **하나**만 작성합니다. (p.9, p.16)
- 각 단계는 **액터나 시스템이 무엇을 하는가**입니다. (p.9) 의도를 적고 조작을 적지 않는 문장 규칙은 [3절](#3-유스케이스-판별-및-문장-규칙--cockburn)을 따릅니다.
- 기본 흐름을 작성하는 동안 떠오르는 예외나 대안은 대체 흐름 섹션에 **조건 이름만** 메모해 두고 기본 흐름 작성에 집중합니다. (p.17)

### 대체 흐름 (Alternate Flows)

> "A list of all the special cases, alternative paths, optional steps, and errors that need to be handled." (p.9)

- 오류 처리뿐만 아니라 **선택적 단계, 특수 사례, 또 다른 성공 경로, 실패 상황**을 모두 한 목록에서 다룹니다. (p.9)
- 초안 단계에서는 세부 절차를 길게 풀지 않고 **조건 이름만** 간결하게 나열합니다. (p.9 그림 5, p.17)
  - 예: `제목이 비어 있다`, `기한을 지정한다`, `미리 알림을 설정한다`, `작성을 취소한다`, `등록에 실패한다`
- **선택적 단계 간의 조합은 새로운 대체 흐름이 아닙니다.** 예를 들어 `기한을 지정한다`와 `미리 알림을 설정한다`는 각각 독립된 대체 흐름 항목입니다. `기본 흐름 + 기한`, `기본 흐름 + 기한 + 알림`, `기본 흐름 + 알림`은 이러한 흐름들을 조합하여 통과하는 **실행 경로(Path)**입니다. (p.28–29)
  - 조합마다 대체 흐름을 개별 생성하면 선택 항목이 늘어날 때마다 조합의 수가 기하급수적으로 증가합니다.
  - 현재 검증할 구체적인 조합은 슬라이스와 테스트 케이스 단계에서 선택합니다.
  - 한쪽이 다른 쪽에 의존한다고 **정한 경우에만** 그 대체 흐름 안에 전제로 적습니다. 알림이 기한 없이 성립하면 전제로 두지 않습니다.
- 해당 경로를 다루는 슬라이스를 구현할 시점이 되었을 때 구체적인 단계를 작성합니다. (p.19)
  - 상세 구체화 예시: [대체흐름 구체화 예제](./예제/대체흐름%20구체화%20예제.md)

### 상세화 수준

- **가벼운 서술(Storytelling)**로 시작합니다. (p.43, p.46)
- 형식적인 상세 명세는 계약, 규제, 안전 등 엄격한 요구가 필요한 경우에만 제한적으로 적용합니다. (p.50)
- **테스트 케이스 동반**: 슬라이스의 구현 완료 여부는 테스트 케이스를 통해 증명됩니다. (p.18) 테스트 케이스가 갖춰지지 않은 슬라이스는 아직 구현 준비가 완료된 것이 아닙니다. (p.40)

### 슬라이스와 백로그

슬라이스는 특정 시점에 구현하고 검증할 종단간(End-to-End) 조각이며, 명시적인 테스트 케이스를 동반합니다. (p.6, p.27) 원문은 서술서 안의 추적 표로 슬라이스를 관리하지만 (p.32), 본 저장소는 **슬라이스를 백로그의 Story 로만** 관리하며 서술서에는 슬라이스 절을 두지 않습니다. 서술서는 흐름까지만 갖습니다.

백로그의 형식과 운영은 `plz-help-issues` 스킬을 따릅니다. 이 절은 유스케이스와 백로그가 만나는 자리만 적습니다.

```
Epic                 한시적 이니셔티브 (발견 · 전달)
  └─ Story           슬라이스 하나. 한 이터레이션에 끝낼 분량. 서술서를 가리킨다
       (Task         독립 완료 조건이 있는 기술 작업. 프로토타입은 발견 에픽의 스파이크 Task)
```

유스케이스는 계층에 칸이 없습니다. Story 를 자르는 사고 도구이자 묶는 단위이며, 서술서가 그 기록입니다.

원문의 작업 항목(Work Item)은 Story 와 Task 에 해당합니다. (p.5–6, p.40) 1인 개발에서는 Story 하나가 곧 작업 항목 하나입니다.

#### 슬라이스 크기

흐름 하나를 Story 하나로 만들지 않습니다. 원문은 슬라이스를 "테스트 케이스 하나만큼 작게도, 흐름 여럿만큼 크게도" 잡을 수 있다고 하고, 기준을 팀이 작업하기 알맞은 크기에 둡니다. (p.29, p.38) 본 저장소의 기준은 **한 번 앉아 끝내고 확인하는 분량**입니다.

| 규칙 | 근거 |
| :--- | :--- |
| 기본 흐름이 첫 Story 입니다. 같은 입력 요소에서 갈라지는 검증 · 그만두기 흐름은 거기에 넣습니다. | 한 입력란의 동작을 나누면 `it` 하나짜리 Story 가 됩니다. |
| 같은 단계에서 갈라지고 같은 장치로 처리되는 흐름은 한 Story 입니다. 실패 · 없는 대상 · 이미 완료됨은 유스케이스마다 하나로 묶습니다. | 원문 예시가 `Alt 3 결제 정보 오류` 와 `Alt 4 결제 시스템 불능` 을 `Slice 4 – Handle Payment Problems` 하나로 묶습니다. (p.11) |
| 새 입력 요소나 별도 장치(확인 대화, 정렬)가 생기는 흐름은 따로 자릅니다. | 한 번에 끝나지 않습니다. |
| 아직 결정이 안 난 흐름은 자르지 않습니다. `BACKLOG.md` 의 나중 구획에 한 줄로 둡니다. | "범위 밖이거나 지금 중요하지 않은 흐름은 자르지 않고 남겨 둔다." (p.11) |

#### Story 이름과 본문

| 자리 | 내용 |
| :--- | :--- |
| **이름** | **목적어 + 조건 + 동사**. `제목만으로 작업 추가`. 목적어와 동사는 유스케이스 이름에서, 조건은 지나는 흐름에서 가져옵니다. 흐름의 조건 이름(`빈 제목`, `대상이 없다`)을 그대로 쓰지 않습니다. |
| **서술서 줄** | 서술서 링크와 지나는 흐름(`BF, A2`). 스킬 템플릿에는 없지만 서술서를 유지하는 프로젝트라 둡니다. |
| **인수 조건** | 묶인 흐름마다 한 문장 이상. EARS 로 씁니다. 조작은 적지 않습니다. |
| **메모** | 프론트 · 백엔드에서 **하기로 한 것**. 조작의 선택, 화면 동작, 공통 규칙에서 벗어난 점, API 모양. 아키텍처를 바꾸지 않는 요구사항별 기술 판단의 자리입니다. 같은 판단이 두 번째 Story 에 나타나면 참조 문서나 결정 기록으로 올립니다. |

서술서 → Story 는 `backlog/stories/` 에서 유스케이스 ID 검색이, Story → 흐름은 Story 의 서술서 줄이 추적합니다. 흐름을 개정하면 그 ID 로 검색해 해당 흐름을 적은 Story 의 인수 조건을 맞춥니다.

원문(p.27)의 6단계 상태(Identified → Defined → Analyzed → Prepared → Implemented → Verified)는 다음과 같이 읽습니다.

| 원문 상태 | 본 저장소의 표시 |
| :--- | :--- |
| **Identified** | Story 파일이 있거나 `BACKLOG.md` 에 한 줄로 있다. |
| **Defined · Analyzed · Prepared** | 인수 조건이 적혀 있고, 지나는 대체 흐름이 서술서에 구체화되어 있다. 구현을 시작할 수 있는 최소 요건입니다. (p.40) |
| **Implemented** | 화면이 목 위에 있고(스파이크), 백엔드가 연결되어 있다. |
| **Verified** | 실제 연결로 인수 조건을 확인했고 `status: closed` 다. |

#### 인수 조건 작성 및 검증 원칙

- **인수 조건의 정의**: 해당 슬라이스가 성공적으로 구현되었을 때 무엇이 참이어야 하는지를 한 문장으로 기술한 것입니다. (p.27, p.40, p.68) 입력값과 그에 따른 관찰 가능한 결과를 명시하며, 이것이 가장 얇은 형태의 테스트 케이스 역할을 합니다.
- **검증 범위**: 시스템 전체가 아닌 **해당 슬라이스가 관통하는 단일 경로**만을 대상으로 합니다. (p.27)
- **검증 방식**:
  - 초기에는 명시된 성공 조건 문장을 따라 수동으로 시나리오를 검증합니다. (p.68)
  - 같은 길을 여러 번 확인하게 되면 그 경로를 도는 종단 자동화가 같은 문장을 확인합니다. 성공 조건이나 검증 자체를 대체하는 것이 아닙니다. (p.40, p.68–69)
  - 단위 테스트는 세부 로직을 보조하지만, 슬라이스 수준의 성공 조건 검증을 완전히 대체하지는 않습니다. (p.12)
- **풀스택 통합 검증**: 프론트엔드와 백엔드가 분리된 구조의 경우, 슬라이스 경로는 두 계층을 모두 관통하므로 연계하여 종단간으로 검증합니다.
- **문장 서술 일관성**:
  - 기본 흐름에 없는 단계를 성공 조건에 끼워 넣지 않습니다. 확정 단계가 없으면 `등록하면`을 쓰지 않습니다.
  - `등록 버튼을 누르면`은 조작입니다. 확정이 흐름에 있으면 `추가를 확정하면`처럼 의도로 적습니다.

#### 실무 운영 수칙

- 슬라이스 착수 시 그 슬라이스가 지나는 대체 흐름을 서술서에 구체화하고, Story 의 인수 조건을 확정합니다.
- 커밋과 병합 요청은 백로그 ID(플랫폼으로 옮긴 뒤에는 이슈 번호)를 가리킵니다.
- 슬라이스를 자르는 예시는 [슬라이스 예제](./예제/슬라이스%20예제.md)를 참고합니다.

## 3. 유스케이스 판별 및 문장 규칙 (Cockburn)

Use-Case 3.0에서 구체적인 규칙을 제시하지 않는 유스케이스 크기 판별과 문장 작성 수칙은 앨리스터 코번(Alistair Cockburn)의 《Writing Effective Use Cases》를 따릅니다.

- 관련 자료: [Humanizing Work 인터뷰](https://www.humanizingwork.com/alistair-cockburn-on-use-cases-user-stories/), [Writing Effective Use Cases (Addison-Wesley)](https://www.informit.com/store/writing-effective-use-cases-9780201702255)
- Jacobson과 Cockburn 공통 기반 문서: [Use-Case Foundation](https://www.ivarjacobson.com/publications/use-case-foundation)

### 크기 판별을 위한 3대 시험

서술 단위가 올바른 사용자 목표 수준인지 다음 3가지 기준으로 점검합니다.

| 시험 | 검증 질문 |
| :--- | :--- |
| **상사 테스트 (Boss Test)** | 하루 종일 이 작업만 했다고 보고했을 때 상사가 가치 있는 일로 인정하는가? |
| **EBP (Elementary Business Process)** | 한 사람, 한 자리, 한 번의 세션에서 완료되며, 측정 가능한 가치를 남기고 데이터를 일관된 상태로 유지하는가? |
| **크기 테스트 (Size Test)** | 기본 흐름이 대략 3~9단계의 상호작용으로 구성되는가? |

> 위 기준을 통과하지 못하는 단위는 독립된 유스케이스가 아니라 다른 유스케이스의 한 단계이거나 대체 흐름일 가능성이 높습니다.

### 잘못 식별하기 쉬운 대표 사례 (안티패턴)

크기 판별 시험을 통과하지 못하는 단위는 대개 다음과 같은 오류 유형에 해당합니다.

| 잘못된 식별 (안티패턴) | 문제점 | 올바른 접근 방향 |
| :--- | :--- | :--- |
| **데이터 조작 단위로 쪼갬** (작업 생성 / 조회 / 수정 / 삭제) | 사용자 목표 부재 (데이터 중심 기능 분해). 동사가 아니라 **쪼개는 기준**이 문제입니다 | 액터의 목표 단위로 다시 묶습니다. 이름은 제품의 말을 따릅니다(`작업 추가` · `작업 보기` · `작업 편집` · `작업 완료`). 이름이 같은 동사여도 그 아래 목표 문장("떠오른 일을 남겨 기억에 의존하지 않는다")이 하나이고 3대 시험을 통과하면 유스케이스입니다. 넷을 묶어 `작업을 관리한다`로 만들면 과도한 요약층이 됩니다. |
| **상세 패널 열기, 저장하기** | UI 위젯 및 화면 조작 수준 서술 | 화면이 아니라 의도. 적힌 것을 보거나, 현실에 맞게 편집한다. |
| **오늘 보기, 종료 보기, 전체 보기** | 단일 목표의 세부 경로를 유스케이스로 승격 | 단일 유스케이스(`작업 보기`)의 기본 흐름 또는 대체 흐름으로 통합. |
| **로그인, 검색** | 대부분 하위 기능 | 로그인은 다른 유스케이스의 전제일 수 있다. 검색은 `작업 보기`의 단계이거나 대체 흐름이다. |
| **제목 수정, 메모 수정, 기한 수정** | 단일 수정 목표를 개별 필드 단위로 분해 | 단일 유스케이스(`작업 편집`) 내의 통합된 흐름으로 다룸. |

> 상세 비교 예시는 [잘못된 잡기 예제](./예제/잘못된%20잡기%20예제.md)를 참고합니다.

#### 왜 CRUD 분해를 피해야 하는가?
데이터 모델이 먼저 보이면 생성·조회·수정·삭제를 각각 별개의 유스케이스 문서로 나누기 쉽습니다. 그러나 이는 '액터가 시스템을 통해 얻는 가치'가 아니라 '시스템이 DB 레코드에 수행하는 동작'을 기준으로 삼았기 때문입니다.
- **상사 테스트 실패**: 하루 종일 레코드를 생성만 했다고 하면 일을 한 것이 아닙니다. 사용자는 잊지 않으려고 작업을 추가하거나, 적힌 것을 현실에 맞추거나, 지금 손댈 일을 고르려고 시스템을 씁니다. `작업 추가`라는 이름은 그 목표를 제품의 말로 부르는 것이지 레코드 생성을 뜻하지 않습니다.
- **문맥과 시나리오의 파편화**: CRUD로 나누면 동일한 목표를 가진 시나리오가 여러 문서로 흩어집니다. 예를 들어 제목 누락 오류는 `생성`에, 대상 누락 오류는 `수정`에 분리되어 전체 상호작용을 하나의 일관된 스토리로 파악하기 어려워집니다. 나중에 기한을 추가하는 선택적 단계도 어느 유스케이스 소관인지 매번 다시 판정해야 합니다. 목표가 하나라면 유스케이스는 하나이며, 생성·수정·삭제는 그 목표를 달성하기 위한 세부 단계나 대체 흐름에 불과합니다. (조회를 `추가`에 억지로 병합하거나, 서로 다른 4개 목표를 `관리한다` 하나로 뭉뚱그려 올리는 것 역시 동일한 오류입니다.)

#### 기타 대표적 오류 유형
- **UI 및 조작 단위**: 화면 레이아웃이나 위젯 조작을 유스케이스로 올리면 UI가 바뀔 때마다 문서 구조가 함께 흔들립니다.
- **조회 조건(뷰) 분리**: '오늘 보기', '종료 보기', '전체 보기'처럼 조회 조건만 다른 경우는 독립된 유스케이스가 아니라 단일 조회 목표 아래의 대체 흐름입니다.
- **하위 기능 승격**: 로그인이나 검색 등은 대부분 독립된 사용자 가치를 주지 못하며, 다른 핵심 목표를 달성하기 위해 거치는 보조 단계(하위 기능)입니다. (단, 인증 시스템 자체가 제품의 목적인 경우와 같은 예외는 존재합니다.)
- **필드 단위 분해**: 속성(제목, 메모, 기한 등)마다 유스케이스를 만들면 문서가 필드 명세서로 전락합니다. 기존 내용을 수정하는 작업은 `작업 편집`와 같은 단일 유스케이스의 흐름 안에서 통합하여 다룹니다.

### 문장 작성 규칙

- **주어-동사-목적어 명시**: 상호작용의 주체(액터인지 시스템인지)가 명확히 드러나도록 서술합니다.
- **조작이 아닌 의도 중심 서술**: UI 클릭이나 입력 조작이 아니라 사용자의 의도와 시스템의 책임을 서술합니다.
  - (X) `주소 입력 필드를 클릭하고 텍스트를 입력한다.`
  - (O) `배송지 주소를 제공한다.`
- **'검사한다' 대신 '검증한다' 사용**: 검증 성공 시 다음 단계로 진행하며, 실패 시 대체 흐름으로 분기하도록 기술합니다.
- **대체 흐름의 종결 명시**: 처리 절차를 쓸 때, 기본 흐름의 특정 단계로 복귀하는지, 다른 성공으로 종료하는지, 실패로 중단하는지 밝힙니다. 초안에서 조건 이름만 나열할 때는 적지 않습니다.

## 체크리스트

### 유스케이스 식별 시

- [ ] 주 액터와 목표가 한 문장으로 명확히 표현되는가?
- [ ] 성공 경로와 실패/예외 경로가 동일한 목표 아래 묶여 있는가?
- [ ] 화면이나 기능 목록이 아닌 액터의 목표 단위인가?
- [ ] 이번 릴리스에서 검증할 만한 실질적 가치가 있는가?

### 서술서 작성 시

- [ ] 목표에 단순 기능명이 아닌 액터가 얻는 실질적 가치가 서술되어 있는가?
- [ ] 기본 흐름의 각 단계가 '누가 무엇을 하는지'로 적혀 있는가?
- [ ] 대체 흐름에 오류뿐만 아니라 선택/특수 사례가 조건 이름으로 정리되어 있는가?
- [ ] 아직 구현하지 않는 대체 흐름을 불필요하게 미리 상세화하지 않았는가?

### 문장 규칙 적용 시 (Cockburn)

- [ ] 화면 조작(클릭, 버튼 등)이 아니라 의도와 책임으로 적혀 있는가?
- [ ] 풀어 쓴 대체 흐름의 끝이 복귀·다른 성공·실패 중 하나로 밝혀져 있는가?
