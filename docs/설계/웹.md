# 웹 애플리케이션 아키텍처 (Angular)

`web/`의 내부 구조 규칙.
시스템 전반의 구성·배포는 [인프라.md](인프라.md), 소비할 API 계약은 [서버.md](서버.md) §1에 있다.

방법론은 **Feature-Sliced Design(FSD) v2.1**을 채택한다 — 근거는 [결정-0008](../결정기록/결정-0008-프론트엔드-FSD-채택.md).
FSD 자체의 상세 규칙은 `.agents/skills/feature-sliced-design/`(스킬)이 정본이다. 이 문서는 **우리 프로젝트가 내린 선택**만 기록한다.

## 1. 레이어와 import 방향

```
app/       앱 초기화, 프로바이더, 라우팅
pages/     라우트 단위 조합 — 자기 로직을 소유한다
widgets/   여러 페이지가 실제로 재사용하는 큰 UI 블록
features/  여러 곳에서 실제로 재사용하는 사용자 상호작용
entities/  여러 곳에서 실제로 재사용하는 비즈니스 도메인 모델
shared/    비즈니스 로직 없는 인프라 (UI 킷, 유틸, API 클라이언트)
```

- import는 **아래 레이어로만** 향한다. 같은 레이어의 슬라이스끼리 교차 import는 금지다.
- 슬라이스 외부에서는 그 슬라이스의 `index.ts`(공개 API)만 import한다. 내부 파일 직접 참조는 금지.
- `shared`는 슬라이스가 없고 세그먼트별로 공개 API를 둔다(`shared/ui/index.ts` 등).

## 2. 최소로 시작한다 — 키트라고 미리 만들지 않는다

**시작 구성은 `app/` + `pages/` + `shared/` 셋뿐이다.** `widgets/`·`features/`·`entities/` 폴더를 미리 만들어 두지 않는다.

키트는 파생 프로젝트에 구조를 물려주는 성격이라 "레이어를 다 갖춰 보여주고 싶은" 유혹이 있다. 그러나 FSD의 핵심 원칙은 "단순하게 시작하고, 실제로 필요해질 때 추출한다"이고, 빈 레이어는 그 자체로 잘못된 신호를 준다 — 파생 프로젝트가 쓰지도 않을 추상을 채워 넣게 만든다.

추출 조건은 **셋 다** 충족할 때다:
1. 같은 코드가 지금 실제로 두 곳 이상에서 쓰이고 있다 (앞으로 쓸 것 같다는 예상은 불가)
2. 그 사용처들이 항상 함께 변경되지는 않는다
3. 경계의 책임이 하나로 좁다

## 3. 우리 프로젝트의 배치 결정

| 대상 | 위치 | 이유 |
|---|---|---|
| API 클라이언트, 엔드포인트 상수 | `shared/api/` | 인프라. 비즈니스 로직 없음 |
| 인증 토큰·세션 관리 | `shared/auth/` | FSD 권고 — 토큰·로그인 DTO는 인증 문맥 전용이라 `entities/user`로 만들지 않는다 |
| 로그인 폼, 회원가입 폼 | 최초에는 `pages/login/ui/` 등 | 한 페이지에서만 쓰이면 그 페이지에 둔다 |
| 서버 에러 코드 → 사용자 문구 매핑 | `shared/api/` | API 계약(서버.md §1.4)의 클라이언트 측 대응물 |
| 전역 스타일·폰트 | `app/` | 앱 전역 자원 |
| 그 외 정적 자산 | 쓰는 코드 옆 | 최상위 `assets/` 세그먼트를 만들지 않는다 |

파일명은 **도메인 기준**으로 짓는다(`model/user.ts`, `api/fetch-profile.ts`). `types.ts`·`utils.ts` 같은 기술 역할 이름은 서로 무관한 도메인을 한 파일에 섞으므로 쓰지 않는다.

## 4. Angular와의 연결

- 라우트 정의는 `app/`이 소유하고, 각 라우트는 `pages/` 슬라이스의 컴포넌트를 지연 로딩한다. 라우팅 설정 자체가 FSD의 슬라이스가 되지는 않는다.
- 경로 별칭(`@/shared/...`)을 `tsconfig`에 설정해 상대 경로 지옥과 레이어 위반을 동시에 줄인다.
- `@angular/ssr`을 사용하며 렌더링 모드는 라우트별로 다르다(§5). 서버에서 실행될 수 있는 코드가 브라우저 전용 API를 건드리지 않도록 주의한다.
- Angular의 DI·시그널 같은 프레임워크 기능은 FSD와 충돌하지 않는다 — 배치 규칙(어느 레이어·세그먼트인가)과 구현 기술은 별개 축이다.

## 5. 렌더링 모드

라우트별로 렌더링 방식을 정하되, **경계는 URL 접두사로 긋는다** — 근거는 [결정-0011](../결정기록/결정-0011-렌더링-모드-경계.md).

| 영역 | 모드 | 대상 |
|---|---|---|
| 공개 | `RenderMode.Prerender` | `/`, `/login`, `/signup` 등 — SEO·초기 로딩이 중요하고 사용자별 데이터가 없다 |
| 인증 이후 | `RenderMode.Client` | `app/**` — SEO 불필요, 인터랙티브 |
| 그 외 | `RenderMode.Server` | fallback |

**인증 후 화면을 추가할 때 `app.routes.server.ts`를 건드리지 않는다.** `app/` 아래에 라우트만 넣으면 모드가 따라온다. 라우트마다 모드를 명시하면 앱 라우트와 서버 라우트를 이중 관리하게 되어 반드시 어긋난다.

주의: Prerender는 **빌드 시점 값이 구워진다.** 런타임 설정(OAuth 클라이언트 ID 등)에 의존하는 공개 페이지는 그 값을 API로 받거나 `RenderMode.Server`로 바꾼다.

## 6. 데이터 로딩과 에러 상태

인증 후 CSR 영역은 **fetch-then-render**를 쓴다. 라우트 리졸버가 데이터를 확보한 뒤 컴포넌트를 마운트하므로 **페이지 안에 로딩 분기가 없다** — 근거와 기각한 대안은 [결정-0012](../결정기록/결정-0012-CSR-데이터-로딩-전략.md).

### 6.1 라우트 진입 데이터 — 리졸버

- 함수형 `ResolveFn`을 쓰고, 결과는 `withComponentInputBinding()`으로 컴포넌트 `input()`에 바인딩한다. `ActivatedRoute` 주입은 쓰지 않는다.
- **필수 데이터만 리졸버에 넣는다.** 페이지 뼈대를 그리는 데 꼭 필요한 것만이며, 부가 데이터는 화면 안에서 가져온다. 그러지 않으면 가장 느린 API 하나가 페이지 진입 전체를 붙잡는다.
- 리졸버는 캐시를 먼저 확인한다. 재방문 시 즉시 표시되고(SWR), 백그라운드 갱신 중에는 콘텐츠 영역을 비우지 않고 얇은 상단 진행바로만 알린다.

### 6.2 전환 오버레이 — 임계 시간 게이트

전환이 느릴 때만 콘텐츠 영역에 페이드 인/아웃 오버레이를 띄운다. **임계 시간(기본 150ms) 안에 끝나면 아예 띄우지 않는다.**

```
전환 시작 → 타이머 시작(150ms)
  ├─ 만료 전 종료 → 오버레이 표시 안 함
  └─ 만료 → 오버레이 표시 → 전환 종료 시 즉시 해제
```

게이트가 없으면 빠른 전환에서 오버레이가 떴다 사라지며 깜빡인다. 페이드 아웃에도 시간이 걸리므로 더 도드라진다.

### 6.3 화면 안의 갱신 — httpResource

이미 마운트된 화면에서 발생하는 요청(필터 변경, 페이지네이션, 폴링)은 리졸버의 대상이 아니다. `httpResource`/`resource`로 처리하고 로컬 로딩 UI를 쓴다.

**리스트·검색 화면은 특히 주의한다.** 필터를 쿼리 파라미터로 표현하면 조작마다 라우트 전환이 일어나 오버레이가 뜰 수 있다. **진입만 리졸버, 이후 필터 변경은 `httpResource`**로 처리하고, 리졸버 재실행 정책(`runGuardsAndResolvers`)을 함께 확인한다.

모달·버튼 클릭으로 발생하는 요청도 마찬가지로 로컬 로딩 UI를 쓴다.

### 6.4 에러 — 유형별로 분기한다

"에러 화면 하나"로 뭉치지 않는다. **리졸버 에러가 네비게이션을 조용히 취소하게 두지 않는다** — 사용자는 "클릭했는데 아무 일도 안 일어남"을 겪는다.

| 유형 | 처리 |
|---|---|
| 401 | 로그인으로 리다이렉트, 원래 경로를 보존해 로그인 후 복귀 |
| 403 | 권한 없음 페이지로 리다이렉트 |
| 404 | 전용 에러 페이지로 리다이렉트 — URL이 의미를 가진다 |
| 5xx | **같은 URL에 머물며** 재시도 UI — URL은 유효하다 |
| 네트워크 오프라인 | 같은 URL 유지, 오프라인 안내 + 재시도 |
| rate limit | 같은 URL 유지, 대기 안내 |
| validation | 라우트 전환과 무관 — 폼 필드 인라인 표시 |

서버 에러 코드(`AUTH_INVALID_CREDENTIALS` 등)를 사용자 문구로 옮기는 매핑은 `shared/api`에 둔다([서버.md](서버.md) §1.4).

### 6.5 빈 상태 — 세 케이스를 구분한다

- **최초 진입(온보딩)**: 이 화면에서 무엇을 할 수 있는지 안내하고 첫 액션 CTA를 둔다
- **필터·검색 결과 없음**: 적용된 조건을 보여주고 초기화 액션을 제공한다
- **삭제·완료 후**: 완료 톤으로 다음 액션을 제안한다

## 7. 강제 장치 — Steiger

구조 규칙은 **[Steiger](https://github.com/feature-sliced/steiger)**(FSD 공식 린터)로 검사하고 CI 게이트에 포함한다. 서버의 ArchUnit과 같은 역할이다 — 강제 장치 없는 구조는 반드시 부패한다.

주요 규칙: `insignificant-slice`(한 페이지만 쓰는 슬라이스는 그 페이지로 합치라), `excessive-slicing`(슬라이스 과다).

린터가 규칙을 가지므로 이 문서는 규칙 목록을 산문으로 반복하지 않는다 — 린터 설정이 곧 표준이다(AGENTS.md 문서 원칙).

## 8. 규칙을 어길 때

FSD 규칙 위반은 금지가 아니라 **의도적 설계 결정이어야 한다.** 교차 import 등이 불가피하면 다른 전략(슬라이스 병합, 하위 레이어로 내리기, 상위 레이어에서 조립)이 왜 적용되지 않는지 코드 주석으로 남기고, 구조적 판단이면 결정기록에 남긴다.
