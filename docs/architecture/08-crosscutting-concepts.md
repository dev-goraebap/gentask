# 8. 횡단 관심사 (Crosscutting Concepts)

여러 빌딩 블록에 걸치는 규약을 정의합니다. 특정 패키지나 슬라이스에 속하지 않고 코드 전반을 가로지르는 것이 이 절의 대상이며, 코드가 어디에 사는가는 [5. 빌딩 블록 뷰](./05-building-block-view.md)가 갖습니다.

[arc42](https://docs.arc42.org/tips/8-10/) 는 이 절에서 다룰 수 있는 주제를 목록으로 제시하되 전부를 채우지 말라고 명시합니다. 아래는 그 목록 가운데 이 저장소가 실제로 규약을 갖는 것들이며, 규약이 생길 때마다 문서를 더합니다.

## 8.1 개발 개념 (Development Concepts)

빌드 · 테스트 · 코드 생성 · 설정, 그리고 코드를 쓰는 방식입니다. 두 컴포넌트가 서로 다른 도구를 쓰므로 문서를 나눕니다.

| 문서 | 담는 것 |
| :--- | :--- |
| [프론트엔드 01. 개발 환경](./frontend/01-dev-environment.md) | 구성 파일, 명령, 경로 별칭, 줄바꿈 정책, 강제 수단의 적용 범위와 예외 |
| [프론트엔드 02. 코드 스타일 가이드](./frontend/02-code-style.md) | 네이밍 · 코드 구조 · TypeScript 관용구 · 주석 · 에러 처리 · 테스트 스타일 (`FE-STY-NNN`) |
| [백엔드 01. 개발 환경](./backend/01-dev-environment.md) | 구성 파일, JVM 요건, 로컬 실행, 빌드 단계, 정적 분석의 분담 |
| [백엔드 02. 코드 스타일 가이드](./backend/02-code-style.md) | 네이밍 · 코드 구조 · Java 관용구 · 주석 · 에러 처리 · 테스트 스타일 (`BE-STY-NNN`) |

스타일 가이드는 두 축이 같은 아홉 절 구성을 씁니다. 각 규칙은 **필수 · 권장 · 취향** 중 하나로 표시하고 `<축>-STY-NNN` 식별자를 가지므로 리뷰에서 번호로 지목할 수 있습니다. 규칙은 한 줄, 근거는 한 줄이며 길어지는 논증은 결정 기록으로 보냅니다.

**포매팅은 어느 쪽도 문서에 적지 않습니다.** 도구가 유일한 기준이며 그 설정과 설치는 개발 환경 문서가 갖습니다.

두 축의 개발 환경 문서는 같은 원칙을 공유합니다. **설정값을 문서에 옮겨 적지 않고 설정 파일을 참조합니다.** 두 벌이 되면 한쪽이 낡기 때문이며, 문서는 규칙과 근거를, 설정 파일은 그 실행 형태를 갖습니다.

**자동 강제되지 않는 규칙은 그 사실을 함께 적습니다.** 강제되는 것과 그렇지 않은 것을 구분하지 않으면 전자만 지켜지고 후자는 지켜지는 것으로 오인됩니다.

## 8.2 그 밖의 주제

아직 문서로 옮기지 않은 주제입니다. 각 항목은 arc42 가 제시하는 범주에 대응합니다. 에러 처리와 테스트는 **작성 방식만** 스타일 가이드가 가져갔고, 응답 형식과 검증 수준의 설계는 여기 남습니다.

| 범주 | 주제 |
| :--- | :--- |
| **사용자 경험** | 디자인 시스템, 레이아웃, 적응형 UI, 접근성 |
| **안전과 보안** | 인증과 세션, 권한 판정, 입력 검증 |
| **내부 동작** | 영속성, 트랜잭션, 조회와 명령의 분리, 에러 코드 체계와 응답 형식, API 계약의 생산과 소비 |
| **운영 개념** | 로그 수집과 추적 식별자의 전파 |

시각 언어의 값과 근거는 아키텍처 문서가 아니라 `web/docs/design/DESIGN.md` 가 소유합니다. 그 경계의 근거는 [결정-0001](./decisions/0001-frontend-design-outside-architecture.md)에 있습니다.
