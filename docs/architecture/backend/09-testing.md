# 09. 테스트

본 문서는 계층별 검증 수준과 제외 범위를 정의합니다.

## 1. 수준별 대상

| 수준 | 대상 | 요건 |
| :--- | :--- | :--- |
| **단위** | 도메인의 불변식과 판정 | 애플리케이션 컨텍스트 없이 돕니다 |
| **구조** | 배치와 참조 규칙 | ArchUnit. [02. 패키지 배치와 참조 규칙](02-package-structure.md) 5절 |
| **통합** | HTTP 에서 데이터베이스까지의 경로 | 컨테이너로 실제 데이터베이스를 띄웁니다 |

**도메인 테스트가 컨텍스트를 요구하기 시작하면 계층 분리가 이름만 남습니다.** 그래서 그 요건을 테스트 자체가 지킵니다 — 스프링 애노테이션 없이 `new` 로 만들어 검증합니다.

**서비스의 단위 테스트를 두지 않습니다.** 명령 서비스는 애그리거트를 꺼내 메서드를 부르고 저장하는 조율이고, 조회 서비스는 포트의 결과를 그대로 전달합니다. 협력자를 가짜로 바꿔 그 흐름을 확인하면 **가짜가 진짜처럼 동작한다는 것을 확인할 뿐**입니다. 그 경로는 통합 테스트가 실제 구현으로 지납니다.

## 2. 슬라이스 식별자

**그 슬라이스의 경로를 처음부터 끝까지 지나는 테스트에만** 붙입니다. 통합 테스트가 여기 해당하며, 이름은 인수 조건의 문장을 그대로 씁니다.

```java
@DisplayName("TK-001 S1: 제목을 적으면 목록에 그 작업이 있다")
```

단위 테스트에는 붙이지 않습니다. 함수 하나의 검증이 성공 조건을 이름으로 가지면 **그 경로가 닫혔다는 거짓 주장**이 됩니다. 단위 테스트는 그 단위가 보장하는 것을 이름으로 갖습니다.

부여 규칙의 원본은 [프로세스 문서](../../process.md)입니다.

## 3. 통합 테스트

| 항목 | 규약 |
| :--- | :--- |
| **데이터베이스** | 컨테이너로 띄웁니다. 로컬 개발용과 분리합니다 |
| **마이그레이션** | 실제로 적용합니다 — 코드 생성은 SQL 파서를 통과하는 것까지만 보장합니다 |
| **격리** | `@Transactional` 로 각 테스트 뒤에 되돌립니다 |
| **진입점** | HTTP 입니다. 서비스를 직접 부르면 컨트롤러의 배선이 빠져도 통과합니다 |

**HTTP 로 들어가는 것이 이 수준의 핵심입니다.** 요청 검증과 직렬화 형식과 상태 코드는 컨트롤러를 지나야 확인되며, 그 셋이 계약의 대부분입니다.

## 4. 검증하지 않는 것

| 대상 | 이유 |
| :--- | :--- |
| **생성 코드** | 우리가 쓰지 않았습니다 |
| **프레임워크 동작** | 그쪽의 테스트가 있습니다 |
| **조회 서비스** | 로직 없이 전달합니다. 통합 테스트가 지납니다 |
| **접근자와 record 의 기본 동작** | 컴파일러가 만든 것입니다 |

## 5. 실패의 재현

테스트 실패는 **로그만으로 원인을 알 수 있어야 합니다.** 빌드 설정이 실패 시 전체 스택트레이스를 남기며, 그러지 않으면 CI 로그를 보고도 로컬에서 다시 돌려야 합니다.

버그를 고칠 때는 **그 버그를 재현하는 테스트를 먼저 씁니다.** 통과하는 테스트를 나중에 붙이면 그것이 정말 그 버그를 잡는지 확인할 수 없습니다.
