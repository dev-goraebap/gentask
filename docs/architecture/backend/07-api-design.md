# 07. API 설계

본 문서는 엔드포인트의 형태와 응답 규약을 정의합니다. 실패 응답의 형식은 [08. 예외 · 에러 코드](08-error-handling.md)가 소유합니다.

**계약의 소유자는 서버입니다.** 계약을 바꾸는 것은 서버의 변경이며 클라이언트는 소비자로서 그것을 참조합니다.

## 1. 경로

```text
/api/v1/tasks
/api/v1/tasks/{taskId}
```

| 규약 | 내용 |
| :--- | :--- |
| **접두사** | `/api` 로 시작합니다. 정적 자원과 섞이지 않습니다 |
| **버전** | 경로에 둡니다 (`/v1`) |
| **자원 이름** | 복수형 명사입니다 |
| **동사** | 쓰지 않습니다. 행위는 메서드가 나타냅니다 |
| **식별자** | 경로 변수이며 이름은 `<자원>Id` 입니다 |

버전을 헤더가 아니라 경로에 두는 이유는 **눈에 보이기 때문**입니다. 브라우저 주소창과 로그와 문서에서 어느 판을 부르는지가 드러나고, 클라이언트가 헤더를 빠뜨려 기본 판으로 떨어지는 일이 없습니다. 대가는 URL 이 길어지는 것과, 판이 갈릴 때 경로가 두 벌이 되는 것입니다.

### 상태를 바꾸는 요청

동사 대신 **바꾸려는 것을 하위 자원으로** 둡니다.

```text
PATCH /api/v1/tasks/{taskId}/completion     완료 여부
PATCH /api/v1/tasks/{taskId}/importance     중요 표시
PATCH /api/v1/tasks/{taskId}/my-day         나의 하루
```

`POST /tasks/{id}/complete` 같은 형태를 쓰지 않습니다. 그것은 자원이 아니라 명령이고, 되돌리는 조작마다 새 엔드포인트가 생깁니다. 하위 자원으로 두면 켜고 끄는 것이 같은 경로의 값 변경입니다.

## 2. 메서드와 상태 코드

| 상황 | 메서드 | 성공 코드 | 본문 |
| :--- | :--- | :--- | :--- |
| 목록 | `GET` | 200 | 배열 |
| 하나 | `GET` | 200 | 객체 |
| 생성 | `POST` | 201 + `Location` | 없음 |
| 전체 교체 | `PUT` | 204 | 없음 |
| 부분 변경 | `PATCH` | 204 | 없음 |
| 삭제 | `DELETE` | 204 | 없음 |

**변경은 결과를 싣지 않습니다.** 클라이언트가 변경 뒤 관련 조회를 다시 부르므로([09. 상태](../frontend/09-state.md) 4.1절) 응답 본문을 읽는 곳이 없고, 읽지 않는 것이 계약에 남으면 명세와 생성 타입과 테스트가 계속 그것을 부양합니다(4절).

생성한 것의 식별자는 `Location` 이 전달합니다. 만든 뒤 그 하나를 곧바로 보여 주는 화면은 그 경로로 조회합니다.

## 3. 요청과 응답의 형태

**봉투를 씌우지 않습니다.** `{ "data": ..., "success": true }` 같은 껍데기를 두지 않고 자원을 그대로 내보냅니다. 성공과 실패는 상태 코드가 가르며, 봉투는 그것을 본문에 한 번 더 적는 일입니다.

```json
GET /api/v1/tasks
[
  { "id": "...", "title": "장 보기", "note": "", "dueDate": null,
    "remindAt": null, "important": false, "myDayOn": null,
    "completedAt": null, "createdAt": "2026-08-23T08:00:00Z" }
]
```

| 값 | 형식 |
| :--- | :--- |
| 식별자 | UUID 문자열 |
| 날짜 | `YYYY-MM-DD` |
| 지역 시각 | `YYYY-MM-DDTHH:mm` — 시간대 지정자를 붙이지 않습니다 |
| 절대 시각 | ISO 8601 UTC (`...Z`) |
| 정하지 않은 값 | `null`. 키를 빼지 않습니다 |

**지역 시각과 절대 시각을 형식으로 구분합니다.** 미리 알림은 사용자가 고른 "그 날 그 시각" 이고 만든 시각은 실제로 일어난 순간이라, 둘을 같은 형식으로 두면 받는 쪽이 시간대를 어떻게 다룰지 알 수 없습니다.

정하지 않은 값의 키를 빼지 않는 이유는 **"값이 없음" 과 "그런 필드가 없음" 을 클라이언트가 구분하지 못하게 하지 않기 위해서**입니다. 키가 사라지면 오타와 미구현이 같은 모양이 됩니다.

## 4. 목록

지금은 **전량을 반환합니다.** 필터와 정렬을 클라이언트가 수행합니다.

개인용 작업 목록에서 한 사람이 갖는 항목 수가 화면이 감당하는 범위에 있고, 관점(나의 하루 · 중요 · 계획된 일정)마다 다른 조건으로 거르는 것이 화면의 일입니다.

**페이징을 도입하는 조건은 하나입니다** — 목록 응답이 클라이언트가 다루기 버거운 크기가 될 때. 그 시점에 조건을 조회 포트로 내리고([05. 조회와 명령](05-query-command.md) 5절) 여기에 페이징 규약을 추가합니다. 쓰지 않는 파라미터가 계약에 남으면 그것도 유지 대상이 됩니다. 미리 넣지 않습니다.

## 5. 클라이언트 타입 생성

프론트엔드가 서버 타입을 손으로 옮겨 적지 않습니다. 계약이 바뀌면 **컴파일이 깨지는 것**이 발견 수단이며, 그 수단의 구성은 프론트엔드 참조 아키텍처의 API 계약 소비 문서가 갖습니다.
