# 백엔드 02. 코드 스타일 가이드

## 1. 목적과 적용 범위

`server/src` 아래의 Java 에 적용합니다. jOOQ 생성 코드는 대상이 아닙니다.

규칙은 세 수준으로 나눕니다. 이 구분이 없으면 리뷰에서 취향 논쟁이 반복됩니다.

| 수준 | 뜻 |
| :--- | :--- |
| **필수** | 어기면 병합하지 않습니다. 대부분 도구가 막습니다 |
| **권장** | 다르게 할 이유를 말할 수 있으면 따르지 않아도 됩니다 |
| **취향** | 규칙을 두지 않습니다. 리뷰에서 지적하지 않습니다 |

기존 코드에 소급하지 않습니다. **손대는 파일만 고칩니다.** 규칙이 바뀔 때마다 전체를 훑으면 변경 이력이 규칙 적용으로 덮여 실제 변경을 찾을 수 없습니다.

각 규칙은 `BE-STY-NNN` 으로 참조합니다. 번호는 부여 뒤 바꾸지 않으며 삭제는 결번, 추가는 말번입니다.

## 2. 포매팅

**BE-STY-001 (필수)** 포매팅은 도구가 강제하며 Spotless 의 `palantirJavaFormat` 이 유일한 기준입니다. 들여쓰기 · 줄 폭 · 임포트 순서를 이 문서에 적지 않습니다. `./gradlew spotlessApply` 가 고칩니다.

**BE-STY-002 (필수)** 별표 임포트와 미사용 임포트를 쓰지 않습니다. Checkstyle 이 막습니다.

## 3. 네이밍

### 3.1 패키지

**BE-STY-003 (필수)** 모듈은 단수 소문자 한 단어입니다. 모듈은 애그리거트의 소유자이지 그것의 컬렉션이 아닙니다.

**BE-STY-004 (필수)** 계층 이름은 `contract` · `application` · `domain` · `infrastructure` 로 고정합니다. 세그먼트에 복수형을 쓰지 않습니다.

### 3.2 클래스

**BE-STY-005 (필수)** `application` 안에서 프레젠테이션과 애플리케이션을 가르는 것은 폴더가 아니라 **접미사이며 ArchUnit 이 이 이름으로 판정합니다.**

| 역할 | 식별 | 자리 |
| :--- | :--- | :--- |
| 컨트롤러 | `@RestController` + `Controller` | `application` |
| 서비스 · 조회 서비스 | `Service` · `QueryService` | `application` |
| 조회 포트 | `Query` | `application` |
| 요청 · 응답 DTO 묶음 | `Requests` · `Views` | `application` |
| 에러 코드 | `ErrorCode` | `application` |
| 저장소 인터페이스 | `Repository` | `domain` |
| 포트 구현 | 기술 접두사 + 포트 이름 | `infrastructure` |

**BE-STY-006 (필수)** 조회 포트를 `QueryRepository` 로 짓지 않습니다. 저장소는 애그리거트를 다루는 계약이고 조회 포트는 화면 구조를 만드는 계약이라 지키는 것이 다릅니다.

**BE-STY-007 (필수)** 포트 이름은 제공하는 것으로 짓습니다. 구현 기술이나 저장 위치를 이름에 담지 않습니다.

**BE-STY-008 (필수)** 인터페이스 이름에 복수형을 쓰지 않습니다. 이 저장소에서 복수형은 **여러 타입을 담은 묶음 클래스**를 뜻하며, 겹치면 이름이 무엇을 가리키는지 흐려집니다.

### 3.3 메서드와 변수

**BE-STY-009 (필수)** 도메인 생성은 업무 낱말을 가진 팩토리이며 `new` 를 공개하지 않습니다. 재구성은 `restore` 로 고정하고 저장소만 호출합니다.

**BE-STY-010 (필수)** `find` 는 대상이 없을 수 있음을, `get` 은 없으면 실패함을 뜻합니다.

**BE-STY-011 (필수)** 접근자에 `get` 을 붙이지 않습니다. `lombok.config` 의 `lombok.accessors.fluent` 가 `@Getter` 도 같은 형태로 만듭니다.

**BE-STY-012 (필수)** 필드와 파라미터는 타입명의 카멜케이스입니다. 같은 타입이 둘 이상이면 역할을 앞에 붙입니다. 재정의 대상이 정한 파라미터 이름은 그대로 씁니다.

```java
TaskRepository taskRepository;   // Good
TaskRepository tasks;            // Bad — 컬렉션인지 포트인지 사라집니다
```

**BE-STY-013 (필수)** 축약하지 않습니다. 한두 글자로 줄인 이름은 그 자리에서 타입을 되짚게 만듭니다.

**BE-STY-014 (필수)** 컬렉션 변수는 담긴 타입의 복수형입니다.

### 3.4 에러 코드 문자열

**BE-STY-015 (필수)** `<모듈>_<사유>` 의 SCREAMING_SNAKE_CASE 입니다. **하이픈은 요구사항 식별자, 언더스코어는 에러 코드**로 갈라 저장소 전체 검색에서 둘이 섞이지 않게 합니다.

## 4. 코드 구조

모듈과 계층의 정의, 참조 방향, `shared` 의 입장 조건은 빌딩 블록 뷰가 갖습니다. 이 절은 **새 코드를 어디에 두는가**를 정합니다.

### 4.1 하위 패키지 승격

**BE-STY-016 (필수)** 새 모듈은 각 계층 아래에 파일을 직접 두고 하위 패키지를 만들지 않습니다. 승격은 **계층마다 따로 판정**합니다.

| 계층 | 분할 축 | 승격 기준 |
| :--- | :--- | :--- |
| `domain` | 애그리거트 | 애그리거트 2개 이상 |
| `application` | 피쳐(유스케이스 단위) | 유스케이스 3개 이상 |

분할 축이 다르므로 임계도 각자 셉니다. 애그리거트가 넷이어도 유스케이스가 둘이면 `application` 은 평면입니다.

**BE-STY-017 (필수)** 피쳐 둘 이상이 쓰는 것은 계층 루트에 평면으로 둡니다. `application/shared/` 나 `common/` 을 만들지 않습니다 — 이름이 내용을 규정하지 못하는 자리에는 무엇이든 쌓입니다.

**BE-STY-018 (권장)** 계층 루트에 파일이 쌓이는 것은 피쳐 경계가 틀렸다는 신호입니다. 공용을 옮길 자리를 찾는 대신 피쳐를 합치는 쪽을 먼저 검토합니다.

**BE-STY-019 (필수)** `infrastructure` 는 피쳐로 나누지 않습니다. 구현체가 포트 이름을 그대로 가져 파일명만으로 짝이 드러납니다. 포트 구현이 아닌 프레임워크 확장은 목적 폴더로 묶습니다.

**BE-STY-020 (필수)** 값 객체가 애그리거트 하나에만 속하면 그 패키지에 두고, **둘째 애그리거트가 쓰기 시작한 시점에** 계층 루트로 올립니다. 먼저 쓴 쪽에 남기면 나중에 쓰는 쪽이 애그리거트 패키지를 임포트하게 됩니다.

### 4.2 DTO

**BE-STY-021 (필수)** 요청과 응답 record 는 모듈당 하나의 묶음 클래스에 중첩합니다. 묶음은 `final` 이고 `private` 기본 생성자를 갖습니다.

```java
public final class TaskRequests {
    private TaskRequests() {}

    public record CreateTask(@NotBlank @Size(max = TaskTitle.MAX) String title) {}
    public record ChangeDueDate(LocalDate dueDate) {}
}
```

record 하나에 파일 하나를 두면 작은 타입이 폴더를 채우고, 폴더를 열어야 이 모듈이 무엇을 받는지 알 수 있습니다.

**BE-STY-022 (권장)** 묶음이 한 화면을 넘기면 피쳐 단위로 나눕니다.

**BE-STY-023 (권장)** 목록과 상세가 같은 형태를 쓰는 동안은 응답 record 를 나누지 않습니다. 미리 나누면 필드 하나가 늘 때마다 두 곳을 고칩니다.

### 4.3 메서드 배치

**BE-STY-024 (필수)** 서비스 클래스는 여섯 블록 순서로 배치하고 각 블록 앞에 구분선 주석을 둡니다. 없는 블록은 주석째 생략합니다.

| 순서 | 블록 | 대상 |
| :--- | :--- | :--- |
| 1 | 상수 | `static final` |
| 2 | 의존 | 주입 필드 |
| 3 | 생성 | 명시적 생성자 |
| 4 | 조회 | `@Transactional(readOnly = true)` |
| 5 | 명령 | `@Transactional` |
| 6 | 보조 | `private` 메서드 |

**BE-STY-025 (필수)** 조회를 명령보다 앞에 둡니다. 두 경로를 나누되 클래스는 합치기로 정했으므로 클래스 안에서 갈려 보여야 그 결정이 코드에 남습니다. 애너테이션은 괄호 안의 차이라 훑을 때 경계가 되지 못합니다.

**BE-STY-026 (필수)** 구분선은 `// --- ` 뒤에 블록명을 두고 대시로 120 컬럼까지 채웁니다. 들여쓰기를 포함한 폭이며 한글은 두 컬럼으로 셉니다.

**BE-STY-027 (권장)** 명령 블록 안은 유스케이스의 생애 순(추가 → 편집 → 상태 변경 → 삭제)이 읽기 쉽습니다.

컨트롤러와 도메인은 대상이 아닙니다. 컨트롤러는 메서드가 엔드포인트 하나씩이라 구획이 생기지 않고, 도메인은 팩토리 · 상태 변경 · 접근자가 이미 형태로 갈립니다.

## 5. Java 관용구

**BE-STY-028 (필수)** `@Setter` 를 쓰지 않습니다. `lombok.config` 가 빌드 오류로 막습니다. 상태 변경은 업무 낱말을 가진 메서드가 하고 그 메서드가 불변식을 함께 지키는데, 필드마다 통로를 내면 그 지점이 사라집니다.

**BE-STY-029 (필수)** DTO 는 `record` 입니다. 접근자와 `equals` · `hashCode` 를 컴파일러가 만듭니다.

**BE-STY-030 (필수)** `Exception` 이나 `RuntimeException` 을 통째로 잡지 않습니다. Checkstyle `IllegalCatch` 가 막습니다. 빈 `catch` 블록도 금지입니다.

**BE-STY-031 (필수)** 문자열 비교에 `==` 를 쓰지 않습니다. Checkstyle 이 막습니다.

**BE-STY-032 (필수)** `switch` 에는 `default` 를 둡니다.

**BE-STY-033 (권장)** `Optional` 은 반환 타입에만 씁니다. 필드와 파라미터에 두지 않습니다 — 직렬화되지 않고 호출부가 두 번 분기하게 됩니다.

## 6. 주석

**BE-STY-034 (필수)** 주석에 태그를 쓰지 않습니다. `<p>` · `{@code}` · `{@link}` 는 렌더링을 위한 표기이며 표기가 늘수록 원문이 읽히지 않습니다.

**BE-STY-035 (필수)** 설계 근거를 소스에 적지 않습니다. 그것은 아키텍처 문서와 결정 기록이 갖습니다. 특히 **하지 않은 선택을 변호하는 문장**을 넣지 않습니다.

| 뺍니다 | 남깁니다 |
| :--- | :--- |
| 설계 선택의 근거, 기각한 대안 | 이 코드가 업무에서 무엇인가 |
| 문서에 이미 있는 규칙 설명 | 유스케이스 ID 와 흐름 번호 |
| 다른 방식의 결과 예측 | 모르면 깨지는 동작상 주의 |

**BE-STY-036 (필수)** 도메인 엔티티의 필드에는 `//` 로 한글 이름을 답니다. 필드명이 영문이라 업무 낱말과 한 겹 떨어져 있고, 서술서와 화면은 한글 낱말로 말합니다.

```java
// 나의 하루에 담은 날짜
private LocalDate myDayOn;
```

**BE-STY-037 (필수)** `TODO` 는 `// TODO(작성자): 내용` 형식입니다.

## 7. 에러 처리와 로깅

**BE-STY-038 (필수)** 비즈니스 실패는 항상 예외로 던집니다. 컨트롤러가 `ResponseEntity` 를 직접 조립하지 않으며 전역 핸들러가 응답으로 변환합니다.

| 던지는 것 | 뜻 | 문장의 성격 |
| :--- | :--- | :--- |
| `BusinessException` | 지금 상태가 이 요청을 허용하지 않는다 | 사용자 문장 |
| `DomainRuleViolation` | 들어온 값이 규칙에 맞지 않는다 | 사용자 문장 |
| `IllegalStateException` | 여기 도달하면 안 되는데 도달했다 | 개발자 문장, 로그만 |

**BE-STY-039 (필수)** 도메인에서 `IllegalArgumentException` 을 던지지 않고 `DomainRuleViolation` 을 씁니다. 전자를 쓰면 핸들러가 우리 것과 라이브러리 것을 구분하지 못해 안전한 쪽으로 전부 덮어쓰게 되고, 도메인이 쓴 문구가 매번 버려집니다.

**BE-STY-040 (필수)** 사용자에게 나가는 문장에 내부 정보(테이블명 · 식별자 · 스택)를 담지 않습니다.

**BE-STY-041 (필수)** 예상된 실패를 `error` 로 남기지 않습니다. 정상 처리된 흐름이 오류 로그를 채우면 진짜 장애가 그 안에 묻힙니다. 500 계열만 `error` 입니다.

**BE-STY-042 (필수)** 비밀 · 토큰 · 개인정보 원문을 기록하지 않습니다. 식별자만 남깁니다.

**BE-STY-043 (필수)** 추적 식별자를 키나 식별자 용도로 쓰지 않습니다. 로그 상관관계를 잇는 값입니다.

## 8. 테스트 코드 스타일

**BE-STY-044 (필수)** 테스트 클래스는 대상 클래스 이름 + `Test` 입니다.

**BE-STY-045 (필수)** 슬라이스 식별자는 **그 슬라이스의 경로를 처음부터 끝까지 지나는 테스트에만** 붙이고 이름은 인수 조건의 문장을 그대로 씁니다.

```java
@DisplayName("TK-001 S1: 제목을 적으면 목록에 그 작업이 있다")
```

**BE-STY-046 (필수)** 단위 테스트에 슬라이스 식별자를 붙이지 않습니다. 함수 하나의 검증이 성공 조건을 이름으로 가지면 **그 경로가 닫혔다는 거짓 주장**이 됩니다.

**BE-STY-047 (필수)** 통합 테스트의 진입점은 HTTP 입니다. 서비스를 직접 부르면 컨트롤러의 배선이 빠져도 통과합니다. 요청 검증과 직렬화 형식과 상태 코드는 컨트롤러를 지나야 확인되며 그 셋이 계약의 대부분입니다.

**BE-STY-048 (필수)** 통합 테스트는 마이그레이션을 실제로 적용합니다. 코드 생성은 SQL 파서를 통과하는 것까지만 보장합니다.

**BE-STY-049 (필수)** 각 테스트는 `@Transactional` 로 되돌립니다.

**BE-STY-050 (필수)** 검증하지 않는 것 — 생성 코드, 프레임워크 동작, 로직 없이 전달하는 조회 서비스, 접근자와 record 의 기본 동작.

**BE-STY-051 (필수)** 버그를 고칠 때는 **그 버그를 재현하는 테스트를 먼저 씁니다.** 통과하는 테스트를 나중에 붙이면 그것이 정말 그 버그를 잡는지 확인할 수 없습니다.

## 9. 예외 처리 절차

**BE-STY-052 (필수)** 규칙을 어겨야 하면 억제 목록에 **사유 주석과 함께** 등록합니다. 그 목록이 표준을 벗어난 위치와 사유의 등록부입니다.

**BE-STY-053 (필수)** 도구 설정으로 예외를 두는 경우 **완화한 규칙의 근거가 왜 그 대상에 적용되지 않는지**를 함께 적습니다.

**BE-STY-054 (필수)** 규칙 자체를 바꾸려면 이 문서를 먼저 고치고 테스트를 함께 고칩니다. **테스트만 완화하는 변경은 허용하지 않습니다.**
