# 결정-0009: 백엔드를 계층과 모듈로 자르고 DDD 의 일부만 차용한다

- 상태: 승인됨
- 날짜: 2026-08-29

## 맥락 (Context)

백엔드의 구조를 정할 때 다투는 힘이 넷입니다.

**첫째, 도메인 규칙이 놓일 자리가 필요합니다.** 규칙을 서비스에 두면 같은 불변식이 유스케이스마다 복제되고, 어느 것이 원본인지 알 수 없게 됩니다. 규칙을 소유하는 객체가 있어야 그 복제가 멈춥니다.

**둘째, 프레임워크가 도메인을 물들이지 않아야 합니다.** 도메인 객체가 영속성 애너테이션과 HTTP 타입을 함께 지고 있으면 규칙 하나를 확인하는 데 애플리케이션 컨텍스트가 필요해집니다.

**셋째, 1인 프로젝트가 감당할 수 있어야 합니다.** DDD 의 산출물을 모두 갖추는 방안은 유비쿼터스 언어 사전, 컨텍스트 맵, 도메인 이벤트, 애그리거트 설계 문서를 요구합니다. 그 대가는 갱신되지 않는 문서가 늘어나는 것이며, 작업자가 한 명이면 문서를 맞추는 일이 곧 자기 자신과의 회의가 됩니다.

**넷째, 모듈이 늘어날 것입니다.** 지금은 `task` 와 `user` 둘이지만 협력이 생기면 서로를 참조하게 되고, 그 참조가 양방향이 되면 두 모듈이 함께만 존재할 수 있게 됩니다.

**전통적 계층형(Controller → Service → Repository)** 은 익숙하고 규칙이 적습니다. 그 대가는 의존이 위에서 아래로만 흐르므로 도메인이 영속성 기술을 참조하게 되는 것입니다. 데이터베이스를 바꾸는 일보다 그것이 도메인 규칙을 순수 단위 테스트로 검증하지 못하게 만드는 쪽이 실질적인 손실입니다.

**헥사고날의 포트와 어댑터를 전면 적용하는 방안**은 모든 외부 접점을 포트로 뒤집습니다. 그 대가는 클래스 수가 늘고, 어댑터 하나뿐인 포트가 대부분이 되는 것입니다.

**모듈 간 협력의 방향을 정하는 문제**는 별도의 힘입니다. 협력이 상호적인 것과 코드 의존이 순환하는 것은 다른 층위이며, 두 모듈이 서로를 필요로 하더라도 컴파일 의존은 한 방향으로 정리할 수 있습니다. 그 정리를 위해 **제공자가 인터페이스를 선언하고 소비자가 구현하는 기법**이 있고, 이것을 `~Spi` 로 부르는 관행이 널리 쓰입니다. Java 에서 SPI 는 구현이 복수이고 구현자를 사전에 알 수 없으며 런타임에 발견되는(`ServiceLoader`) 확장 지점을 뜻하므로, 구현이 단일하고 컴파일 시점에 확정되는 자리에 그 이름을 붙이면 교체 가능하다는 오해를 부릅니다. Cockburn 의 원전도 primary · secondary(driving · driven)를 쓰고 API · SPI 를 쓰지 않습니다.

## 결정 (Decision)

**차용 범위**

- DDD 의 전술 패턴 가운데 **애그리거트 · 값 객체 · 저장소** 셋만 차용합니다. 도메인 이벤트, 명세(Specification), 팩토리는 필요가 드러날 때 도입합니다.
- 유비쿼터스 언어 사전과 컨텍스트 맵을 문서로 두지 않습니다. 용어의 원본은 유스케이스 서술서이며, 모듈 사이의 관계는 코드의 의존 방향이 드러냅니다.
- 애그리거트 간 참조는 식별자로만 합니다. 객체 참조를 허용하면 경계가 트랜잭션 하나로 뭉칩니다.

**계층**

- 계층을 프레젠테이션 · 애플리케이션 · 도메인 · 인프라 넷으로 나눕니다. 프레젠테이션과 애플리케이션은 같은 패키지(`application`)에 두며, 둘을 가르는 것은 폴더가 아니라 클래스의 역할과 접미사입니다. 컨트롤러와 서비스의 변경 생애주기가 일치하기 때문입니다.
- 도메인은 상위 계층과 프레임워크를 참조하지 않는 순수 Java 객체입니다. 애플리케이션 컨텍스트 없이 규칙을 검증할 수 있어야 합니다.
- 애플리케이션이 포트를 선언하고 인프라가 구현합니다. 의존 역전은 이 자리에만 두고 모든 외부 접점으로 넓히지 않습니다.

**모듈**

- 모듈을 **애그리거트 소유 단위**로 나눕니다. 같은 애그리거트를 다루는 유스케이스는 그 애그리거트를 소유한 모듈 안에 둡니다. 한 모듈이 애그리거트 여럿을 소유할 수 있습니다.
- 모듈 간 참조는 단방향이며 순환을 금지합니다. 순환이 생기면 두 가지 중 하나입니다 — 경계를 잘못 그었거나(용어가 같고 함께 변경되고 따로 살 수 없다면 합칩니다), 의존만 얽힌 것입니다(그러면 방향을 뒤집습니다).

**모듈 간 협력**

- 타 모듈에 공개하는 것은 **모듈 루트에 직접** 둡니다. 별도의 공개 패키지를 두지 않고 루트 자체가 소통 창구이며, 하위 패키지는 모듈 내부 전용입니다.
- 공개 요소는 방향을 갖습니다. **`in`** 은 이 모듈이 제공하고 타 모듈이 호출하는 것이며, **`out`** 은 이 모듈이 요구하고 타 모듈이 구현하는 것입니다.
- **`out` 은 세 조건을 모두 충족할 때만 만듭니다.** 이 모듈이 자기 불변식 검증을 위해 그 정보를 요구하고, 스스로 판정할 수 없으며, **호출 인자로 전달받을 수 없어야 합니다.** 세 번째가 남용을 막는 관문입니다 — "파라미터로 전달하면 되지 않는가"에 답할 수 없으면 만들지 않습니다.
- **`~Spi` 로 이름 짓지 않습니다.** `in` · `out` 이 더 정확한 구분 축이며, SPI 는 런타임에 발견되는 복수 구현을 뜻하는 말입니다.
- 공개 요소가 주고받는 타입은 내부 엔티티가 아니라 별도로 정의합니다. 도메인 계층은 이 타입을 참조하지 않습니다 — 도메인이 창구를 거꾸로 참조하게 되기 때문입니다.
- 상류의 타입을 그대로 쓸지(순응), 자기 언어로 포트를 선언하고 어댑터가 번역할지(부패 방지)는 상류의 변경 빈도와 그 의존의 중요도로 판단합니다. 번역할 고유 언어가 없으면 어댑터를 두지 않습니다.

## 결과 (Consequences)

도메인 규칙이 한 자리를 갖고 프레임워크 없이 검증됩니다. 규칙을 확인하는 테스트가 컨텍스트 기동을 요구하지 않으므로 그 검증이 실제로 자주 실행됩니다.

모듈의 공개 면이 루트 한 자리로 좁아집니다. 어떤 모듈이 무엇을 열어 두었는지 파일 목록으로 읽히고, 내부를 고치는 변경이 다른 모듈로 새지 않습니다.

`out` 의 세 조건이 협력의 방향을 지킵니다. 조건을 통과하지 못하면 호출자가 먼저 판정하고 결과를 넘기는 방식으로 남으므로, 인터페이스를 세우기 전에 그 필요를 매번 다시 묻게 됩니다.

감수하는 것이 넷입니다.

- **모듈 루트의 공개 범위를 기계가 강제하지 않습니다.** 하위 패키지를 참조해도 컴파일이 통과하며 규약으로만 지켜집니다. 모듈이 셋을 넘거나 위반이 실제로 발생하면 ArchUnit 도입을 다시 판단합니다.
- **경계를 다시 그으려면 코드를 옮겨야 합니다.** 애그리거트 소유가 모듈을 정하므로 애그리거트의 자리가 바뀌면 유스케이스가 함께 따라갑니다. 컨텍스트 맵이 없어 그 영향 범위를 문서로 미리 보지 못하고 코드를 읽어 확인합니다.
- **DDD 를 아는 사람이 없는 것을 찾을 수 있습니다.** 도메인 이벤트와 명세를 두지 않았으므로 그 패턴을 기대하고 코드를 읽으면 자리가 비어 있습니다. 필요가 드러나기 전에 두지 않는다는 것이 결정이며 부재가 실수는 아닙니다.
- **`in` 과 `out` 을 접미어와 문서로만 가릅니다.** 루트에 둘이 섞여 있고 기계가 구분하지 않습니다. `out` 이 서넛으로 늘면 하위 패키지로 나누고 강제하는 방안을 검토합니다.

아래 상황에서 이 결정을 다시 판단합니다.

- 두 번째 작업자가 참여할 때 규약으로만 지켜지는 것들의 강제 수단을 다시 판단합니다.
- 모듈이 다섯을 넘을 때 경계 검사와 협력 방식의 문서화를 다시 판단합니다.
- 한 트랜잭션이 여러 모듈의 상태를 함께 바꿔야 할 때 도메인 이벤트의 도입을 다시 판단합니다.
