# 결정-0009: 백엔드를 계층과 모듈로 자르고 DDD 의 일부만 차용한다

- 상태: 승인됨
- 날짜: 2026-08-29

## 맥락 (Context)

백엔드 아키텍처 구조를 결정할 때 상충하는 네 가지 고려 사항이 있다.

**첫째, 도메인 비즈니스 불변식을 캡슐화할 전용 계층이 필요하다.** 규칙을 서비스 계층에 분산 배치하면 동일한 불변식이 유스케이스마다 중복 구현되어 단일 원본이 훼손된다. 비즈니스 규칙을 전담 소유하는 순수 도메인 객체가 있어야 중복이 방지된다.

**둘째, 프레임워크 기술 의존성이 도메인 코드를 오염시키지 않아야 한다.** 도메인 객체가 영속성 애너테이션이나 HTTP 요청/응답 타입을 직접 참조하면 비즈니스 규칙 검증 시마다 무거운 프레임워크 컨텍스트 기동이 필요해진다.

**셋째, 1인 개발 환경의 관리 복잡도를 통제해야 한다.** DDD(Domain-Driven Design)의 모든 산출물(유비쿼터스 언어 사전, 컨텍스트 맵, 도메인 이벤트, 애그리거트 명세 등)을 전면 작성하면 실제 코드 변경 시마다 동기화되지 않는 유휴 문서가 급증한다.

**넷째, 모듈 확장에 따른 의존성 통제가 필요하다.** 도메인 모듈이 확장될 때 모듈 간 상호 참조가 발생하면 양방향 순환 참조가 발생하여 모듈 간 강결합이 유발된다.

**전통적인 3계층 아키텍처(Controller → Service → Repository)**는 구조가 단순하지만 의존성이 상위에서 하위로 일방향 결합되어 비즈니스 계층이 데이터베이스 기술에 종속된다. 도메인 규칙을 데이터베이스나 Spring 컨텍스트 없이 순수 단위 테스트로 고속 검증하기 어렵다.

**헥사고날(포트와 어댑터) 아키텍처 전면 도입 방안**은 모든 인바운드/아웃바운드 접점을 포트 인터페이스로 역전시킨다. 그러나 단일 구현체만 존재하는 상황에서도 과도한 보일러플레이트 인터페이스가 양산된다.

**모듈 간 협력 방향 설정**: 두 모듈 간에 비즈니스 협력이 존재하더라도 컴파일 타임 의존성은 단방향으로 통제할 수 있다. 이를 위해 인터페이스 기반 의존 역전을 적용하되, 자바 표준 SPI(`ServiceLoader`)와 같이 런타임 다중 구현체 플러그인 메커니즘을 의미하는 `~Spi` 명명은 지양하고, 시스템 내부의 명확한 `in`(인바운드 제공)/`out`(아웃바운드 요구) 포트 계약으로 표현해야 한다.

## 결정 (Decision)

**DDD 차용 범위**

- 전술 패턴 중 **애그리거트, 값 객체(Value Object), 리포지토리** 3가지만 선별 채택한다. 도메인 이벤트, 명세(Specification), 팩토리는 실질적 복잡성이 요구되는 시점에 도입한다.
- 유비쿼터스 언어 사전과 컨텍스트 맵 문서를 별도 관리하지 않는다. 용어 원본은 유스케이스 서술서이며, 모듈 간 관계는 코드 패키지 의존 구조로 표현한다.
- 애그리거트 간 참조는 식별자(ID)로만 한정하여 단일 트랜잭션 경계 비대화를 방지한다.

**계층 구조**

- 프레젠테이션, 애플리케이션, 도메인, 인프라 4계층으로 분리한다. 프레젠테이션과 애플리케이션은 동일 패키지(`application`)에 배치하되 접미사로 역할을 구분한다.
- 도메인 계층은 상위 계층 및 프레임워크에 의존하지 않는 순수 Java POJO로 유지한다.
- 애플리케이션 계층이 영속성 포트를 정의하고 인프라 계층이 이를 구현하여 의존성을 역전시킨다.

**모듈 경계**

- 모듈은 **애그리거트 소유 단위**로 분할한다. 동일 애그리거트를 제어하는 유스케이스는 해당 모듈 내부에 둔다.
- 모듈 간 참조는 단방향 원칙을 엄격히 준수하며 순환 참조를 금지한다.

**모듈 간 협력 규약**

- 타 모듈에 노출하는 인터페이스는 **모듈 루트 패키지에 직접 선언**한다. 하위 내부 패키지는 비공개 캡슐화한다.
- 공개 인터페이스는 방향성을 갖는다. **`in`**은 해당 모듈이 제공하는 서비스 인터페이스이며, **`out`**은 해당 모듈이 타 모듈에 요구하는 협력 포트이다.
- **`out` 포트는 다음 세 조건을 모두 충족할 때만 생성한다.** 1) 자기 불변식 검증을 위해 외부 정보가 필요하고, 2) 자체 판정이 불가능하며, 3) **호출자의 메서드 파라미터로 전달받을 수 없는 경우**에 한한다. 호출 시 파라미터로 주입받을 수 있는 값은 `out` 포트로 추상화하지 않는다.
- 명칭에 `~Spi`를 사용하지 않고 `in` 및 `out` 접미어로 명확히 구분한다.
- 모듈 간 데이터 교환 시 내부 도메인 엔티티를 직접 노출하지 않고 전용 전달 모델을 정의한다.
- 외부 모듈과의 통합 시 단순 데이터 참조는 상류 모델을 수용(순응)하고, 개념적 변환이 필요한 경우에 한해 부패 방지 계층(ACL) 어댑터를 둔다.

## 결과 (Consequences)

도메인 비즈니스 규칙이 프레임워크 독립적인 순수 단위 테스트로 고속 검증된다. 모듈의 외부 접점이 루트 패키지로 한정되어 변경 영향도가 명확히 제어된다.

감수하는 제약 사항은 다음과 같다.

- 모듈 루트 패키지 공개 규칙을 기계적(ArchUnit 등)으로 강제하지 않고 팀 규약으로 관리한다.
- 애그리거트 재분할 시 관련 유스케이스 코드의 물리적 이동이 수반된다.
- 도메인 이벤트 등 고급 DDD 패턴의 부재로 이벤트 주도 비동기 처리가 제한된다.
- `in`/`out` 구분을 접미어로만 관리한다.

다음 상황 발생 시 본 결정을 재검토한다.

- 복수 개발자가 협업하여 모듈 의존성 강제 검증 도구(ArchUnit)가 필요할 때.
- 모듈 수가 5개를 초과하여 모듈 간 협력 맵 문서화가 요구될 때.
- 단일 트랜잭션 내 다중 모듈 상태 변경으로 인해 도메인 이벤트 도입이 필수적일 때.
