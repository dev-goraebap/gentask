# 결정-0003: API 계약을 서버가 소유하고 생성된 타입으로 전달한다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

클라이언트와 서버가 단일 저장소에 위치하며([결정-0001](./0001-shared-monorepo.md)) HTTP로 통신한다. 클라이언트는 서버 응답의 구조를 참조해야 하므로, API 계약 정보의 관리 위치와 동기화 방식을 결정해야 한다.

**타입을 수동 작성하는 방안**에서는 수동 작성된 타입이 서버 코드의 변경과 무관하게 컴파일을 통과하므로, 서버가 필드를 변경했을 때 클라이언트가 런타임에야 불일치를 감지한다. 반면 **명세를 기반으로 타입을 생성하는 방안**은 서버 코드가 OpenAPI 명세를 생성하고 클라이언트가 해당 명세로부터 TypeScript 타입을 자동 생성하므로, 계약 불일치가 컴파일 오류로 조기 감지된다. 트레이드오프로 서버가 응답 타입을 바꿀 때마다 타입 생성을 재수행해야 한다.

경로 및 표현 방식에서도 세 가지 항목을 결정해야 한다.

**API 버전의 위치**: URI 경로 방식과 요청 헤더 방식이 있다. URI 경로에 명시하면 브라우저 주소창, 서버 로그, API 명세에 호출 대상 버전이 명확히 노출되며, 클라이언트의 헤더 누락으로 인한 기본 버전 폴백 문제를 방지한다. 헤더 방식은 단일 URI 경로를 유지한 상태에서 버전만 분기한다.

**상태 변경 요청의 경로**: 동사 기반 경로와 하위 자원 기반 경로가 있다. 동사를 경로에 포함하면 완료 및 완료 취소와 같이 상태를 전환하는 조작마다 엔드포인트가 무분별하게 증가한다. 상태를 하위 자원으로 표현하면 활성화 및 비활성화 조작을 동일 경로에 대한 단일 상태 값 변경(`PATCH`)으로 일관되게 처리할 수 있다.

**시각 데이터의 표현**: 단일 형식과 형식 분리(로컬 시각 / 절대 시각) 방식이 있다. 사용자가 지정한 달력 시각과 시스템에서 발생한 절대 시각을 동일한 형식으로 전달하면 소비 측에서 시간대(Timezone) 처리 방식을 명확히 판별할 수 없다. 형식을 분리하면 해당 기준이 API 계약 단계에서 확정되며, 저장 계층의 컬럼 타입 결정 기준과도 일치한다.

## 결정 (Decision)

**소유권**: API 계약의 정의와 변경 권한은 서버가 주도하고 클라이언트는 소비자 역할을 수행한다.

**전달 경로**: 서버가 런타임에 OpenAPI 명세를 제공하고, 클라이언트는 해당 명세로부터 TypeScript 타입을 생성하여 커밋한다. 생성된 타입 파일은 수동으로 수정하지 않는다.

```text
서버 코드 → OpenAPI 명세 → 타입 생성 → 클라이언트 코드
```

분리 커밋 시 중간 커밋에서 빌드가 실패하므로, 타입 재생성 결과와 이를 사용하는 클라이언트 코드는 단일 커밋에 담아 원자적으로 반영한다.

**경로와 표현**:

- API 버전은 URI 경로에 명시한다(`/api/v1/tasks`).
- 상태 변경은 동사가 아닌 하위 자원으로 표현한다(`PATCH /api/v1/tasks/{taskId}/completion`).
- 시각은 로컬 시각(`YYYY-MM-DDTHH:mm`)과 절대 시각(ISO 8601 UTC)을 형식으로 구분한다.

OpenAPI 명세를 제공하지 않는 백엔드와 연동해야 하는 경우 명세 발행을 우선 요구한다. 불가피하게 수동 타입을 정의해야 한다면 아키텍처 결정 기록(ADR)에 예외 사유와 영향 범위를 기록한다. 예외 상황을 이유로 표준 아키텍처 문서를 임의 완화하지 않는다.

## 결과 (Consequences)

계약 불일치가 컴파일 시점에 검출된다. 서버가 필드를 제거하거나 타입을 변경하면 클라이언트가 타입을 재생성한 순간 컴파일 오류가 발생하므로, 클라이언트와 서버 간의 불일치가 배포 이후가 아니라 빌드 단계에서 조기 확인된다.

감수하는 제약 사항은 다음과 같다.

- 서버가 응답 타입을 변경할 때마다 타입 생성을 재실행해야 한다. 실행을 누락하면 생성된 타입이 명세보다 이전 상태로 남는다.
- 신규 API 버전이 추가되면 버전별로 엔드포인트 경로가 공존한다.
- 생성된 타입은 서버 명명 체계를 그대로 사용한다. 클라이언트 전용 변환 계층을 두지 않으므로 서버가 정한 타입명이 화면 코드에 그대로 드러난다.
- 명세를 제공하지 않는 백엔드와는 이 방식이 성립하지 않는다.

다음 상황 발생 시 본 결정을 재검토한다.

- 차기 API 버전을 발행할 때: 경로 다중화 비용과 헤더 기반 전환 비용을 비교 검토한다.
- 서버 타입 명칭이 화면 코드의 가독성을 저해할 때: 클라이언트 전용 변환 계층 도입 여부를 판단한다.
