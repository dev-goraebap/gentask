# 결정-0010: 첨부 파일을 Active Storage 방식으로 file 모듈이 소유한다

- 상태: 승인됨
- 날짜: 2026-08-29

## 맥락 (Context)

기존에는 두 도메인 모듈이 파일 첨부를 상이하게 처리했다. `task` 모듈은 `task_files` 전용 테이블을 운영한 반면 `user` 모듈은 `users.profile_image_key` 단일 문자열 컬럼만 유지했다. 단일 컬럼 방식은 원본 파일명, 미디어 타입(MIME Type), 파일 크기 메타데이터를 보관하지 못해 정보가 유실되었다. 또한 업로드 발급과 첨부 확정 처리 흐름이 동일함에도 불구하고 도메인별로 중복 구현되어 있었다.

[5. 빌딩 블록 뷰](../05-building-block-view.md) §5.3.1에서 '단일 모듈에서 주요 업무 애그리거트와 관련 파일 첨부 애그리거트를 함께 소유하는 구성'을 언급하고 있으나, 도메인 모듈이 확장됨에 따라 파일 처리 로직의 중복이 가중되는 문제가 있었다.

**도메인별 전용 테이블을 유지하는 방안**: 외래 키 제약 조건으로 무결성을 보장할 수 있지만 도메인 추가 시마다 테이블이 증식하고 파일 처리 로직이 반복 구현된다.

추가로 다음 세 가지 구조적 결함이 존재했다:

- 사전 서명 발급 후 실제 확정되지 않고 방치된 스토리지 객체를 추적할 수단이 없어 유휴 객체 정리가 불가능했다.
- 첨부 대상의 유효성을 오브젝트 스토리지 키의 접두어 문자열 검사(`objectKey.startsWith(...)`)에 의존하고 있어 키 명명 규칙 변경 시 검증이 깨지는 취약점이 있었다.
- 발급 엔드포인트를 도메인별로 분산할지 통합할지 결정해야 했다. 도메인별로 두면 엔드포인트와 클라이언트 코드가 중복된다. 반면 `file` 모듈로 통합하되 권한 검증을 소유 모듈에 위임하면 [결정-0009](./0009-backend-layered-structure.md)의 `out` 포트가 불필요하게 복잡해진다. Rails의 Active Storage처럼 사전 서명 업로드 발급은 소유자를 알 필요 없이 blob만 생성하고, 실제 첨부 연결 시점에 도메인 모듈이 권한을 검증하는 2단계 접근법이 적합하다.

## 결정 (Decision)

**저장 구조**

- 파일 관리를 전담하는 독립 `file` 모듈을 신설한다. Ruby on Rails의 Active Storage 설계를 준용하여 `blobs`(파일 원본 메타데이터)와 `attachments`(다형적 연결)로 테이블을 분리한다. 연결은 `owner_type`, `owner_id`, `name` 복합 컬럼으로 관리하며 RDB 물리적 외래 키는 설정하지 않는다.
- 첨부 위치는 `(owner_type, name)` 쌍으로 식별하며, 해당 정의에 스토리지 경로 접두어, 허용 확장자, 최대 크기, 최대 파일 개수 정책을 선언한다.
- 다형적 연결 특성상 데이터베이스 계층의 외래 키 CASCADE가 동작하지 않으므로, 부모 레코드 삭제 시 첨부 정리 작업은 해당 도메인 모듈이 명시적으로 실행한다.

**업로드 프로세스**

- 파일 바이너리는 백엔드 서버를 경유하지 않고 클라이언트가 스토리지(S3/MinIO)에 직접 전송한다(Direct Upload).
- **사전 서명 URL 발급은 `file` 모듈이 단일 엔드포인트로 처리한다**(`POST /api/v1/attachments/presign`). 발급 단계에서는 어느 도메인 레코드에 연결될지 알 필요가 없으므로 통합 엔드포인트로 제공한다.
- **첨부 확정 및 연결은 부모 레코드를 소유한 도메인 모듈이 처리한다.** 엔티티 소유권 검증 및 비즈니스 권한 판정은 도메인 모듈의 고유 책임이다.
- 발급된 업로드 요청은 `pending_uploads` 테이블에 기록하여 발급자 사용자 ID를 보관한다. 첨부 확정 시 발급자와 연결 요청자의 일치 여부를 검증하며 스토리지 키 문자열 접두어 검사는 배제한다.
- 첨부 확정 시 실제 파일 크기는 클라이언트 전달값이 아닌 스토리지 메타데이터 조회를 통해 실측 검증한다.
- 파일 크기와 MIME 타입 제약은 발급 단계에서 검증하고, 첨부 가능 개수 제약은 확정 단계에서 검증한다.

**모듈 협력**

- `file` 모듈은 타 모듈의 비즈니스 권한을 직접 판정하지 않으며 `out` 포트를 두지 않는다. 발급 단계는 로그인 세션만 검증하고, 연결 단계는 소유 도메인 모듈이 사전 검증을 완료한 후 `file` 모듈 서비스를 호출한다.
- 파일 정책 위반 시 에러 코드는 `file` 모듈이 정의한 공통 에러 코드를 반환한다.

## 결과 (Consequences)

파일 저장 및 처리 메커니즘이 단일 모듈로 일원화된다. 신규 도메인이 추가되어도 테이블 생성 없이 첨부 정책 설정만 추가하면 되며 클라이언트 업로드 코드도 재사용된다.

사전 서명 후 미확정된 객체가 `pending_uploads`에 기록되므로 주기적인 가비지 컬렉션의 추적 기반이 마련된다.

모듈 간 의존성이 `task → file`, `user → file` 단방향으로 유지된다.

감수하는 제약 사항은 다음과 같다.

- 다형적 연결 구조로 인해 데이터베이스 레벨의 외래 키 무결성 제약이 부재한다.
- 파일 개수 초과 여부를 사전 서명 발급 시점이 아닌 최종 첨부 확정 시점에 검증한다.
- 에러 코드가 `TASK_FILE_*`, `PROFILE_IMAGE_*`에서 `FILE_*`로 통합 변경되었다.
- 마이그레이션된 기존 프로필 이미지의 미디어 타입 및 크기 메타데이터가 0/기본값으로 유지된다.

다음 상황 발생 시 본 결정을 재검토한다.

- 첨부 확정 단계까지 `file` 모듈로 통합해야 하는 요구가 발생할 때.
- 썸네일 생성 등 이미지 변환 파생물 보관이 요구될 때.
