# 결정-0004: 실패 응답을 RFC 9457 형식으로 반환하고 코드를 분기 계약으로 둔다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

서버는 다양한 유형의 실패를 반환하고 클라이언트는 이를 화면에 표시합니다. 실패 응답의 형식과 클라이언트의 예외 처리 분기 기준을 결정해야 합니다.

**응답 형식**은 자체 규격과 표준 규격 중 하나입니다. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)은 HTTP 응답의 문제 상세(Problem Details) 표현을 정의하며 Spring이 `ProblemDetail`로 구현을 제공합니다. 자체 규격을 정의하면 필드 이름을 자유롭게 정할 수 있으나, 표준 필드의 의미를 다시 합의해야 하고 프레임워크가 기본 제공하는 값을 직접 구성해야 합니다.

**분기 근거**는 HTTP 상태 코드와 애플리케이션 코드 중 하나입니다. 상태 코드만으로 분기하면 동일한 400 상태 코드 내에서 서로 다른 실패를 구분할 수 없습니다. 응답 문구로 분기하면 서버가 문구를 수정할 때 클라이언트 분기 로직이 손상됩니다. 애플리케이션 코드를 별도 필드로 두면 문구는 변경 가능한 값이 되고 코드가 고정 계약이 됩니다.

**코드의 정의 위치**는 중앙 등록부와 모듈별 열거형 중 하나입니다. 등록부를 문서로 두면 코드를 추가할 때 두 곳을 고쳐야 하고 한쪽이 낡습니다. 모듈별 열거형은 열거형 자체가 등록부 역할을 수행하며, 컴파일러가 중복과 오타를 판정합니다.

**실패 사유의 세분화**는 진단 가능성과 정보 노출이 상충하는 영역입니다. 대상 자원이 존재하지 않는 경우와 접근 권한이 없는 경우를 다른 코드로 구분하면 클라이언트가 상황에 맞는 안내를 표시할 수 있습니다. 그러나 그 차이가 곧 해당 식별자를 가진 자원이 존재한다는 정보가 되며, 이는 1.2 품질 목표의 보안 특성과 충돌합니다.

## 결정 (Decision)

**형식**: 실패 응답은 RFC 9457의 문제 상세 형식을 따릅니다. 표준 필드에 더해 `code`와 `traceId`를 확장 속성으로 포함합니다. `title`은 프레임워크가 상태 코드에서 설정하도록 위임하고 열거형에 별도로 정의하지 않습니다.

**코드 체계**: 모듈마다 열거형을 정의하고 상태 코드와 기본 문구를 함께 선언합니다. 코드 문자열은 `<모듈>_<사유>` 형식이며 접두사 등록부를 문서로 따로 두지 않습니다. 잘못된 요청, 충돌, 서버 오류 등 모듈에 속하지 않는 사유는 공용 기반에 단일 정의하고 모듈 열거형에 복제하지 않습니다.

**자원 열거 방지**: 대상 자원의 부재와 접근 권한 없음을 같은 코드로 응답합니다. 소유자가 아닌 요청은 조회 단계에서 제외되어 존재하지 않는 자원과 동일한 응답을 받습니다.

**필드 검증 실패**: 필드 이름과 검증 메시지를 배열로 포함합니다. 사용자가 입력한 원본 값은 포함하지 않습니다.

**메시지 소유권**: 서버는 코드와 문장을 함께 반환하고, 클라이언트는 코드를 우선 근거로 삼되 대응하는 문구가 없으면 서버의 문장을 그대로 표시합니다.

**필터 단계의 실패**: 전역 예외 처리기는 컨트롤러 진입 이전의 실패를 처리하지 못하므로, 필터에서 반환하는 실패 응답도 동일한 형식을 생성하는 전용 컴포넌트를 경유합니다.

## 결과 (Consequences)

서버가 문구를 수정해도 클라이언트 분기가 유지됩니다. 코드가 고정 계약이므로 문구는 서버가 자유롭게 조정할 수 있고, 클라이언트는 화면 맥락에 맞는 문구를 선택하되 알지 못하는 코드가 도착해도 서버의 문장으로 화면에 표시합니다.

감수하는 것이 넷입니다.

- 자원의 부재와 권한 없음을 구분해 안내할 수 없습니다. 사용자는 자신에게 권한이 없는 자원과 삭제된 자원을 같은 문구로 보게 됩니다.
- 응답에 같은 정보가 두 필드로 실릴 수 있습니다. `code`와 `detail`은 같은 실패를 각각 기계용과 사람용으로 표현합니다.
- 모듈이 늘어날 때마다 열거형이 늘어납니다. 코드 전체를 한 화면에서 보려면 여러 파일을 열어야 합니다.
- 클라이언트가 코드로 분기하려면 코드마다 문구 대응을 유지해야 합니다. 현재 클라이언트는 분기 지점이 없어 detail 을 그대로 표시하며, 코드 기반 분기는 그 필요가 생기는 화면에서 도입합니다.

아래 상황에서 이 결정을 다시 판단합니다.

- 권한 없음을 사용자에게 구분해 알려야 하는 화면이 생길 때. 자원 열거 위험과 안내의 정확성을 그 시점에 비교합니다.
- 클라이언트의 코드 대응표가 커져 유지 비용이 드러날 때. 문구를 서버로 되돌릴지 판단합니다.
