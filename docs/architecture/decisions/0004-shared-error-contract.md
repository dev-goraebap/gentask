# 결정-0004: 실패 응답을 RFC 9457 형식으로 반환하고 코드를 분기 계약으로 둔다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

서버는 다양한 유형의 실패를 반환하고 클라이언트는 이를 화면에 표시한다. 실패 응답의 형식과 클라이언트의 예외 처리 분기 기준을 결정해야 한다.

**응답 형식**: 자체 규격과 표준 규격 중 하나를 선택해야 한다. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)은 HTTP 응답의 문제 상세(Problem Details) 표준 표현을 정의하며 Spring Boot가 `ProblemDetail`로 구현을 기본 제공한다. 자체 규격을 정의하면 임의의 필드명을 자유롭게 구성할 수 있으나, 표준 필드의 의미를 재정의해야 하고 프레임워크가 제공하는 기본 오류 처리 메커니즘을 전면 재작성해야 한다.

**분기 근거**: HTTP 상태 코드와 애플리케이션 에러 코드 중 하나를 선택해야 한다. HTTP 상태 코드만으로 분기하면 동일한 400 Bad Request 내에서 서로 다른 비즈니스 실패 사유를 식별할 수 없다. 에러 메시지 문자열로 분기하면 서버의 메시지 수정 시 클라이언트 분기 로직이 깨진다. 애플리케이션 에러 코드를 별도 필드로 분리하면 문구는 가변적인 표현이 되고 코드가 고정 계약이 된다.

**코드의 정의 위치**: 중앙 문서 등록부와 모듈별 Java 열거형 중 하나이다. 등록부를 별도 문서로 관리하면 신규 코드 추가 시 두 곳을 동기화해야 하므로 문서가 쉽게 노후화된다. 모듈별 열거형은 코드 자체가 단일 등록부 역할을 수행하며 컴파일러가 중복과 오타를 검증한다.

**실패 사유의 세분화**: 상세 진단 편의성과 정보 누출(Resource Enumeration) 방어 간의 상충이다. 대상 자원이 존재하지 않는 경우와 접근 권한이 없는 경우를 다른 코드로 구분하면 사용자 안내는 정밀해지지만, 악의적인 사용자가 식별자를 대입하여 자원의 존재 여부를 탐지할 수 있는 보안 취약점이 발생한다.

## 결정 (Decision)

**형식**: 실패 응답은 RFC 9457의 Problem Details 형식을 채택한다. 표준 필드에 `code`와 `traceId`를 확장 속성으로 추가한다. `title`은 프레임워크 기본값에 위임하고 모듈 열거형에 별도 정의하지 않는다.

**코드 체계**: 모듈별로 에러 코드 열거형을 정의하고 HTTP 상태 코드와 기본 메시지를 함께 선언한다. 코드 문자열은 `<모듈>_<사유>` 형식을 따르며, 접두사 등록부를 문서로 별도 관리하지 않는다. 공통 실패(잘못된 요청, 리소스 충돌, 시스템 오류 등)는 공용 패키지에 단일 정의하고 모듈별로 복제하지 않는다.

**자원 열거 방어**: 대상 자원의 부재와 접근 권한 없음을 동일한 에러 코드로 응답한다. 비소유자 요청은 데이터베이스 조회 조건에서 원천 제외되어 부재 상태와 동일하게 처리된다.

**필드 검증 실패**: 필드 이름과 검증 메시지를 배열 구조로 응답한다. 사용자가 입력한 원본 값은 민감 정보 노출 방지를 위해 응답에서 제외한다.

**메시지 소유권**: 서버는 코드와 메시지를 함께 반환하고, 클라이언트는 에러 코드를 우선 매핑하되 미매핑 시 서버 메시지를 기본 노출한다.

**필터 계층 실패**: 서블릿 필터 단계의 실패 응답도 동일한 RFC 9457 형식을 생성하는 전용 필터를 경유하도록 구성한다.

## 결과 (Consequences)

서버가 오류 문구를 수정하더라도 클라이언트 분기 로직이 안정적으로 유지된다. 에러 코드가 고정 계약으로 기능하므로 서버는 메시지를 자유롭게 개선할 수 있고, 클라이언트는 화면 맥락에 적합한 문구를 매핑하되 신규 코드가 수신되어도 서버 메시지를 화면에 정상 표시한다.

감수하는 제약 사항은 다음과 같다.

- 자원의 부재와 권한 없음을 사용자에게 명확히 구분하여 안내하지 못한다.
- 기계 판독용 `code`와 사람 판독용 `detail` 필드가 응답에 함께 포함된다.
- 모듈 증가에 따라 열거형 파일이 분산 관리된다.
- 클라이언트가 정밀한 화면 안내를 위해 코드별 문구 매핑을 관리해야 한다.

다음 상황 발생 시 본 결정을 재검토한다.

- 권한 없음을 명확히 안내해야 하는 비즈니스 화면이 요구될 때.
- 클라이언트 코드 매핑표의 유지보수 비용이 과도해질 때.
