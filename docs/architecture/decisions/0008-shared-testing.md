# 결정-0008: 테스트의 소유를 나누고 인수 테스트를 인수 조건에 대응시킨다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

- 구현 코드와 테스트 코드를 에이전트가 작성하며 작업자는 테스트 코드를 전수 열람하지 않는다. 검증 코드를 직접 읽지 않는 환경에서는 테스트가 통과하더라도 무엇을 보호하는지 명확히 전달되지 않는다.
- 에이전트는 구현 코드를 기반으로 테스트를 작성하므로, 테스트가 요구 명세가 아닌 현재 코드의 동작을 그대로 단언하는 동어반복(Tautology)이 되기 쉽고 잠재 결함을 놓칠 위험이 있다.
- 작성 시점 기준 전체 테스트 250건 중 인수 조건과 직접 연결된 테스트는 64건이었다. 명세 문장과 연결되지 않은 테스트는 명칭만으로 실패 원인을 판별하기 어렵다.
- 작업자가 매일 화면을 직접 조작하므로 가시적인 결함은 자동화 테스트보다 작업자가 먼저 식별한다. 서버 계층은 화면 인터랙션이 없으므로 API를 직접 호출해야 검증된다.
- 테스트 피라미드와 테스트 트로피는 검증 비용 대비 효과를 고려한 계층 배분 모델이다. 본 프로젝트에서 실행 비용이 낮고 피드백이 빠른 계층을 중심으로 검증 전략을 수립해야 한다.
- **코드 커버리지 수치를 목표로 삼는 방안**: 도구 측정이 용이하지만 실행된 코드 라인 수만 집계할 뿐 핵심 불변식 검증 여부를 보장하지 못한다.
- **모든 테스트를 유지하는 방안**: 기존 코드를 보존할 수 있으나 인지 범위 밖의 테스트가 누적되어 리팩터링 시 유지보수 비용을 가중시킨다.
- **단위 테스트를 전면 배제하고 종단 테스트만 유지하는 방안**: 검증 계층을 단순화할 수 있다. 그러나 월말 기한 계산이나 시각 변환과 같은 복잡한 도메인 경계 조건을 브라우저 UI 조작만으로 정밀 검증하기 어렵고, 미인증 요청과 같은 비정상 인입 경로를 재현하는 데 과도한 비용이 발생한다.
- **종단 테스트 도구**: Playwright를 채택했다. 브라우저 인스턴스를 단일 기동한 후 테스트별 브라우저 컨텍스트 격리를 지원하여 병렬 실행 성능이 우수하고, `route.abort()`를 통해 실제 네트워크 실패를 시뮬레이션할 수 있으며, 실패 시 타임라인 추적, DOM 스냅숏, 네트워크 트레이스를 자동 보존한다. 반면 Cypress는 병렬 실행이 상용 클라우드에 종속되고 Selenium은 WebDriver 프로토콜 왕복 오버헤드로 인해 실행 속도가 현저히 느리다.
- **변이 테스트(Mutation Testing) 도입 방안**: 소스 코드를 인위적으로 변경하여 테스트의 결함 검출력을 판정하는 방안이다. 동어반복 테스트 식별에 효과적이나 실행 비용이 과도하여 현 단계에서는 도입을 유보한다.

## 결정 (Decision)

**소유권 분리**

- 테스트 소유권을 이원화한다. **작업자가 직접 관리하는 테스트는 두 종류이다.** 인수 조건을 검증하는 인수 테스트와, 백엔드 애플리케이션 및 도메인 계층의 단위 테스트이다. 작업자는 이 테스트들을 직접 검토하고 유지보수한다.
- **그 외 테스트는 에이전트가 관리한다.** 에이전트가 자체 판단으로 수정하거나 정리한다.
- 에이전트 관리 테스트 역시 아래 명시된 유효 계층 범주 내로 한정한다.

**판정 기준**

- 테스트 명칭은 관찰 가능한 비즈니스 결과를 기술한다. 내부 구현 구조가 아닌 외부에서 검증 가능한 동작을 명시한다.
- 작업자의 일상적인 화면 확인으로 결함 식별이 가능한 UI 요소는 자동화 테스트를 중복 작성하지 않는다.

**계층별 검증 범위**

- 인수 테스트는 Playwright 기반 E2E(End-to-End) 테스트로 구현하며, 브라우저부터 실제 백엔드 서버와 데이터베이스까지 전체 실행 경로를 검증한다.
- E2E 테스트는 워커별로 독립 계정을 생성하고 세션을 재사용한다. 워커 간 데이터 간섭이 없으므로 병렬 실행이 안전하며 중복 로그인 오버헤드를 방지한다.
- 테스트 픽스처 데이터는 화면 조작이 아닌 백엔드 API 호출을 통해 사전 생성한다. 검증 대상 핵심 경로만 브라우저 UI로 수행한다.
- 백엔드 통합 테스트는 HTTP 엔드포인트부터 실제 데이터베이스까지 검증하며, E2E 테스트로 도달하기 어려운 권한 경계, Bearer 토큰 인증, 비정상 요청, 상태 코드 및 Problem Details 응답, DB 마이그레이션을 검증한다.
- 백엔드 단위 테스트는 애플리케이션 계층과 도메인 계층에 집중 작성한다.
- 프론트엔드 단위 테스트는 순수 계산 경계값, 시간 정책, 복원 상태, 웹 접근성 속성, HTTP 요청 형태의 5개 범주로 한정한다.
- **CLI 축 테스트는 명령 실행 시 백엔드 API를 올바르게 호출하는지 검증한다.** CLI는 브라우저를 경유하지 않으므로 E2E 테스트가 도달하지 못하는 영역을 검증한다.
- 프론트엔드 화면 컴포넌트 테스트는 E2E로 재현하기 어려운 IME 한글 조합 상태, 중간 로딩 과도기 상태, 요청 미발생 단언, 복잡한 시각 선택기 조작으로 한정한다.
- 반응형 분기는 자동화 테스트에서 제외하고 작업자가 화면 조작으로 검증한다.
- 디자인 시스템 명도 대비비(WCAG)는 색상 모드별 조합 수가 방대하므로 자동화 테스트로 실측 검증한다.

**중복 제거**

- 동일한 검증 대상을 복수 계층이 중복 단언할 경우 하위 계층 테스트를 정리한다.
- 상위 테스트가 일부만 단언하는 경우에는 하위 단위 테스트를 보존한다. 테스트 명칭이 아닌 실제 단언(assertion) 대상을 기준으로 중복 여부를 판정한다.
- 삭제 단위는 개별 테스트 메서드 단위로 수행한다.

**인수 조건과 검증 계층 매핑**

- **화면 너비에 따른 반응형 배치는 인수 조건으로 기술하지 않는다.** 레이아웃 분기는 비즈니스 목표가 아닌 표현 수단이며 자동화 테스트 검증 대상에서 제외되었으므로, 배치의 의도는 화면 설계 문서나 Story 메모로 관리한다.
- **인수 조건 1건당 단일 검증 계층을 매핑한다.** 브라우저 UI로 검증 가능하면 E2E 테스트가, 불가능하면 백엔드 통합 테스트가 전담한다.
- 브라우저 UI로 도달할 수 없는 인수 조건은 문두에 `[서버]` 접두어를 부여한다. 백엔드 통합 테스트 또는 CLI 테스트가 검증을 담당함을 명시하기 위함이다.
- Story 완료 판정은 비`[서버]` 인수 조건이 E2E 테스트로 검증되고, `[서버]` 인수 조건이 통합 테스트로 검증되었을 때 작업자가 최종 판정한다.

**테스트 안정성**

- 일시적 재시도로 통과시키는 방식은 비결정적 결함(Flaky Test)을 은폐하므로, E2E 테스트의 재시도(Retry) 횟수는 0으로 고정한다.
- 간헐적 실패 테스트는 원인을 근본 해결하거나 제거하며, 임의의 대기 시간(sleep)으로 회피하지 않는다.
- 실패한 E2E 테스트는 실행 타임라인, 단계별 DOM 스냅숏, 네트워크 트레이스를 아티팩트로 보존하여 사후 디버깅을 지원한다.

## 결과 (Consequences)

인수 조건마다 검증 계층과 테스트가 1:1 대응하여 검증 책임이 명확해진다.

인수 조건과 연결되지 않는 순수 계산 경계값, 대비비, 시간 정책 등은 명시된 유효 범주 내에서 유지되며 에이전트가 소유권을 갖는다.

감수하는 제약 사항은 다음과 같다.

- 실패 발생 시 상세 원인 파악을 위해 상위 계층 실행 트레이스를 분석해야 한다.
- 통합 테스트만으로는 하위 세부 분기의 조합 폭발을 전수 방어하기 어렵다.
- 예외 경로 검증이 E2E 테스트에 편중된다.
- 반응형 분기 결함의 기계적 회귀 탐지가 불가능하다.
- E2E 테스트 추가로 전체 빌드 및 검증 시간이 증가한다.
- 에이전트 소유 테스트가 리팩터링 시 마찰 비용으로 작용할 수 있다.

다음 상황 발생 시 본 결정을 재검토한다.

- 협업 작업자가 추가될 때.
- E2E 테스트의 비결정적 실패 빈도가 증가할 때.
- 원격 CI 환경을 구축할 때.
- 변이 테스트 도구를 공식 도입할 때.
