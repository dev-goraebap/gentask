# 결정-0009: 모듈의 소통 창구를 모듈 루트에 두고 첨부 파일을 file 모듈이 소유한다

- 상태: 승인됨
- 날짜: 2026-08-29

## 맥락 (Context)

- 첨부 파일을 두 모듈이 각자 다르게 다루고 있었습니다. `task` 는 `task_files` 전용 표를 갖고 `user` 는 `users.profile_image_key` 컬럼 하나를 가졌습니다. 컬럼 하나뿐인 쪽은 파일명과 미디어 타입과 크기를 보관할 자리가 없어 그 값들을 잃었습니다.
- 발급(presign) 후 확정 전까지의 객체를 아무도 갖지 않았습니다. 확정하지 않고 떠나면 보관소에 객체가 남고 그것을 가리키는 행이 없어 청소의 근거가 없었습니다.
- 붙일 대상이 맞는지를 보관소 키의 접두어로 검사하고 있었습니다(`objectKey.startsWith("tasks/" + taskId + "/")`). 이 방식은 키 형식이 소유자를 담고 있어야만 성립하므로 키 규칙을 바꾸면 검사가 무너집니다.
- [5. 빌딩 블록 뷰](../05-building-block-view.md) §5.3.1 이 "하나의 모듈에서 주요 업무 애그리거트와 관련 파일 첨부 애그리거트를 함께 소유하는 구성"을 예시로 들고 있습니다. `task` 의 기존 구성은 규칙 위반이 아니었고, 뽑아내는 근거는 규칙이 아니라 중복입니다.
- **첨부를 별도 모듈로 두지 않는 방안**은 각 모듈이 자기 첨부를 계속 갖는 것입니다. 이 방안의 대가는 도메인이 늘 때마다 보관 정책과 발급 절차가 한 벌씩 복제되는 것이며, 이미 두 벌이 서로 다른 모양으로 존재했습니다.
- **다형 연결을 쓰지 않고 도메인마다 첨부 표를 두는 방안**은 외래 키로 생명주기를 표가 지켜 줍니다. 이 방안의 대가는 표가 도메인 수만큼 늘고 보관 절차가 그 수만큼 복제되는 것입니다.
- 첨부를 쓰는 모듈이 `file` 을 부르고 `file` 이 접근 판정을 위해 그 모듈을 되부르면 협력이 오갑니다. 이 왕복을 인터페이스로 역전시켜 컴파일 의존을 단방향으로 유지하는 기법이 있으나, 되부를 필요가 실제로 있는지는 별개의 판단입니다.

## 결정 (Decision)

**모듈의 공개 범위**

- 타 모듈에 공개하는 인터페이스와 타입을 **모듈 루트에 직접** 둡니다. 별도의 공개 패키지를 두지 않고 루트 자체가 소통 창구입니다. 하위 패키지(`application` · `domain` · `infrastructure`)는 모듈 내부 전용입니다.
- 공개 요소는 방향을 갖습니다. **`in`** 은 이 모듈이 제공하고 타 모듈이 호출하는 것이며, **`out`** 은 이 모듈이 요구하고 타 모듈이 구현하는 것입니다.
- **`out` 은 세 조건을 모두 충족할 때만 만듭니다.** 이 모듈이 자기 불변식 검증을 위해 그 정보를 요구하고, 스스로 판정할 수 없으며, 호출 인자로 전달받을 수 없어야 합니다. 세 번째가 남용을 막는 관문입니다.
- **`~Spi` 로 이름 짓지 않습니다.** Java 에서 SPI 는 구현이 복수이고 구현자를 사전에 알 수 없으며 런타임에 발견되는 확장 지점을 뜻합니다. 여기의 구현은 단일하고 구현자가 컴파일 시점에 확정되므로 그 이름은 교체 가능하다는 오해를 부릅니다. `in` · `out` 이 이미 더 정확한 구분 축입니다.
- 공개 요소가 주고받는 타입은 내부 엔티티가 아니라 별도로 정의합니다. 도메인 계층은 이 타입을 참조하지 않습니다 — 도메인이 창구를 거꾸로 참조하게 되기 때문입니다.

**첨부 파일**

- 첨부를 `file` 모듈이 소유합니다. Ruby on Rails 의 Active Storage 를 준용하여 `blobs`(파일 실체)와 `attachments`(다형 연결)로 나눕니다. 연결은 `owner_type` · `owner_id` · `name` 을 갖고 외래 키를 걸지 않습니다.
- 첨부가 놓이는 자리는 `(owner_type, name)` 쌍이며 그 쌍이 보관소 접두어와 개수·크기·허용 형식을 함께 갖습니다. 개수와 크기는 표 제약이 아니라 애플리케이션이 강제합니다. 하나만 허용하는 자리와 여럿을 허용하는 자리가 같은 표에 살기 때문입니다.
- **크기와 형식은 발급이, 개수는 붙이기가 강제합니다.** 발급은 붙을 레코드를 모르므로 이미 몇 개가 붙어 있는지 셀 수 없습니다.
- **자리 발급은 `file` 의 경로 하나가 받습니다**(`POST /api/v1/attachments/presign`). 발급은 보관소에 자리를 잡는 일일 뿐 어느 레코드에 붙을지와 무관하므로 도메인마다 두지 않습니다. Rails 의 Active Storage 도 direct upload 를 애플리케이션 전체에 하나만 두고, Uppy Companion 의 `/s3/params` 도 같습니다.
- **붙이는 것은 그 레코드를 소유한 모듈의 경로가 받습니다.** 어디에 매는지를 정하는 일이라 소유 판정이 필요하고, 그 판정은 소유 모듈의 규칙입니다.
- 발급한 업로드를 `pending_uploads` 가 갖습니다. 붙을 대상이 아니라 **발급한 사람**을 담으며, 붙일 때 발급자와 붙이는 사람이 같은지를 이 행으로 봅니다. 보관소 키의 접두어는 검사하지 않습니다.
- 붙일 때의 크기는 클라이언트가 알린 값이 아니라 보관소의 실측으로 판정합니다.
- **`file` 은 접근 권한을 판정하지 않으며 `out` 을 두지 않습니다.** 발급 경로는 소유자를 받지 않으므로 판정할 것이 없고(로그인 여부로 충분합니다), 붙이는 경로는 소유 모듈이 이미 판정한 뒤 부릅니다. 위 세 조건 중 "호출 인자로 전달받을 수 없어야 한다"를 넘지 못합니다.
- 정책 위반은 `file` 의 오류 코드가 냅니다. 검사하는 자리와 오류를 내는 자리를 같은 곳에 둡니다.
- 다형 연결에는 외래 키가 없으므로 소유 레코드가 사라질 때 첨부를 걷는 것은 그 레코드를 소유한 모듈이 수행합니다.

## 결과 (Consequences)

첨부의 보관 절차가 한 벌이 됩니다. 도메인이 늘어도 표는 늘지 않고 자리 열거에 값이 하나 늘 뿐이며, 프로필 이미지가 잃고 있던 파일명과 미디어 타입과 크기를 되찾습니다.

발급하고 붙이지 않은 객체가 목록으로 남아 청소의 근거가 생깁니다. **걷어 내는 일은 이 결정이 다루지 않으며** 그때까지 목록과 보관소의 객체가 쌓입니다. 소유자 판정이 키 형식에서 분리되어 보관소 키 규칙을 바꿔도 검사가 무너지지 않습니다.

`file` 이 어느 모듈도 참조하지 않습니다. 의존이 `task → file` · `user → file` 단방향으로만 흐르고 순환이 없습니다.

발급 경로가 하나로 모여 도메인이 늘어도 늘지 않습니다. 프런트엔드의 업로드 코드도 자리 이름만 바꿔 부르는 한 벌이 됩니다.

감수하는 것이 넷입니다.

- **다형 연결에 외래 키가 없습니다.** 참조 대상 표가 행마다 다르기 때문이며, 소유 레코드가 사라질 때 첨부를 걷는 것을 표가 대신해 주지 않습니다. 지우는 경로마다 첨부 정리를 함께 부르지 않으면 보관소에 객체가 남고, 이것을 기계가 판정하지 못합니다.
- **모듈 루트의 공개 범위를 기계가 강제하지 않습니다.** 하위 패키지를 참조해도 컴파일이 통과하며 규약으로만 지켜집니다. 모듈이 셋을 넘거나 위반이 실제로 발생하면 ArchUnit 도입을 다시 판단합니다.
- **개수 초과를 발급 시점에 알리지 못합니다.** 붙이는 시점에야 거절하므로 사용자가 올리기를 마친 뒤에 거절을 봅니다. 클라이언트가 같은 상한으로 먼저 막고 있어 실제로 이 경로를 타는 것은 그 가드를 지난 요청뿐입니다.
- **오류 코드가 바뀌었습니다.** `TASK_FILE_*` 과 `PROFILE_IMAGE_*` 가 `FILE_*` 로 통일되어 API 계약이 변경되었습니다. 클라이언트가 코드로 분기하지 않으므로 화면 동작은 유지되나, 코드로 분기하는 소비자가 생기면 그 시점에 계약의 안정성을 다시 판단해야 합니다.
- **옮겨 온 프로필 이미지가 미디어 타입과 크기를 갖지 않습니다.** 옛 자리가 그 값을 보관하지 않아 되찾을 수 없습니다. 파일명은 보관소 키의 마지막 마디로 두었고 크기는 0 이며, 다음 교체 때 실측 값으로 채워집니다.

아래 상황에서 이 결정을 다시 판단합니다.

- 붙이는 것까지 `file` 의 경로가 받아야 할 요구가 생길 때 `out` 의 세 조건을 다시 검토합니다. 그 경로는 소유자를 인자로 받으므로 판정이 필요해집니다.
- 자리마다 정책이 갈라져 열거 하나가 감당하지 못할 때 자리의 소유를 다시 판단합니다.
