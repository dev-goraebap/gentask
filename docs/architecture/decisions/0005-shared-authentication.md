# 결정-0005: 브라우저는 쿠키 세션으로, 그 밖의 클라이언트는 Bearer 토큰으로 인증한다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

서버는 요청자의 신원을 판정해야 하고, 판정 근거가 되는 자격 증명을 클라이언트가 보관하고 전송해야 한다.

초기 클라이언트는 브라우저 웹 애플리케이션 단일 환경이었으며 인증은 쿠키 세션으로 판정했다. 이후 로컬 에이전트가 사용자 계정으로 API를 호출하는 요구사항(`GT-29`)이 추가되면서 브라우저 외부의 CLI 도구가 클라이언트로 확장되었다. 쿠키 관리자가 없는 CLI 환경 특성상 두 번째 인증 수단이 필요해졌다.

**단일 수단으로 통일하는 방안**은 클라이언트 실행 환경 차이로 인해 제한된다. 쿠키는 브라우저가 자동으로 전송하며 그 자동 전송이 `HttpOnly` 속성의 전제이다. 브라우저 외부 클라이언트에는 이러한 자동화 메커니즘이 없다. 반대로 브라우저에 Bearer 토큰 방식을 적용하면 토큰을 로컬 스토리지 등에 보관해야 하므로 스크립트 접근에 의한 XSS 탈취 위험에 노출된다.

**토큰의 저장 형태**: 원문 저장과 해시 저장 중 하나이다. 원문을 저장하면 조회가 단순하지만 저장소가 유출되었을 때 즉시 인증 도용이 가능하다. 해시를 저장하면 유출 시에도 직접 인증에 악용할 수 없으나, 인입된 토큰을 매번 해싱하여 비교해야 하고 분실된 원문을 복구할 수 없다.

**세션 수명 정책**: 고정 만료와 슬라이딩 갱신 중 하나이다. 고정 만료는 작업 도중에도 만료되어 재인증을 요구한다. 슬라이딩 갱신은 사용할 때마다 만료를 연장하여 작업 흐름을 보장하는 대신, 지속 사용 시 세션이 무기한 유지될 수 있고 요청마다 세션 저장소 쓰기가 발생한다.

**인터셉터의 적용 범위**: 보호 대상 화이트리스트와 예외 대상 블랙리스트 중 하나이다. 보호 경로를 나열하면 신규 엔드포인트 추가 시 등록을 누락한 경로가 미인증 상태로 외부에 열린다. 미인증 허용 엔드포인트만 예외로 나열하면 누락된 경로는 닫힌 상태로 보호된다.

## 결정 (Decision)

**인증 수단**: 동일한 인터셉터가 두 요청 경로를 모두 처리한다. `Authorization: Bearer` 헤더가 존재하면 API 토큰으로, 없으면 세션 쿠키로 판정한다. 검증을 통과하면 요청 속성에 사용자 식별자를 설정하고, 이후 비즈니스 코드는 어떤 수단으로 인증되었는지 구분하지 않는다.

**쿠키 속성**: `HttpOnly`를 활성화하고, `SameSite=Lax`, `Path=/`로 설정한다. `Secure`는 환경별 설정으로 주입한다.

**토큰 저장**: 서버는 토큰 원문을 저장하지 않는다. 발급 시점에만 원문을 생성해 클라이언트에 전달하고 저장소에는 HMAC 해시를 보관한다. 해시 계산 시 토큰 용도(Scope)를 결합하여 동일한 원문이라도 세션과 API 토큰이 상이한 해시 결과를 갖도록 보장한다. 해시 비밀키는 환경 변수로 관리하며 최소 길이를 미달하면 부트스트랩 시점에 애플리케이션 기동이 실패한다.

**세션 수명**: 슬라이딩 갱신을 적용하되 절대 상한과 갱신 간격을 함께 둔다. 상한은 최초 발급 시점을 기준으로 하며, 갱신 간격 이내의 요청은 세션 유효성만 확인하고 저장소 쓰기를 생략한다. 만료된 세션은 존재하지 않는 세션과 동일한 실패 응답을 반환한다.

**적용 범위**: 인터셉터가 API 경로 전체를 기본 보호하고 미인증 허용 엔드포인트만 화이트리스트 예외로 제외한다. 회원가입, 로그인, 이메일 확인, 비밀번호 재설정이 예외 엔드포인트에 해당한다. 비밀번호 재설정은 미로그인 상태에서 진행되므로 세션을 요구하지 않고, [결정-0012](./0012-shared-credential-policy.md)의 일회용 코드로 신원을 검증한다. 비밀번호 변경은 로그인 상태에서 수행하므로 예외가 아니다.

**클라이언트 처리**: 클라이언트는 토큰 원문을 직접 다루지 않고 브라우저의 기본 쿠키 메커니즘에 위임한다. 화면 진입 시 인증 상태 확인은 라우트 가드가 내 정보 API를 조회하여 판정하고, 세션 만료 응답 처리는 HTTP 인터셉터가 전담한다. 로그인 실패 응답 자체는 인터셉터 처리 대상에서 제외한다. 프리렌더 빌드 경로에서는 가드가 진입을 허용한다.

## 결과 (Consequences)

세션 토큰이 클라이언트 스크립트에 노출되지 않는다. `HttpOnly` 쿠키는 스크립트 접근이 원천 차단되므로 XSS로 세션이 탈취되지 않으며, 데이터베이스가 유출되어도 보관된 해시로는 직접 인증할 수 없다.

감수하는 제약 사항은 다음과 같다.

- 인증 수단이 둘이므로 판정 경로도 둘이다. 인증 관련 변경은 두 경로 모두에서 정합성을 검토해야 한다.
- 자격 증명 저장 구조가 두 벌로 분리된다. 세션 토큰과 API 토큰은 해시 알고리즘과 조회 구조가 유사하지만 수명 정책 유무에 따라 엔티티와 저장소가 분리되어 있다.
- API 토큰에는 세션 만료 정책이 적용되지 않는다. 토큰 유출 시 사용자가 직접 폐기하거나 비밀번호를 재설정할 때까지 유효하다.
- `SameSite=Lax`는 화면과 API가 동일 출처라는 전제 위에서 동작한다. 타 출처에서 API를 호출하면 쿠키가 전송되지 않으므로 배포 환경에서 단일 도메인(Reverse Proxy) 구성이 전제된다.
- 라우트 가드의 조회 요청으로 인해 화면 진입 시 1회의 네트워크 왕복이 추가된다.
- 라우트 가드는 최종 보안 인가 수단이 아니며 실제 보안 판정은 백엔드 API 인터셉터가 매 요청마다 수행한다.
- 만료와 부재를 구분하여 응답하지 않는다.

다음 상황 발생 시 본 결정을 재검토한다.

- 화면과 API를 서로 다른 도메인 출처에 분리 배치해야 할 때.
- 세션 저장소 쓰기 부하가 성능 임계치에 도달할 때.
