# 결정-0002: 단일 브랜치에서 작업하고, 커밋에 유형 접두어를 붙이며, 배포를 셸 스크립트로 수행한다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

저장소는 두 축을 함께 갖는 모노레포([결정-0001](./0001-shared-monorepo.md))이며 작업자가 한 명입니다. 병합을 검토할 상대가 없고, 배포 대상은 서버 한 대이며 운영 환경은 하나입니다. 사용자는 아직 없습니다.

**다중 브랜치 모델**은 각 브랜치가 작업자 사이의 경계를 표현할 때 성립합니다. 통합 브랜치는 여러 작업자의 기능이 병합되는 지점이고, 릴리스 브랜치는 기능 투입을 중단하고 안정화하는 구간이며, 긴급 수정 브랜치는 운영에 배포된 코드와 개발 중인 코드가 분기했을 때 필요합니다. 작업자가 한 명이고 운영 환경이 하나이면 세 브랜치의 존재 조건이 모두 충족되지 않으므로, 브랜치를 추가해도 관리 대상만 늘고 판단 기준은 늘지 않습니다.

**커밋 메시지**는 현재 130건 전부 한국어 현재형 평서문이며 유형 접두어가 없습니다. 이력에서 특정 성격의 변경만 추리려면 제목을 읽어야 하고, 두 축이 한 저장소에 있으므로 어느 축을 변경한 커밋인지도 제목에서만 확인됩니다.

[관례적 커밋(Conventional Commits)](https://www.conventionalcommits.org/ko/v1.0.0/)은 유형과 범위를 제목 앞의 고정 위치에 두어 이 두 가지를 기계가 판독할 수 있는 형태로 만듭니다. 대가는 기존 이력 130건과 형식이 분리되는 것입니다. 이력을 재작성하지 않으므로 특정 커밋을 경계로 두 형식이 공존하는 상태가 영구히 남습니다.

**제목까지 영어로 전환하는 방안**은 채택하지 않았습니다. 유형과 범위만 영어 고정어로 두고 제목은 한국어 현재형을 유지하면, 기계가 판독하는 부분과 사람이 읽는 부분이 분리되고 기존 130건과 제목 문체가 연속됩니다.

**이슈 참조**는 GitHub 이슈를 사용하지 않으므로 `#번호` 형식이 성립하지 않습니다. 백로그 항목은 트래커에 있고 식별자는 `TG-NNN` 입니다. 참조는 그 식별자로 수행합니다. 항목을 닫는 일은 트래커에서 일어나므로 커밋과 같은 자리에서 대조되지 않으며, 그 대가는 [결정-0007](./0007-shared-software-process.md)이 적어 둡니다.

**CI/CD 도구 도입**도 검토했습니다. 얻는 것은 병합 시점의 자동 검증과 배포 재현성입니다. 대가는 러너 환경 구성과 자격 증명의 이관입니다. 접속 대상과 서버 내 경로는 추적되지 않는 `.deploy.env` 가 소유하는데, 파이프라인에서 배포하려면 이 값들을 저장소 비밀(Secret)에 등록해야 합니다. 저장소가 유출되었을 때의 노출 범위가 로컬 파일 하나에서 저장소 설정으로 확대됩니다.

자동 검증이 차단할 대상도 한정적입니다. 검토를 받을 상대가 없으므로 파이프라인이 차단하는 것은 작업자 자신의 실행 누락 하나이며, 그 누락은 배포 직전에 스크립트가 차단해도 동일하게 차단됩니다.

두 수단은 판정 시점이 다릅니다. 파이프라인은 병합 시점에 판정하고 스크립트는 배포 시점에 판정하므로, 검증을 통과하지 못하는 `main` 이 배포를 시도하기 전까지 저장소에 남을 수 있습니다. 단독 작업 동안은 그 사이에 해당 `main` 을 내려받는 작업자가 없어 손실이 발생하지 않습니다.

## 결정 (Decision)

**브랜치**: `main` 에서 기능 브랜치를 분기하고 `main` 으로 병합합니다. 중간 브랜치를 두지 않습니다.

**커밋**: 제목은 `<유형>(<범위>): <한국어 현재형 평서문>` 입니다. 범위는 생략할 수 있습니다.

- `feat` 사용자에게 드러나는 기능
- `fix` 결함 수정
- `refactor` 동작을 바꾸지 않는 구조 변경
- `perf` 동작을 바꾸지 않는 성능 변경
- `docs` 문서
- `test` 테스트 코드
- `build` 빌드 설정과 의존성
- `chore` 위 어디에도 속하지 않는 저장소 관리

범위는 축 이름을 그대로 사용합니다. `frontend` · `backend` · `shared` 중 하나이며, 축에 속하지 않는 변경(저장소 설정, 배포 스크립트, 백로그)은 범위를 생략합니다.

백로그 항목의 참조는 [트레일러](https://git-scm.com/docs/git-interpret-trailers)로 표기합니다.

```text
docs(shared): 인증 경로와 세션 관리를 개념 문서로 세운다

Refs: TG-029
```

- `Refs: <ID>` — 해당 항목의 작업이지만 닫지는 않습니다.
- `Closes: <ID>` — 해당 항목을 닫습니다. 이 트레일러를 쓰는 커밋은 그 항목의 `status` 를 `닫힘` 으로 바꾸는 수정을 함께 담습니다.

파괴적 변경 표기(`!` · `BREAKING CHANGE`)는 두지 않습니다. 두 축이 한 저장소에 있어 계약 변경과 그 소비 측 수정이 같은 커밋에 담기므로([결정-0001](./0001-shared-monorepo.md)) 별도로 알릴 소비자가 없습니다.

**환경**: 개발 서버를 두지 않습니다. 로컬과 운영 두 환경입니다.

**배포**: CI/CD 도구를 사용하지 않고 `scripts/` 의 셸 스크립트가 배포를 수행합니다. 스크립트는 산출물을 전송하기 전에 아래를 판정하고, 하나라도 충족되지 않으면 중단합니다.

- 현재 브랜치가 `main` 인가
- 작업 트리에 커밋되지 않은 변경이 없는가
- 로컬 `main` 이 `origin/main` 과 같은 커밋인가
- 두 축의 검증 명령이 통과하는가
- 배포 설정 파일이 존재하고 필수 변수가 채워져 있는가

배포한 커밋 해시를 릴리스 디렉터리에 기록하여 서버의 산출물이 어느 커밋에서 생성되었는지 추적할 수 있게 합니다.

## 결과 (Consequences)

배포 경로가 저장소 내부의 셸 스크립트로 한정됩니다. 외부 서비스에 의존하지 않으므로 파이프라인 설정과 실제 배포 동작이 불일치할 가능성이 없고, 절차 변경이 스크립트 수정과 동일한 작업이 됩니다.

감수하는 것이 다섯입니다.

- 병합 시점을 판정하는 주체가 없습니다. 검증을 통과하지 못하는 `main` 이 배포 시도 전까지 발견되지 않습니다.
- 운영 환경에서만 재현되는 문제를 사전에 확인할 수단이 없습니다. 개발 서버가 없으므로 배포가 최초 확인 시점입니다.
- 자격 증명이 작업자의 기기에만 존재합니다. 해당 기기를 분실하면 배포를 수행할 수 없습니다.
- 커밋 형식을 판정하는 수단이 없습니다. 훅과 파이프라인이 모두 없으므로 유형과 범위의 정확성은 작업자의 검토에만 의존합니다.
- 이력이 두 형식으로 분리됩니다. 이 결정 이전의 130건은 유형 접두어를 갖지 않으므로, 유형으로 이력을 집계하면 그 구간이 누락됩니다.

아래 상황에서 이 결정을 다시 판단합니다.

- 두 번째 작업자가 참여할 때. 검토 없는 `main` 직접 병합과 단일 기기에만 존재하는 자격 증명이 모두 성립하지 않게 됩니다.
- 사용자가 생겨 운영 중단이 손실로 이어질 때. 배포가 최초 확인 시점인 구조를 다시 판단합니다.
