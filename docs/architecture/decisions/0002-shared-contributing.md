# 결정-0002: 단일 브랜치에서 작업하고, 커밋에 유형 접두어를 붙이며, 배포를 셸 스크립트로 수행한다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

저장소는 두 축을 함께 관리하는 모노레포([결정-0001](./0001-shared-monorepo.md))이며 작업자가 1인이다. 병합을 검토할 동료 작업자가 없고, 배포 대상은 단일 서버이며 운영 환경 1벌로 구성되어 있다. 엔드유저는 아직 없다.

**다중 브랜치 모델(Git Flow 등)**은 복수 작업자 간의 작업 경계를 격리할 때 효용이 발생한다. 통합 브랜치(`develop`)는 여러 작업자의 기능이 병합되는 지점이고, 릴리스 브랜치는 신규 기능 투입을 동결하고 안정화하는 구간이며, 핫픽스 브랜치는 운영 배포 코드와 개발 진행 코드가 분기했을 때 필요하다. 작업자가 1인이고 운영 환경이 단일한 환경에서는 세 브랜치의 존재 조건이 충족되지 않으므로, 브랜치 관리 비용만 증가한다.

**기존 커밋 메시지**는 130건 전부 유형 접두어 없는 한국어 평문 제목이었다. 이력에서 특정 성격의 변경만 필터링하려면 제목 본문을 읽어야 하고, 두 축이 한 저장소에 있어 어느 축의 변경인지도 본문에서만 식별 가능했다.

[Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/) 규약은 유형과 범위를 제목 선두의 고정 위치에 두어 기계 판독이 가능한 규격으로 정형화한다. 트레이드오프로 기존 130건의 이력과 형식이 분리된다. 과거 이력을 강제 재작성(Rebase)하지 않으므로 특정 커밋을 기점으로 두 형식이 영구히 공존한다.

**제목 본문까지 영어로 전환하는 방안**은 채택하지 않았다. 유형과 범위만 영어 표준 식별자로 규격화하고 제목 본문은 한국어로 유지하면, 기계 판독 영역과 작업자 가독 영역이 명확히 분리되고 기존 130건의 이력 맥락과도 자연스럽게 연결된다.

**이슈 참조**는 GitHub 이슈를 사용하지 않으므로 `#번호` 형식이 아닌 백로그 트래커 식별자(`GT-NNN`)를 사용한다. 백로그 상태 갱신은 트래커 CLI를 통해 수행되며, 관련 운영 프로세스는 [결정-0007](./0007-shared-software-process.md)에 기술되어 있다.

**클라우드 CI/CD 도구 도입**도 검토했다. 병합 시점의 자동 검증과 배포 재현성을 확보할 수 있지만 러너 환경 구성과 서버 접근 시크릿 이관 비용이 수반된다. 서버 접속 대상과 경로는 추적되지 않는 `.deploy.env`에서 단일 관리되는데, 파이프라인에서 배포하려면 이 값들을 원격 저장소 시크릿에 등록해야 하므로 보안 노출 면적이 확장된다.

자동 검증의 실질적 차단 대상도 한정적이다. 동료 리뷰가 없는 1인 개발 환경에서 파이프라인이 방어하는 것은 작업자 자신의 검증 스크립트 실행 누락뿐이며, 이는 배포 스크립트의 사전 검증 단계에서도 동일하게 차단된다.

파이프라인은 병합 시점에 판정하고 스크립트는 배포 시점에 판정하므로, 검증을 통과하지 못하는 커밋이 일시적으로 `main`에 존재할 수 있다. 단독 작업 환경에서는 병렬 체크아웃하는 타 작업자가 없으므로 실질적인 손실이 발생하지 않는다.

## 결정 (Decision)

**브랜치 전략**: `main` 브랜치에서 토픽 브랜치를 분기하고 작업 완료 후 `main`으로 직접 병합한다. 중간 완충 브랜치를 두지 않는다.

**커밋 규약**: 제목은 `<유형>(<범위>): <제목>` 형식을 준수한다. 범위는 생략 가능하다.

- `feat`: 사용자에게 노출되는 기능 추가
- `fix`: 버그 및 결함 수정
- `refactor`: 인터페이스 및 외부 동작을 변경하지 않는 내부 구조 개선
- `perf`: 외부 동작을 변경하지 않는 성능 최적화
- `docs`: 문서 작성 및 수정
- `test`: 테스트 코드 추가 및 수정
- `build`: 빌드 시스템 설정 및 외부 의존성 변경
- `chore`: 저장소 설정 및 일상적 유지보수

범위는 아키텍처 축 이름을 사용한다(`frontend`, `backend`, `shared`). 축에 속하지 않는 전역 설정 및 배포 스크립트는 범위를 생략한다.

백로그 항목 참조는 Git 트레일러(Trailer) 형식을 적용한다.

```text
docs(shared): 인증 경로와 세션 관리 개념 문서 작성

Refs: GT-29
```

- `Refs: <ID>`: 해당 항목과 연관된 작업 커밋 (상태 미변경)
- `Closes: <ID>`: 해당 항목을 완료 처리하는 커밋

모노레포 구조상 API 계약 변경과 클라이언트 소비 코드가 단일 커밋에 원자적으로 수정되므로([결정-0001](./0001-shared-monorepo.md)), 외부 소비자를 위한 별도 파괴적 변경 표기(`!`, `BREAKING CHANGE`)는 적용하지 않는다.

**환경 구성**: 별도의 상시 개발 서버를 운영하지 않고 로컬 개발 환경과 상시 가용 운영 환경 2단계로 단순화한다.

**배포 절차**: 클라우드 CI/CD 도구를 배제하고 `scripts/` 디렉터리의 셸 스크립트로 배포를 실행한다. 배포 스크립트는 산출물 전송 전 다음 조건을 검증하여 하나라도 불만족 시 배포를 즉시 중단한다.

- 현재 체크아웃 브랜치가 `main`인가
- 작업 트리에 미커밋 변경사항이 없는가
- 로컬 `main`이 원격 `origin/main`과 동기화되어 있는가
- 프론트엔드 및 백엔드 축의 필수 검증 명령이 모두 통과하는가
- 배포 설정 파일(`.deploy.env`)이 존재하고 필수 환경 변수가 정의되어 있는가

배포 완료 시 배포 커밋 해시를 릴리스 디렉터리에 기록하여 서버 산출물의 추적성을 보장한다.

## 결과 (Consequences)

배포 경로가 저장소 내부 셸 스크립트로 단일화된다. 외부 파이프라인 서비스 의존성이 제거되므로 설정 불일치가 발생하지 않으며, 배포 절차 변경이 스크립트 수정과 동일한 작업 단위가 된다.

감수하는 제약 사항은 다음과 같다.

- 병합 시점의 강제 검증 게이트가 없다. 검증 실패 상태의 커밋이 배포 시점 전까지 `main`에 잔존할 수 있다.
- 별도 개발 서버가 없으므로 운영 환경 배포 시점이 실환경 최초 검증 시점이 된다.
- 배포 자격 증명이 작업자 로컬 머신에 국한된다.
- 커밋 메시지 규약을 강제하는 Git 훅이나 CI 린터가 없으므로 작업자의 준수 검토에 의존한다.
- 이력 형식이 양분된다. 본 결정 이전 130건은 유형 접두어가 없으므로 유형별 자동 통계 시 누락된다.

다음 상황 발생 시 본 결정을 재검토한다.

- 복수 작업자가 협업에 참여할 때.
- 실제 사용자가 유입되어 운영 환경 장애가 즉각적인 비즈니스 손실로 이어질 때.
