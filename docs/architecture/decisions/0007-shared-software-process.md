# 결정-0007: 요구사항을 유스케이스와 슬라이스로 관리하고 백로그를 파일로 둔다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

- 지금까지 요구사항 문서와 무관하게 코드를 먼저 작성했고, 그 코드가 왜 필요한지 되짚을 근거가 남지 않았습니다.
- 요구사항을 관리하되 1인 개발에 형식 절차를 도입하지 않으려 합니다. 관리 대상은 작업자가 직접 읽고 판단할 수 있는 분량이어야 합니다.
- **이슈 플랫폼에 등록하는 방안**은 상태 전이와 검색과 중복 검사를 도구가 수행합니다. 대가는 요구사항이 저장소 밖에 위치하는 것입니다. 에이전트가 이 프로젝트의 맥락을 읽으려면 별도의 인증과 API 호출이 필요하고, 저장소만으로는 요구사항을 알 수 없습니다.
- **파일로 두는 방안**은 요구사항이 코드와 같은 커밋 이력을 갖고, 에이전트가 저장소를 읽는 것만으로 맥락을 얻습니다. 대가는 상태 전이와 중복 검사를 작업자가 수행하는 것입니다.
- **Use-Case 3.0 의 산출물을 모두 갖추는 방안**은 표준을 온전히 따릅니다. 유스케이스 모델(Use-Case Model)이 전체 목록과 액터 정의를 갖고, 보충 명세(Supplementary Specification)가 흐름에 속하지 않는 요구사항을 받습니다. 대가는 1인 프로젝트에서 갱신되지 않는 문서가 늘어나는 것입니다.
- 프로토타입 없이 유스케이스를 확정할 수 있는지는 주제마다 다릅니다. 화면을 확인해야 흐름이 정해지는 주제가 존재합니다.

## 결정 (Decision)

**요구사항의 원본**

- Use-Case 3.0 과 이슈 관리 기법을 따르되 산출물을 축소합니다. 유스케이스 모델과 보충 명세는 작성하지 않습니다.
- 서술서는 식별된 하위 도메인별 디렉터리에 배치합니다. `docs/spec/<도메인>/`
- 서술서 하나가 한 액터의 목표 하나를 서술하며 기본 흐름과 대체 흐름과 예외 흐름을 갖습니다.
- 서술서는 프로젝트가 끝날 때까지 개정되는 참조 문서입니다. 착수 시점에 확정하지 않습니다.
- **서술서는 조작 단위로 자릅니다.** 추가 · 보기 · 편집 · 삭제 · 완료가 각각 문서 하나이며, 이름은 제품에서 통용되는 말을 씁니다. 목표 단위로 묶으려고 우회 표현을 만들지 않습니다.
- 다만 **목표 문장이 하나로 써지는지**가 판정 기준입니다. 서로 다른 목표를 한 문서로 묶으면 그 아래 흐름이 서로 관계없는 것들의 목록이 됩니다.
- **조회는 그 자체로 끝나는 목표일 때만 독립 문서입니다.** 조회 뒤에 반드시 다른 조작이 따라오면 그 조작의 첫 단계로 둡니다.
- 서술서 ID 는 `<도메인>-NNN` 이며 도메인 안에서 **읽는 순서**를 따릅니다. 순서를 바꾸는 삽입이 생기면 그 도메인을 재채번합니다. 이는 번호 불변 규칙의 예외입니다.

**착수**

- 에이전트와 제품 아이디어를 논의하여 PRD 를 작성합니다. `docs/prd.md`
- PRD 에서 유스케이스를 도출할 수 있으면 서술서를 먼저 작성합니다.
- 화면을 확인해야 흐름이 정해지면 프로토타입을 먼저 만듭니다. 이 작업은 발견(Discovery) 트랙의 Epic 이며 그 하위는 스파이크 Task 입니다. 요구사항이 아닙니다.
- 프로토타입이 판단 근거를 제공하는 시점에 유스케이스를 다시 정의합니다. 이 왕복은 유스케이스가 확정될 때까지 반복합니다.

**백로그**

- 백로그와 Epic 과 Story 와 Task 를 마크다운 파일로 관리합니다. 이슈 플랫폼을 사용하지 않습니다.
- 서술서의 흐름을 조합해 슬라이스를 만들고, 슬라이스 하나가 Story 하나가 됩니다.
- 슬라이스는 테스트할 수 있는 단위여야 합니다.
- 흐름은 서술서가, 슬라이스는 백로그가 갖습니다. 인수 조건과 지나는 흐름은 Story 파일에 적고 서술서에 적지 않습니다.
- 인수 조건은 EARS 로 씁니다. 그 경로를 지나는 테스트가 같은 문장을 이름으로 갖습니다.
- 아키텍처를 바꾸지 않는 요구사항별 기술 판단은 Story 의 메모에 적습니다. 같은 판단이 두 번째 Story 에 나타나면 참조 문서나 결정 기록으로 올립니다.

**구현**

- 목 계층 뒤에서 UI 를 먼저 만들고 백엔드가 생기면 의존성 주입 교체로 연결합니다.
- UI 는 서비스 인터페이스 뒤의 목 구현을 통해서만 데이터에 접근합니다. 이 인터페이스의 타입이 API 계약의 입력입니다.
- 화면을 목 위에 만드는 작업은 Story 가 아니라 스파이크 Task 입니다. 화면이 확정되고 서비스 인터페이스가 API 계약 초안이 되면 닫습니다.

**검증**

- 완료의 정의는 코드가 동작하는 것이 아니라 인수 조건이 참임이 확인된 것입니다.
- Story 는 목이 아니라 실제 백엔드 연결로 확인했을 때 닫습니다. 목 위의 화면 테스트는 프론트엔드 경로까지 참이라는 뜻이며, 단위 테스트만으로는 검증되지 않습니다.

**변경**

- 요구사항 변경이 흐름을 바꾸면 서술서를 먼저 개정합니다.
- 개정으로 근거를 잃은 Story 는 검증된 적이 없으므로 완료로 처리하지 않습니다.
- 개정을 승인하는 절차를 두지 않습니다. 다인 조직에서 이 위치를 담당하는 것은 요구사항 베이스라인과 변경 통제이며, 승인자와 피승인자가 동일인이면 성립하지 않습니다.

**추적**

- 커밋은 백로그 항목을 트레일러로 참조합니다. 트레일러의 형식은 [결정-0002](./0002-shared-contributing.md)가 소유합니다.
- 백로그 항목을 갖지 않는 작업(문서 · 설정 · 리팩터링)은 트레일러를 붙이지 않습니다.
- 테스트의 추적 키는 슬라이스 ID 입니다. 원본이 서술서이고 백로그는 그것의 진행 상태이므로 백로그 ID 를 쓰지 않습니다.
- 슬라이스 ID 는 그 슬라이스의 경로를 처음부터 끝까지 지나는 테스트에만 붙입니다. 단위 테스트에 붙이면 함수 하나의 통과가 경로가 닫혔다는 거짓 주장이 됩니다.
- 소스 주석에는 채번하지 않습니다.

## 결과 (Consequences)

코드에서 요구사항까지 경로가 성립합니다. 커밋의 트레일러가 Story 를 가리키고, Story 가 서술서와 흐름을 가리키므로, 임의의 커밋에서 그 변경이 어느 목표를 위한 것인지 되짚을 수 있습니다.

감수하는 것이 다섯입니다.

- 상태 전이와 중복 검사를 작업자가 수행합니다. 항목이 늘어나면 같은 요구사항이 두 Story 로 존재해도 도구가 알려 주지 않습니다.
- 유스케이스 전체 목록과 액터 정의가 한곳에 없습니다. 유스케이스 모델을 두지 않으므로 서술서 디렉터리를 훑어야 전체를 파악할 수 있습니다.
- 흐름에 속하지 않는 요구사항을 받을 자리가 좁습니다. 보충 명세를 두지 않으므로 비기능 요구사항은 참조 아키텍처가 받고, 그곳에도 자리가 없는 것은 기록되지 않습니다.
- 프로토타입 왕복에 종료 조건이 없습니다. 반복을 끝내는 판단이 작업자에게 있으며 판정 기준이 문서에 없습니다.
- 근거를 잃은 Story 를 표시할 상태값이 없습니다. 상태는 `open` · `in-progress` · `closed` 셋이고 `closed` 는 검증 완료를 뜻하므로, 요구사항 변경으로 무효가 된 Story 를 놓을 위치가 없습니다.

아래 상황에서 이 결정을 다시 판단합니다.

- 두 번째 작업자가 참여할 때. 파일 백로그의 동시 편집과 승인 절차 부재를 다시 판단합니다.
- 서술서가 한 번에 파악되지 않을 만큼 늘어날 때. 유스케이스 모델의 도입을 다시 판단합니다.
