# 결정-0007: 요구사항을 유스케이스와 슬라이스로 관리하고 백로그를 트래커에 둔다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

- 요구사항 문서 없이 코드를 먼저 작성함에 따라 코드의 필요성을 역추적할 근거가 부재했다.
- 1인 개발 환경에서 요구사항을 관리하되 형식적 절차 도입을 지양한다. 관리 대상은 작업자가 직접 읽고 판단할 수 있는 규모여야 한다.
- **외부 이슈 플랫폼 등록 방안**: 상태 전이, 검색, 중복 검사를 도구가 수행하지만 요구사항이 저장소 외부에 분리된다. 에이전트가 프로젝트 맥락을 파악하려면 별도의 인증과 API 호출이 필요하다.
- **저장소 파일 관리 방안**: 요구사항이 코드와 동일한 커밋 이력을 유지하며 에이전트가 로컬 파일 열람만으로 맥락을 파악할 수 있다. 반면 상태 전이와 중복 검사를 작업자가 수동으로 수행해야 한다.
- **파일 기반 도구 방안**: 마크다운 파일을 저장소에 두되 CLI와 웹 GUI가 상태 전이와 검색을 지원한다. 트레이드오프로 파일 형식이 도구의 메타데이터 규약에 종속된다.
- **Use-Case 3.0 산출물 전면 도입 방안**: 유스케이스 모델이 전체 목록과 액터를 정의하고 보충 명세가 비기능 요구사항을 수용한다. 1인 개발 환경에서는 지속 갱신되지 않는 유휴 문서가 증가한다.
- 프로토타입 없이 유스케이스를 조기 확정할 수 있는지는 주제마다 다르다. UI 화면을 직접 확인해야 인터랙션 흐름이 도출되는 영역이 존재한다.
- **모든 항목을 Epic 하위에 종속시키는 방안**: 계층 구조가 균일해지고 상위 단위로 진행률을 파악할 수 있다. 그러나 단일 자식만 포함하는 불필요한 Epic이 양산되어 형식적 계층 관리 비용이 발생한다. 주요 이슈 관리 도구(Jira, Linear, Plane)의 권장 관례 역시 Epic 소속을 필수로 강제하지 않는다. 단독 개선 작업이나 기술 Task는 최상위 항목으로 배치하는 것이 실무적이다. 다만 팀 규모가 다수로 확장되면 최상위 단독 항목 증가로 인해 백로그 정렬과 의존성 추적이 복잡해질 수 있다.

## 결정 (Decision)

**요구사항의 원본**

- Use-Case 3.0 및 이슈 관리 기법을 준용하되 산출물을 실용적으로 축소한다. 유스케이스 모델과 보충 명세는 별도 작성하지 않는다.
- 서술서는 식별된 하위 도메인별 디렉터리(`docs/spec/<도메인>/`)에 배치한다.
- 서술서 1건은 단일 액터의 단일 목표를 기술하며 기본 흐름, 대체 흐름, 예외 흐름을 포함한다.
- 서술서는 프로젝트 종료 시점까지 지속적으로 개정되는 참조 문서이며 착수 시점에 조기 확정하지 않는다.
- 서술서는 조작 단위로 분할한다. 추가, 보기, 편집, 삭제, 완료를 각각 개별 문서로 구성한다.
- 문서 분할의 판정 기준은 단일 목표 문장의 성립 여부이다. 서로 다른 목표를 단일 문서로 묶지 않는다.
- 조회는 그 자체로 완결되는 독립 목표일 때만 별도 문서로 작성한다. 후속 조작이 반드시 수반되는 조회는 해당 조작의 첫 단계 흐름으로 통합한다.
- 서술서 ID는 `<도메인>-NNN` 형식이며 도메인 내 열람 순서를 따른다. 순서를 변경하는 삽입이 발생하면 해당 도메인의 ID를 재채번한다. 이는 번호 불변 규칙의 유일한 예외이다.

**착수**

- 에이전트와 제품 아이디어를 논의하여 PRD(`docs/prd.md`)를 작성한다.
- PRD에서 유스케이스를 명확히 도출할 수 있으면 서술서를 먼저 작성한다.
- 화면을 확인해야 흐름이 정해지는 경우 프로토타입을 먼저 제작한다. 이 작업은 발견(Discovery) 트랙의 Epic 및 하위 스파이크 Task로 분류하며 공식 요구사항이 아니다.
- 프로토타입이 판단 근거를 제공하는 시점에 유스케이스를 확정 정의한다. 이 반복은 유스케이스가 안정화될 때까지 지속한다.

**백로그**

- Epic, Story, Task, Bug는 **자체 운영 트래커**에서 통합 관리한다. 저장소 내부 파일이나 외부 상용 플랫폼에 의존하지 않는다. 작업자는 웹 인터페이스로, 에이전트는 `gentask issue` CLI로 조회하고 수정한다.
- **2026-09-02에 파일 기반 백로그(`backlog/`, [Backlog.md](https://github.com/MrLesk/Backlog.md))에서 자체 트래커로 이관했다.** 이관 목적은 실사용 검증(Dogfooding)이다. 저장소의 실제 백로그를 자체 제품으로 관리함으로써 트래커의 결함과 미구현 기능이 사용 과정에서 즉각 식별된다. 실제 이관 직후 부모 항목을 연결하는 API 결손이 확인되어 즉시 보완했다.
- 데이터 스키마가 동일하며 계층 구조로만 분기하므로, 백로그 항목은 단일 테이블에서 관리하며 `kind` 속성으로 `EPIC`, `STORY`, `TASK`, `BUG`를 분류한다.
- **상태는 5단계로 관리한다** — `BACKLOG`(백로그), `TODO`(예정), `IN_PROGRESS`(진행 중), `DONE`(완료), `CANCELLED`(취소). Plane 및 Linear의 상태 분류 체계를 준용한다. `BACKLOG`와 `TODO`의 구분 기준은 착수 결정 여부이다. 둘 다 미착수 상태이지만 `TODO`는 실행이 확정된 항목이다. `DONE`은 인수 조건 충족이 검증된 상태이고, `CANCELLED`는 근거 상실로 폐기된 상태이다.
- 항목 ID는 `GT-NNN` 형식이며 **유형 및 계층과 무관하게 단일 수열로 채번한다.** 접두어는 프로젝트를 식별하며 작업 유형을 나타내지 않는다.
- **계층 관계는 식별자 번호가 아닌 부모 참조 필드로 관리한다.** 소속을 식별자에 포함하면 부모 변경 시 ID가 함께 변경되어 기존 커밋 및 테스트 코드의 참조가 깨지므로, 식별자 불변 원칙에 따라 부모 식별자 접두 방식을 2026-09-01에 폐기하고 참조 필드 방식으로 전환했다.
- **Epic 소속은 선택 사항이다.** 복수 서술서에 걸치는 증분 기능은 Epic 하위에 배치하고, 사용자 가치를 직접 제공하지 않는 기술 작업은 최상위 Task로 배치한다. 단일 자식만 포함하는 Epic은 생성하지 않는다.
- 목록 이원화에 따른 화면, CLI, 검색 인터페이스의 중복 복제를 방지하기 위해, 서술서와 인수 조건이 아직 정의되지 않은 착수 후보는 별도 목록으로 분리하지 않고 `BACKLOG` 상태 속성으로 통합 관리한다.
- 착수가 결정되면 `TODO` 상태로 변경한다. 별도의 승격 절차를 두지 않는다.
- **부모 항목 연결은 `--parent` 옵션으로 설정한다.** 생성 및 수정 시 부모 식별자를 전달하며, 옵션을 비우면 최상위 항목으로 전환된다. 부모 변경 시에도 항목 고유 ID는 유지된다.
- 슬라이스는 서술서의 흐름을 조합한 테스트 가능한 최소 단위이다. 조합 결과물이므로 별도 식별자나 문서를 두지 않으며, Story 본문에 대상 흐름을 명시하고 Story ID를 해당 슬라이스의 식별자로 사용한다.
- **슬라이스는 단일 서술서 범위 내에서 분할한다.** 복수 서술서에 걸치는 기능 묶음은 슬라이스가 아닌 증분(Increment)이며 Epic으로 관리한다. Use-Case 3.0 원칙 10은 슬라이스를 '단일 유스케이스를 관통하는 하나 이상의 실행 경로'로 정의한다.
- **기본 원칙은 단일 서술서당 단일 Story 구성이다.** 서술서 전체 흐름을 한 번에 인도하고 검증할 수 있다면 추가 분할하지 않는다. 분할 기준은 인도의 크기이며 단순 분류가 아니다. 인수 조건이 1개인 Story도 성립한다.
- 유스케이스 흐름은 서술서에서 관리하고, 검증 대상 흐름과 인수 조건은 Story 본문에 기술한다. 서술서에는 인수 조건을 중복 기술하지 않는다.
- 인수 조건은 EARS 문법으로 작성하고 Story 내에서 `#<n>` 번호를 순차 부여한다. 번호는 부여 후 불변이며 추가 시 마지막 번호를 채번하고 삭제 시 결번 처리한다.
- **인수 조건의 경계 마커를 별도로 두지 않는다.** 리치 텍스트 편집기(ProseMirror/Tiptap)가 마크다운 변환 시 HTML 주석을 보존하지 못하고 유실시키므로, 2026-09-02에 `<!-- AC:BEGIN -->` 주석 경계 방식을 폐기했다. `- [ ] #<n> <문장>` 형태의 체크리스트 항목 자체가 인수 조건이며 본문 내 위치와 무관하게 인식된다.
- 줄을 삭제하면 후속 번호가 당겨져 기존 테스트 및 커밋 참조가 어긋나므로, 결번 발생 시 번호를 삭제하지 않고 문장을 `(결번)`으로 치환한다.
- **인수 조건 1건은 단일 기대 응답을 기술한다.** 응답이 둘 이상이면 문장을 분할하여 후속 번호를 부여한다. 복수 트리거 조건은 단일 문장에 나열 가능하며 파라미터화 테스트로 검증한다.
- 아키텍처에 영향을 주지 않는 요구사항 단위의 기술 판단은 Story 본문에 기록한다. 동일 판단이 2회 이상 반복되면 참조 아키텍처 문서나 ADR로 승격한다.

**구현**

- 목(Mock) 계층 기반으로 UI를 우선 구현하고 백엔드 구현 완료 시 의존성 주입을 통해 실제 연동으로 교체한다.
- UI는 서비스 인터페이스 기반 목 구현체를 통해서만 데이터에 접근하며, 해당 인터페이스 정의가 API 계약의 입력이 된다.
- 목 기반 화면 구현 작업은 Story가 아닌 스파이크 Task로 관리하며, 화면이 확정되고 인터페이스가 확정되면 Task를 종료한다.

**검증**

- 완료의 정의는 단순 코드 동작이 아닌 인수 조건의 참 판정이다.
- Story는 목 구현이 아닌 실제 백엔드 연동 상태에서 인수 조건이 검증되었을 때 닫는다. 목 기반 화면 테스트는 프론트엔드 단독 경로 검증이며 전체 비즈니스 검증을 대체하지 못한다.

**변경**

- 요구사항 변경으로 흐름이 바뀌면 서술서를 먼저 개정한다.
- 개정으로 근거를 상실한 Story는 유효성이 검증되지 않았으므로 완료 처리하지 않는다.
- 1인 개발 환경이므로 형식적 변경 승인 절차는 두지 않는다.

**추적**

- 커밋은 백로그 항목을 Git 트레일러로 참조한다([결정-0002](./0002-shared-contributing.md)).
- 백로그 항목과 무관한 전역 작업(문서, 설정, 리팩터링)은 트레일러를 생략한다.

## 결과 (Consequences)

코드에서 요구사항까지 양방향 추적성이 확보된다. 커밋 트레일러가 Story를 참조하고 Story가 서술서 흐름을 참조하므로, 임의의 커밋이 어떤 비즈니스 요구사항을 구현한 것인지 역추적할 수 있다.

감수하는 제약 사항은 다음과 같다.

- 백로그 중복 검사를 작업자가 수동 수행한다.
- **ID만으로는 항목의 상위 계층을 식별할 수 없다.** 평평한 단일 수열 ID 체계이므로 부모를 확인하려면 항목 세부 정보를 조회해야 한다.
- 유스케이스 전체 목록과 액터 정의를 종합한 단일 유스케이스 모델 문서를 두지 않는다.
- 비기능 요구사항을 수용할 별도의 보충 명세서를 두지 않으며 아키텍처 문서로 직접 수렴한다.
- 프로토타입 탐색의 명시적 종료 조건이 작업자의 주관적 판단에 의존한다.
- 번호 없는 일반 체크리스트 항목이 본문에 포함되면 인수 조건 파서와 혼동될 수 있다.
- 인수 조건의 테스트 통과 여부를 기계적으로 강제 검증하지 않으며 작업자가 테스트 결과를 확인하고 닫는다.
- 기술 작업 Task가 누적될 경우 최상위 항목이 증가하여 백로그 가독성이 저하될 수 있다.
- **백로그 원본이 저장소 외부(트래커 DB)로 분리되었다.** 코드와 동일한 형상 커밋 이력을 공유하지 않는다.
- **백로그 조회를 위해 자체 트래커 서버가 기동되어 있어야 한다.**

다음 상황 발생 시 본 결정을 재검토한다.

- 복수 작업자가 참여하여 동시 백로그 편집 및 공식 승인 절차가 요구될 때.
- 서술서 규모가 급증하여 유스케이스 모델 도입이 불가피해질 때.
