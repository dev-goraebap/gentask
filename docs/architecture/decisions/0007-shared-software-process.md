# 결정-0007: 요구사항을 유스케이스와 슬라이스로 관리하고 백로그를 파일로 둔다

- 상태: 승인됨
- 날짜: 2026-08-28

## 맥락 (Context)

- 요구사항 문서 없이 코드를 먼저 작성함에 따라, 코드의 필요성을 역추적할 근거가 남지 않았습니다.
- 1인 개발 환경에서 요구사항을 관리하되 형식적 절차 도입을 지양합니다. 관리 대상은 작업자가 직접 읽고 판단할 수 있는 규모여야 합니다.
- **이슈 플랫폼에 등록하는 방안**은 상태 전이, 검색, 중복 검사를 도구가 수행합니다. 이슈 플랫폼에 등록하는 방안의 대가는 요구사항이 저장소 밖에 위치하는 것입니다. 에이전트가 이 프로젝트의 맥락을 읽으려면 별도의 인증과 API 호출이 필요하고, 저장소만으로는 요구사항을 알 수 없습니다.
- **파일로 두는 방안**은 요구사항이 코드와 동일한 커밋 이력을 유지하며, 에이전트가 저장소 열람만으로 맥락을 파악할 수 있습니다. 파일로 두는 방안의 대가는 상태 전이와 중복 검사를 작업자가 수행하는 것입니다.
- **파일을 도구로 다루는 방안**은 마크다운 파일을 저장소에 두되 CLI 와 웹 GUI 가 상태 전이, 검색, 계층 조회를 수행합니다. 파일을 도구로 다루는 방안의 대가는 파일 형식이 도구의 규약에 종속되는 것입니다. 프런트매터의 필드 이름과 인수 조건의 마커를 도구가 정하므로, 도구를 바꾸면 형식을 함께 옮겨야 합니다.
- **Use-Case 3.0 의 산출물을 모두 갖추는 방안**은 표준을 준수하여 유스케이스 모델(Use-Case Model)이 전체 목록과 액터 정의를 관리하고, 보충 명세(Supplementary Specification)가 흐름 외 요구사항을 수용합니다. Use-Case 3.0 의 산출물을 모두 갖추는 방안의 대가는 1인 프로젝트에서 갱신되지 않는 문서가 늘어나는 것입니다.
- 프로토타입 없이 유스케이스를 확정할 수 있는지는 주제마다 다릅니다. 화면을 확인해야 흐름이 정해지는 주제가 존재합니다.
- **모든 항목을 Epic 아래 두는 방안**은 계층이 고르게 서고 상위 묶음으로 진행을 읽을 수 있습니다. 그 대가는 자식 하나뿐인 Epic 이 생기는 것이며, 그것은 계층을 형식으로만 채웁니다. 이슈 도구의 관례도 소속을 강제하지 않습니다 — Jira 는 백로그에 ["Issues without epic"](https://community.atlassian.com/forums/Jira-questions/Issues-without-epics-kanban-board/qaq-p/2290730) 구획을 정상 자리로 두고, 필수로 만들려면 [워크플로 검증기를 따로 겁니다](https://community.atlassian.com/forums/Jira-questions/Is-it-possible-to-disallow-non-epics-without-parent-orphan/qaq-p/2687194). Atlassian 은 [Epic 을 선별적으로 쓰라고](https://www.atlassian.com/agile/project-management/epics-stories-themes) 적으며, 작은 독립 개선과 기술 작업은 단독으로 두는 것이 [일반적 안내](https://plane.so/blog/epic-vs-feature-vs-user-story-vs-task-understanding-the-differences)입니다. 다만 같은 자료가 여러 팀으로 확장하면 단독 항목이 늘어 정렬과 의존 추적이 깨진다고 함께 적습니다.

## 결정 (Decision)

**요구사항의 원본**

- Use-Case 3.0 및 이슈 관리 기법을 준용하되 산출물을 축소합니다. 유스케이스 모델과 보충 명세는 작성하지 않습니다.
- 서술서는 식별된 하위 도메인별 디렉터리(`docs/spec/<도메인>/`)에 배치합니다.
- 서술서 1건은 단일 액터의 단일 목표를 기술하며 기본 흐름, 대체 흐름, 예외 흐름을 포함합니다.
- 서술서는 프로젝트 종료 시점까지 지속적으로 개정되는 참조 문서이며 착수 시점에 확정하지 않습니다.
- 서술서는 조작 단위로 분할합니다. 추가, 보기, 편집, 삭제, 완료를 각각 개별 문서로 구성하며 제품에서 통용되는 용어를 명칭으로 사용합니다. 목표 단위로 묶기 위한 우회 표현을 사용하지 않습니다.
- 문서 분할의 판정 기준은 단일 목표 문장의 성립 여부입니다. 서로 다른 목표를 단일 문서로 묶지 않습니다.
- 조회는 그 자체로 끝나는 목표일 때만 독립 문서로 작성합니다. 후속 조작이 반드시 수반되는 조회는 해당 조작의 첫 단계로 둡니다.
- 서술서 ID 는 `<도메인>-NNN` 형식이며 도메인 내 열람 순서를 따릅니다. 순서를 바꾸는 삽입이 발생하면 해당 도메인의 ID 를 재채번합니다. 이는 번호 불변 규칙의 예외로 적용합니다.

**착수**

- 에이전트와 제품 아이디어를 논의하여 PRD(`docs/prd.md`)를 작성합니다.
- PRD 에서 유스케이스를 도출할 수 있으면 서술서를 먼저 작성합니다.
- 화면을 확인해야 흐름이 정해지면 프로토타입을 먼저 제작합니다. 이 작업은 발견(Discovery) 트랙의 Epic 및 하위 스파이크 Task 로 분류하며 요구사항이 아닙니다.
- 프로토타입이 판단 근거를 제공하는 시점에 유스케이스를 다시 정의합니다. 이 왕복은 유스케이스가 확정될 때까지 반복합니다.

**백로그**

- Epic, Story, Task 를 마크다운 파일로 관리하며 이슈 플랫폼을 사용하지 않습니다. 파일은 [Backlog.md](https://github.com/MrLesk/Backlog.md) 로 다루고 `backlog/` 아래에 둡니다.
- 항목은 유형과 무관하게 `backlog/tasks/` 하나에 두고 프런트매터의 `type` 이 `epic` · `story` · `task` 를 가릅니다.
- **상태는 다섯입니다** — `백로그` · `예정` · `진행 중` · `닫힘` · `취소`. 이름과 자리는 Plane 과 Linear 의 상태 묶음을 따릅니다. `백로그` 와 `예정` 을 가르는 축은 착수 여부가 아니라 **하기로 정했는가**이며, 둘 다 시작하지 않은 것입니다. `닫힘` 은 인수 조건이 참임을 확인한 것이고 `취소` 는 근거를 잃어 더 이상 유효하지 않은 것입니다.
- 항목 ID 는 `TG-NNN` 이며 자식은 부모의 ID 를 앞에 답니다(`TG-003.05`). 접두어는 프로젝트를 가리키며 유형을 가리키지 않습니다. 도구가 프로젝트당 접두어 하나만 지원하고 그것이 채번 전용이기 때문입니다.
- **Epic 소속은 선택입니다.** 여러 서술서에 걸치는 증분이면 Epic 아래 두고, 사용자 가치를 직접 내지 않는 기술 작업은 최상위 Task 로 둡니다. 자식 하나뿐인 Epic 을 만들지 않습니다. 계층을 형식으로만 채우게 되기 때문입니다.
- 서술서와 인수 조건을 아직 갖지 않은 착수 후보는 `백로그` 상태로 둡니다. **별도 목록이 아니라 상태 하나입니다** — Jira · Linear · Plane 셋 다 이 자리를 같은 항목의 상태로 두며, 목록을 둘로 나누면 화면 · 명령줄 · 검색이 두 벌이 됩니다.
- 착수하기로 정하면 `예정` 으로 옮깁니다. 승격이라는 별도 절차를 두지 않습니다.
- **파일 백로그를 쓰는 동안은 도구의 Draft 가 그 자리를 대신합니다.** [Backlog.md](https://github.com/MrLesk/Backlog.md) 가 상태 셋만 제공하므로 `backlog/drafts/` 와 `backlog draft promote` 를 그대로 쓰며, 착수 순서는 Draft 번호가 갖습니다. 트래커로 옮기는 시점에 상태 하나로 흡수합니다.
- 슬라이스는 서술서의 흐름을 조합한 것이며 테스트할 수 있는 단위입니다. 조합의 결과이므로 자체 식별자를 갖지 않고 문서로도 존재하지 않으며, Story 파일이 해당 조합을 기록하고 Story ID 가 그 식별자입니다.
- **슬라이스는 서술서 하나 안에서 자릅니다.** 여러 서술서에 걸치는 묶음은 슬라이스가 아니라 증분(Increment)이며 그 자리는 Epic 입니다. Use-Case 3.0 의 원칙 10 이 슬라이스를 "하나의 유스케이스를 지나는 하나 이상의 경로"로 규정합니다.
- **기본값은 서술서 하나에 Story 하나입니다.** 흐름 전체를 한 번에 인도해서 검증할 수 있으면 쪼개지 않습니다. 쪼개는 근거는 한 번에 인도하기에 크다는 것이며 분류가 아닙니다. 인수 조건이 하나뿐인 Story 도 성립합니다.
- 흐름은 서술서가 관리하고 인수 조건과 대상 흐름은 Story 파일이 갖습니다. 서술서에는 인수 조건을 적지 않습니다.
- 인수 조건은 EARS 로 작성하고 Story 내에서 `#<n>` 번호를 부여합니다. 번호는 부여 후 불변이며 추가 시 마지막 번호를 부여하고 삭제 시 결번 처리합니다.
- 결번은 번호를 지우지 않고 문장을 `(결번)` 으로 바꾸어 표시합니다. 도구의 `--remove-ac` 는 뒤 번호를 당기므로 사용하지 않습니다.
- **인수 조건 하나는 응답 하나를 갖습니다.** 응답이 둘이면 문장을 둘로 나누고, 뒤 문장이 마지막 번호를 받습니다. 트리거가 여럿 열거되는 것은 허용하며 파라미터화 테스트 하나가 그것을 받습니다.
- 아키텍처를 변경하지 않는 요구사항 단위의 기술 판단은 Story 의 메모에 기록합니다. 동일 판단이 두 번째 Story 에 나타나면 참조 문서나 결정 기록으로 승격합니다.

**구현**

- 목(Mock) 계층 기반으로 UI 를 먼저 구현하고 백엔드 구현 완료 시 의존성 주입 교체로 연결합니다.
- UI 는 서비스 인터페이스 뒤의 목 구현을 통해서만 데이터에 접근합니다. 해당 인터페이스의 타입 정의가 API 계약의 입력입니다.
- 목 기반의 화면 구현 작업은 Story 가 아닌 스파이크 Task 로 관리합니다. 화면이 확정되고 서비스 인터페이스가 API 계약 초안이 되면 해당 Task 를 닫습니다.

**검증**

- 완료의 정의는 코드가 동작하는 것이 아니라 인수 조건이 참임이 확인된 것입니다.
- Story 는 목이 아니라 실제 백엔드 연결로 확인했을 때 닫습니다. 목 기반의 화면 테스트는 프론트엔드 경로까지 참이라는 의미이며, 단위 테스트만으로는 검증되지 않습니다.

**변경**

- 요구사항 변경이 흐름을 바꾸면 서술서를 먼저 개정합니다.
- 개정으로 근거를 잃은 Story 는 검증된 적이 없으므로 완료로 처리하지 않습니다.
- 개정을 승인하는 절차를 두지 않습니다. 다인 조직에서 이 위치를 담당하는 것은 요구사항 베이스라인과 변경 통제이며, 승인자와 피승인자가 동일인이면 성립하지 않습니다.

**추적**

- 커밋과 테스트는 동일한 추적 키를 사용하며 키는 Story ID 입니다.
- 커밋은 백로그 항목을 트레일러로 참조합니다. 트레일러 형식은 [결정-0002](./0002-shared-contributing.md)가 규정합니다.
- 백로그 항목을 갖지 않는 작업(문서, 설정, 리팩터링)은 트레일러를 붙이지 않습니다.
- 테스트의 추적 키는 `TG-NNN.NN #<n>` 이며 테스트 이름의 접두어로 둡니다. 테스트의 추적 키로 서술서 ID 를 쓰지 않는 것은 서술서가 인수 조건을 갖지 않기 때문입니다. 테스트가 단언하는 것은 인수 조건이므로 그것을 소유하지 않는 문서의 ID 로는 무엇을 단언하는지 지목되지 않습니다.
- 접두어는 인수 조건의 경로를 처음부터 끝까지 지나는 테스트에만 붙입니다. 단위 테스트에 붙이면 함수 하나의 통과가 경로가 닫혔다는 거짓 주장이 됩니다.
- 인수 조건 하나에 인수 테스트 하나를 대응시킵니다. 인수 조건이 응답 하나를 갖도록 쓰여 있으면 이 대응이 성립합니다.
- 준비를 공유하느라 테스트 하나가 여러 인수 조건을 지탱하게 되면 접두어에 함께 기술합니다. 이는 대응이 성립하지 않는 상태이며 인수 조건이나 테스트를 나눌 자리를 가리킵니다.
- 테스트 이름의 나머지는 인수 조건 문장과 일치시키지 않습니다. 문장을 다듬어도 추적이 깨지지 않게 하기 위해서입니다.
- 소스 코드 주석에는 식별자를 채번하지 않습니다.

## 결과 (Consequences)

코드에서 요구사항까지 추적 경로가 성립합니다. 커밋의 트레일러가 Story 를 가리키고, Story 가 서술서와 흐름을 가리키므로, 임의의 커밋에서 해당 변경이 어느 목표를 위한 것인지 역추적할 수 있습니다.

인수 조건이 테스트로 충족되었는지를 기계가 판정합니다. Story 파일의 `AC` 번호가 테스트 이름에 포함되는지 대조하며, 문장 자체를 대조하지 않으므로 문서 문체를 수정해도 판정이 유지됩니다.

감수하는 것이 여덟입니다.

- 중복 검사를 작업자가 수행합니다. 도구가 검색을 제공하나 같은 요구사항이 두 Story 로 존재하는 것을 판정하지는 않습니다.
- Story 를 다른 Epic 으로 옮기면 ID 가 바뀌고 그 Story 를 가리키던 추적 키가 무효가 됩니다. 소속을 ID 로 읽기 위해 감수한 것이며, 평평한 채번과 `parent_task_id` 조합으로도 계층은 성립합니다.
- 유스케이스 전체 목록과 액터 정의가 한곳에 없습니다. 유스케이스 모델을 두지 않으므로 서술서 디렉터리를 직접 확인해야 전체를 파악할 수 있습니다.
- 흐름에 속하지 않는 요구사항을 받을 위치가 좁습니다. 보충 명세를 두지 않으므로 비기능 요구사항은 참조 아키텍처가 받고, 그곳에도 위치가 없는 것은 기록되지 않습니다.
