# 결정-0011: 메일을 Gmail SMTP 로 보내고 발송 책임을 포트 뒤에 둔다

- 상태: 승인됨
- 날짜: 2026-08-30

## 맥락 (Context)

기존 시스템의 사용자 알림 경로는 웹 푸시 단일 경로였으며, 이는 이미 기기를 등록한 사용자에게만 유효했다. 회원가입([USR-001](<../../spec/user/USR-001(계정 회원가입).md>)) 및 비밀번호 재설정([USR-005](<../../spec/user/USR-005(비밀번호 재설정).md>))에서 이메일 소유권 검증 요구사항이 추가됨에 따라 미등록 사용자에게 전달 가능한 이메일 발송 수단이 필요해졌다.

**발송 인프라 선택**: 전문 이메일 전송 서비스(SendGrid, Amazon SES, Resend)와 Gmail SMTP를 비교 검토했다. 전송 서비스는 높은 발송 한도와 반송(Bounce) 추적을 제공하지만 도메인 인증(SPF, DKIM) 및 별도 계정 관리가 수반된다. 반면 Gmail SMTP는 Google 앱 비밀번호를 통해 일 500통 한도로 즉시 연동 가능하다. 현재 가입 및 비밀번호 재설정 트래픽 규모에서 일 500통은 충분한 용량이다.

**발송 방식**: 동기 발송과 비동기 큐잉 방식을 검토했다. 인메모리 큐 기반 비동기 발송은 HTTP 응답 속도를 개선하지만 프로세스 재시작 시 유실 위험이 있고, 발송 실패 시 사용자에게 즉각 피드백을 제공할 수 없다. 가입과 재설정 과정에서 사용자는 인증 코드를 즉시 대기하므로 동기 발송으로 실패를 즉각 반환하는 것이 적합하다.

## 결정 (Decision)

**발송 인프라**

- Gmail SMTP(`smtp.gmail.com:587`, STARTTLS)를 채택한다. 인증은 2단계 인증 기반 앱 비밀번호(App Password)를 사용한다.
- SMTP 접속 계정과 앱 비밀번호는 애플리케이션 환경 변수로 주입하며 누락 시 부트스트랩 단계에서 기동이 실패한다.
- 발신자 주소(`From`)와 표시 이름을 설정 파일에서 관리한다.

**계층 구조 및 추상화**

- 발송 기능을 애플리케이션 아웃바운드 포트(`MailSender`)로 추상화하고 인프라 계층이 JavaMail 기반으로 구현한다. `PushSender`와 동일한 패턴이며 비즈니스 로직은 전송 기술에 결합되지 않는다.
- 포트 인터페이스는 수신자 주소, 제목, 본문을 인자로 받아 전송 결과를 반환한다.
- 별도 템플릿 엔진을 도입하지 않고 Java 텍스트 블록 기반 문자열 포맷팅으로 본문을 구성한다.

**실행 및 오류 처리**

- 이메일 발송은 동기식으로 실행하며 발송 완료 후 HTTP 응답을 반환한다.
- 발송 실패 시 해당 요청을 에러로 응답하여 사용자에게 즉시 알리며, 인증 코드가 저장된 채 메일만 유실되는 상태를 방지한다.
- 시스템 레벨의 자동 재시도는 적용하지 않으며 사용자의 인증 코드 재요청 인터랙션에 위임한다.

## 결과 (Consequences)

이메일 발송이 아웃바운드 포트로 추상화되어 향후 전송 인프라 변경 시 비즈니스 로직 수정이 불필요하다.

감수하는 제약 사항은 다음과 같다.

- 실제 SMTP 전송 경로는 통합/종단 테스트에서 가짜(Mock/Fake)로 대체되므로 실제 SMTP 인증 및 네트워크 결함은 실환경 발송 시점에 검증된다.
- SMTP 네트워크 왕복 지연이 HTTP 응답 시간에 포함된다.
- 일일 500통 발송 한도 제약이 존재한다.
- 앱 비밀번호는 발송 전용 권한으로 축소할 수 없어 유출 시 계정 보안 위험이 있다.
- 잘못된 주소 발송 시 비동기 반송 메일을 추적하지 못한다.

다음 상황 발생 시 본 결정을 재검토한다.

- 일일 발송량이 500통 한도에 근접할 때: 전문 이메일 전송 서비스(SES 등)로 전환.
- 이메일 유형이 3종 이상으로 증가할 때: 템플릿 엔진 도입 검토.
- 서버 인스턴스가 다중화될 때.
