# 결정-0014: 개발용 데이터베이스와 파일 보관소를 작업자별 로컬 컨테이너로 구동한다

- 상태: 승인됨
- 날짜: 2026-09-03

## 맥락 (Context)

작업자가 늘어나면서 개발 데이터를 작업자별로 격리해야 한다. 피처 브랜치에서 PR을 여는 모델이므로 브랜치 전환이 잦고, 브랜치마다 마이그레이션 구성이 다르다. 공유 데이터베이스를 사용하면 전환할 때마다 Flyway 체크섬이 어긋나 애플리케이션이 기동하지 않는다.

**Docker 실행 환경은 이미 저장소의 전제 조건이다.** 통합 테스트가 Testcontainers로 PostgreSQL 컨테이너를 구동하며, Docker가 실행되지 않으면 서버 테스트 160여 건이 실패한다. 개발용 컨테이너를 추가해도 새로운 사전 요건이 발생하지 않는다.

**데이터베이스와 오브젝트 스토리지는 같은 위치에 배치한다.** 첨부 파일은 데이터베이스의 메타데이터와 스토리지의 바이너리가 함께 존재해야 조회할 수 있다. 한쪽만 로컬로 구성하면 파일 조회 시점에 404가 발생한다.

**홈서버 공유 방안**은 공용 PostgreSQL에 작업자별 데이터베이스와 계정을 분리하고 MinIO 버킷을 나누는 구성이다. 작업자가 추가될 때마다 데이터베이스, 전용 계정, Nginx IP 화이트리스트를 함께 늘려야 한다. 신규 작업자는 공인 IP가 등록되기 전까지 파일 첨부 기능을 사용할 수 없으므로 합류 시점에 대기가 발생한다. 홈서버 장애나 정전은 전체 작업자의 개발을 동시에 중단시킨다.

**운영 Cloudflare R2에 개발 버킷을 생성하는 방안**은 운영 계정 오염과 추가 과금 위험이 있어 배제한다.

## 결정 (Decision)

**인프라 배치**

- 개발용 PostgreSQL과 MinIO를 `compose.yaml`로 정의하고 작업자의 로컬 머신에서 구동한다.
- `spring-boot-docker-compose` 의존성이 애플리케이션 기동 시 컨테이너를 함께 실행한다.
- 데이터베이스와 버킷은 작업자마다 독립적이다. 다른 작업자의 개발 데이터를 참조하지 않는다.
- PostgreSQL 메이저 버전은 운영 인스턴스와 일치시킨다.
- 오브젝트 스토리지는 개발 환경에서 MinIO를, 운영 환경에서 Cloudflare R2를 사용한다. 애플리케이션은 S3 호환 인터페이스로 두 구현체를 동일하게 다룬다.

**데이터 재생성**

- 데이터베이스를 삭제하고 재생성하는 명령을 제공한다. 브랜치 전환으로 Flyway 체크섬이 어긋나면 재생성으로 복구한다.
- 개발 데이터 시드 스크립트를 제공한다. 재생성 후 테스트 계정과 프로젝트를 복원한다.

**접근 제어**

- 개발용 컨테이너는 로컬 루프백에만 바인딩한다. 외부 노출 경로와 IP 화이트리스트를 두지 않는다.
- 접속 정보는 `server/.env`에서 단일 관리한다.

**테스트 환경**

- 통합 테스트는 Testcontainers의 일회용 컨테이너를 사용하며 개발용 컨테이너와 분리한다.

## 결과 (Consequences)

작업자 추가 시 저장소 체크아웃과 Docker 실행만으로 개발 환경이 구성된다. 서버 측 계정 발급과 IP 등록 절차가 없으므로 합류 당일에 개발을 시작할 수 있다.

브랜치별 마이그레이션 차이가 다른 작업자에게 전파되지 않는다. 체크섬 충돌은 자기 데이터베이스를 재생성하여 즉시 해결한다.

네트워크 왕복이 사라져 쿼리와 파일 업로드 지연이 감소한다. 홈서버 장애가 개발을 중단시키지 않는다.

감수하는 제약 사항은 다음과 같다.

- 개발 데이터가 로컬 Docker 볼륨에 있으므로 작업 머신을 변경하면 시드 스크립트로 다시 생성해야 한다.
- 컨테이너 2개가 개발 머신의 메모리와 디스크를 점유한다.
- 개발 스토리지(MinIO)와 운영 스토리지(R2)의 구현체 차이가 남는다.
- Docker가 실행되지 않으면 애플리케이션과 통합 테스트가 모두 기동하지 않는다.

다음 상황 발생 시 본 결정을 재검토한다.

- 여러 작업자가 동일한 개발 데이터를 참조해야 하는 요구가 발생할 때.
- 개발 머신의 자원 부족으로 컨테이너 구동이 어려워질 때.
