# 결정-0001: 제품을 이루는 축들을 한 저장소에 둔다

- 상태: 승인됨
- 날짜: 2026-08-17

## 맥락 (Context)

이 시스템은 프론트엔드 화면과 백엔드 API를 모두 필요로 한다. 두 축은 프로그래밍 언어, 빌드 도구, 배포 산출물이 중복되지 않는다. 프론트엔드는 TypeScript와 npm으로 정적 애셋 번들을 빌드하고, 백엔드는 Java와 Gradle로 실행 가능한 JAR 아카이브를 빌드한다. 배포 대상 인프라와 배포 시점도 상이하다.

이후 세 번째 축인 CLI 에이전트 도구가 추가되었다([AGT-001](<../../spec/agent/AGT-001(에이전트로 작업 다루기).md>)). 사용자의 로컬 환경에서 실행되는 CLI 도구이므로 배포 대상 인프라가 중앙 서버가 아니다. 다른 두 축과 언어, 산출물, 배포 대상이 상이하지만 백엔드 API를 소비한다는 점에서 프론트엔드와 동일한 클라이언트 계층에 위치한다.

**저장소를 축별로 분리하는 방안**에서는 각 축이 독립된 버전과 릴리스 주기를 갖고, 접근 권한과 CI 파이프라인도 독립 운영된다. 축별 전담 조직이 나뉜 환경에서는 이러한 멀티레포 구조가 적합하다.

그러나 본 프로젝트는 1인 개발 환경이다. 독립 릴리스, 권한 분리, 작업 격리와 같은 멀티레포의 이점은 다수 작업자가 서로 다른 축을 병렬 개발할 때 발생하는 충돌을 방지하기 위한 것이며, 현재 개발 환경에서는 해당 문제가 발생하지 않는다.

반면 저장소를 분리하면 즉시 발생하는 관리 비용이 크다. 축 간의 유일한 연결점은 OpenAPI 명세에서 생성하는 TypeScript 타입인데, 저장소가 분리되면 API 변경 작업 1건이 다수의 저장소 PR로 분할된다. 백엔드 명세를 먼저 반영하고 클라이언트 타입을 사후 갱신하는 순서를 수동 관리해야 하며, 그사이의 타입 불일치는 각 저장소 CI에서 검출되지 않는다. 단일 저장소(Monorepo) 구조에서는 동일한 API 변경이 단일 커밋의 diff에 반영되어 원자적 정합성 검증이 가능하다.

또한 본 저장소는 프로젝트 참조 아키텍처 축적을 목적으로 한다. 상당수 설계 규칙이 여러 축에 걸치거나 상호 참조되므로, 저장소가 분리되면 공통 문서의 관리 위치가 분산된다.

## 결정 (Decision)

단일 저장소에 `server/`와 `clients/`를 나란히 배치하고, 공통 아키텍처 문서와 백로그는 루트에 배치한다. `clients/`는 npm 워크스페이스 구조를 채택하여 `apps/`에 개별 애플리케이션 축을 배치하고 `packages/`에 공용 라이브러리를 배치한다. 빌드와 검증은 축마다 독립 도구가 수행하며 저장소 전체를 묶는 통합 빌드 스크립트는 두지 않는다. 워크스페이스가 통합하는 범위는 패키지 의존성과 잠금 파일(`package-lock.json`)로 한정한다.

**독립 축의 판정 기준은 배포 산출물이다.** 독자적인 빌드 명령과 검증 명령을 갖고 독립 배포되는 단위를 축으로 정의한다. 이를 충족하지 못하는 모듈은 독립 축이 아닌 특정 축의 내부 패키지로 구성한다.

## 결과 (Consequences)

API 계약을 변경하는 작업이 단일 커밋에 원자적으로 반영된다. OpenAPI 명세와 이를 소비하는 프론트엔드 및 CLI 코드가 동일 diff에 포함되므로 불일치 상태로 병합되는 오류가 원천 차단된다. 특히 클라이언트 소비자가 둘로 확장된 이후 이 이점은 더욱 커졌다. 참조 아키텍처 문서 역시 단일 저장소에서 축 간 설계를 통합 기술하고 상호 비교할 수 있다.

감수하는 제약 사항은 다음과 같다.

- 축마다 독립된 릴리스 주기와 버전 태그를 분리 관리하지 못한다. 배포는 산출물 단위로 개별 수행되지만 형상 이력은 단일 커밋 트리를 공유한다.
- 특정 축만 수정하더라도 저장소 전체 코드를 체크아웃해야 하므로 초기 클론 크기와 CI 캐시 용량이 증가한다.
- **아키텍처 이식 단위가 축 단위가 아닌 저장소 단위로 묶인다.** 프론트엔드 규칙만 타 프로젝트로 분리 이식할 때 루트 트리의 공통 문서를 선별 분리해야 한다.

다음 조건이 충족될 때 본 결정을 재검토한다.

- 개발 조직이 다수로 확장되어 축별 전담 작업이 분리될 때.
- CLI 도구를 범용 외부 패키지로 npm 등에 독립 배포해야 할 때.
- 특정 축을 타 프로젝트에서 독립 패키지로 재사용하려는 요구가 실재할 때.

저장소를 분리하는 비용은 커밋 이력을 분할하는 작업이 수반되므로 초기 분리 비용보다 증가하지만 1회성 마이그레이션으로 완료 가능하다.
