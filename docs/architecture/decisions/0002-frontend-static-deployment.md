# 결정-0002: 프론트엔드를 정적 산출물로 배포하고 실행 프로세스를 두지 않는다

- 상태: 승인됨
- 날짜: 2026-08-27
- 관련 문서: [7. 배포 뷰](../07-deployment-view.md), [2. 제약 조건](../02-architecture-constraints.md), [5. 빌딩 블록 뷰](../05-building-block-view.md)

## 맥락

프로젝트는 Angular 의 하이브리드 렌더링 설정(`outputMode: "server"`)으로 시작했습니다. 이 설정은 빌드 산출물에 Node 서버 번들을 포함하며, 배포 환경은 그 번들을 실행하는 컨테이너 하나를 상시 구동해야 합니다.

그러나 라우트별 렌더링 지정을 세어 보면 서버 렌더링(`RenderMode.Server`)으로 지정된 경로가 하나도 없습니다.

```typescript
export const serverRoutes: ServerRoute[] = [
  { path: '', renderMode: RenderMode.Prerender },
  { path: '**', renderMode: RenderMode.Client },
];
```

진입 경로는 빌드 시점에 프리렌더되고 나머지는 브라우저에서 렌더링됩니다. 요청 시점에 서버가 HTML 을 만드는 경로는 없으며, 구동 중인 Node 프로세스는 정적 파일을 전달하는 일만 수행합니다.

이 구조는 애플리케이션이 인증 후 개인 데이터를 다루는 화면으로만 구성된 데서 비롯합니다. 검색 엔진에 노출할 공개 문서가 없고 로그인 전 화면은 로그인과 가입 둘뿐이므로, 서버 렌더링이 제공하는 초기 HTML 의 이점이 성립할 지점이 없습니다.

## 검토한 대안

### 대안 1: 하이브리드 렌더링 설정 유지

| 구분 | 내용 |
| :--- | :--- |
| **장점** | 서버 렌더링이 필요한 경로가 생겼을 때 빌드 설정과 배포 구성을 바꾸지 않고 라우트 지정만 변경하면 됩니다 |
| **단점** | 렌더링을 수행하지 않는 프로세스 하나를 상시 구동하고 감시해야 합니다. 컨테이너 이미지, 포트 할당, 환경 변수(`NG_ALLOWED_HOSTS`)가 함께 따라오며, 이 환경 변수가 누락되면 SSRF 방어 정책이 모든 요청을 HTTP 400 으로 종료시킵니다 |
| **기각 사유** | 서버 렌더링 경로가 0 개인 상태에서 서버를 유지하는 구성입니다. 운영 대상이 하나 늘고 그 대가로 얻는 동작이 없습니다 |

### 대안 2: 정적 산출물 배포와 프리렌더 유지 (채택)

| 구분 | 내용 |
| :--- | :--- |
| **장점** | 실행 프로세스가 없습니다. 배포는 릴리스 디렉터리를 올리고 심볼릭 링크를 교체하는 것으로, 롤백은 링크를 되돌리는 것으로 완료됩니다 |
| **단점** | 정적 진입점이 둘입니다. 프리렌더된 `index.html` 과 CSR 셸 `index.csr.html` 을 웹 서버가 구분해야 합니다 |

### 대안 3: 정적 산출물 배포와 순수 클라이언트 렌더링

| 구분 | 내용 |
| :--- | :--- |
| **장점** | 정적 진입점이 하나로 줄어 웹 서버 설정이 단순해집니다. 프리렌더 단계가 사라져 빌드에서 서버 엔트리가 불필요해집니다 |
| **단점** | 진입 경로 `/` 의 처리가 늦어집니다 |
| **기각 사유** | 아래 서술 |

대안 3 은 대안 2 의 유일한 단점을 제거합니다. 현재 프리렌더가 생성하는 산출물은 252 바이트의 리다이렉트 문서 하나뿐이고, 그 하나 때문에 웹 서버가 진입점 둘을 구분해야 하기 때문입니다.

그러나 두 방식은 `/` 진입 시 브라우저가 수행하는 작업이 다릅니다. 대안 3 에서 브라우저는 63 KB 의 셸과 195 KB(전송 기준)의 초기 번들을 내려받아 애플리케이션을 부팅한 뒤에야 라우터가 `/tasks/all` 로 이동합니다. 대안 2 에서는 252 바이트 문서를 받고 즉시 다음 URL 을 요청합니다. 웹 서버 설정 한 줄과 번들 부팅 한 회의 교환이며, 후자의 비용이 더 큽니다.

## 결정

`outputMode` 를 `static` 으로 지정하고 프리렌더를 유지합니다. 빌드 산출물 `dist/web/browser` 를 nginx 가 직접 제공하며, 프론트엔드는 실행 프로세스를 갖지 않습니다.

## 결과

- 프론트엔드의 운영 대상이 파일 집합으로 축소됩니다. 실행 프로세스, 컨테이너 이미지, 포트, 환경 변수가 모두 사라집니다.
- 배포와 롤백이 심볼릭 링크 교체로 통일되며 웹 서버 재시작을 수반하지 않습니다.
- 감수하는 것
  - 서버 렌더링이 필요해지면 빌드 설정을 되돌리고 실행 환경을 다시 구성해야 합니다.
  - 웹 서버가 정적 진입점 둘을 구분해야 합니다. 프리렌더된 `index.html` 은 애플리케이션 셸이 아니라 `<meta http-equiv="refresh">` 리다이렉트 문서이므로, 통상적인 `try_files $uri /index.html` 규칙을 적용하면 모든 경로가 이 문서를 받아 리다이렉트가 반복됩니다. 대체 경로는 `index.csr.html` 이어야 합니다.
- 순수 클라이언트 렌더링(대안 3)은 기각했습니다. 진입 경로의 부팅 비용이 웹 서버 설정의 단순함보다 큽니다.

## 재검토 조건

- 검색 엔진 노출이나 소셜 미리보기가 필요한 공개 경로가 생길 때. 서버 렌더링 또는 해당 경로의 프리렌더 확장을 다시 판단합니다.
- 로그인 전 화면이 늘어 초기 번들의 부팅 시간이 사용자 경험을 좌우하게 될 때.

## 개정

**2026-08-27** — 느린 회선에서 진입 경로를 확인한 결과, 프리렌더 스텁은 다음 문서가 도착할 때까지 화면에 그려진 채 남습니다. "결정" 절이 인용한 "252 바이트를 받고 즉시 다음 URL 을 요청한다"는 서술은 요청 시점만 가리키며, 그 사이 사용자가 `Redirecting to ...` 문서를 보게 된다는 사실을 빠뜨렸습니다.

결정은 유지합니다. 진입 라우트가 장차 랜딩 페이지를 갖게 되면 같은 자리에서 프리렌더가 실제 HTML 을 굽게 되므로, 그때 되돌릴 구조를 지금 해체하지 않습니다. 대신 빌드 후처리(`web/tools/decorate-prerender-stub.mjs`)로 스텁에 셸과 같은 배경과 부팅 표시를 입혀 두 문서가 같은 화면으로 이어지게 했습니다. 진입 라우트가 실제 페이지를 갖게 되면 스텁이 생기지 않으므로 이 후처리는 자동으로 손을 뗍니다.
