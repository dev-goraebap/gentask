# 11. 위험과 기술 부채 (Risks and Technical Debt)

식별된 기술 위험과 기술 부채를 우선순위 순으로 기록합니다. 위험(Risk)은 아직 손실이 발생하지 않았으나 조건이 충족되면 발생하는 잠재적 요인이며, 기술 부채(Technical Debt)는 이미 규격과 어긋난 채 유지되고 있는 요소를 의미합니다.

각 항목은 측정한 현상, 예상되는 영향 및 손실, 착수 판정 기준을 함께 명시합니다. 해소된 항목은 목록에서 제거하며, 수치는 측정 시점을 함께 기록하여 재측정 전까지의 기준값으로 관리합니다.

## 11.1 위험 (Risks)

### 커밋 이력에 남은 배포 접속 정보

Git 추적 대상 파일에는 배포 대상 호스트 정보가 존재하지 않습니다(0건). 다만 과거 커밋 이력 3건에 해당 정보가 잔존해 있습니다. 현재 설정값은 추적 대상에서 제외된 `.deploy.env`에서 관리합니다.

저장소를 공개로 전환하면 이력에서 호스트를 복원할 수 있습니다. 계정과 키가 함께 노출된 것은 아니므로 즉시 침해로 이어지지 않으나, 대상이 특정되는 것만으로 공격 표면이 됩니다.

**착수 기준**: 저장소를 공개로 전환하기 전. 이력 재작성은 기존 커밋 해시를 전부 바꾸므로, 저장소를 참조하는 사본이 늘어나기 전이 비용이 가장 낮은 시점입니다.

### 실패 임계에 접근한 초기 번들

`ng build` 측정값입니다 (2026-08-28).

- 초기 번들 합계 899.85 kB — 전송 추정 195.03 kB
- 경고 임계 500 kB — 399.85 kB 초과
- 실패 임계 1 MB — 여유 100.15 kB

번들 구성은 벤더 청크 408.52 kB, `main` 294.72 kB, 전역 스타일시트 195.42 kB, 나머지 1.18 kB 입니다.

실패 임계를 넘으면 프로덕션 빌드가 실패하므로 그 시점부터 배포 경로가 막힌 채로 작업하게 됩니다. 전송 추정치 195.03 kB 는 압축 후 값이라 현재 체감 성능 문제로 드러나지 않으며, 이것이 경고를 400 kB 초과한 상태로 유지해 온 근거입니다.

파일 업로더가 ESM이 아닌 의존성 6건을 경유하여 최적화 우회(Optimization Bailout) 경고를 발생시킵니다. 초기 번들 축소 착수 시 이 경고가 첫 번째 확인 대상입니다.

**착수 기준**: 초기 번들에 새 의존성을 추가하는 변경. 그 시점에 남은 여유를 다시 측정합니다.

## 11.2 기술 부채 (Technical Debt)

### 실행 주체가 없는 검증

배포 시점은 [결정-0002](./decisions/0002-shared-contributing.md)의 스크립트가 판정합니다. 커밋과 병합 시점은 판정하는 주체를 갖지 않습니다. CI 워크플로와 커밋 훅이 모두 부재하므로, 검증을 통과하지 못하는 `main` 이 배포를 시도하기 전까지 저장소에 남을 수 있습니다.

두 문서가 현재 구축되지 않은 CI를 강제 수단으로 지목하고 있습니다.

- [프론트엔드 02. 코드 스타일 가이드](./concepts/frontend-02-code-style.md) `FE-STY-076` — 생성 타입 파일의 수동 편집을 "CI 의 재생성 검사"가 막는다고 기술
- [프론트엔드 01. 개발 환경](./concepts/frontend-01-dev-environment.md) — 린터가 막지 못하는 영역을 "CI 의 재생성 일치 검증"으로 대체한다고 기술

강제된다고 기술된 규칙이 실제로는 강제되지 않는 상태입니다. 표기가 없으면 확인하게 되지만 틀린 표기는 확인하지 않게 만듭니다.

**착수 기준**: 저장소에 두 번째 작업자가 참여하는 시점. 단독 작업 동안은 깨진 `main` 을 가져가는 상대가 없어 배포 직전 판정으로 충분합니다.

### 강제 수단이 표기되지 않은 규칙

[1. 서론과 목표](./01-introduction-and-goals.md)의 문서화 원칙은 각 규칙이 기계적 강제 수단의 유무를 명시하도록 규정합니다. 코드 스타일 규칙 270건(`FE-STY` 175 · `BE-STY` 95) 가운데 도구 이름을 명시한 규칙은 15건입니다.

나머지 255건은 문서만 읽어서는 도구가 판정하는 규칙인지 사람이 판정하는 규칙인지 알 수 없습니다. 실제로는 도구가 잡는 규칙도 여기 섞여 있으므로 255건 전부가 검토 의존이라는 뜻은 아니며, 그 구분이 문서에 없다는 것이 부채입니다.

**착수 기준**: 규칙을 수정할 때 그 규칙에 강제 수단 표기를 함께 붙입니다. 일괄 조사는 수행하지 않습니다. 도구 설정이 바뀌면 표기도 함께 낡으므로, 규칙을 건드리지 않는 동안 붙여 둔 표기는 검증되지 않은 채 축적됩니다.

### 두 벌로 나뉜 자격 증명 저장 구조

세션 토큰과 API 토큰은 형태와 해시 방식과 조회 방식이 동일합니다. 둘 다 불투명 난수이고, 둘 다 HMAC-SHA256 해시로만 저장되며, 조회도 토큰 해시로 수행합니다. 다른 것은 수명 컬럼 세 개(`expires_at` · `last_used_at`, 그리고 슬라이딩 갱신 로직)뿐입니다.

그런데도 테이블 둘, 도메인 타입 둘, 저장소 인터페이스 둘, 인터셉터 분기 둘을 갖습니다. 인증 저장 구조를 바꾸는 변경은 매번 두 곳에서 같은 수정을 반복합니다.

원인은 [결정-0005](./decisions/0005-shared-authentication.md)의 맥락에 있습니다. 쿠키 세션이 먼저 있었고 `ST-017` 이 두 번째 경로를 요구했으므로, 두 번째 수단이 첫 번째와 별개의 구조로 추가되었습니다.

**착수 기준**: 인증 저장 구조를 다른 사유로 변경할 때. 단독으로 착수하지 않습니다. 통합하려면 배포된 스키마를 변경해야 하며, 운반 수단(쿠키와 헤더)은 클라이언트 환경이 다르므로 통합 대상이 아닙니다.

### 리다이렉트 스텁에 머문 프리렌더

프리렌더 대상은 루트 경로 하나이며 나머지 경로는 모두 클라이언트 렌더링입니다. 루트 경로의 산출물(`index.html`)은 목록 화면으로 보내는 252 바이트 메타 새로고침 스텁입니다.

정적 배포가 근거로 삼은 첫 페인트 단축과 검색 노출은 아직 실현되지 않았습니다. 느린 회선에서는 스텁이 그려진 뒤 번들을 내려받는 동안 빈 화면이 유지됩니다.

이 구간에 부트 화면을 넣으려면 색상 모드 제어를 `styles.css` 한 곳에 두는 규칙을 깨야 하므로, 프리렌더가 실제 화면을 생성하기 전까지는 넣지 않습니다.

**착수 기준**: 인증이 필요 없는 공개 화면이 생기는 시점. 그 화면을 `RenderMode.Prerender` 로 두고 [7. 배포 뷰](./07-deployment-view.md)의 nginx 폴백 대상을 함께 재검토합니다.
