# 9. 아키텍처 결정 (Architecture Decisions)

본 문서는 본 저장소의 아키텍처 결정을 시간순으로 나열한다. 세부 결정 본문은 각 ADR 파일에 기술하며, 본 문서에는 상태와 핵심 요약만을 기록한다.

의사결정 맥락 유실로 인한 반복적인 논의와 시행착오를 방지하기 위해, **결정 기록은 승인 후 불변으로 관리한다.** 결론이 변경되면 기존 문서를 임의로 수정하지 않고 신규 결정을 발행하여 이전 결정을 대체한다.

**초기 개발 단계에서는 예외를 허용한다.** 유지보수 Epic이 백로그에 등록되기 전까지는 기존 결정을 직접 개정한다. 대체 결정을 중복 발행하지 않고 본문을 수정하며, 결론이 변경되는 경우도 이에 포함한다.

유지보수 Epic 등록 이전에는 요구사항과 구현이 빈번하게 조정된다. 이때 사유가 소멸한 이전 결정을 유지한 채 대체 결정을 중첩하면 현재 유효 규격을 확인하기 위해 다수의 문서를 대조해야 하므로, 변경 이력의 누적보다 **현재 시스템 규격의 명확성과 정합성**을 우선한다.

개정 과정에서 이전 결정의 변천 이력은 **Git 버전 관리 이력**을 통해 추적한다. 결정 문서의 커밋 메시지가 변경 맥락을 기록하므로 정보 유실이 발생하지 않는다.

유지보수 Epic이 백로그에 등록되면 이 예외를 종료하고 아래의 정규 대체 절차를 적용한다.

## 파일명

`NNNN-<축>-<요약슬러그>.md` 형식이다.

| 항목 | 규격 |
| :--- | :--- |
| **`NNNN`** | 4자리 일련번호. **축과 무관하게 단일 수열**을 사용한다. 저장소 전체의 결정 승인 순서이다. |
| **`<축>`** | `shared` · `frontend` · `backend` · `cli` 중 하나. 결정이 적용되는 주 대상 축을 나타낸다. |
| **`<요약슬러그>`** | 영문 케밥 케이스(kebab-case). 식별을 위한 축약 표현을 사용한다. |

시간순 정렬을 보장하기 위해 순번을 축 접두어보다 앞에 배치한다. 축별 필터링은 파일명의 축 식별자를 참조한다.

여러 축에 걸쳐 적용되는 결정은 `shared`로 분류한다. 한 축에서 시작되었더라도 다른 축의 규칙 변경이 수반되면 `shared`로 발행한다.

## 작성 판별식

**아키텍처 구조, 비기능 요구사항, 의존성 방향, 인터페이스 계약, 핵심 구축 기법 중 하나에 영향을 주는가.** 하나라도 해당하면 결정 기록으로 작성하고, 해당하지 않는 세부 규칙은 참조 문서 본문에 기술한다. 일반적인 프레임워크 관례나 취향에 따른 선택은 작성 대상에서 제외한다.

형식은 [Michael Nygard의 ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions.html) 양식을 준용한다. **기각된 대안은 별도 절을 두지 않고 맥락(Context) 절 내에 함께 기술한다.** 각 대안의 트레이드오프와 기각 사유를 단일 맥락에서 기술함으로써 형식 채우기식 서술을 방지하기 위함이다.

템플릿은 [0000-template.md](./decisions/0000-template.md)이다.

## 대체 절차

유지보수 Epic 등록 이후 적용한다. 그 전에는 본문을 직접 개정한다.

단일 커밋으로 원자적으로 처리한다.

1. **신규 결정 작성**: 대체 사유와 배경을 맥락 절에 기술한다.
2. **목차 갱신**: 아래 표에서 기존 결정의 상태를 `대체됨 (→ NNNN)`으로 변경한다.
3. **참조 갱신**: 참조 문서 내 링크를 신규 결정으로 전환한다.

## 발행 예정

아래는 판별식을 통과하지만 아직 작성되지 않은 결정이다. 해당 참조 문서를 이식하거나 규칙을 처음 적용할 때 함께 발행한다.

**공통**

- **프론트엔드 정적 배포** — 작성되어 있으나 번호 재부여를 대기 중이다. 본문은 `tmp/0003-frontend-static-deployment.md`에 위치한다.

**프론트엔드**

- **모듈 분할 방법론** — FSD를 채택한 근거. 대안은 기능별 폴더, 계층별 폴더, Nx 라이브러리 경계.
- **UI 킷 조달** — Spartan의 brain + helm 조합 채택. 대안은 완제품 UI 킷 채택 또는 자체 구현.
- **적응형 판정 축** — 뷰포트 폭 기반 컴포넌트 분기 선택. 대안은 포인터 정밀도, 사용자 명시적 설정.
- **서버 상태 조회 수단** — `httpResource`를 조회의 단일 수단으로 설정한 근거. 대안은 라우트 리졸버, 외부 상태 관리 라이브러리.
- **데이터 로딩 모델** — 화면 진입 후 비동기 조회 및 베일(Veil) 표시 모델. 대안은 리졸버 사전 로딩.
- **폼 구현 수단** — 시그널 기반 폼과 유효성 검증 배치. 대안은 리액티브 폼 유지.
- **데이터 신선도 정책** — 화면 진입 및 변경 후 조회 기준. 캐시 및 무효화 정책 도입 시 속도와 정합성의 트레이드오프가 발생한다.
- **URL 기반 필터 및 정렬 동기화** — URL을 필터와 정렬의 원본으로 설정하여 상태 복원 보장. 대안은 컴포넌트 로컬 상태 보관.

**백엔드**

- **조회와 명령의 서비스 클래스 분리** — 단일 서비스 내 저장소와 조회 포트 참조 허용. 대안은 명령 서비스와 조회 서비스의 엄격한 분리 및 도구 강제.
- **저장소와 조회 포트의 경계** — 반환 타입을 기준으로 한 분리 기준. 대안은 메서드 의도 기반 분류.
- **에러 코드의 표현 체계** — 모듈별 열거형과 인터페이스 default 메서드 활용. 대안은 예외 클래스 세분화 또는 `MessageSource` 외부화.
- **도메인 모델과 영속 모델의 분리** — 순수 도메인 객체와 jOOQ 레코드의 분리 및 매핑.
- **정적 분석 도구 조합** — Checkstyle, SpotBugs 등 정적 분석 도구의 역할 분담 및 빌드 실패 임계치 설정.
- **값 객체의 영속화 재구성 경로** — 데이터베이스 조회 시 유효성 재검증 생략 정책.
- **생성 코드 비커밋 정책** — jOOQ 및 OpenAPI 생성 코드를 버전 관리에서 제외하고 빌드 시점에 생성.
- **마이그레이션 단일 원본 및 down 스크립트 배제** — Flyway 기반 단방향 전진 마이그레이션 적용.
