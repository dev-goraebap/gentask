# 프론트엔드 05. 디자인 시스템

UI 킷이 2단계 계층 구조로 분리되어 동작하는 메커니즘, 디자인 토큰의 원본 위치와 계약, 그리고 색상 모드가 전환되는 경로를 서술한다. 컴포넌트의 물리적 배치 규격은 빌딩 블록 뷰가 정의하며, 검증 가능한 세부 코딩 규칙은 코드 스타일 가이드가 다룬다.

## 1. UI 킷 계층 구조와 소스 코드 배치

| 계층 | 위치 | 소유 | 담당 |
| :--- | :--- | :--- | :--- |
| **brain** | `@spartan-ng/brain` (npm) | 외부 | 접근성, 포커스 관리, 키보드 조작, ARIA, 오버레이 |
| **helm** | `shared/ui/` (소스) | 프로젝트 | 마크업, 클래스, 시각적 표현 |
| **기반** | `@angular/cdk` (npm) | 외부 | brain이 사용하는 프리미티브 |

brain과 CDK는 대체 관계가 아니라 **brain이 CDK를 기반으로 구축된 계층**이다.

helm 컴포넌트는 npm 패키지가 아닌 CLI 명령을 통해 소스 코드를 프로젝트 내부로 복사하여 관리한다. 초기화 명령이 의존성을 설치하고 전역 스타일에 Tailwind 계층, Spartan 프리셋 임포트, 테마 변수를 기록한다. `angular.json`은 수정하지 않으므로 스타일 진입점 경로를 변경한 경우 생성기 실행 시 해당 경로를 명시해야 한다.

마크업과 클래스 스타일 유형(`style`)은 컴포넌트 추가 전에 사전 확정한다. 색상 팔레트와 독립된 축이며, 사후 변경 시 이미 복사된 컴포넌트 사본을 재생성해야 하므로 기존 커스텀 수정 사항이 덮어쓰여 소실되기 때문이다.

### 컴포넌트 디렉터리 구조와 공개 API 매핑

생성기는 컴포넌트마다 중첩된 디렉터리 구조를 생성하고 `tsconfig`가 진입점을 컴포넌트별 경로로 매핑한다.

```ts
import { HlmButton } from '@/shared/ui/button';
import { HlmSheet } from '@/shared/ui/sheet';
```

세그먼트 배럴(Barrel) 파일을 두지 않는다. 배럴에서 즉시 참조 심볼과 지연 로딩 대상 심볼을 함께 노출하면 정적 참조가 확정되어 지연 청크가 분리되지 않기 때문이다. 배럴 파일을 제거함으로써 초기 번들 크기를 544 kB에서 275 kB로 감축했다.

이 구조는 FSD(Feature-Sliced Design) 린트 규칙과 충돌한다.

| 충돌 | 해소 방식 |
| :--- | :--- |
| 컴포넌트 폴더에 공개 API 파일이 없음 | 해당 경로만 규칙 검사에서 제외 |
| 폴더명이 세그먼트명과 중복됨 | 동일한 방식으로 규칙 검사에서 제외 |
| 컴포넌트별 경로를 내부 우회로 판정 | 규칙을 해제하고 ESLint 패턴 검사로 대체 |

디렉터리 구조를 수동으로 평탄화하면 컴포넌트 추가 및 재생성 시마다 반복 수정이 필요하므로 상기 두 가지 린트 규칙은 예외 처리한다. 반면 `@/shared/ui/button`은 `tsconfig`가 매핑하는 공개 API 경로이며 내부 우회 참조가 아니다. 정적 분석 도구가 경로 패턴만으로 이를 판정하지 못하므로 해당 린트 규칙은 전역 해제하고, 슬라이스 내부 파일 직접 임포트 차단은 ESLint 커스텀 경로 규칙으로 검증한다.

## 2. Helm 컴포넌트 수정 권한과 책임 격리

**helm 컴포넌트는 프로젝트 요구사항에 맞춰 자유롭게 수정한다.** 마크업 구조, 클래스, 입출력 API 모두 커스터마이징 대상이다.

수정 권한을 허용하는 이유는 적응형 UI 요구사항을 충족하기 위함이다. 동일한 논리 컴포넌트라도 뷰포트 너비에 따라 상이한 DOM 트리와 상호작용 모델을 지원해야 하므로 단순 스타일 토큰 교체만으로는 한계가 있기 때문이다.

업스트림 라이브러리의 시각적 스타일 개선은 자동으로 반영되지 않는다. API 수준 변경은 생성기의 점검 툴로 검출 가능하므로 시각적 개선 사항만 수동 선별 반영한다.

접근성과 동작 로직은 외부 brain 패키지가 관리하고 helm은 시각적 표현 계층에 집중하므로, helm 코드를 수정하더라도 포커스 트랩, 키보드 조작, ARIA 속성 바인딩의 정합성은 지속 유지된다. 소스 사본 분리로 인해 감수하는 비용은 시각 스타일 동기화일 뿐 웹 접근성 보장은 훼손되지 않는다.

반대로 Spartan brain 디렉티브 연결을 임의로 제거하면 웹 접근성 보장이 상실되며, 이는 화면상으로 즉시 드러나지 않으므로 주의해야 한다.

## 3. 디자인 토큰 원본 위치와 참조 체계

| 대상 | 원본 위치 |
| :--- | :--- |
| 토큰 이름의 집합 | 이 문서가 고정 |
| 각 이름에 담기는 값 | `src/app/styles.css` |

토큰 속성값을 본 문서에 중복 기술하지 않는다. 스타일시트(`styles.css`)를 단일 진실 공급원으로 유지하여 명세와 구현의 불일치를 방지한다.

전역 스타일시트는 Tailwind 계층과 함께 Spartan 프리셋을 임포트한다. 프리셋이 애니메이션 유틸리티와 CDK 오버레이 스타일을 함께 제공하므로, 임포트 누락 시 모달 다이얼로그와 팝오버의 레이아웃 배치가 깨진다.

### 시맨틱 토큰 명명 체계와 토큰 쌍 규격

| 짝을 이루는 토큰 | 용도 |
| :--- | :--- |
| `background` / `foreground` | 화면 기본 배경 및 전경 |
| `card` / `card-foreground` | 카드 표면 |
| `popover` / `popover-foreground` | 오버레이 표면 |
| `primary` / `primary-foreground` | 주 동작 |
| `secondary` / `secondary-foreground` | 보조 동작 |
| `muted` / `muted-foreground` | 약화된 영역 |
| `accent` / `accent-foreground` | 강조 영역 |
| `destructive` / `destructive-foreground` | 파괴적 동작 |

짝이 없는 단독 토큰은 `border`, `input`, `ring`이며, `--radius`와 사이드바 계열 토큰이 추가로 존재한다. 색상 팔레트를 신규 정의할 때는 상기 토큰 집합을 빠짐없이 선언해야 한다. 누락된 토큰은 해당 값을 참조하는 컴포넌트 렌더링 시점에 UI 결함으로 나타난다.

`-foreground` 전경색 쌍이 없는 배경 토큰을 생성하지 않는다. 배경 위에 배치할 텍스트 색상의 판단 기준이 모호해져 접근성 대비 결함을 유발하기 때문이다.

글꼴 패밀리는 기본/모노 두 가지 슬롯을 정의하며, 글자 크기와 두께에 대한 별도 토큰은 신설하지 않고 Tailwind CSS 표준 척도를 준용한다.

### 신규 토큰 확장과 테마 유틸리티 등록

새로운 토큰을 추가할 때는 CSS 변수 값 선언과 테마 유틸리티 등록을 함께 정의한다.

```css
:root {
  --warning: /* 라이트와 다크 값 */;
  --warning-foreground: /* 라이트와 다크 값 */;
}

@theme inline {
  --color-warning: var(--warning);
  --color-warning-foreground: var(--warning-foreground);
}
```

신규 토큰 추가 시 CSS 변수 선언과 `@theme inline` 등록을 동시에 수행한다. 등록이 누락되면 Tailwind 유틸리티 클래스가 생성되지 않는다. 신규 토큰은 라이트 모드와 다크 모드 값을 쌍으로 정의해야 하며, 한쪽만 선언하면 모드 전환 시 색상 대비가 깨진다.

## 4. 뷰포트 기반 치수 정책과 최소 터치 타겟

컨트롤의 물리적 치수는 뷰포트 너비에 따라 결정된다. helm의 기본 치수는 데스크톱 마우스 입력을 전제하므로 모바일 뷰포트에서는 터치 접근성 최소 기준에 미달한다.

치수 전환에는 런타임 분기가 불필요하다. `max-md:` 반응형 유틸리티 클래스를 통해 순수 CSS 미디어 쿼리로 처리하며, 프리렌더 환경에서도 깜빡임 없이 동일하게 동작한다. 뷰포트 판정 시그널은 컴포넌트 DOM 구조 자체를 교체할 때 한정하여 사용한다.

치수 전환 임계값은 적응형 레이아웃의 판정 축과 동일한 경계(`48rem`)를 사용한다. 두 영역에 서로 다른 임계값을 적용하면 컴포넌트가 교체되는 지점과 치수가 변경되는 지점이 어긋나기 때문이다.

크기 변형마다 값을 분산하지 않고 컴포넌트의 기본 베이스 클래스에 최소 터치 타겟 치수(44px)를 선언한다. 특정 크기 변형에만 적용하면 향후 추가되는 변형에서 기준이 누락되기 쉽다.

```ts
const TOUCH_TARGET = 'max-md:min-h-11 max-md:min-w-11';
```

데이터 테이블 행 내부 버튼처럼 시각적 크기를 키우기 어려운 고밀도 영역에서는 시각적 크기를 유지하되 히트 영역(Hit Target)만 확장한다. 기본 원칙은 시각적 크기를 함께 확대하는 것이며, 히트 영역 확장 예외를 기본값으로 남용하지 않는다.

### 입력 컨트롤 폰트 크기와 포인터 미디어 쿼리 판정

**사용자 텍스트 입력 컨트롤의 폰트 크기는 유일하게 포인터 미디어 쿼리로 판정한다.** 16px를 기본값으로 두고, 정밀 포인터(`pointer: fine`)가 명확히 감지될 때만 폰트 크기를 축소한다.

뷰포트 너비로 판정할 경우 가로 모드 태블릿 등에서 폰트 크기가 16px 미만으로 축소되어, iOS Safari 브라우저 진입 시 뷰포트가 강제 자동 확대되는 심각한 상호작용 결함이 발생하기 때문이다. 포인터 쿼리가 오판되어 정밀 포인터가 감지되지 않더라도 16px 기본값이 유지되므로 화면 자동 확대 문제를 안전하게 방지할 수 있다.

## 5. 색상 대비 하한 기준과 자동 검증

| 대상 | 기준 |
| :--- | :--- |
| 본문 · 보조 · 삼차 텍스트 | 4.5:1 |
| 큰 텍스트 | 3:1 |
| 폼 컨트롤 경계와 포커스 링 | 3:1 |
| 장식선 | 면제 |

대비 기준은 라이트 모드와 다크 모드 양쪽 모두에서 충족해야 한다.

경계선 유형에 따라 대비 적용 기준을 구분한다. `border`는 면과 면을 구분하는 장식선으로서 식별 불가 시에도 조작성을 저해하지 않으므로 대비 기준에서 제외된다. 여기에 3:1 기준을 강제하면 모든 면 사이에 짙은 회색 선이 그어져 미세 경계선으로 구조를 표현하는 설계가 불가능해진다. 반면 `input` 경계선은 입력 필드의 경계를 인지시키는 유일한 단서이므로 3:1 대비를 엄격히 적용한다.

색상 대비 기준은 수치 명시에 그치지 않고 빌드 시 단위 테스트로 자동 검증한다. 토큰 정의를 파싱하여 대비를 산출하는 단위 테스트를 두어, 팔레트를 교체하거나 오버라이드를 삭제하면 빌드 단계에서 즉시 실패하도록 강제한다.

Spartan 기본 테마의 일부 토큰(라이트 모드 `muted-foreground`, `input`, `ring`)은 접근성 기준에 미달하므로 프로젝트 전역 스타일에서 재정의하여 보정한다.

## 6. 색상 모드 전환 경로와 렌더링 동기화

색상 모드 판정의 기준은 CSS `color-scheme`이다. 시스템 설정을 기본으로 따르며, 사용자의 명시적 선택 시 문서 루트(`<html>`)에 클래스를 부여하여 덮어쓴다. 클래스를 주입하는 로직은 `app` 계층이 소유한다.

색상 모드는 첫 페인트(First Paint) 이전에 결정되어야 화면 깜빡임(FOUC)을 방지할 수 있다. 색상 토큰을 `light-dark()` 함수를 통해 선언하면 자바스크립트 실행 전에도 브라우저 CSS 엔진에 의해 시스템 설정이 즉시 반영된다.

### 프리셋 `dark` 변형 불일치와 커스텀 변형 선언

라이브러리 프리셋의 `dark:` 변형 선언을 그대로 사용하지 않는다. 프리셋은 클래스 기반으로만 동작하는 반면, 색상 토큰은 `color-scheme`과 `light-dark()` 메커니즘을 통해 전환된다. 사용자가 시스템 모드로 설정한 상태에서는 토큰이 OS 설정을 따라 다크로 전환되지만, `dark:` 유틸리티 클래스는 루트에 `.dark` 클래스가 없어 적용되지 않는 불일치가 발생한다.

이 불일치는 배경색만 다크로 바뀌고 일부 컨트롤은 라이트 모드 스타일을 유지하는 형태로 나타난다.

전역 스타일시트에서 프리셋 임포트 직후에 커스텀 변형을 다시 선언하여 두 경로를 모두 수용한다.

```css
@custom-variant dark {
  &:where(.dark, .dark *) { @slot; }

  @media (prefers-color-scheme: dark) {
    &:where(:not(.light):not(.light *)) { @slot; }
  }
}
```

`.light` 제외 조건이 누락되면 OS가 다크 모드인 상태에서 사용자가 라이트 모드를 선택하더라도 `dark:` 유틸리티가 계속 적용된다. 이 문제는 코드 리뷰에서 확인한다.

문서 루트에만 적용되는 선택자는 화면 내 부분 다크 모드를 지원하지 않는다. 하위 요소에 `.dark` 클래스를 부여하더라도 변수 재정의가 전파되지 않아 두 모드를 한 화면에 병렬로 배치할 수 없다.

## 7. 접근성 책임 분담과 구현 우선순위

접근성 보장은 단일 계층에 집중되지 않고 세 영역이 책임을 분담한다.

| 담당 | 범위 |
| :--- | :--- |
| brain · CDK | 포커스 트랩, 포커스 복귀, 키보드 조작, ARIA 속성 연결, 오버레이 접근성 |
| HTML 시맨틱 | 요소 역할, 기본 키보드 동작, 스크린리더 인식 |
| 구현부 | 시맨틱 요소 선택, 접근 가능한 이름, 색상 대비, 상태 전달 |

접근성 구현은 세 단계의 우선순위를 따른다.

1. **시맨틱 HTML로 해결한다.** 네이티브 `<button>`은 클릭, 엔터·스페이스 키보드 활성화, 포커스 수신 동작을 브라우저 수준에서 기본 제공한다.
2. 시맨틱 요소만으로 충족할 수 없는 복합 상호작용은 **Spartan brain 프리미티브를 사용한다.**
3. 두 수단으로 해결할 수 없는 경우에만 직접 구현한다.

복합 위젯(달력 그리드 등)의 방향키 탐색, 로빙 포커스, ARIA 바인딩은 brain 계층에서 캡슐화하여 처리하므로 호출부는 한국어 라벨링과 텍스트 바인딩에 집중한다.

접근성 책임이 하위 계층에 격리되어 있으므로 helm 컴포넌트의 마크업을 자유롭게 수정하더라도 접근성 보장이 유지된다.

## 8. 모달 및 오버레이 컴포넌트 분류와 명명 체계

모달 오버레이는 보조기술 인터랙션과 URL 라우팅 계약에 따라 세 가지로 분류한다.

| 컴포넌트 | ARIA 역할 | 주 용도 | URL 주소 | 좁은 화면 (Compact) |
| :--- | :--- | :--- | :--- | :--- |
| `AlertDialog` | `alertdialog` | 삭제 확인 등 되돌릴 수 없는 결정 확인 | 주소 없음 | 중앙 정렬 모달 패널 |
| `Dialog` | `dialog` | 데이터 생성 및 수정 등 완결된 작업 폼 | **URL 쿼리** | 전체 화면 채움 |
| `BottomSheet` | `dialog` | 단일 값 선택 (피커/셀렉트의 모바일 적응형) | 주소 없음 | 하단 슬라이드 시트 |

명칭은 WAI-ARIA 패턴 및 Spartan/shadcn UI 명명 체계를 따른다. 모달 오버레이를 총칭할 때는 오버레이(Overlay) 또는 모달(Modal) 용어를 사용한다.

### `AlertDialog`와 `Dialog`의 구분 기준

스크린리더의 초기 낭독 동작이 다르다. `alertdialog`는 모달 오픈 즉시 본문 전체가 자동 낭독되며, `dialog`는 `aria-labelledby` 및 `aria-describedby`를 통해 지정된 요소만 읽힌다. 파괴적 액션 확인 시에는 반드시 `alertdialog`를 적용해야 한다.

`alertdialog`는 명시적 상호작용 컨트롤(확인/취소 버튼)을 포함해야 한다. 단순 알림만을 목적으로 하는 경우에는 `alert` 역할을 사용한다.

### URL 상태 관리 원칙

독립된 목적지 화면을 구성하는 `Dialog`만 URL 쿼리 파라미터를 갖는다. 세부 기준은 [프론트엔드 04. 적응형 레이아웃](./frontend-04-adaptive-layout.md)에 기술되어 있다.

단순 확인 다이얼로그(`AlertDialog`)와 일시적 선택기(`BottomSheet`)는 URL 주소를 갖지 않는다. 일시적 조작에 URL 상태를 부여하면 조작 횟수만큼 뒤로가기가 중단되는 문제가 발생하기 때문이다.

### 팝오버의 좁은 화면 바텀 시트 전환

넓은 화면에서 트리거 요소에 인접하여 표시되는 팝오버는 좁은 화면에서 하단 바텀 시트로 전환된다. 이는 개별 화면 컴포넌트가 아닌 공통 팝오버 계층에서 일괄 처리한다. 개별 컴포넌트에서 전환 규칙을 분산 정의하면 화면 간 동작 불일치가 발생하기 때문이다.

| 항목 | 넓은 화면 (Wide) | 좁은 화면 (Compact) |
| :--- | :--- | :--- |
| 표시 위치 | 트리거 요소 인접 상대 위치 | 뷰포트 하단 고정 |
| 백드롭 | 투명 또는 비활성화 | 배경 백드롭 표시 |
| 오버레이 패널 | 지정 너비, 전체 모서리 둥글림 | 뷰포트 전체 너비, 상단 모서리만 둥글림 |

전환 메커니즘은 트리거 요소의 오리진(Origin) 해제와 글로벌 바텀 위치 전략 교체를 통해 구현한다.

파괴적 액션 확인을 수행하는 `AlertDialog`는 모바일 뷰포트에서도 바텀 시트로 전환하지 않고 중앙 모달 형태를 유지한다. 파괴적 작업의 중대성을 시각적으로 유지하기 위함이다.

## 9. `shared/ui` 컴포넌트 배치 경계

| 포함 대상 | 제외 대상 |
| :--- | :--- |
| 버튼, 입력, 선택, 다이얼로그, 표, 배지 | 특정 도메인 전용 카드나 행 |
| 레이아웃 프리미티브 | 특정 화면 전용 조합 컴포넌트 |
| 로딩 인디케이터, 빈 상태 표시 | 업무 규칙이 포함된 렌더링 로직 |
| 아이콘 래퍼 | 서버 데이터 조회 로직 |

판정 기준은 **타 프로젝트로 독립 분리해도 의미가 성립하는가**이다. 도메인 중립적이고 재사용 가능한 프리미티브만 `shared/ui`에 배치하며, 업무 규칙이나 서버 데이터 조회가 결합된 컴포넌트는 상위 계층(`features` 또는 `entities`)에 배치한다.

아이콘은 단일 아이콘 래퍼 컴포넌트로 캡슐화하여 사용한다. 크기 및 색상 토큰 적용을 중앙에서 일관되게 보장하고, 아이콘 세트를 교체할 때 호출부 코드를 일일이 수정하지 않기 위함이다. 프로젝트 내에서는 단일 아이콘 세트로 고정하고 선 굵기(Stroke weight)를 혼용하지 않는다.
