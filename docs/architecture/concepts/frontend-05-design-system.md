# 프론트엔드 05. 디자인 시스템

UI 킷이 두 층으로 분리되어 동작하는 메커니즘, 디자인 토큰의 원본 위치와 계약, 그리고 색상 모드가 전환되는 경로를 서술합니다. 컴포넌트의 물리적 배치 규격은 빌딩 블록 뷰가 정의하며, 검증 가능한 세부 코딩 규칙은 코드 스타일 가이드가 다룹니다.

## 1. UI 킷 계층 구조와 소스 코드 배치

| 층 | 위치 | 소유 | 담당 |
| :--- | :--- | :--- | :--- |
| **brain** | `@spartan-ng/brain` (npm) | 외부 | 접근성, 포커스 관리, 키보드 조작, ARIA, 오버레이 |
| **helm** | `shared/ui/` (소스) | 프로젝트 | 마크업, 클래스, 시각적 표현 |
| **기반** | `@angular/cdk` (npm) | 외부 | brain이 사용하는 프리미티브 |

brain과 CDK는 대체 관계가 아니라 **brain이 CDK 위에 세워진 층**입니다.

helm 컴포넌트는 npm 패키지가 아니라 CLI로 소스 코드를 프로젝트 내부로 복사해 옵니다. 초기화 명령이 의존성을 설치하고 전역 스타일에 Tailwind 계층, Spartan 프리셋 임포트, 테마 변수를 기록합니다. **`angular.json`은 수정하지 않으므로** 스타일 진입점을 옮겨 두었다면 생성기 실행 시 해당 경로를 명시해야 합니다.

**마크업과 클래스의 형태를 정하는 축(`style`)은 컴포넌트를 추가하기 전에 확정합니다.** 이는 색상 팔레트와 별개의 축이며, 사후에 변경하면 이미 복사된 사본을 재생성해야 하므로 그동안 수정한 내용이 덮어써집니다.

### 컴포넌트 디렉터리 구조와 공개 API 매핑

생성기는 컴포넌트마다 중첩된 디렉터리 구조를 생성하고 `tsconfig`가 진입점을 컴포넌트별 경로로 매핑합니다.

```ts
import { HlmButton } from '@/shared/ui/button';
import { HlmSheet } from '@/shared/ui/sheet';
```

**세그먼트 배럴을 두지 않습니다.** 배럴에서 즉시 사용하는 심볼과 지연 대상 심볼을 함께 가져오면 배럴 모듈이 정적 의존성으로 확정되어 지연 청크가 분리되지 않습니다. 선행 저장소에서 배럴을 제거한 결과 초기 번들이 544 kB에서 275 kB로 줄었습니다.

이 구조는 FSD(Feature-Sliced Design) 린트 규칙과 충돌합니다.

| 충돌 | 해소 방식 |
| :--- | :--- |
| 컴포넌트 폴더에 공개 API 파일이 없음 | 해당 경로만 규칙 검사에서 제외 |
| 폴더명이 세그먼트명과 중복됨 | 동일한 방식으로 규칙 검사에서 제외 |
| 컴포넌트별 경로를 내부 우회로 판정 | 규칙을 해제하고 ESLint 패턴 검사로 대체 |

구조를 수동으로 평탄화하면 컴포넌트를 추가하거나 재생성할 때마다 동일한 수정을 반복해야 하므로 앞의 두 규칙은 해제합니다. 세 번째 항목은 성격이 다릅니다. `@/shared/ui/button`은 `tsconfig`가 매핑하는 **해당 컴포넌트의 공개 API**이며 내부 파일이 아닙니다. 정적 분석 도구가 경로 문자열만으로 판정하여 규칙 단위 예외를 둘 수 없으므로 린트 규칙을 전역 해제하고, 슬라이스 내부 파일 직접 임포트 방지는 ESLint 경로 패턴으로 대신 검증합니다.

## 2. Helm 컴포넌트 수정 권한과 책임 격리

**helm 컴포넌트는 프로젝트 요구에 맞춰 자유롭게 수정합니다.** 마크업 구조, 클래스, 입출력 API 모두 변경 대상입니다.

수정 권한을 갖는 근거는 적응형 UI 요구 때문입니다. 동일한 논리적 컴포넌트라도 화면 폭에 따라 서로 다른 DOM과 상호작용 모델을 가져야 하므로, 토큰과 클래스만 변경하는 방식으로는 이를 구현할 수 없습니다.

**대가는 업스트림의 시각적 개선이 자동으로 오지 않는다는 것입니다.** API 수준의 갱신은 생성기의 점검 명령이 폐기된 API를 조정해 주므로, 시각적 개선 사항만 수동으로 따라갑니다.

**층이 분리되어 있어 이 대가를 감당할 수 있습니다.** 접근성과 동작은 brain이 소유하고 helm은 시각 층을 담당하므로, helm을 수정하더라도 포커스 트랩, 키보드 조작, ARIA 속성 연결은 brain이 계속해서 보장합니다. **사본이 낡아서 잃는 것은 시각적 개선이지 접근성이 아닙니다.**

반대로 **brain 디렉티브 연결을 임의로 제거하면 접근성 보장이 함께 사라지며, 이는 시각적으로 드러나지 않습니다.**

## 3. 디자인 토큰 원본 위치와 참조 체계

| 대상 | 원본 위치 |
| :--- | :--- |
| 토큰 이름의 집합 | 이 문서가 고정 |
| 각 이름에 담기는 값 | `src/app/styles.css` |

**토큰 값을 이 문서에 옮겨 적지 않습니다.** 런타임이 해석하는 파일과 개발자가 참조하는 파일이 단일하므로 명세와 구현이 어긋날 여지가 없습니다.

전역 스타일시트는 Tailwind 계층과 함께 Spartan 프리셋을 임포트합니다. 이 프리셋이 애니메이션 유틸리티와 **CDK 오버레이 스타일**을 함께 제공하므로, 임포트가 누락되면 다이얼로그와 팝오버의 배치가 깨집니다.

### 시맨틱 토큰 명명 체계와 토큰 쌍 규격

| 짝을 이루는 토큰 | 용도 |
| :--- | :--- |
| `background` / `foreground` | 화면 기본 배경 및 전경 |
| `card` / `card-foreground` | 카드 표면 |
| `popover` / `popover-foreground` | 오버레이 표면 |
| `primary` / `primary-foreground` | 주 동작 |
| `secondary` / `secondary-foreground` | 보조 동작 |
| `muted` / `muted-foreground` | 약화된 영역 |
| `accent` / `accent-foreground` | 강조 영역 |
| `destructive` / `destructive-foreground` | 파괴적 동작 |

짝이 없는 단독 토큰은 `border` · `input` · `ring`이며, `--radius`와 사이드바 계열 토큰이 추가로 존재합니다. **팔레트를 새로 구성할 때는 이 이름 집합을 빠짐없이 채워야 하며, 누락된 이름은 해당 토큰을 참조하는 컴포넌트 렌더링 시점에 드러납니다.**

**`-foreground` 짝이 없는 배경 토큰을 만들지 않습니다.** 배경 위에 올릴 텍스트 색상의 판단 기준이 모호해져 접근성 대비 문제를 유발하기 때문입니다.

폰트 패밀리는 두 슬롯을 정의하지만 **글자 크기와 두께에는 별도 디자인 토큰을 두지 않습니다.** Tailwind CSS 유틸리티에 이미 검증된 척도가 내장되어 있어 별도 토큰을 정의하면 중복 관리가 발생합니다.

### 신규 토큰 확장과 테마 유틸리티 등록

새로운 토큰을 추가할 때는 CSS 변수 값 선언과 테마 유틸리티 등록을 함께 정의합니다.

```css
:root {
  --warning: /* 라이트와 다크 값 */;
  --warning-foreground: /* 라이트와 다크 값 */;
}

@theme inline {
  --color-warning: var(--warning);
  --color-warning-foreground: var(--warning-foreground);
}
```

테마 등록이 누락되면 Tailwind 유틸리티 클래스가 생성되지 않아 변수만 정의된 채 스타일에서 참조할 수 없습니다. **새 토큰은 라이트와 다크 모드의 값을 동시에 정의합니다.** 한쪽 모드만 정의하면 반대 모드에서 색상 대비가 깨지며, 해당 모드로 진입하기 전까지는 결함이 드러나지 않습니다.

## 4. 뷰포트 기반 치수 정책과 최소 터치 타겟

컨트롤의 물리적 치수는 뷰포트 폭에 따라 결정됩니다. helm의 기본 치수는 마우스 환경을 전제하므로, 좁은 화면에서는 터치 접근성의 최소 기준에 미달합니다.

**치수 조정에는 런타임 판정이 필요하지 않습니다.** `max-md:` 변형 클래스가 미디어 쿼리로 컴파일되므로 CSS만으로 처리되며, 프리렌더 경로에서도 깜빡임 없이 동일하게 동작합니다. 뷰포트 폭 판정 신호는 컴포넌트 구조 자체를 교체할 때 사용하는 것이지 단순 크기 변경에 사용하는 것이 아닙니다.

치수 전환 임계값은 적응형 레이아웃의 판정 축과 동일한 경계(`48rem`)를 사용합니다. 두 영역에 서로 다른 임계값을 적용하면 컴포넌트가 교체되는 지점과 치수가 변경되는 지점이 어긋나기 때문입니다.

**크기 변형마다 값을 분산하지 않고 컴포넌트의 기본 클래스에 최소 터치 타겟을 선언합니다.** 특정 크기 변형에만 적용하면 향후 추가되는 변형에서 기준이 누락되기 쉽습니다.

```ts
const TOUCH_TARGET = 'max-md:min-h-11 max-md:min-w-11';
```

표의 행 내부 조작 버튼처럼 시각적 치수를 키우기 어려운 고밀도 영역에서는 보이는 크기를 유지하되 히트 영역(Hit target)만 확장합니다. **기본 정책은 시각적 치수를 함께 키우는 것이며, 히트 영역 확장 예외를 기본값으로 사용하지 않습니다.**

### 입력 컨트롤 폰트 크기와 포인터 미디어 쿼리 판정

**글자를 입력하는 컨트롤의 폰트 크기는 유일하게 포인터 미디어 쿼리로 판정합니다.** 16px를 기본값으로 두고, 정밀 포인터(`pointer: fine`)가 감지될 때만 폰트 크기를 축소합니다.

이 영역을 뷰포트 폭으로 판정하지 않는 이유는 **실패의 성격이 다르기 때문입니다.** 태블릿 가로 모드는 넓은 화면으로 판정되어 폰트 크기가 줄어드는데, iOS Safari는 16px 미만의 입력 필드에 포커스가 진입하면 뷰포트를 강제로 확대하며 **사용자가 그 배율을 손으로 되돌려야 합니다.** 다른 치수의 오판은 시각적 어긋남에 그치지만, 입력 폰트 크기 오판은 사용자가 직접 수습해야 하는 상호작용 결함으로 이어집니다.

포인터 미디어 쿼리의 오판 또한 이 상황에서는 안전한 방향으로 동작합니다. 정밀 포인터가 없다고 잘못 보고되더라도 16px 기본값이 유지되어 화면 확대 문제가 발생하지 않습니다.

## 5. 색상 대비 하한 기준과 자동 검증

| 대상 | 기준 |
| :--- | :--- |
| 본문 · 보조 · 삼차 텍스트 | 4.5:1 |
| 큰 텍스트 | 3:1 |
| 폼 컨트롤 경계와 포커스 링 | 3:1 |
| 장식선 | 면제 |

대비 하한은 라이트와 다크 **양쪽 모드 모두에서** 충족해야 합니다.

**두 경계선의 기준이 다릅니다.** `border`는 동일 평면에서 면을 구분하는 장식선이며, 선이 보이지 않더라도 컴포넌트의 식별과 조작이 불가능해지지 않으므로 대비 기준 적용 대상에서 제외됩니다. 여기에 3:1 기준을 강제하면 모든 면 사이에 짙은 회색 선이 그어져 미세한 경계선(Hairline)으로 구조를 표현하는 설계가 불가능해집니다. 반면 `input` 경계선은 "이 영역이 입력 필드"임을 인지시키는 유일한 시각적 단서이므로 3:1 대비를 엄격히 적용합니다. 이는 **기준을 느슨하게 한 것이 아니라 더 정교하게 나눈 것**입니다.

**수치를 문서에 기록하는 것에 그치지 않고 자동 검증합니다.** 토큰 정의를 파싱하여 대비를 산출하는 단위 테스트를 두어, 팔레트를 교체하거나 오버라이드를 삭제하면 빌드 단계에서 즉시 실패하도록 만듭니다. 문서에만 적힌 기준은 테마가 변경될 때 조용히 위반되기 때문입니다.

**Spartan 기본 테마는 이 기준을 충족하지 않습니다.** 실측 결과 라이트 모드에서 `muted-foreground`가 `muted` 배경 위에서 4.34:1, `input`이 배경 위에서 1.26:1, `ring`이 2.59:1로 측정되었습니다. 생성기가 제공한 기본값을 그대로 유지하면 이 세 항목이 접근성 기준에 미달합니다.

## 6. 색상 모드 전환 경로와 렌더링 동기화

모드 판단의 원본은 `color-scheme`입니다. 기본 상태에서는 시스템 OS 설정을 따르고, 사용자가 명시적으로 선택하면 문서 루트(`<html>`)의 클래스가 이를 덮어씁니다. 클래스를 주입하는 로직은 `app` 계층이 소유합니다.

**색상 모드는 첫 페인트(First Paint) 이전에 결정되어야 합니다.** 애플리케이션 컴포넌트 코드에서 모드를 전환하면 초기 렌더링 후 모드가 바뀌는 화면 깜빡임(FOUC)이 발생합니다. 색상 토큰이 단일 정의 내에 라이트와 다크 값을 함께 선언하면 스크립트 실행 전에도 브라우저 CSS 엔진만으로 시스템 설정이 즉시 반영되므로 깜빡임이 발생하지 않습니다.

### 프리셋 `dark` 변형 불일치와 커스텀 변형 선언

**프리셋이 기본 선언한 `dark` 변형을 그대로 사용하지 않습니다.** 프리셋은 클래스 존재 여부만 판정하는 반면, 색상 토큰은 `color-scheme`과 `light-dark()` 메커니즘을 통해 전환됩니다. 사용자가 시스템 모드로 설정한 상태에서는 **토큰이 OS 설정을 따라 다크로 전환되지만, `dark:` 유틸리티 클래스는 루트에 `.dark` 클래스가 없어 전혀 적용되지 않는 불일치가 발생합니다.**

이 불일치는 배경색만 다크로 바뀌고 일부 컨트롤은 라이트 모드 스타일을 유지하는 형태로 나타납니다. 실제로 시스템 모드와 다크 모드 간 본문 배경색은 동일하지만 입력 컨트롤의 배경색만 달라지는 결함이 발생합니다.

전역 스타일시트에서 프리셋 임포트 직후에 커스텀 변형을 다시 선언하여 두 경로를 모두 수용합니다.

```css
@custom-variant dark {
  &:where(.dark, .dark *) { @slot; }

  @media (prefers-color-scheme: dark) {
    &:where(:not(.light):not(.light *)) { @slot; }
  }
}
```

`.light` 제외 조건이 누락되면 OS가 다크 모드인 상태에서 사용자가 라이트 모드를 선택하더라도 `dark:` 유틸리티가 계속 적용됩니다. 이 문제는 **자동 강제 수단이 없고 세 모드의 계산값을 비교하지 않으면 시스템 모드에서만 드러나므로 코드 리뷰에서 확인합니다.**

문서 루트에만 적용되는 선택자는 화면 내 부분 다크 모드를 지원하지 않습니다. 하위 요소에 `.dark` 클래스를 부여하더라도 변수 재정의가 전파되지 않아 두 모드를 한 화면에 병렬로 배치할 수 없습니다. 선택자 범위를 확장하면 가능해지지만 의도치 않은 하위 영역 재정의를 유발할 수 있으므로, 향후 모드 병렬 표시 요구가 발생할 경우 이를 우선 검토 대상으로 다룹니다.

## 7. 접근성 책임 분담과 구현 우선순위

접근성 보장은 단일 계층에 집중되지 않고 세 영역이 책임을 분담합니다.

| 담당 | 범위 |
| :--- | :--- |
| brain · CDK | 포커스 트랩, 포커스 복귀, 키보드 조작, ARIA 속성 연결, 오버레이 접근성 |
| HTML 시맨틱 | 요소 역할, 기본 키보드 동작, 스크린리더 인식 |
| 구현부 | 시맨틱 요소 선택, 접근 가능한 이름, 색상 대비, 상태 전달 |

**접근성 구현은 세 단계의 우선순위를 따릅니다.**

1. **시맨틱 HTML로 해결합니다.** 네이티브 `<button>`은 클릭, 엔터·스페이스 키보드 활성화, 포커스 수신 동작을 브라우저 수준에서 기본 제공합니다.
2. 시맨틱 요소만으로 충족할 수 없는 복합 상호작용은 **brain 프리미티브를 사용합니다.**
3. 두 수단으로 해결할 수 없는 경우에만 직접 구현합니다.

**복합 위젯의 접근성 동작은 대부분 brain 층이 흡수합니다.** 결함이 자주 발생하는 날짜 그리드도 방향키와 `Home` · `End` · `PageUp` · `PageDown` 이동, 로빙 탭인덱스, `role="grid"`와 셀 단위 ARIA 속성 관리가 brain에 구현되어 있어 직접 구현 대상이 아니며, 구현부는 라벨의 한국어화만 담당합니다.

접근성 책임이 하위 층에 격리되어 있으므로 helm 컴포넌트의 마크업을 자유롭게 수정하더라도 접근성 보장이 유지됩니다. **다만 디렉티브 연결을 끊으면 그 보장이 함께 사라지고 그것은 시각적으로 드러나지 않습니다.**

## 8. 덮개의 종류와 어휘

화면을 덮는 것을 셋으로 가릅니다. 겉모습의 취향이 아니라 **보조기술의 동작과 주소 규약이 갈리므로** 이름을 고정합니다.

| 이름 | ARIA 역할 | 안에서 하는 일 | 주소 | 좁은 화면 |
| :--- | :--- | :--- | :--- | :--- |
| `AlertDialog` | `alertdialog` | 묻고 답 하나 받기. 지우기처럼 되돌릴 수 없는 것 | 갖지 않음 | 그대로 작은 상자 |
| `Dialog` | `dialog` | 그 안에서 일을 하기. 세우기 · 고치기 같은 폼 | **쿼리** | 화면을 채움 |
| `BottomSheet` | `dialog` | 값 하나 고르기. 넓은 화면의 고르개가 좁은 화면에서 되는 것 | 갖지 않음 | 아래에서 올라옴 |

이름은 [WAI-ARIA 역할](https://www.w3.org/WAI/ARIA/apg/patterns/alertdialog/)과 이 저장소가 쓰는 UI 킷(Spartan · shadcn)의 컴포넌트 이름을 함께 따릅니다. 셋이 한 이름이라 명세와 코드와 문서가 갈리지 않습니다. `BottomSheet` 만 ARIA 역할이 아니라 `Dialog` 가 놓이는 자리이며, 아우르는 말이 필요하면 **덮개**로 적습니다.

### `AlertDialog` 와 `Dialog` 를 가르는 근거

**스크린리더의 동작이 다릅니다.** `alertdialog` 는 열리는 순간 본문이 자동으로 읽히고, `dialog` 는 `aria-labelledby` · `aria-describedby` 로 묶어야 읽힙니다. "지우시겠습니까"를 `Dialog` 로 띄우면 그 문장이 읽히지 않을 수 있으므로, 이 구분은 지켜야 하는 계약입니다.

`alertdialog` 는 상호작용 컨트롤을 가져야 합니다. 알리기만 하고 답을 받지 않으면 `alert` 를 씁니다.

### 주소를 갖는 것은 `Dialog` 하나입니다

`Dialog` 는 그 자체로 하나의 일이므로 목적지이며, 열림 상태를 주소의 쿼리에 둡니다. 판정과 규약은 [프론트엔드 04. 적응형 레이아웃](./frontend-04-adaptive-layout.md) 4절이 갖습니다.

`AlertDialog` 와 `BottomSheet` 는 주소를 갖지 않습니다. 방금 누른 것에 대한 되물음이거나 값 하나를 고르는 자리라 새로고침에 되살아날 이유가 없고, 주소를 주면 뒤로가기가 되물은 횟수만큼 멈춥니다.

### 팝오버로 뜨는 것은 좁은 화면에서 시트가 됩니다

**자리마다 판정하지 않습니다.** 넓은 화면에서 트리거 옆에 붙어 뜨는 고르개는 좁은 화면에서 아래에서 올라오는 시트가 되며, 이것은 팝오버 층이 갖는 규칙입니다. 쓰는 쪽은 아무것도 하지 않고 새로 만드는 고르개도 그대로 따릅니다. 자리마다 정하면 같은 모양이 화면마다 다르게 뜨고, 나중에 만드는 것이 규칙에서 빠집니다.

바뀌는 것은 셋입니다.

| 것 | 넓은 화면 | 좁은 화면 |
| :--- | :--- | :--- |
| 뜨는 자리 | 트리거에 붙음 | 화면 아래에 붙음 |
| 뒤 | 그대로 | 덮음 |
| 판 | 제 폭, 사방이 둥금 | 화면 폭, 위쪽만 둥금 |

**셋을 가르는 장치는 원점입니다.** 트리거에 붙는 전략은 원점이 있을 때만 서므로, 좁은 화면에서는 전역 전략을 대신 돌려주어 그 자리를 비웁니다.

`AlertDialog` 는 이 규칙 밖입니다 — 아래 절이 그 근거를 갖습니다.

### 좁은 화면에서 확인을 시트로 바꾸지 않습니다

`BottomSheet` 는 탐색적인 것이 가는 자리입니다. 파괴적 동작 앞의 확인을 시트로 띄우면 **그 행위의 무게가 축소되고**, 사용자는 더 단호한 멈춤을 기대합니다. `AlertDialog` 는 좁은 화면에서도 `AlertDialog` 로 둡니다.

## 9. `shared/ui` 컴포넌트 배치 경계

| 포함 대상 | 제외 대상 |
| :--- | :--- |
| 버튼, 입력, 선택, 다이얼로그, 표, 배지 | 특정 도메인 전용 카드나 행 |
| 레이아웃 프리미티브 | 특정 화면 전용 조합 컴포넌트 |
| 로딩 인디케이터, 빈 상태 표시 | 업무 규칙이 포함된 렌더링 로직 |
| 아이콘 래퍼 | 서버 데이터 조회 로직 |

**판정 기준은 하나입니다 — 다른 프로젝트에 그대로 옮겨도 의미가 통하는가.** 범용적으로 통용되면 `shared/ui`에 배치하고, 그렇지 않다면 도메인 지식이 결합된 컴포넌트입니다. `Card` 프리미티브는 `shared/ui`에 속하며, 도메인 할일 카드는 `Card`를 조합하여 상위 슬라이스가 구성합니다.

아이콘은 단일 래퍼 컴포넌트를 정의하고 이를 통해서만 사용합니다. 크기 및 색상 토큰 적용을 중앙에서 일관되게 보장하고, 아이콘 세트를 교체할 때 호출부 코드를 일일이 수정하지 않기 위함입니다. 어떤 아이콘 세트를 채택할지는 프로젝트가 결정하며, 이 문서는 **단일 세트로 고정하고 선 굵기(Stroke weight)를 혼용하지 않는다**는 원칙만 고정합니다.
