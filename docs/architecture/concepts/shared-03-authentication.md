# 공통 03. 인증 경로와 세션 관리 체계

요청자의 신원을 판정하는 경로와, 그 판정의 근거가 발급되고 만료되기까지의 세션 수명 관리 메커니즘을 서술한다. 서버가 판정하고 클라이언트는 결과에 따라 동작하므로 프론트엔드와 백엔드 두 영역에 동시에 적용되는 공통 규격이다.

## 1. 클라이언트 인증 경로와 식별 방식

브라우저와 브라우저 밖의 클라이언트는 서로 다른 인증 수단을 사용한다.

| 경로 | 수단 | 대상 환경 |
| :--- | :--- | :--- |
| 세션 | HttpOnly 쿠키 | 브라우저 웹 애플리케이션 |
| API 토큰 | `Authorization: Bearer` | 외부 에이전트, 스크립트, CLI |

동일한 인터셉터가 두 경로의 요청을 모두 수신한다. **인증 헤더가 존재하면 API 토큰으로, 없으면 쿠키로 판정한다.** 어느 경로든 검증을 통과하면 요청 속성에 사용자 식별자가 설정되며, 후속 비즈니스 코드는 어떤 수단으로 인증되었는지 구분하지 않는다.

두 수단을 분리한 이유는 **쿠키 인증이 브라우저 외부 환경에서 동작하지 않기 때문**이다. 브라우저는 쿠키를 자동으로 전송하며 `HttpOnly` 속성을 통해 스크립트 접근을 차단하지만, 외부 에이전트나 스크립트 클라이언트에는 브라우저 쿠키 관리자가 존재하지 않는다. 반대로 브라우저 환경에서 Bearer 토큰을 사용하면 토큰을 로컬 스토리지 등에 저장해야 하므로 XSS 공격에 의한 토큰 탈취 위험에 노출된다.

## 2. 토큰 저장 구조와 해시 검증 방식

**서버는 토큰 원문을 저장하지 않는다.** 발급 시점에만 원문을 클라이언트에 전달하고, 데이터베이스에는 HMAC 해시 값을 저장한다. 인증 검증은 인입된 토큰을 동일한 비밀키로 해싱하여 일치 여부를 비교한다.

데이터베이스가 유출되어도 저장된 해시 값으로 직접 인증할 수 없도록 방어하기 위함이다. 해시 비밀키는 애플리케이션 환경 변수로 관리하며, 32자 미만인 경우 부트스트랩 시점에 애플리케이션 기동이 실패하도록 강제한다.

**해시 생성 시 토큰의 용도(Scope)를 결합한다.** 동일 키 해싱에 따른 세션 토큰과 API 토큰 간 교차 대입 공격을 방지하기 위함이다. 용도 식별자를 결합하여 동일한 원문이라도 용도별로 상이한 해시 결과가 생성되도록 보장한다.

토큰 원문은 암호학적으로 안전한 난수로 생성하며 URL-Safe Base64로 인코딩한다. 쿠키 및 HTTP 헤더 전송 시 인코딩 오류를 방지하기 위함이다.

## 3. 세션 쿠키 보안 속성과 전송 정책

| 속성 | 설정 | 근거 |
| :--- | :--- | :--- |
| `HttpOnly` | 활성화 | 자바스크립트 접근을 차단하여 XSS 기반 토큰 탈취 방어 |
| `Secure` | 환경별 분기 | 로컬 HTTP 환경에서는 비활성화하고 운영 HTTPS 환경에서 활성화 |
| `SameSite` | `Lax` | 외부 사이트에서 시작된 교차 출처 요청의 쿠키 전송을 차단하여 CSRF 방어 |
| `Path` | `/` | 화면과 API가 동일 출처이므로 전역 경로에서 전송 |

**`SameSite=Lax`는 화면과 API가 동일 출처라는 전제 위에서 동작한다.** 다른 출처에서 API를 호출하면 쿠키가 전송되지 않으므로, 배포 환경에서 프론트엔드와 백엔드를 단일 도메인(Reverse Proxy) 아래 통합하는 구성이 전제된다. 외부 클라이언트를 위한 별도 도메인은 쿠키가 아닌 Bearer 토큰을 사용하므로 영향을 받지 않는다.

로그아웃 시에는 동일한 이름의 빈 쿠키를 수명 0(`Max-Age=0`)으로 재발급하여 브라우저 쿠키를 만료 처리한다.

## 4. 세션 수명 주기와 만료 판정 기준

세 가지 설정값이 결합하여 세션의 수명을 결정한다.

| 설정값 | 역할 |
| :--- | :--- |
| 유효 기간 (TTL) | 요청 시마다 해당 기간만큼 만료 시점이 연장됨 |
| 절대 상한 (Max Lifetime) | 지속 사용 여부와 무관하게 최초 발급 시점부터 최대 수명을 제한함 |
| 갱신 간격 (Update Interval) | 해당 간격 이내의 재사용 시에는 데이터베이스 갱신 쓰기를 생략함 |

**슬라이딩 갱신에 최소 간격을 두는 이유는 데이터베이스 쓰기 부하를 방지하기 위함이다.** 모든 조회 요청마다 만료 시각을 갱신하면 세션 저장소 쓰기 부하가 급증한다. 갱신 간격 이내의 요청은 세션 유효성만 검증하고 저장소 갱신은 생략한다.

**절대 상한이 없으면 활성 세션이 무기한 유지될 위험이 있다.** 사용자가 지속적으로 접속하더라도 최초 발급 시점 기준 상한에 도달하면 주기적인 재인증을 강제한다.

만료 여부는 요청 처리 시점에 판정한다. 만료와 부재를 구분하여 응답하면 토큰의 과거 존재 여부가 노출되므로, 만료된 세션은 미등록 세션과 동일한 실패 응답(401)을 반환한다.

## 5. 인증 필터 적용 범위와 경로 보호 정책

보호 대상을 개별 나열하면 신규 엔드포인트 추가 시 보안 설정 누락으로 비인가 엔드포인트가 노출되는 취약점이 발생하므로, 인터셉터가 전체 API 경로를 기본으로 보호하고 **회원가입과 로그인만 화이트리스트 예외로 제외한다.**

인증 실패 시 인터셉터 단계에서 즉시 예외를 발생시키며, 전역 예외 처리기가 RFC 9457 공통 형식으로 변환하여 응답한다. 컨트롤러는 인증 검증 책임을 갖지 않는다.

## 6. 클라이언트 인증 처리 흐름과 계층별 역할

**클라이언트는 토큰 원문을 직접 다루지 않는다.** 브라우저 로컬 저장소에 보관하거나 헤더에 수동 부착하지 않으며, 브라우저 기본 쿠키 메커니즘에 위임한다. 클라이언트 인증 로직은 세 영역으로 구분된다.

| 대상 작업 | 처리 방식 |
| :--- | :--- |
| 로그인 · 가입 · 로그아웃 요청 | 명령 전용 서비스 |
| 화면 진입 시 인증 여부 확인 | 라우트 가드가 내 정보 API를 조회하여 판정 |
| 세션 만료 응답 처리 | 인터셉터가 로그인 화면으로 이동 |

**라우트 가드는 최종 보안 인가 수단이 아니다.** 클라이언트 코드는 조작 가능하므로 가드 통과가 보안 권한을 보장하지 않는다. 가드의 역할은 **미인증 사용자가 불완전한 화면에 진입한 후 비동기 에러로 튕겨 나가는 UX 결함을 방지하는 것**이며, 실제 보안 검증은 백엔드 API 인터셉터가 매 요청마다 수행한다.

가드가 내 정보 조회를 수행하므로 초기 화면 진입 시 1회의 추가 네트워크 왕복이 발생한다. 쿠키 유효성을 클라이언트가 자체 검증할 수 없으므로 지불하는 정합성 비용이다.

**프리렌더 빌드 경로에서는 라우트 가드가 진입을 차단하지 않도록 허용한다.** 빌드 시점에는 쿠키와 세션이 없어 가드가 동작하면 모든 프리렌더 페이지가 로그인 화면으로 생성되기 때문이다. 실제 인증 판정은 브라우저 런타임에서 수행한다.

화면 컴포넌트별로 개별 처리할 경우 발생하는 라우팅 충돌을 방지하기 위해, 인증 만료 처리는 **HTTP 인터셉터에서 일원화하여 전담한다.** 단, 로그인 실패 응답을 세션 만료로 오인하여 로그인 페이지로 재이동시키는 문제를 방지하기 위해 **인증 요청 자체의 실패 응답은 세션 만료 처리에서 제외한다.**
