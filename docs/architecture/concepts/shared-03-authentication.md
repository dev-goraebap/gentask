# 공통 03. 인증 경로와 세션 관리 체계

요청자의 신원을 판정하는 경로와, 그 판정의 근거가 발급되고 만료되기까지의 세션 수명 관리 메커니즘을 서술합니다. 서버가 판정하고 클라이언트는 결과에 따라 동작하므로 프론트엔드와 백엔드 두 영역에 동시에 적용되는 공통 규격입니다.

## 1. 클라이언트 인증 경로와 식별 방식

브라우저와 브라우저 밖의 클라이언트는 서로 다른 인증 수단을 사용합니다.

| 경로 | 수단 | 대상 환경 |
| :--- | :--- | :--- |
| 세션 | HttpOnly 쿠키 | 브라우저 |
| API 토큰 | `Authorization: Bearer` | 브라우저 밖 클라이언트 |

동일한 인터셉터가 두 경로의 요청을 모두 수신합니다. **인증 헤더가 있으면 API 토큰으로, 없으면 쿠키로 판정합니다.** 어느 경로든 검증을 통과하면 요청 속성에 사용자 식별자가 설정되며, 후속 비즈니스 코드는 어떤 수단으로 인증되었는지 구분하지 않습니다.

두 수단을 나눈 이유는 **쿠키가 브라우저 밖에서 성립하지 않기 때문**입니다. 쿠키는 브라우저가 자동으로 실어 보내며 그 자동화가 곧 보안 속성(`HttpOnly`)의 근거가 되지만, 스크립트나 외부 에이전트에는 해당 자동화 메커니즘이 없습니다. 반대로 브라우저에 Bearer 토큰을 사용하면 토큰을 어딘가에 저장해야 하고 **저장한 순간 스크립트가 읽을 수 있게 됩니다.**

## 2. 토큰 저장 구조와 해시 검증 방식

**서버는 토큰 원문을 저장하지 않습니다.** 발급 시점에만 원문을 생성하여 클라이언트에 전달하고, 데이터베이스에는 HMAC 해시 값을 저장합니다. 인증 검증은 인입된 토큰을 동일한 방식으로 해싱하여 비교합니다.

저장소가 유출되어도 해당 값으로 직접 인증할 수 없도록 방어하는 것이 이 구조의 목적입니다. **해시 키는 애플리케이션 설정에 있고 32자 미만이면 기동이 실패합니다.** **짧은 키가 조용히 통과하면 그 사실이 운영에서만 드러납니다.**

**해시 생성 시 토큰의 용도를 함께 결합합니다.** 세션과 API 토큰이 동일한 키로 해싱되면 한쪽 값을 다른 쪽 조회에 교차 대입할 여지가 생깁니다. 용도 식별자가 다르면 동일한 원문이라도 서로 다른 해시 결과가 생성됩니다.

토큰 원문은 암호학적 난수로 생성하며 URL 안전(Safe) 문자로 인코딩합니다. 쿠키 값과 HTTP 헤더에 인코딩 손상 없이 직접 전달하기 위함입니다.

## 3. 세션 쿠키 보안 속성과 전송 정책

| 속성 | 값 | 이유 |
| :--- | :--- | :--- |
| `HttpOnly` | 켬 | 스크립트가 읽지 못합니다. XSS 로 탈취되지 않는 근거입니다 |
| `Secure` | 환경별 | 로컬은 HTTP 라 끄고 배포에서 켭니다. 설정으로 주입합니다 |
| `SameSite` | `Lax` | 다른 사이트에서 시작한 요청에 실리지 않아 CSRF 를 막습니다 |
| `Path` | `/` | 화면과 API 가 같은 출처이므로 전 경로에서 실립니다 |

**`SameSite=Lax` 는 화면과 API 가 같은 출처라는 전제 위에 섭니다.** 다른 출처에서 API 를 호출하면 쿠키가 실리지 않으므로, 배포 환경에서 화면과 API 를 단일 도메인 아래 두는 구성이 이 보안 설정과 맞물립니다. 브라우저 밖 클라이언트를 위한 별도 도메인은 쿠키가 아닌 Bearer 토큰을 사용하므로 영향을 받지 않습니다.

로그아웃은 동일한 이름의 빈 쿠키를 수명 0으로 다시 내려 클라이언트 쿠키를 제거합니다.

## 4. 세션 수명 주기와 만료 판정 기준

세 가지 설정 값이 결합하여 세션의 수명을 결정합니다.

| 값 | 역할 |
| :--- | :--- |
| 유지 기간 | 쓸 때마다 이 길이만큼 뒤로 밀립니다 |
| 절대 상한 | 계속 써도 최초 발급 시점부터 이 길이를 넘지 못합니다 |
| 갱신 간격 | 이 간격 안에 다시 쓰면 밀지 않습니다 |

**슬라이딩 갱신에 간격을 두는 이유는 쓰기 때문입니다.** 요청마다 만료 시각을 갱신하면 단순 조회 요청 하나에도 세션 저장소 쓰기가 따라붙습니다. 갱신 간격 이내의 재사용은 세션의 유효성만 확인하고 갱신 쓰기를 생략합니다.

**절대 상한이 없으면 세션이 영구히 살아 있을 수 있습니다.** 사용자가 지속적으로 접속하는 한 만료가 계속 뒤로 밀리므로, 최초 발급 시점을 기준으로 상한을 두어 주기적으로 다시 인증하게 만듭니다.

만료 판정은 요청 조회 시점에 이루어집니다. 만료된 세션은 존재하지 않는 것과 동일한 실패 응답을 받습니다. **만료와 부재를 구분해 알려 주면 그 차이가 곧 그 토큰이 존재했다는 정보가 됩니다.**

## 5. 인증 필터 적용 범위와 경로 보호 정책

인터셉터가 API 경로 전체를 기본으로 보호하고 **가입과 로그인만 예외로 제외합니다.** 보호할 경로를 나열하는 방식을 쓰지 않는 이유는, 신규 엔드포인트를 추가할 때 목록 등록을 누락하면 **그 경로가 조용히 열리기 때문**입니다. **제외 목록 방식에서는 잊어도 닫힌 채로 남습니다.**

인증에 실패하면 인터셉터 단계에서 즉시 예외가 발생하고 전역 오류 핸들러가 공통 실패 계약의 형식으로 변환합니다. 컨트롤러는 인증 여부를 직접 판단하지 않습니다.

## 6. 클라이언트 인증 처리 흐름과 계층별 역할

**클라이언트는 토큰 원문을 직접 다루지 않습니다.** 브라우저 저장소에 보관하거나 헤더에 붙이지 않으며, 브라우저의 자동 쿠키 전송에 위임합니다. 클라이언트의 인증 처리는 세 영역으로 분리됩니다.

| 대상 작업 | 처리 방식 |
| :--- | :--- |
| 로그인 · 가입 · 로그아웃 요청 | 명령 전용 서비스 |
| 화면 진입 시 인증 여부 확인 | 라우트 가드가 내 정보를 조회해 판정 |
| 세션이 끊긴 응답의 처리 | 인터셉터가 로그인 화면으로 이동 |

**가드는 인가 수단이 아닙니다.** 클라이언트 코드는 조작 가능하므로 가드를 통과했다는 사실이 권한을 보장하지 않습니다. 가드가 하는 일은 **인증되지 않은 사용자가 불완전한 화면을 보고 뒤늦게 튕겨 나가는 UX 문제를 방지하는 것**이며, 실제 보안 판정은 매 요청마다 서버가 다시 수행합니다.

가드가 조회를 한 번 보내므로 **화면 진입에 왕복이 하나 더 붙습니다.** 쿠키만으로는 그것이 아직 유효한지 클라이언트가 알 수 없기 때문에 치르는 비용입니다.

**프리렌더 경로에서는 가드가 통과시킵니다.** 빌드 시점에는 쿠키도 서버 세션도 없어 판정할 근거가 없으며, 여기서 막으면 프리렌더가 로그인 화면을 생성해 버리기 때문입니다. 실제 인증 판정은 브라우저 런타임에서 다시 일어납니다.

인증 만료 처리는 **인터셉터 한 곳에서 전담합니다.** 화면이 각자 판단하면 여러 화면이 동시에 로그인 화면으로 이동을 시도합니다. 다만 **인증 요청 자체의 실패는 제외합니다.** 로그인 시도가 실패한 것을 세션 만료로 보고 다시 로그인 화면으로 보내면 **사용자는 아무 일도 일어나지 않은 것처럼 느낍니다.**
