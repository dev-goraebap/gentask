# 공통 02. 오류 계약과 실패 처리 체계

요청이 실패했을 때 서버가 반환하는 응답 형식과, 클라이언트가 이를 해석하여 화면에 표시하기까지의 실행 흐름과 처리 메커니즘을 서술합니다. 이 문서는 프론트엔드와 백엔드 두 영역에 동시에 적용되는 공통 규격입니다.

## 1. 서버 검증 계층과 유효성 검증 경계

동일한 요청이라도 세 검증 지점을 거치며 각 지점이 보호하는 범위와 반환 형식이 다릅니다.

```text
요청 ─▶ [DTO]          형식이 틀렸다        → 필드 목록, 코드는 공통값
         │ 통과
         ▼
       [application]   지금 상태가 아니다   → 모듈 에러 코드
         │ 통과
         ▼
       [domain]        애초에 만들 수 없다  → 문장, 코드는 공통값
         │ 통과
         ▼
       저장
```

| | DTO 검증 | 도메인 검증 |
| :--- | :--- | :--- |
| 묻는 것 | 이 **요청**이 형식에 맞는가 | 이 **객체**가 존재할 수 있는가 |
| 판정 시점 | 컨트롤러 진입 전 | 객체 생성 순간 |
| 지키는 범위 | HTTP 요청 경로 | 모든 생성 경로 |
| 필드 정보 | 있다 | 없다 |

**두 검증이 겹치는 것은 중복이 아닙니다.** DTO 검증은 HTTP 요청 하나를 지키고 도메인 검증은 그 타입을 만드는 모든 경로를 지킵니다. 배치 처리처럼 컨트롤러를 거치지 않는 경로가 생기면 도메인 검증만 남습니다. 반대로 DTO 검증을 지우면 필드 단위 오류 표시가 사라지고 트랜잭션을 연 뒤에야 400 이 나갑니다.

검증의 근거가 되는 제약 값과 메시지는 값 객체가 소유하고 DTO가 이를 참조합니다. **검증은 두 번 실행되지만 고칠 자리는 한 곳입니다.**

## 2. 에러 코드 체계

`code`는 클라이언트가 분기 처리에 사용하는 계약입니다. **문구는 바뀔 수 있지만 코드는 고정입니다.**

모듈마다 열거형을 정의하고 상태 코드와 오류 문구를 함께 선언합니다. 코드 문자열은 `<모듈>_<사유>` 형식이며, **접두사 등록부를 문서로 따로 두지 않습니다.** 열거형 집합 자체가 등록부 역할을 수행하므로 별도 문서를 관리할 경우 동기화 불일치가 발생하기 때문입니다.

**모듈 열거형에는 해당 모듈 고유의 사유만 선언합니다.** 잘못된 요청, 충돌, 서버 오류 등 공통 예외는 공용 기반에 한 벌만 정의하고 모듈 확장 시 복제하지 않습니다.

### 문제 요약 필드 제외 정책

RFC 9457의 `title`은 문제 유형에 대한 정적 요약값입니다. 클라이언트의 분기 기준은 `code`이며 사람이 읽을 메시지는 `detail`에 담기므로, 열거형에 사람이 읽을 문구를 요약으로 두면 **같은 문장이 응답에 두 번 실립니다.** 상태 코드의 기본 명칭은 프레임워크가 채우도록 위임합니다.

### 자원 열거 방지 정책

사유를 세분화하되 **그 구분이 존재 여부를 알려 주는 신호가 되지 않게 합니다.** 대상 자원이 존재하지 않는 경우와 접근 권한이 없는 경우를 다른 코드로 구분하면, 그 차이가 곧 해당 식별자를 가진 자원의 존재 여부를 노출하는 정보가 됩니다. 따라서 두 경우 모두 동일한 코드로 응답합니다.

## 3. 오류 응답 구조와 직렬화 형식

```json
{
  "status": 400,
  "detail": "제목을 입력해 주세요",
  "code": "COMMON_INVALID_REQUEST",
  "traceId": "...",
  "errors": [
    { "field": "title", "message": "제목을 입력해 주세요" }
  ]
}
```

**DTO 검증 실패는 배열 구조를 유지하여 직렬화합니다.** 필드 이름을 단일 문자열로 결합하면 클라이언트가 이를 파싱해야 하며, 서버의 문구 변경 시 파싱 로직이 손상됩니다.

**필드 이름과 유효성 검증 메시지만 전달하고 사용자가 입력한 원본 값은 싣지 않습니다.** 메시지는 서버 애너테이션에 선언된 검증 문구입니다. 입력값을 응답에 포함하면 **민감한 입력이 에러 응답으로 되반사됩니다.**

전역 예외 처리기(`@RestControllerAdvice`)는 컨트롤러 진입 이전인 필터 단계의 실패를 처리하지 못합니다. 필터에서 실패 응답을 반환할 때는 **동일한 형식을 직접 생성하는 전용 컴포넌트를 경유합니다.** 그렇지 않으면 서블릿 컨테이너의 기본 오류 페이지가 반환되어 응답 형식이 불일치해지고, 클라이언트가 해당 경로에 대해 예외적인 파싱 처리를 수행해야 합니다.

## 4. 오류 메시지 소유권과 클라이언트 해석 기준

**서버는 코드와 문장을 함께 반환하고 클라이언트는 코드를 우선하여 사용합니다.**

```ts
const text = MESSAGES[problem.code] ?? problem.detail;
```

코드가 안정적인 계약으로 작동하므로 서버는 세부 문구를 변경할 수 있으며, 클라이언트는 화면 맥락에 적합한 문구를 표시하되 **모르는 코드가 와도 화면이 비지 않습니다.**

도메인 불변식 위반은 공통 오류 코드 하나를 사용하므로 클라이언트 분기 대상이 아니며, 결과적으로 서버가 전달한 메시지가 그대로 표시됩니다. **도메인이 던지는 문장을 사용자 문장으로 쓰는 규칙의 근거가 여기 있습니다.** 이는 도메인 예외 메시지에 테이블명이나 내부 식별자 같은 구현 세부사항을 포함하지 않는 이유이기도 합니다.

## 5. 클라이언트 오류 처리 경로와 계층별 책임

오류 처리가 화면 단위로 개별 구현되면 표시 일관성이 저하되고 예외 누락이 발생합니다. 공통 처리 계층과 화면 컴포넌트 간의 책임을 명확히 분리합니다.

| 계층 | 책임 |
| :--- | :--- |
| HTTP 인터셉터 | 응답 해석, 인증 만료 처리, 재시도, 관측 전송 |
| 전역 에러 핸들러 | 처리되지 않은 예외 포착, 관측 전송 |
| 화면 | 사용자에게 보여줄 내용과 위치 결정 |

**인터셉터는 발생한 오류의 유형을 판별하고 화면은 노출할 내용과 방식을 결정합니다.** 인터셉터가 UI 표시를 직접 제어하면 화면 컴포넌트가 해당 표시 상태를 제어할 수 없게 됩니다.

| 분류 | 처리 위치 | 사용자에게 |
| :--- | :--- | :--- |
| 네트워크 실패 | 인터셉터가 재시도 후 화면에 전달 | 연결 문제 안내와 재시도 수단 |
| 인증 만료 | 인터셉터가 세션 정리 후 로그인 이동 | 이동 사유 안내 |
| 권한 없음 | 화면 | 접근 불가 안내 |
| 입력 오류 | 화면 | 필드별 메시지 |
| 서버 오류 | 화면 | 일시적 오류 안내와 재시도 수단 |

**인증 만료에 한하여 인터셉터가 페이지 이동까지 전담합니다.** 세션이 만료된 상태에서 각 화면이 개별적으로 판단하면 **여러 화면이 동시에 로그인으로 이동시키려 합니다.**

### 오류 표시 위치와 화면 렌더링 범위

| 범위 | 표시 위치 |
| :--- | :--- |
| 화면 전체를 그릴 수 없음 | 화면 영역 전체를 에러 상태로 대체 |
| 화면 일부 영역만 실패 | 해당 영역만 에러 상태로 대체 |
| 사용자 동작의 결과 | 동작 지점 인근 |
| 입력값 문제 | 해당 필드 아래 |

목록 조회가 실패했을 때 토스트 알림만 표시하고 빈 목록을 렌더링하면 **사용자는 데이터가 없는 것으로 오해합니다.** 실패가 발생한 영역은 오류 상태임을 해당 위치에 명시하고 재시도 수단을 함께 제공합니다.

**자동 재시도는 조회 요청에만 한정하여 적용합니다.** 상태 변경 요청에 자동 재시도를 적용할 경우 중복 처리가 발생합니다.

### 사용자 대상 오류 문구 구성 및 내부 정보 격리

실패한 원인과 사용자가 취할 수 있는 후속 조치를 서술합니다. 기술 용어와 HTTP 상태 코드를 직접 노출하지 않고 사실 위주로 기술하되, 사용자를 탓하거나 불필요한 사과 문구를 반복하지 않습니다.

**서버가 사용자 대상 문장을 제공하는 경우 이를 우선하여 표시합니다.** 클라이언트가 상태 코드에만 의존하여 문구를 생성하면 서버가 전달하는 세부 맥락이 소실됩니다.

클라이언트에 노출하는 내부 진단 정보는 **추적 식별자(`traceId`) 하나로 제한합니다.** 사용자가 추적 식별자를 전달하면 서버 로그에서 해당 요청을 조회할 수 있습니다. 스택 트레이스, 데이터베이스 쿼리, 내부 식별자는 응답 및 화면에 노출하지 않습니다.
