# 공통 02. 오류 계약과 실패 처리 체계

요청이 실패했을 때 서버가 반환하는 응답 형식과, 클라이언트가 이를 해석하여 화면에 표시하기까지의 실행 흐름과 처리 메커니즘을 서술한다. 이 문서는 프론트엔드와 백엔드 두 영역에 동시에 적용되는 공통 규격이다.

## 1. 서버 검증 계층과 유효성 검증 경계

동일한 요청이라도 세 검증 지점을 거치며 각 지점이 보호하는 범위와 반환 형식이 다르다.

```text
요청 ─▶ [DTO]          형식 오류           → 필드 목록, 공통 에러 코드
         │ 통과
         ▼
       [application]   상태 불일치         → 모듈 고유 에러 코드
         │ 통과
         ▼
       [domain]        불변식 위반         → 도메인 메시지, 공통 에러 코드
         │ 통과
         ▼
       저장
```

| 구분 | DTO 검증 | 도메인 검증 |
| :--- | :--- | :--- |
| **검증 대상** | HTTP 요청 데이터의 형식 적합성 | 도메인 객체의 생성 및 존재 가능성 |
| **판정 시점** | 컨트롤러 진입 전 | 도메인 객체 생성 순간 |
| **보호 범위** | HTTP 요청 진입 경로 | 모든 객체 생성 경로 (배치, 이벤트 포함) |
| **필드 에러 목록** | 제공함 | 제공하지 않음 |

**두 검증 계층이 공존하는 것은 중복이 아니다.** DTO 검증은 인바운드 HTTP 요청을 검증하고 도메인 검증은 도메인 객체가 생성되는 모든 실행 경로를 보호한다. 배치 작업처럼 컨트롤러를 거치지 않는 실행 경로에서는 도메인 검증만 동작한다. 반대로 DTO 검증을 생략하면 필드 단위 오류 피드백이 불가능해지고 비즈니스 트랜잭션이 시작된 이후에야 400 오류가 발생한다.

검증 기준이 되는 제약 조건과 오류 문구는 값 객체(Value Object)에 정의하고 DTO가 이를 참조한다. **검증은 두 계층에서 각각 수행되지만 규칙의 단일 원본은 한곳에서 관리한다.**

## 2. 에러 코드 체계

`code`는 클라이언트가 분기 처리에 사용하는 계약이다. **문구는 변경될 수 있지만 코드는 불변이다.**

모듈별로 에러 코드 열거형을 정의하고 HTTP 상태 코드와 오류 문구를 함께 선언한다. 코드 문자열은 `<모듈>_<사유>` 형식이다. 열거형 정의 자체가 등록부 역할을 수행하므로, 접두사 등록부를 문서로 별도 관리하지 않는다.

**모듈 열거형에는 해당 도메인 고유의 에러 코드만 선언한다.** 잘못된 요청, 리소스 충돌, 시스템 오류 등 공통 예외는 공용 기반 패키지에 정의하고 모듈 확장 시 복제하지 않는다.

### 문제 요약 필드 제외 정책

RFC 9457의 `title`은 문제 유형에 대한 정적 요약값이다. 클라이언트의 분기 기준은 `code`이며 사용자 대상 메시지는 `detail`에 담기므로, 열거형에 별도 요약 문구를 두면 동일한 문장이 응답에 중복 포함된다. 상태 코드 기본 명칭은 프레임워크가 자동 채우도록 위임한다.

### 자원 열거 방지 정책

사유를 세분화하되 **에러 코드가 자원의 존재 여부를 노출하는 정보 누출(Resource Enumeration) 취약점이 되지 않도록 방어한다.** 대상 자원이 존재하지 않는 경우와 접근 권한이 없는 경우를 서로 다른 에러 코드로 분기하면, 악의적인 사용자가 식별자를 무차별 대입하여 자원 존재 여부를 탐지할 수 있다. 따라서 두 경우 모두 동일한 에러 코드로 응답한다.

## 3. 오류 응답 구조와 직렬화 형식

```json
{
  "status": 400,
  "detail": "제목을 입력해 주세요",
  "code": "COMMON_INVALID_REQUEST",
  "traceId": "...",
  "errors": [
    { "field": "title", "message": "제목을 입력해 주세요" }
  ]
}
```

필드 이름을 단일 문자열로 결합할 경우 서버 문구 변경 시 클라이언트 파싱 오류가 발생하므로, **DTO 검증 실패는 배열 구조를 유지하여 직렬화한다.**

입력값을 에러 응답에 그대로 반사할 경우 발생하는 민감 정보 노출을 방지하기 위해, **필드 이름과 유효성 검증 메시지만 전달하고 사용자가 입력한 원본 값은 포함하지 않는다.**

전역 예외 처리기(`@RestControllerAdvice`)는 컨트롤러 진입 이전인 서블릿 필터 단계의 실패를 처리하지 못한다. 서블릿 기본 오류 페이지가 반환되면 클라이언트의 일관된 응답 처리가 불가능해지므로, 필터에서 실패 응답을 반환할 때는 동일한 RFC 9457 형식을 생성하는 전용 컴포넌트를 경유하여 응답한다.

## 4. 오류 메시지 소유권과 클라이언트 해석 기준

**서버는 코드와 메시지를 함께 반환하고 클라이언트는 에러 코드를 우선하여 사용자 메시지에 매핑한다.**

```ts
const text = MESSAGES[problem.code] ?? problem.detail;
```

에러 코드가 안정적인 계약으로 기능하므로 서버는 세부 문구를 변경할 수 있으며, 클라이언트는 화면 맥락에 적합한 문구를 매핑하여 표시하되 매핑되지 않은 신규 코드가 수신되어도 서버 `detail` 메시지를 기본 노출하므로 화면이 빈 상태로 남지 않는다.

도메인 불변식 위반은 공통 오류 코드를 사용하므로 클라이언트 분기 대상이 아니며, 서버가 전달한 메시지가 화면에 직접 노출된다. 도메인이 발행하는 예외 메시지는 최종 사용자에게 전달되므로 테이블명이나 내부 식별자 같은 구현 세부사항을 포함하지 않는다.

## 5. 클라이언트 오류 처리 경로와 계층별 책임

오류 처리가 화면 단위로 분산 구현되면 표시 일관성이 저하되고 예외 누락이 발생한다. 공통 인프라 계층과 화면 컴포넌트 간의 책임을 명확히 분리한다.

| 계층 | 책임 |
| :--- | :--- |
| HTTP 인터셉터 | 응답 해석, 인증 만료 처리, 재시도, 관측 도구 전송 |
| 전역 에러 핸들러 | 미처리 예외 포착, 모니터링 시스템 보고 |
| 화면 컴포넌트 | 사용자 피드백 표시 위치와 UI 표현 방식 결정 |

**인터셉터는 발생한 오류의 유형을 판별하고 화면은 노출할 내용과 방식을 결정한다.** 인터셉터가 UI 표시를 직접 제어하면 화면 컴포넌트의 상태 제어권이 훼손된다.

| 분류 | 처리 위치 | 사용자 피드백 |
| :--- | :--- | :--- |
| 네트워크 실패 | 인터셉터가 재시도 후 화면에 전달 | 연결 오류 안내 및 재시도 버튼 |
| 인증 만료 | 인터셉터가 세션 정리 후 로그인 이동 | 세션 만료 안내 |
| 권한 없음 | 화면 컴포넌트 | 접근 불가 안내 |
| 입력 오류 | 화면 컴포넌트 | 필드별 인라인 에러 메시지 |
| 서버 오류 | 화면 컴포넌트 | 일시적 시스템 장애 안내 및 재시도 버튼 |

화면 컴포넌트별로 개별 처리할 경우 발생하는 동시 다발적 라우팅 충돌을 방지하기 위해, **인증 만료(401)에 한하여 인터셉터가 세션 정리와 로그인 페이지 이동을 전담한다.**

### 오류 표시 위치와 화면 렌더링 범위

| 범위 | 표시 위치 |
| :--- | :--- |
| 화면 전체 렌더링 불가 | 화면 전체를 에러 상태 UI로 대체 |
| 화면 일부 영역 조회 실패 | 해당 영역만 인라인 에러 상태로 대체 |
| 사용자 명령 실패 | 상호작용 지점 인접 위치에 피드백 표시 |
| 폼 입력 유효성 실패 | 해당 입력 필드 하단에 메시지 표시 |

목록 조회가 실패했을 때 토스트 알림만 띄우고 빈 목록을 표시하면 사용자가 데이터를 정상적인 빈 상태로 오인한다. 실패가 발생한 영역은 오류 상태임을 해당 위치에 명시하고 재시도 수단을 함께 제공한다.

**자동 재시도는 조회(GET) 요청에만 한정하여 적용한다.** 상태 변경 요청에 자동 재시도를 적용할 경우 중복 처리가 발생한다.

### 사용자 대상 오류 문구 구성 및 내부 정보 격리

실패 원인과 사용자가 취할 수 있는 후속 조치를 간결한 사실 위주로 기술한다. 기술 용어나 HTTP 상태 코드를 직접 노출하지 않으며, 방어적인 사과 문구를 배제한다.

클라이언트가 상태 코드에만 의존하여 문구를 임의 생성하면 서버가 전달하는 세부 맥락이 소실되므로, **서버가 사용자 대상 메시지를 제공하는 경우 이를 우선하여 표시한다.**

클라이언트에 노출하는 내부 진단 정보는 **추적 식별자(`traceId`) 하나로 한정한다.** 사용자가 추적 식별자를 전달하면 운영자가 서버 로그에서 해당 요청을 추적할 수 있다. 스택 트레이스, 데이터베이스 쿼리, 내부 시스템 식별자는 응답 및 화면에 일절 노출하지 않는다.
