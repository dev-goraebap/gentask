# 프론트엔드 03. 데이터 흐름과 상태 동기화

서버의 데이터가 화면에 도달하고 화면의 변경이 서버에 전달되어 반영되기까지의 데이터 흐름과 처리 메커니즘을 서술한다. 세그먼트 배치 규격은 빌딩 블록 뷰가 정의하며, 검증 가능한 세부 코딩 규칙은 코드 스타일 가이드가 다룬다.

## 1. 상태 분류와 관리 위치

상태는 **원본이 어디에 위치하는가**에 따라 구분된다. 이 구분이 데이터의 관리 위치와 동기화 방식을 결정한다.

| 구분 | 원본 위치 | 화면이 보유한 데이터 | 관리 위치 |
| :--- | :--- | :--- | :--- |
| **서버 상태** | 서버 | 사본 (시간 경과에 따라 만료 가능) | 조회 지점의 `api` 세그먼트 |
| **클라이언트 상태** | 화면 (컴포넌트) | 원본 | 해당 슬라이스의 `model` 세그먼트 |
| **URL 상태** | 브라우저 히스토리 | 원본 | Angular Router |

**서버 상태는 항상 만료될 수 있는 사본으로 취급한다.** 조회 결과를 컴포넌트 시그널에 복사하여 직접 수정하면 서버와 화면 간의 불일치를 추적할 수 없으므로, 데이터 변경은 반드시 서버 명령을 거쳐 재조회하는 흐름으로 동기화한다.

## 2. 서버 상태 동기화 단계와 기본 정책

서버 데이터와 클라이언트 사본의 일관성을 유지하는 수단에는 단계가 있다.

| 단계 | 수단 | 획득하는 이점 |
| :--- | :--- | :--- |
| 1 | 화면 진입 시마다 조회 | — |
| 2 | 진입 조회 + 변경 후 재조회 | 사용자 변경 사항의 화면 반영 |
| 3 | 캐시 및 키 기반 무효화 | 동일 데이터의 중복 네트워크 요청 제거 |
| 4 | 캐시 우선 노출 후 백그라운드 갱신 (SWR) | 화면 전환 대기 시간 최소화 |
| 5 | 서버 푸시 (Websocket / SSE) | 타 사용자의 변경 사항 실시간 반영 |

**본 아키텍처는 2단계를 기본 정책으로 채택한다.** 조회는 라우트 스코프의 `httpResource`가 담당하고, 변경 명령이 성공하면 호출부가 동일 조회를 다시 실행하여 화면을 갱신한다.

동기화 단계가 올라갈수록 응답 속도와 사용자 편의가 향상되지만 데이터 일관성 관리의 복잡도와 정합성 위험이 증가한다. 1·2단계는 별도의 클라이언트 캐시를 유지하지 않으므로 만료된 사본이 화면에 노출될 위험이 없다. 3단계부터는 캐시 무효화 전략이 요구되며, 4단계는 갱신 시점 제어를 도구에 위임하게 되고, 5단계는 네트워크 단절 시의 복구 메커니즘을 추가로 다루어야 한다. 정량적 측정으로 복잡도 도입의 필요성이 입증되기 전까지는 2단계를 기본 원칙으로 유지한다.

## 3. 조회 처리 경로

```text
라우트 providers ─▶ 조회 서비스(httpResource) ─▶ status 신호 ─▶ 화면
        │                                            │
        └ 라우트 이탈 시 인스턴스 소멸                 └ loading · reloading · error
```

데이터 조회는 `httpResource`로 일원화한다. 화면 진입에 필수적인 데이터도 동일한 방식을 사용한다. 진입 필수 여부는 데이터 접근 도구가 아닌 **서비스의 소유 스코프**와 **대기 상태의 표현 방식**을 결정한다.

| 조회 구분 | 소유 주체 | 대기 상태 표현 |
| :--- | :--- | :--- |
| 화면 진입 필수 | 라우트 스코프 서비스 | 화면 전체를 베일(Veil)로 오버레이 |
| 부가 데이터 (진입 비필수) | 사용하는 화면의 `api` 세그먼트 | 해당 영역 내부 인디케이터 표시 |

**라우트의 계층 깊이가 서비스의 수명주기를 결정한다.** 진입 필수 조회를 담당하는 서비스는 해당 라우트의 `providers`에 등록한다. 사용자가 라우트 구역을 벗어나면 서비스 인스턴스가 소멸하여 만료된 사본이 남지 않으며, 하위 라우트 화면들이 동일 인스턴스를 공유하므로 같은 데이터를 화면마다 중복 요청하지 않는다.

```ts
@Injectable()
export class TaskList {
  private readonly resource = httpResource<readonly Task[]>(() => ENDPOINTS.tasks);

  readonly tasks = computed(() => (this.resource.hasValue() ? this.resource.value() : []));
  readonly status = this.resource.status;

  reload(): void {
    this.resource.reload();
  }
}
```

### 신호 기반 조회 채택 근거

라우터 리졸버(Resolver)는 로딩 및 에러 상태가 라우터 내부에 캡슐화되어 컴포넌트가 참조할 수 있는 시그널이 노출되지 않으며, 데이터 재조회를 위해 라우터 네비게이션을 다시 실행해야 한다. 반면 `httpResource`는 대기와 실패 상태를 `status` 시그널로 직접 노출하며, 최초 조회와 재조회의 구분을 프레임워크 수준에서 제공한다.

리졸버가 제공하던 '데이터 수신 완료 후 화면을 표시하여 불완전한 렌더링을 방지한다'는 목적은 화면 계층의 베일 메커니즘을 통해 동일하게 달성한다. 조회가 완료되기 전까지는 빈 상태 UI를 노출하지 않고 베일로 화면을 보호한다.

### 최초 로딩과 재로딩 상태 분리

`loading`은 최초 조회이거나 요청 파라미터가 변경된 상태를 나타내고, `reloading`은 `reload()` 호출을 통한 명시적 재조회 상태를 나타낸다. 두 상태를 동일한 분기로 처리하면 재조회 시마다 화면 영역이 비워졌다가 다시 렌더링되는 화면 깜빡임이 발생한다. `reloading` 상태 동안 `httpResource`는 기존 데이터를 유지하므로, 화면은 이전 값을 유지한 채 갱신 인디케이터만 중첩하여 표시한다.

## 4. 명령 처리 경로

```text
화면 ─▶ 명령 서비스(HttpClient) ─▶ 성공 ─▶ resource.reload() ─▶ 재조회 실행
                                    │
                                    └ 실패 시 예외 발생 및 재조회 중단
```

상태 변경 요청에는 `HttpClient`를 사용한다. `httpResource`는 읽기 전용 데이터 조회용이며 요청 파라미터 변경 시 진행 중인 작업을 취소하므로, 상태 변경 작업이 중간에 중단되는 문제를 방지하기 위함이다.

**명령 메서드는 연관된 조회를 소유한 서비스 클래스에 함께 캡슐화한다.** 조회 리소스와 해당 조회를 무효화하는 명령들을 단일 클래스에서 관리하며, 명령 처리가 성공하면 내부 리소스의 `reload()`를 직접 호출한다. 이를 통해 호출부 컴포넌트가 재조회 시점을 별도로 관리하지 않도록 책임을 은닉한다.

```ts
async setCompleted(id: string, completed: boolean): Promise<void> {
  await this.patch(ENDPOINTS.taskCompletion(id), { completed });
  this.resource.reload();
}
```

**조회 없이 명령만 독립적으로 호출하는 사용처가 발생하면 명령 서비스를 분리한다.** `httpResource`는 인스턴스 생성 시점에 즉시 조회를 발행하므로, 단일 서비스에 결합된 상태에서 명령만 주입받으면 불필요한 조회가 함께 실행되기 때문이다(예: 로그인 화면에서 인증 명령만 필요하고 내 정보 조회가 불필요한 경우). 분리 기준은 개념적 구분이 아닌 **독립적인 호출부의 존재 여부**이다.

### 계층 간 무효화 메커니즘

변경을 수행하는 계층(`features`)과 조회를 소유하는 계층(`pages`)은 계층 구조상 상호 직접 참조할 수 없다. 이를 위해 **공통 무효화 버스(`InvalidationBus`)를 `shared` 계층에 배치한다.** 이벤트 키 기반의 시그널을 매개로 통신하므로 계층 간 직접적인 참조 없이 조회를 무효화한다.

```ts
const tick = inject(InvalidationBus).tick('task');
const list = httpResource<TaskListResponse>(() => {
  tick();                                    // 신호 변경 시 자동으로 재요청 실행
  return `/api/tasks?page=${page()}`;
});
```

### 낙관적 업데이트의 제한적 적용

낙관적 업데이트(Optimistic Update)는 요청 실패 시의 롤백 처리와 그사이에 발생한 다른 상태 변경과의 충돌 조정 경로를 추가로 구현해야 한다. 따라서 기본 정책은 서버 응답 완료 후 화면을 갱신하는 방식을 따르며, 복잡도 감수의 이점이 측정으로 입증된 특정 화면에 한해서만 결정 기록(ADR)을 작성하고 예외적으로 적용한다.

## 5. 대기 상태 표현 정책과 베일 메커니즘

**완전하게 렌더링 가능한 화면만 사용자에게 노출한다.** 부분적으로 렌더링된 화면이나 순차적인 레이아웃 이동(Layout Shift)을 방지하는 것이 대기 표현의 기본 원칙이다.

전통적인 브라우저 탐색 모델에서는 다음 문서가 완전히 준비될 때까지 이전 화면을 유지하다가 교체한다. 단일 페이지 애플리케이션(SPA) 환경에서도 조회 상태 신호와 베일(Veil) 컴포넌트를 통해 이 일관성을 보장한다.

### 상황별 대기 표현 정책

| 구분 | 대기 표현 |
| :--- | :--- |
| 화면 전환 (지연 청크) | 베일 (셸이 라우터 이벤트로 표시) |
| 진입 데이터의 최초 조회 | 베일 (화면이 자체 조회 상태로 표시) |
| 화면 내 갱신 (필터 · 정렬 · 페이지 · 재조회) | 이전 내용 유지 + 인라인 인디케이터 |
| 오버레이 내부 조회 | 크기 트랜지션 (베일 비적용) |
| 덧붙는 로딩 (무한 스크롤) | 하단 인라인 인디케이터 |
| 명령 실행 | 동작을 유발한 버튼 내부 진행 표시 |

상황별 표현이 갈리는 기준은 **이전 상태의 시각적 맥락 유지 가능 여부**이다. 오버레이는 여는 행위 자체가 즉각적인 피드백이며, 덧붙는 로딩과 화면 내 갱신은 기존 콘텐츠가 시각적 기준점 역할을 한다. 명령 실행은 화면 전체가 아닌 해당 사용자 액션에 대한 피드백이 필요하다.

### 베일과 인디케이터 판정 기준

**경로(Path)가 변경되면 베일을 적용하고, 쿼리 파라미터만 변경되면 인디케이터를 적용한다.** `NavigationStart` 시점에 현재 URL과 대상 URL의 경로 세그먼트를 비교하여 자동으로 판정한다. 필터, 정렬, 페이징 상태를 URL 쿼리 파라미터로 관리하는 결정이 이 판정 메커니즘을 성립시키는 기반이다.

화면 내 갱신에 베일을 적용하지 않는 이유는 세 가지이다. 첫째, 사용자가 방금 조작한 컨트롤이 가려지는 것을 방지한다. 둘째, 체크박스나 필터를 연속으로 조작하는 입력을 차단하지 않는다. 셋째, 헤더나 테이블 컬럼 등 레이아웃 구조가 유지되므로 전체 차단이 불필요하다.

### 대기 시간 정책과 임계값

| 설정값 | 기본값 | 역할 |
| :--- | :---: | :--- |
| `--wait-delay` | 200ms | 이 시간 안에 응답이 완료되면 베일을 노출하지 않음 |
| `--wait-min` | 400ms | 베일이 노출된 경우 깜빡임 방지를 위해 최소 유지되는 시간 |

대기 시간 정책은 베일 컴포넌트가 중앙에서 관리한다. 화면마다 개별 값을 적용하면 동일한 네트워크 대기에서도 일관성 없는 시각 경험이 발생하기 때문이다. 지연 시간(200ms)을 두는 이유는 극히 짧은 대기에서 인디케이터가 순간적으로 노출되었다가 사라지는 시각적 소음을 방지하기 위함이며, 사용자 인지 연구에 따르면 500ms 미만의 구간에서는 표시자 없는 빈 상태가 더 빠르게 인지된다.

**에러 발생 시에는 최소 유지 시간(400ms)을 적용하지 않고 즉시 베일을 해제하여 에러 상태로 전환한다.** 실패 피드백을 지연시킬 이유가 없기 때문이다.

### 빈 상태 UI의 렌더링 시점

빠른 응답은 지연 시간(200ms) 내에 완료되어 베일 없이 바로 데이터가 렌더링된다. 이때 조회가 진행 중인 찰나에 빈 상태 안내를 먼저 렌더링하면 '데이터 없음'이 깜빡인 후 목록으로 전환되는 결함이 발생한다. 따라서 목록 화면과 빈 상태 UI는 조회가 완전히 완료된 이후에만 렌더링한다. 조회 실패를 빈 데이터 상태로 표시하지 않는 것 또한 사용자가 통신 장애를 데이터 부재로 오인하는 문제를 방지하기 위함이다.

### 베일 적용 범위와 프레임 경계

베일은 콘텐츠 영역만 덮으며 전역 네비게이션은 제외한다. 대기 중에도 사용자가 다른 화면으로 자유롭게 이동할 수 있어야 하기 때문이다.

| 골격 | 덮는 곳 | 덮지 않는 곳 |
| :--- | :--- | :--- |
| 셸 직속 화면 | 셸의 본문 영역 | 상단 바, 푸터, 하단 네비게이션 |
| 사이드바를 가진 프레임 | 프레임의 콘텐츠 열 | 상단 바, 푸터, 하단 네비게이션, 사이드바 |

사이드바는 해당 하위 영역의 이동 수단이므로 베일 적용 범위에서 제외한다. 뷰포트 전체를 덮는 요소로 구현하지 않고 명시적인 콘텐츠 기준 컨테이너를 지정한다. 뷰포트 전체를 덮으면 크롬 영역까지 가려지며, `z-index`로 크롬을 제외하는 방식은 레이아웃 컴포넌트 추가 시 유지보수 누락을 유발하기 때문이다.

셸과 프레임의 베일 영역이 중첩될 경우 내부 프레임이 우선권을 갖고 셸의 베일은 비활성화된다. 이때 셸이 현재 경로를 직접 검사해 분기하지 않는다. 셸이 개별 화면 경로를 알게 되면 레이아웃 캡슐화 원칙이 훼손되기 때문이다. 셸은 내부 프레임의 활성화 여부만 확인한다.

## 6. URL 상태 관리와 라우터 연동

리소스 식별자는 경로 파라미터에, 목록의 필터와 정렬, 페이지, 탭 상태는 쿼리 파라미터에 배치한다. 새로고침 시 상태 복원, 브라우저 뒤로가기 지원, 링크 공유가 별도 추가 코드 없이 동작하기 때문이다. 컴포넌트 시그널에 보관하면 세 가지 기능을 개별 구현해야 하며, 라우터가 관여하지 않아 베일과 인디케이터의 판정도 성립하지 않는다.

읽기는 라우트 입력 바인딩으로 받는다. 시그널이므로 조회의 요청 계산식에 그대로 연결할 수 있다.

```ts
export class TaskDetailPage {
  readonly id = input.required<string>();                     // 경로 파라미터
  readonly page = input(1, { transform: numberAttribute });   // 쿼리 파라미터
}
```

**상태 변경에 따른 URL 갱신은 히스토리 교체(replace)로 처리한다.** 필터를 변경하는 것은 라우터 이동이며, 브라우저 히스토리를 적재하지 않도록 현재 항목을 덮어쓴다. 히스토리를 적재하면 필터를 조작한 횟수만큼 뒤로가기를 실행해야 이전 화면으로 복귀할 수 있기 때문이다.

**모달 오버레이 오픈과 필터 조작은 히스토리 관리 규칙이 다르다.** 오버레이를 열 때는 히스토리를 적재(push)해야 뒤로가기 시 오버레이가 닫히며, 내부 입력값 반영은 적재하지 않아야(replace) 뒤로가기가 입력 문자 단위로 되감기지 않는다. 라우터를 호출하는 진입점은 일원화하여 관리한다. 오버레이가 자체적으로 URL을 변경하면 열림 상태의 진실 공급원이 분산되어 히스토리 추적이 어려워지기 때문이다.

### 목록·상세 동시 노출 화면의 식별자 배치

목록과 상세를 단일 화면에 나란히 배치하려면 **선택된 항목 식별자를 쿼리 파라미터에 배치한다.** 식별자를 경로에 두는 일반 규칙의 예외이다.

경로가 변경되면 라우터가 이전 라우트의 컴포넌트를 언마운트한다. 목록과 상세가 서로 다른 경로를 가지면 상세를 여는 순간 목록 컴포넌트가 언마운트되어 동시 노출이 불가능하며, 화면 전환 베일이 남아 있어야 할 목록 영역까지 덮기 때문이다.

| 상세 화면 오픈 시 | 식별자 배치 위치 |
| :--- | :--- |
| 목록이 사라져도 되는가 | 경로 파라미터 |
| 목록이 곁에 남아야 하는가 | 쿼리 파라미터 |

**오버레이 오픈 시에는 히스토리를 적재(push)하고, 닫을 때는 교체(replace)한다.** 오픈 시 적재해야 뒤로가기가 오버레이 닫기로 동작한다. 닫을 때 히스토리를 다시 적재하면 닫힌 직후 뒤로가기 시 방금 닫은 오버레이가 재오픈되기 때문이다.

**민감 정보는 URL에 포함하지 않는다.** 브라우저 히스토리, HTTP Referer 헤더, 서버 접근 로그에 잔존하기 때문이다.

## 7. 폼 데이터 검증과 오류 처리

**프론트엔드 검증은 서버 검증을 대체하지 않는다.** 프론트엔드 검증의 목적은 즉시 피드백이며, 클라이언트 코드는 조작 가능하므로 검증을 우회한 요청이 서버에 도달할 수 있다.

동일한 유효성 검증 규칙이 양쪽에 존재하는 것은 정상적인 방어 계층이며 제거 대상이 아니다.

| 구분 | 프론트엔드 | 서버 |
| :--- | :--- | :--- |
| **목적** | 즉시 피드백 | 데이터 무결성 |
| **신뢰 수준** | 신뢰하지 않음 | 최종 판정 |
| **누락 시** | 사용자 경험 저하 | 데이터 손상 |

중복을 제거하기 위해 프론트엔드 검증을 생략하면 사용자가 제출 후에야 오류를 인지하게 되고, 서버 검증을 생략하면 데이터 무결성이 손상된다.

권한에 따른 입력 허용 여부와 타 데이터와의 정합성은 프론트엔드가 단독으로 판정할 수 없다. 판정에 필요한 데이터가 화면에 없거나 변조 가능하기 때문이다. 중복 확인처럼 서버 조회가 필요한 검증은 입력 중 비동기 검증으로 처리하되 값 확정 시점에만 질의한다. 그렇지 않으면 키 입력마다 불필요한 네트워크 요청이 발생한다.

### 검증 오류 응답 처리와 필드 매핑

제출 실패 응답 수신 시 서버가 전달한 필드별 에러 메시지를 해당 필드에 표시하고, 폼 전역 오류는 상단 영역에 표시한다. 서버 응답의 에러 필드명과 폼 필드의 매핑은 공통 에러 처리 계층에서 일원화하여 처리한다.

검증 오류는 해당 필드에서 포커스가 벗어난(`blur`) 이후에 표시한다. 입력 도중 즉시 표시하면 작성을 방해하기 때문이다. 제출 실패 시 첫 번째 오류 필드로 포커스를 자동 이동한다.

## 8. OpenAPI 기반 타입 자동 생성과 계약 관리

```text
백엔드 OpenAPI 명세 ──(openapi-typescript)──▶ clients/packages/api-types ──▶ 화면과 에이전트 도구
```

서버 응답과 요청의 타입은 백엔드 OpenAPI 명세로부터 자동 생성하며 수동 작성하지 않는다. 수동으로 작성하면 서버 계약이 변경되어도 정적 컴파일을 통과하여 런타임 장애로 이어지기 때문이다.

**생성된 타입 산출물은 형상 관리(Git)에 포함하여 커밋한다.** API 계약의 변경 이력이 Pull Request의 코드 변경 차이(Diff)에 명확히 드러나며, 필드 삭제나 타입 변경을 코드 병합 전에 리뷰 단계에서 식별할 수 있다. 또한 CI 및 로컬 빌드 시 백엔드 서버 기동 없이도 독립적인 빌드가 가능해진다.

**생성된 타입을 상위 계층에서 화면 전용 모델로 재변환하지 않고 직접 사용한다.** 단순 필드 전달 목적의 매핑 계층을 배제하여 백엔드 필드 변경 시의 수정 비용을 최소화하기 위함이다. 백엔드 스키마 변경이 화면 코드까지 전파되고 서버 명명 체계가 화면에 노출되는 트레이드오프가 발생하지만, 불필요한 수동 매핑 계층의 유지보수 비용을 제거하는 이점이 우선한다.

### API 계약 변경 영향과 대응

| 변경 | 프론트 영향 | 대응 |
| :--- | :--- | :--- |
| 응답 필드 추가 | 없음 | 타입 파일 재생성 |
| 필드 삭제 · 타입 변경 | 컴파일 오류 | 사용처 코드 수정 |
| 엔드포인트 경로 변경 | **런타임 실패** | 경로 상수 수정 |

엔드포인트 경로 변경은 문자열 기반이므로 컴파일 단계에서 자동으로 검출되지 않는다. 따라서 API 경로는 개별 호출부에 분산하지 않고 전역 경로 상수로 집중 관리한다. 타입 재생성 결과와 화면 코드의 수정은 단일 커밋에 담아 빌드 무결성을 유지한다.

### 프로토타입 Mock에서 실제 API 연동으로의 전환

프로토타입 개발 단계에서는 InjectionToken 뒤에 Mock 구현체를 배치하며, 해당 인터페이스의 타입 정의가 백엔드 API 명세의 요구사항 입력으로 기능한다. 백엔드 연동 시점에 OpenAPI 명세를 전달받아 타입을 생성한 후, **Mock 인터페이스와 생성된 타입을 대조하여 스펙 누락 및 불일치 사항을 식별**한다.

연동 전환이 완료되면 Mock 구현체와 인터페이스를 제거한다. 단일 구현체만 존재하는 불필요한 간접 참조 계층을 정리하고, 계약 검증 책임을 자동 생성된 정적 타입 시스템으로 이관한다.
