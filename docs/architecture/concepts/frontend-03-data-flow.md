# 프론트엔드 03. 데이터가 오가는 길

서버의 데이터가 화면에 도달하고 화면의 변경이 서버에 전달되어 반영되기까지의 데이터 흐름과 처리 메커니즘을 서술합니다. 세그먼트 배치 규격은 빌딩 블록 뷰가 정의하며, 검증 가능한 세부 코딩 규칙은 코드 스타일 가이드가 다룹니다.

## 1. 세 종류의 상태

상태는 **원본이 어디에 위치하는가**에 따라 구분됩니다. 이 구분이 데이터의 관리 위치와 동기화 방식을 결정합니다.

| 구분 | 원본 위치 | 화면이 보유한 데이터 | 관리 위치 |
| :--- | :--- | :--- | :--- |
| **서버 상태** | 서버 | 사본 (시간 경과에 따라 만료 가능) | 조회 지점의 `api` 세그먼트 |
| **클라이언트 상태** | 화면 (컴포넌트) | 원본 | 해당 슬라이스의 `model` 세그먼트 |
| **URL 상태** | 브라우저 히스토리 | 원본 | Angular Router |

**서버 상태는 항상 만료될 수 있는 사본으로 취급합니다.** 조회 결과를 컴포넌트 신호(Signal)에 복사해 직접 수정하면 서버와 화면 간의 불일치를 추적할 수 없게 되므로, 데이터 변경은 반드시 서버 명령을 거쳐 다시 조회하는 흐름으로 동기화합니다.

## 2. 사본을 원본과 맞추는 단계

서버 데이터와 클라이언트 사본의 일관성을 유지하는 수단에는 단계가 있습니다.

| 단계 | 수단 | 획득하는 이점 |
| :--- | :--- | :--- |
| 1 | 화면 진입 시마다 조회 | — |
| 2 | 진입 조회 + 변경 후 재조회 | 사용자 변경 사항의 화면 반영 |
| 3 | 캐시 및 키 기반 무효화 | 동일 데이터의 중복 네트워크 요청 제거 |
| 4 | 캐시 우선 노출 후 백그라운드 갱신 (SWR) | 화면 전환 대기 시간 최소화 |
| 5 | 서버 푸시 (Websocket / SSE) | 타 사용자의 변경 사항 실시간 반영 |

**이 아키텍처는 2단계를 기본 정책으로 채택합니다.** 조회는 라우트 스코프의 `httpResource`가 담당하고, 변경 명령이 성공하면 호출부가 동일 조회를 다시 실행하여 화면을 갱신합니다.

단계가 올라갈수록 응답 속도와 사용자 편의를 얻는 대신 데이터 일관성 관리의 복잡도가 증가합니다. 1·2단계는 별도의 클라이언트 캐시를 유지하지 않으므로 만료된 사본이 화면에 노출될 위험이 없습니다. **가장 단순한 단계가 가장 정확하며, 위로 올라가며 사는 것은 속도이고 파는 것은 정확성입니다.** 3단계부터는 캐시 무효화 전략이 요구되며, 4단계는 갱신 시점 제어를 도구에 위임하게 되고, 5단계는 네트워크 단절 시의 복구 메커니즘을 추가로 다루어야 합니다. 따라서 측정으로 복잡도 도입의 필요성이 입증되기 전까지는 2단계를 유지합니다.

## 3. 조회가 흐르는 길

```text
라우트 providers ─▶ 조회 서비스(httpResource) ─▶ status 신호 ─▶ 화면
        │                                            │
        └ 라우트 이탈 시 인스턴스 소멸                 └ loading · reloading · error
```

데이터 조회는 `httpResource`로 통일합니다. 화면 진입에 필수적인 데이터도 동일한 방식을 사용합니다. 진입 필수 여부는 데이터 접근 도구가 아닌 **서비스의 소유 스코프**와 **대기 상태의 표현 방식**을 결정합니다.

| 조회 구분 | 소유 주체 | 대기 상태 표현 |
| :--- | :--- | :--- |
| 화면 진입 필수 | 라우트 스코프 서비스 | 화면 전체를 베일(Veil)로 오버레이 |
| 부가 데이터 (진입 비필수) | 사용하는 화면의 `api` 세그먼트 | 해당 영역 내부 인디케이터 표시 |

**라우트의 깊이가 서비스의 수명주기를 결정합니다.** 진입 필수 조회를 담당하는 서비스는 해당 라우트의 `providers`에 등록합니다. 사용자가 라우트 구역을 벗어나면 서비스 인스턴스가 소멸하여 만료된 사본이 남지 않으며, 하위 라우트 화면들이 동일 인스턴스를 공유하므로 같은 데이터를 화면마다 중복 요청하지 않습니다.

```ts
@Injectable()
export class TaskList {
  private readonly resource = httpResource<readonly Task[]>(() => ENDPOINTS.tasks);

  readonly tasks = computed(() => (this.resource.hasValue() ? this.resource.value() : []));
  readonly status = this.resource.status;

  reload(): void {
    this.resource.reload();
  }
}
```

### 리졸버 대신 신호 기반 조회를 사용하는 이유

리졸버(Resolver)는 로딩 및 에러 상태가 라우터 내부에 캡슐화되어 컴포넌트가 참조할 수 있는 신호가 노출되지 않으며, 데이터 재조회를 위해 라우터 네비게이션을 다시 실행해야 합니다. 반면 `httpResource`는 대기와 실패 상태를 `status` 신호로 직접 노출하며, 최초 조회와 재조회의 구분을 프레임워크 수준에서 제공합니다.

리졸버가 제공하던 '데이터 수신 완료 후 화면을 표시하여 불완전한 렌더링을 방지한다'는 목적은 화면 계층의 베일 메커니즘을 통해 동일하게 달성합니다. 조회가 완료되기 전까지는 빈 상태 UI를 노출하지 않고 베일로 화면을 보호합니다.

### loading과 reloading의 분리

`loading`은 최초 조회이거나 요청 파라미터가 변경된 상태를 나타내고, `reloading`은 `reload()` 호출을 통한 명시적 재조회 상태를 나타냅니다. **두 상태를 동일한 분기로 처리하면 재조회 시마다 화면 영역이 비워졌다가 다시 렌더링되는 깜빡임이 발생합니다.** `reloading` 상태 동안 `httpResource`는 기존 데이터를 유지하므로, 화면은 이전 값을 유지한 채 갱신 인디케이터만 중첩하여 표시합니다.

## 4. 명령이 흐르는 길

```text
화면 ─▶ 명령 서비스(HttpClient) ─▶ 성공 ─▶ resource.reload() ─▶ 재조회 실행
                                    │
                                    └ 실패 시 예외 발생 및 재조회 중단
```

상태 변경 요청에는 `HttpClient`를 사용합니다. `httpResource`는 읽기 전용 데이터 조회용이며 요청 파라미터 변경 시 진행 중인 작업을 중단하므로, 상태 변경 작업이 중간에 취소되는 문제를 방지하기 위함입니다.

**명령 메서드는 연관된 조회를 소유한 서비스 클래스에 함께 캡슐화합니다.** 조회 리소스와 해당 조회를 무효화하는 명령들을 단일 클래스에서 관리하며, 명령 처리가 성공하면 내부 리소스의 `reload()`를 직접 호출합니다. 이를 통해 호출부 컴포넌트가 재조회 시점을 별도로 관리하지 않도록 책임을 은닉합니다.

```ts
async setCompleted(id: string, completed: boolean): Promise<void> {
  await this.patch(ENDPOINTS.taskCompletion(id), { completed });
  this.resource.reload();
}
```

**조회 없이 명령만 독립적으로 호출하는 사용처가 발생하면 명령 서비스를 분리합니다.** `httpResource`는 인스턴스 생성 시점에 즉시 조회를 발행하므로, 단일 서비스에 결합된 상태에서 명령만 주입받으면 불필요한 조회가 함께 실행됩니다(예: 로그인 화면에서 인증 명령만 필요하고 내 정보 조회가 불필요한 경우). 분리 기준은 개념적 구분이 아닌 **독립적인 호출부의 존재 여부**입니다.

### 계층 간 무효화 메커니즘

변경을 수행하는 계층(`features`)과 조회를 소유하는 계층(`pages`)은 계층 구조상 상호 직접 참조할 수 없습니다. 이를 위해 **공통 무효화 버스(`InvalidationBus`)를 `shared` 계층에 배치합니다.** 이벤트 키 기반의 신호를 매개로 통신하므로 계층 간 직접적인 참조 없이 조회를 무효화합니다.

```ts
const tick = inject(InvalidationBus).tick('task');
const list = httpResource<TaskListResponse>(() => {
  tick();                                    // 신호 변경 시 자동으로 재요청 실행
  return `/api/tasks?page=${page()}`;
});
```

### 낙관적 업데이트의 제한적 적용

낙관적 업데이트(Optimistic Update)는 요청 실패 시의 롤백 처리와 그사이에 발생한 다른 상태 변경과의 충돌 조정 경로를 추가로 구현해야 합니다. 따라서 기본 정책은 서버 응답 완료 후 화면을 갱신하는 방식을 따르며, 복잡도 감수의 이점이 측정으로 입증된 특정 화면에 한해서만 결정 기록(ADR)을 남기고 예외적으로 적용합니다.

## 5. 대기가 표현되는 자리

**완전하게 렌더링 가능한 화면만 사용자에게 노출합니다.** 부분적으로 렌더링된 화면이나 순차적인 레이아웃 이동(Layout Shift)을 방지하는 것이 대기 표현의 기본 원칙입니다.

전통적인 브라우저 탐색 모델에서는 다음 문서가 완전히 준비될 때까지 이전 화면을 유지하다가 교체합니다. 단일 페이지 애플리케이션(SPA) 환경에서도 조회 상태 신호와 베일(Veil) 컴포넌트를 통해 이 일관성을 보장합니다.

### 상황별 대기 표현 정책

| 층 | 대기 표현 |
| :--- | :--- |
| 화면 전환 (지연 청크) | 베일 (셸이 라우터 이벤트로 표시) |
| 진입 데이터의 최초 조회 | 베일 (화면이 자체 조회 상태로 표시) |
| 화면 내 갱신 (필터 · 정렬 · 페이지 · 재조회) | 이전 내용 유지 + 인라인 인디케이터 |
| 오버레이 내부 조회 | 크기 트랜지션 (베일 비적용) |
| 덧붙는 로딩 (무한 스크롤) | 하단 인라인 인디케이터 |
| 명령 실행 | 동작을 유발한 버튼 내부 진행 표시 |

상황별 표현이 갈리는 기준은 **이전 상태의 시각적 맥락 유지 가능 여부**입니다. 오버레이는 여는 행위 자체가 즉각적인 피드백이며, 덧붙는 로딩과 화면 내 갱신은 기존 콘텐츠가 시각적 기준점 역할을 합니다. 명령 실행은 화면 전체가 아닌 해당 사용자 액션에 대한 피드백이 필요합니다.

### 베일과 인디케이터의 판정

**경로(Path)가 변경되면 베일을 적용하고, 쿼리 파라미터만 변경되면 인디케이터를 적용합니다.** `NavigationStart` 시점에 현재 URL과 대상 URL의 경로 세그먼트를 비교하여 자동으로 판정합니다. 필터, 정렬, 페이징 상태를 URL 쿼리 파라미터로 관리하는 결정이 이 판정 메커니즘을 성립시키는 기반입니다.

화면 내 갱신에 베일을 적용하지 않는 이유는 세 가지입니다. 첫째, 사용자가 방금 조작한 컨트롤이 가려지는 것을 방지합니다. 둘째, 체크박스나 필터를 연속으로 조작하는 입력을 차단하지 않습니다. 셋째, 헤더나 테이블 컬럼 등 레이아웃 구조가 유지되므로 덮을 대상이 없습니다.

### 시간 정책과 임계값

| 설정값 | 기본값 | 역할 |
| :--- | :---: | :--- |
| `--wait-delay` | 200ms | 이 시간 안에 응답이 완료되면 베일을 노출하지 않음 |
| `--wait-min` | 400ms | 베일이 노출된 경우 깜빡임 방지를 위해 최소 유지되는 시간 |

대기 시간 정책은 베일 컴포넌트가 중앙에서 관리합니다. 화면마다 개별 값을 적용하면 동일한 네트워크 대기에서도 일관성 없는 시각 경험이 발생하기 때문입니다. 지연 시간(200ms)을 두는 이유는 극히 짧은 대기에서 인디케이터가 순간적으로 노출되었다가 사라지는 시각적 소음을 방지하기 위함이며, 사용자 인지 연구에 따르면 500ms 미만의 구간에서는 표시자 없는 빈 상태가 더 빠르게 인지됩니다.

**에러 발생 시에는 최소 유지 시간(400ms)을 적용하지 않고 즉시 베일을 해제하여 에러 상태로 전환합니다.** 실패 피드백을 불필요하게 지연시킬 이유가 없기 때문입니다.

### 빈 상태의 렌더링 시점

빠른 응답은 지연 시간(200ms) 내에 완료되어 베일 없이 바로 데이터가 렌더링됩니다. 이때 조회가 진행 중인 찰나에 빈 상태 안내를 먼저 렌더링하면 '데이터 없음'이 깜빡인 후 목록으로 전환되는 결함이 발생합니다. 따라서 목록 화면과 빈 상태 UI는 조회가 완전히 완료된 이후에만 렌더링합니다. 조회 실패를 빈 데이터 상태로 표시하지 않는 것 또한 사용자가 통신 장애를 데이터 부재로 오인하는 문제를 방지하기 위함입니다.

### 베일의 적용 범위와 프레임 경계

베일은 콘텐츠 영역만 덮으며 전역 네비게이션은 제외합니다. 대기 중에도 사용자가 다른 화면으로 자유롭게 이동할 수 있어야 하기 때문입니다.

| 골격 | 덮는 곳 | 덮지 않는 곳 |
| :--- | :--- | :--- |
| 셸 직속 화면 | 셸의 본문 영역 | 상단 바, 푸터, 하단 네비게이션 |
| 사이드바를 가진 프레임 | 프레임의 콘텐츠 열 | 상단 바, 푸터, 하단 네비게이션, 사이드바 |

사이드바는 해당 하위 영역의 이동 수단이므로 베일 적용 범위에서 제외합니다. 뷰포트 전체를 덮는 요소로 구현하지 않고 명시적인 콘텐츠 기준 컨테이너를 지정합니다. 뷰포트 전체를 덮으면 크롬 영역까지 가려지고, `z-index` 로 크롬을 하나씩 빼내는 방식은 크롬이 늘 때마다 함께 고쳐야 하는 값을 만들고, **빠뜨리면 조용히 가려집니다.**

셸과 프레임의 자리가 중첩될 경우 내부 프레임이 우선권을 갖고 셸의 베일은 물러납니다. 이때 셸이 현재 경로를 직접 검사해 분기하지 않습니다. 셸이 어느 화면인지 알게 되면 **호출부가 골격을 모른다는 원칙이 뒤집힙니다.** 셸은 안쪽이 자리를 가져갔는지만 묻습니다.

## 6. URL 이 소유하는 상태

리소스 식별자는 경로 파라미터에, 목록의 필터와 정렬과 페이지와 공유 대상 탭은 쿼리 파라미터에 둡니다. **이유는 구현 절약입니다** — 새로고침 복원과 뒤로가기 대응과 링크 공유가 별도 코드 없이 동작합니다. 컴포넌트 신호에 두면 이 셋을 각각 구현해야 하고, 라우터가 관여하지 않아 베일과 인디케이터의 판정도 성립하지 않습니다.

읽기는 라우트 입력 바인딩으로 받습니다. 신호이므로 조회의 요청 계산식에 그대로 넣을 수 있습니다.

```ts
export class TaskDetailPage {
  readonly id = input.required<string>();                     // 경로 파라미터
  readonly page = input(1, { transform: numberAttribute });   // 쿼리 파라미터
}
```

**쓰기는 상태 갱신이 아니라 이동입니다.** 필터를 바꾸는 것은 라우터 호출이며, 다만 히스토리를 쌓지 않도록 현재 항목을 덮습니다. 쌓으면 뒤로가기를 여러 번 눌러야 이전 화면으로 돌아갑니다.

**여는 것과 값을 바꾸는 것은 규칙이 다릅니다.** 오버레이를 여는 것은 히스토리를 쌓아야 뒤로가기가 곧 닫기가 되고, 그 안의 입력 반영은 쌓지 않아야 뒤로가기가 글자 단위로 되감기지 않습니다. 같은 파라미터라도 조작의 성격이 다릅니다. **라우터를 호출하는 곳은 하나로 둡니다** — 오버레이가 자기 주소를 직접 고치면 열림 상태의 원본이 두 곳이 되고 어느 쪽이 히스토리를 쌓는지 추적할 수 없습니다.

### 곁에 남아야 하는 화면의 식별자

목록과 상세를 한 화면에 나란히 두려면 **열린 항목을 쿼리 파라미터에 둡니다.** 식별자를 경로에 두라는 규칙의 예외입니다.

경로가 바뀌면 라우터가 이전 라우트의 컴포넌트를 언마운트합니다. 목록과 상세가 서로 다른 경로를 가지면 상세를 여는 순간 목록이 사라지므로 곁에 둘 수 없고, 전환 베일까지 관여해 남아 있어야 할 목록을 덮습니다.

| 상세를 열었을 때 | 식별자의 자리 |
| :--- | :--- |
| 목록이 사라져도 되는가 | 경로 파라미터 |
| 목록이 곁에 남아야 하는가 | 쿼리 파라미터 |

**여는 것은 히스토리에 쌓고 닫는 것은 덮습니다.** 쌓으면 뒤로가기가 곧 닫기가 되어 사용자가 기대하는 동작이 별도 구현 없이 성립합니다. 닫기는 새로운 자리가 아니므로 덮으며, **쌓으면 닫은 직후의 뒤로가기가 방금 닫은 것을 다시 엽니다.**

**민감정보는 어디에도 URL 에 두지 않습니다.** 히스토리와 리퍼러와 서버 로그에 남기 때문입니다.

## 7. 폼이 서버에 닿는 길

**프론트엔드 검증은 서버 검증을 대체하지 않습니다.** 프론트엔드 검증의 목적은 즉시 피드백이며, 클라이언트 코드는 조작 가능하므로 검증을 우회한 요청이 서버에 도달할 수 있습니다.

같은 규칙이 양쪽에 있는 것은 **정상이며 제거 대상이 아닙니다.**

| 구분 | 프론트엔드 | 서버 |
| :--- | :--- | :--- |
| **목적** | 즉시 피드백 | 데이터 무결성 |
| **신뢰 수준** | 신뢰하지 않음 | 최종 판정 |
| **누락 시** | 사용자 경험 저하 | 데이터 손상 |

**중복을 없애려고 프론트엔드 검증을 생략하면** 사용자가 제출 후에야 오류를 알게 되고, 서버 검증을 생략하면 데이터가 손상됩니다.

**프론트엔드가 판정할 수 없는 것도 있습니다.** 권한에 따른 입력 허용 여부와 다른 데이터와의 정합성은 판정에 필요한 근거가 화면에 없거나, 있어도 조작할 수 있습니다. 중복 확인처럼 서버에 물어야 하는 것은 입력 중 조회로 처리하되 값 확정 시점에만 묻습니다 — 그러지 않으면 타이핑마다 요청이 나갑니다.

### 결과가 돌아오는 자리

제출 응답이 실패면 서버가 내려준 필드별 메시지를 해당 필드에 표시하고, 필드를 특정할 수 없는 오류는 폼 상단에 둡니다. **서버 응답의 필드명과 폼 필드의 대응은 한 곳에서 처리합니다** — 각 화면이 응답을 파싱해 필드를 찾는 코드를 반복하면 응답 형식이 바뀔 때 전부 고쳐야 합니다.

오류는 해당 필드를 벗어난 뒤에 보입니다. 입력 중 즉시 띄우면 다 입력하기 전부터 빨간 메시지가 뜹니다. 제출이 실패하면 첫 오류 필드로 포커스를 옮깁니다.

## 8. 타입이 오는 길

```text
백엔드 OpenAPI 명세 ──(openapi-typescript)──▶ shared/api/generated/ ──▶ 화면
```

서버 응답과 요청의 타입은 백엔드 OpenAPI 명세로부터 자동 생성하며 수동 작성하지 않습니다. 수동으로 작성하면 서버 계약이 변경되어도 정적 컴파일을 통과하여 런타임 장애로 이어지기 때문입니다.

**생성된 타입 산출물은 형상 관리(Git)에 포함하여 커밋합니다.** API 계약의 변경 이력이 Pull Request의 코드 변경 차이(Diff)에 명확히 드러나며, 필드 삭제나 타입 변경을 코드 병합 전에 리뷰 단계에서 식별할 수 있습니다. 또한 CI 및 로컬 빌드 시 백엔드 서버 기동 없이도 독립적인 빌드가 가능해집니다.

**생성된 타입을 상위 계층에서 화면 전용 모델로 재변환하지 않고 직접 사용합니다.** 단순 필드 전달 목적의 매핑 계층을 제거하여, 백엔드 필드 추가 시의 수정 비용을 없애기 위함입니다. 대가는 분명합니다 — **백엔드 리팩터링이 화면 코드까지 전파되고 서버 어휘로 된 타입명이 화면에 그대로 드러납니다.** 그 대가를 치르고 매핑 유지 비용을 없앱니다.

### 계약 변경 시의 영향과 대응

| 변경 | 프론트 영향 | 대응 |
| :--- | :--- | :--- |
| 응답 필드 추가 | 없음 | 타입 파일 재생성 |
| 필드 삭제 · 타입 변경 | 컴파일 오류 | 사용처 코드 수정 |
| 엔드포인트 경로 변경 | **런타임 실패** | 경로 상수 수정 |

엔드포인트 경로 변경은 문자열 기반이므로 컴파일 단계에서 자동으로 검출되지 않습니다. 따라서 API 경로는 개별 호출부에 흩뿌리지 않고 전역 경로 상수로 집중 관리합니다. 타입 재생성 결과와 화면 코드의 수정은 단일 커밋에 담아 빌드 무결성을 유지합니다.

### 프로토타입에서 실제 연동으로의 전환

프로토타입 개발 단계에서는 InjectionToken 뒤에 Mock 구현체를 배치하며, 해당 인터페이스의 타입 정의가 백엔드 API 명세의 요구사항 입력으로 기능합니다. 백엔드 연동 시점에 OpenAPI 명세를 전달받아 타입을 생성한 후, **Mock 인터페이스와 생성된 타입을 대조하여 스펙 누락 및 불일치 사항을 식별**합니다.

연동 전환이 완료되면 Mock 구현체와 인터페이스를 제거합니다. 단일 구현체만 존재하는 불필요한 간접 참조 계층을 정리하고, 계약 검증 책임을 자동 생성된 정적 타입 시스템으로 이관합니다.
