# 프론트엔드 04. 적응형 레이아웃과 화면 골격 구조

동일한 애플리케이션이 넓은 화면과 좁은 화면에서 다르게 적응하는 메커니즘, 뷰포트 판정의 위치와 기준, 그리고 화면 골격(Layout)의 소유권과 스크롤 격리 구조를 서술한다. 컴포넌트의 물리적 배치 규격은 빌딩 블록 뷰가 정의하며, 검증 가능한 세부 코딩 규칙은 코드 스타일 가이드가 다룬다.

## 1. 반응형 레이아웃과 적응형 컴포넌트의 구분

두 개념은 해결하려는 문제의 층위가 다르다. 둘을 혼동하면 CSS로 처리해야 할 스타일에 런타임 분기가 침투하거나, 상호작용 모델을 전환해야 하는 지점에 무리한 CSS 제약이 적용되는 문제가 발생한다.

| 구분 | 반응형 (Responsive) | 적응형 (Adaptive) |
| :--- | :--- | :--- |
| **바뀌는 것** | 레이아웃 (배치 · 크기 · 여백) | 컴포넌트와 상호작용 모델 |
| **수단** | CSS 미디어 쿼리 | 런타임 분기 (`@if`, 시그널 분기) |
| **DOM 구조** | 동일 DOM 유지 | DOM 트리 교체 |
| **대표 사례** | 그리드 3열이 1열로 재배치 | 드롭다운 팝오버가 바텀 시트로 교체 |

**CSS로 해결 가능한 문제는 반응형 스타일로 처리하는 것을 기본 원칙으로 한다.** 런타임 분기는 두 가지 UI 표현을 모두 관리해야 하므로 유지보수 비용과 테스트 범위가 증가하기 때문이다.

두 방식을 구분하는 기준은 측정 대상 값이 아닌 **교체되는 대상**이다. 적응형 역시 뷰포트 너비를 측정하므로 판정 입력값은 동일하다. 동일한 뷰포트 너비 조건에서 레이아웃 스타일만 변경되면 반응형이고 컴포넌트 트리가 교체되면 적응형이다.

## 2. 뷰포트 판정 기준과 브레이크포인트

`(min-width: 48rem)`을 기준으로 `wide`와 `compact`를 구분한다. Tailwind CSS의 `md` 브레이크포인트에 해당하며, 별도의 임의 토큰을 신설하지 않고 해당 기준 척도를 일관되게 적용한다.

### 포인터 및 호버 특성 배제 근거

입력 장치 관점에서는 포인터 특성(`pointer`, `hover`)이 더 정확한 기준일 수 있다. 터치 기기에서는 마우스 호버가 지원되지 않고 손가락 터치에 최적화된 바텀 시트 인터페이스가 필요하기 때문이다. 그럼에도 포인터 미디어 쿼리를 사용하지 않는 이유는 **브라우저의 포인터 특성 감지 결과를 신뢰할 수 없기 때문**이다.

터치스크린이 장착된 데스크톱 환경에서 마우스가 연결되어 동작 중인 상태(`pointerType: "mouse"`)임에도 브라우저 미디어 쿼리는 다음과 같이 측정된다.

| 쿼리 | 값 |
| :--- | :--- |
| `(pointer: fine)` · `(hover: hover)` | false |
| `(any-pointer: fine)` · `(any-hover: hover)` | **false** |
| `(any-pointer: coarse)` | true |
| `navigator.maxTouchPoints` | 10 |

마우스 입력 장치가 활성화되어 동작하는 환경에서도 `any-` 축을 포함한 모든 포인터 쿼리가 `false`로 보고되었으며, 마우스 조작 중에도 미디어 쿼리 상태 변경 이벤트가 발생하지 않았다. 터치스크린이 장착된 데스크톱 환경에서는 마우스 연결 여부와 무관하게 시스템이 터치 전용 기기로 오판하며, 애플리케이션 레벨에서 이를 교정할 수단이 없다.

두 판정 축의 실질적 차이는 이론적 정밀도가 아닌 **판정 오류 발생 시의 파급 영향**에 있다.

| 구분 | 포인터 축 (`pointer` / `hover`) | 뷰포트 폭 축 (`min-width`) |
| :--- | :--- | :--- |
| **입력값의 성격** | 브라우저가 추정한 값 | 브라우저가 아는 사실 |
| **오판의 결과** | 마우스 사용자에게 모달 시트가 뜬다 | 좁게 줄인 창의 마우스 사용자에게 시트가 뜬다 |
| **코드로 교정** | 불가능하다 | 임계값을 옮긴다 |
| **확인 방법** | 해당 기기를 확보해야 한다 | 창을 줄인다 |

뷰포트 너비 기준으로 판정할 때 발생하는 오판은 터치 노트북이나 가로 모드 태블릿이 `wide`로 판정되어 드롭다운 팝오버가 표시되거나, 좁게 줄인 데스크톱 브라우저 창이 `compact`로 판정되어 바텀 시트가 표시되는 경우이다. 두 경우 모두 UI 접근성과 기능 조작성은 유지된다. 최소 터치 타겟 크기(44px)를 컴포넌트 기본 베이스 스타일로 상시 유지하면 팝오버 형태에서도 터치 입력이 정상 동작한다. 이것이 뷰포트 너비를 단일 판정 축으로 채택하는 근거이다.

## 3. 뷰포트 판정 로직의 캡슐화와 주입 함수

```ts
// shared/lib/adaptive/viewport-class.ts
export function injectViewportClass(): Signal<'wide' | 'compact'> {
  const isBrowser = isPlatformBrowser(inject(PLATFORM_ID));
  const observer = inject(BreakpointObserver);
  const state = toSignal(observer.observe(WIDE), { initialValue: null });

  return computed(() => {
    if (!isBrowser) return 'wide';
    return state()?.matches ? 'wide' : 'compact';
  });
}
```

컴포넌트 내부에서 미디어 쿼리 문자열을 직접 참조하지 않고 판정 함수(`injectViewportClass`)를 주입받아 사용한다. 판정 기준이 변경될 경우 해당 주입 헬퍼 한 곳만 수정하기 위함이다.

내부 구현에는 Angular CDK의 `BreakpointObserver`를 사용한다. Spartan brain 라이브러리가 이미 CDK를 요구하므로 추가 의존성 없이 활용할 수 있으며, 리스너 해제와 중복 구독 처리가 검증되어 있기 때문이다.

판정 함수의 반환 타입은 판정 대상을 명확히 드러내야 한다. 반환값을 `'pointer' | 'touch'`로 명명하면 입력 장치 판정으로 오인되어 잘못된 분기 로직이 작성될 위험이 있다.

### 비브라우저 환경의 기본값 처리

서버 렌더링 환경에는 뷰포트 개념이 존재하지 않으므로 기본 판정값은 항상 `wide`로 고정한다.

Angular CDK는 비브라우저 환경에서 `MediaMatcher`를 `noopMatchMedia`로 대체하며, 모든 미디어 쿼리에 대해 `matches: false`를 기본 반환한다. 별도 예외 처리가 없으면 `(min-width: 48rem)` 역시 `false`로 평가되어 비브라우저 판정이 `compact`로 처리되고, 넓은 데스크톱 화면의 초기 페인트에서 바텀 시트가 노출되는 깜빡임이 발생한다. 따라서 비브라우저 환경 분기를 선제적으로 평가하여 `wide`를 반환하도록 고정한다.

어느 한쪽을 기본값으로 지정하더라도 반대쪽 환경에서는 초기 하이드레이션 깜빡임이 불가피하다. 프리렌더 대상 경로에서 반응형 적응 컴포넌트 사용을 배제하는 이유가 여기에 있다.

## 4. 적응형 컴포넌트 구현 패턴

다음 순서에 따라 컴포넌트 적응 방식을 결정한다.

```text
0. 독립적인 목적지 화면인가?           → URL 쿼리 파라미터를 부여한다. 이후 A~C로 표현을 결정한다.
1. 화면 내 표시 위치만 다른가?         → 패턴 A: 오버레이 위치 전략 교체
2. 상호작용 모델 자체가 다른가?        → 패턴 B: 전용 표현 컴포넌트 교체
3. 패턴 B 적용 시 번들 크기 문제가 실측되었는가? → 패턴 C: 패턴 B에 지연 로딩 추가
```

독립적인 목적지 화면(생성 폼, 상세 보기)은 그 자체로 완결된 작업 흐름을 구성하므로 URL 쿼리 파라미터로 열림 상태를 관리한다. 반면 일시적 조작(필터, 정렬, 피커)은 단일 값을 선택하는 보조 조작이므로 URL 상태를 갖지 않는다. 일시적 조작에 URL 상태를 부여하면 조작 횟수만큼 브라우저 뒤로가기가 중단되는 문제가 발생한다.

목적지 열림 상태는 경로(Path)가 아닌 쿼리(Query)로 관리한다. 경로 변경 시 기존 화면 컴포넌트가 언마운트되고 화면 전환 베일이 활성화되는 반면, 쿼리 파라미터 변경 시에는 기존 화면이 유지된 상태에서 오버레이만 활성화되기 때문이다.

OS 네이티브 컨트롤 위임(모바일 네이티브 날짜 피커 등)은 채택하지 않는다. 운영체제와 브라우저 엔진에 따라 UI 외형과 동작 일관성을 제어할 수 없기 때문이다. 웹 표준 컴포넌트로 직접 구현하며, 웹 접근성 제약은 Spartan brain 프리미티브를 통해 충족한다.

### 패턴 A: 오버레이 위치 전략 교체

드롭다운과 바텀 시트의 차이가 표시 위치뿐인 경우에 적용한다. 콘텐츠 DOM을 공유하므로 컴포넌트를 중복 작성하지 않는다.

```ts
const positionStrategy = computed(() =>
  viewport() === 'compact' ? positionBuilder.global().bottom('0').centerHorizontally() : null,
);
```

`BrnPopover` 컴포넌트의 위치 전략 계산은 오리진(Origin) 요소의 유무를 우선 확인하며, 오리진이 지정되어 있으면 해당 요소 기준의 상대 위치 전략을 생성한다. 트리거 디렉티브는 클릭 시점에 호스트 요소를 오리진으로 자동 설정한다. 따라서 `compact` 뷰포트에서 글로벌 바텀 위치 전략을 적용하려면 오리진 설정을 명시적으로 초기화(`null`)해야 한다.

```ts
effect(() => {
  popover().setOrigin(viewport() === 'compact' ? null : button().nativeElement);
});
```

위치 전략 전환 시 표면(Surface) 스타일 클래스도 함께 동기화한다. 위치만 하단으로 이동하고 팝오버 너비 클래스를 유지하면 트리거 너비에 고정된 작은 패널이 화면 하단에 어색하게 표시된다. 뷰포트에 따른 클래스 분기를 위해 고정 클래스를 갖는 helm 디렉티브 대신 동적 클래스 바인딩을 적용한다.

바텀 시트 고유의 제스처(드래그 닫기, 스냅 포인트)가 필요한 경우에는 패턴 B로 승격하여 처리한다.

### 패턴 B: 전용 표현 컴포넌트 교체

```text
shared/ui/navigation/
├── navigation.ts              공개 API. 항목과 현재 위치만 소유한다
├── navigation-sidebar.ts      wide 표현
├── navigation-bottom-tabs.ts  compact 표현
└── index.ts                   navigation 만 내보낸다
```

하위 표현 컴포넌트는 모듈 외부에 직접 노출하지 않고 컨테이너 컴포넌트만 공개 API로 내보낸다. 외부 호출부는 단일 인터페이스만 참조하며 내부 표현 방식에 관여하지 않는다. 복수의 표현 컴포넌트는 동일한 입출력 계약(Inputs/Outputs)을 준수해야 한다. 계약이 다르면 상위 컴포넌트에서 분기 로직을 알아야 하므로 캡슐화가 훼손된다.

### 패턴 C: 적응형 컴포넌트 지연 로딩

두 표현 컴포넌트가 번들에 동시 포함되는 오버헤드가 실측으로 입증된 경우에만 지연 로딩을 도입한다. 번들 크기 절감과 초기 로딩 지연 간의 트레이드오프를 고려해야 한다. 지연 로딩 적용 시 배럴 파일이 아닌 해당 컴포넌트의 진입점 경로를 직접 임포트한다.

## 5. 레이아웃 골격과 표면 구조

레이아웃은 `app` 계층이 소유한다. `pages` 슬라이스는 자신이 어떤 레이아웃 내부에 배치되는지 알지 못한다.

| 레이아웃 | 용도 | 골격 축 |
| :--- | :--- | :---: |
| **랜딩** | 공개 소개 화면 | 없음 |
| **인증** | 로그인 · 가입 | 없음 |
| **앱셸** | 인증 후 업무 화면 | 있음 |
| **문서형** | 문서 · 도움말 | 있음 |

랜딩과 인증 화면은 네비게이션 구조가 없거나 최소화되어 있으므로 별도의 골격 축을 두지 않는다.

### 레이아웃 골격별 스크롤 컨테이너 위치 구조

| 골격 | 구조 | 스크롤 컨테이너 |
| :--- | :--- | :--- |
| `topbar` | 헤더가 전폭, 그 아래 네비게이션과 본문 | 문서 전체. 스크롤바가 뷰포트 오른쪽 끝 |
| `sidebar` | 사이드바가 전고, 헤더는 콘텐츠 열 안 | 콘텐츠 박스. 스크롤바가 안쪽 |

시각적 외형 배치가 아닌 **스크롤 컨테이너의 위치 차이**가 골격을 구분하는 기준이다. 표면 스타일(`bordered`, `inset`)은 콘텐츠와 네비게이션 영역의 구분 방식(경계선 또는 여백)을 정의하며, `topbar` 골격은 `bordered` 스타일로 고정한다. 문서 전체가 스크롤되는 구조에서 여백(`inset`) 방식을 적용하면 스크롤 시 배경이 함께 이동하여 레이아웃 경계가 깨지기 때문이다.

### 구조적 템플릿 분기와 페인트 CSS 분기

```text
스크롤 컨테이너의 위치가 달라지는가?
  예   → 구조. 템플릿 분기
  아니오 → 색 · 경계 · 여백만 달라지는가?
            예 → 페인트. 루트 data 속성 + CSS 변수
```

스크롤 컨테이너의 지정은 CSS `overflow` 속성의 소유 주체를 변경하는 구조적 작업이므로 순수 CSS 변수만으로는 처리할 수 없다. 반면 색상과 테두리는 DOM 변경 없이 CSS 속성으로 전환하는 것이 효율적이다. 골격 템플릿만 분기하며 네비게이션 항목, 헤더 컨트롤, 본문 슬롯 등 내부 콘텐츠는 두 템플릿이 공유한다.

## 6. 레이아웃 소유권과 골격 캡슐화

라우트는 레이아웃 컴포넌트 하나만 참조하며 구체적인 골격 구현체를 직접 참조하지 않는다.

```text
app/layout/
├── app-shell.ts            공개. 골격을 판정해 분기한다
├── app-shell-topbar.ts     비공개
└── app-shell-sidebar.ts    비공개
```

패턴 B와 동일한 구조적 캡슐화 원칙을 따른다.

- **플로팅 상호작용 요소**: 플로팅 컨트롤의 위치는 해당 요소를 소유한 내부 프레임이 결정한다. 셸이 라우트 경로를 검사하여 직접 렌더링하면 특정 화면의 구현 상세에 종속된다.
- **오른쪽 aside 슬롯**: 셸은 슬롯 영역의 컨테이너만 제공하며 실제 내용은 개별 화면이 주입한다. 셸은 슬롯 채움 여부만 인지하고 내부 구성 요소는 알지 못한다.
- **화면 전환 베일**: 셸과 프레임의 베일 영역이 중첩될 경우 내부 프레임이 우선권을 갖고 셸의 베일은 비활성화된다.

### Aside 슬롯 템플릿 전달 메커니즘과 반응형 전환

전달 메커니즘은 Angular `<ng-template>`을 사용한다. 화면 컴포넌트가 템플릿 참조를 슬롯 서비스에 등록하고 셸이 이를 렌더링한다. 서비스는 `shared` 계층에 배치하여 `app`과 `pages`가 상호 직접 의존 없이 통신하도록 한다. 템플릿을 매개로 전달하므로 의존성 주입 컨텍스트는 템플릿이 선언된 화면 컴포넌트의 스코프를 유지한다.

aside 패널은 뷰포트 전체 높이를 차지하며 헤더 영역까지 함께 밀어낸다. 좁은 화면에서는 나란히 배치할 공간이 부족하므로 콘텐츠 열 전체를 숨기고 aside 패널이 화면 전체를 덮는다. 헤더가 숨겨지므로 aside 패널 내부에 닫기 버튼을 반드시 제공해야 한다. 동일한 DOM 트리를 기반으로 CSS 레이아웃만 변경하므로 반응형 미디어 쿼리로 처리하며 런타임 분기를 두지 않는다.

패널 등장 및 퇴장 애니메이션 시 화면 외부에 위치한 요소로 인해 불필요한 가로 스크롤바가 생성되지 않도록 셸 컨테이너에 `overflow-x: clip`을 적용한다. `overflow-x: hidden`은 새로운 스크롤 컨테이너를 생성하여 내부 `position: sticky` 요소의 기준점을 왜곡하므로 사용하지 않는다.

## 7. 골격별 스크롤 격리와 라우터 연동 제약

`position: sticky`는 가장 인접한 스크롤 컨테이너를 기준으로 고정된다. 동일한 컴포넌트가 `topbar` 골격에서는 고정되고 `sidebar` 골격에서는 고정되지 않는 이유가 여기에 있다.

Angular Router의 기본 스크롤 위치 복원 기능은 window 레벨의 문서 스크롤만 지원한다. `sidebar` 골격처럼 내부 컨테이너가 스크롤되는 구조에서는 자동 복원이 동작하지 않으므로, 목록 스크롤 후 상세 이동 후 복귀 시 스크롤 위치가 유지되지 않는다. 내부 스크롤 구조 채택 시 스크롤 위치 저장과 복원 로직을 별도로 구현해야 한다.

고정 헤더가 존재하는 화면에서는 뷰포트 스크롤러의 오프셋을 함께 지정한다. 라우터의 앵커 이동은 스크립트 기반 좌표 이동이므로 CSS `scroll-margin-top`이 적용되지 않는다. 오프셋을 지정하지 않으면 앵커 이동 시 대상 요소가 헤더에 가려진다.

### 오버레이 스크롤 잠금 정책과 라우팅 충돌 방지

오버레이 열림 시 배경 스크롤을 제어할 때는 CDK 기본 잠금 전략을 준용한다.

오버레이 내부 링크를 통해 다른 화면으로 이동하는 경우 스크롤 잠금 해제와 라우터 스크롤 복원 타이밍이 충돌할 수 있다. 오버레이 닫힘 애니메이션 완료 시점에 스크롤이 복원되면서 라우터가 새로 이동한 페이지의 상단 위치를 덮어쓰는 문제가 발생하기 때문이다. 따라서 페이지 이동을 유발하는 링크나 네비게이션을 포함하는 오버레이 컴포넌트에는 백드롭 스크롤 잠금을 적용하지 않는다.

## 8. 시스템 오류 및 상태 화면 배치 정책

**401, 403, 404, 500 오류는 전체 화면 에러 페이지로 전환하며 셸 네비게이션을 노출하지 않는다.**

세션 만료나 애플리케이션 초기화 실패 시에는 네비게이션 메뉴를 구성하는 데이터를 신뢰할 수 없기 때문이다.

전체 화면 에러 페이지는 명확한 상황 설명, 복구 액션(로그인 이동, 홈 이동 등), 문제 해결을 위한 추적 식별자(Trace ID)를 포함한다. 복구 액션이 누락되면 사용자가 취할 수 있는 조치가 제한되므로, 셸 네비게이션을 제거하는 대신 화면 내에 명확한 복구 경로를 제공한다.

일시적인 네트워크 지연, 세션 만료 임박 안내, 점검 공지 등 기존 화면 콘텐츠가 유효한 상태 알림은 전체 화면을 대체하지 않고 인라인 배너로 표시한다. 배너는 고정 높이를 차지하며 콘텐츠를 아래로 밀어내도록 배치한다.

조회 결과 데이터가 존재하지 않는 빈 상태(Empty State)는 에러가 아닌 정상 응답이다. 콘텐츠 영역 내부에 안내 문구와 신규 데이터 생성 액션을 제공한다.

시스템 전체 점검 화면은 애플리케이션 내부 라우트로 구성하지 않고 웹 서버나 CDN 등 인프라 계층에서 정적 HTML로 응답하도록 구성한다. 애플리케이션 배포 장애 시에도 점검 안내가 정상 노출되어야 하기 때문이다.

## 9. 인쇄 미디어 대응과 전용 스타일 정책

인쇄(Print) 미디어 출력 시에는 네비게이션과 불필요한 크롬 요소를 숨기고, 내부 스크롤 컨테이너의 `overflow`와 고정 높이 제약을 해제하여 전체 문서가 연속 인쇄되도록 처리한다. 인쇄 스타일은 레이아웃 컴포넌트에서 중앙 집중식으로 정의한다. 개별 화면에서 인쇄 스타일을 분산 정의하지 않는다.
