# 프론트엔드 04. 적응형 레이아웃과 화면 골격 구조

동일한 애플리케이션이 넓은 화면과 좁은 화면에서 다르게 적응하는 메커니즘, 뷰포트 판정의 위치와 기준, 그리고 화면 골격(Layout)의 소유권과 스크롤 격리 구조를 서술합니다. 컴포넌트의 물리적 배치 규격은 빌딩 블록 뷰가 정의하며, 검증 가능한 세부 코딩 규칙은 코드 스타일 가이드가 다룹니다.

## 1. 반응형 레이아웃과 적응형 컴포넌트의 구분

두 용어는 해결하려는 문제의 층위가 다릅니다. 이 둘을 혼동하면 CSS로 풀어야 할 스타일에 런타임 분기가 침투하거나, 반대로 상호작용 모델을 전환해야 하는 자리에 무리한 스타일 제약이 걸리게 됩니다.

| 구분 | 반응형 (Responsive) | 적응형 (Adaptive) |
| :--- | :--- | :--- |
| **바뀌는 것** | 레이아웃 (배치 · 크기 · 여백) | 컴포넌트와 상호작용 모델 |
| **수단** | CSS 미디어 쿼리 | 런타임 분기 (`@if`, 신호 분기) |
| **DOM 구조** | 동일 DOM 유지 | DOM 트리 교체 |
| **대표 사례** | 그리드 3열이 1열로 재배치 | 드롭다운 팝오버가 바텀시트로 교체 |

**CSS로 해결되면 반응형으로 처리하는 것이 기본 원칙입니다.** 런타임 분기는 두 표현을 모두 유지해야 하고 테스트도 두 배가 됩니다.

두 방식을 가르는 기준은 **재는 값이 아니라 바뀌는 대상**입니다. 적응형도 뷰포트 폭을 재므로 판정에 쓰이는 입력값은 같습니다. 동일한 폭을 재더라도 레이아웃만 달라지면 반응형이고 컴포넌트가 교체되면 적응형입니다.

## 2. 뷰포트 판정 기준과 브레이크포인트

`(min-width: 48rem)` 을 기준으로 `wide` 와 `compact` 를 가릅니다. Tailwind CSS의 `md` 브레이크포인트에 해당하며, 별도의 임의 토큰을 두지 않고 이 기준 척도로 일관되게 다룹니다.

### 포인터 및 호버 특성 배제 근거

원리만 보면 포인터 특성(`pointer`, `hover`)이 입력 장치에 기반한 더 정확한 축입니다. 바텀시트는 화면이 좁아서가 아니라 손가락으로 조작하고 호버가 없어서 필요하기 때문입니다. 그럼에도 쓰지 않는 이유는 **브라우저가 이 값을 신뢰할 수 있게 보고하지 않기 때문**입니다.

터치스크린이 달린 Windows 11 데스크탑에서 Chrome 151로 측정한 값입니다. 마우스가 연결되어 동작 중이었고 페이지는 `pointerType: "mouse"` 인 포인터 이벤트를 실제로 받고 있었습니다.

| 쿼리 | 값 |
| :--- | :--- |
| `(pointer: fine)` · `(hover: hover)` | false |
| `(any-pointer: fine)` · `(any-hover: hover)` | **false** |
| `(any-pointer: coarse)` | true |
| `navigator.maxTouchPoints` | 10 |

마우스가 동작하는 동안에도 `any-` 축까지 전부 false였고 마우스를 움직여도 미디어 쿼리는 변경 이벤트를 한 번도 내지 않았습니다. 이 기기에서 포인터 축은 마우스가 달린 데스크탑을 터치 기기로 판정하며 애플리케이션 코드로 교정할 수단이 없습니다.

두 축의 차이는 이론적 정확도가 아니라 **틀렸을 때 벌어지는 일**에 있습니다.

| 구분 | 포인터 축 (`pointer` / `hover`) | 뷰포트 폭 축 (`min-width`) |
| :--- | :--- | :--- |
| **입력값의 성격** | 브라우저가 추정한 값 | 브라우저가 아는 사실 |
| **오판의 결과** | 마우스 사용자에게 모달 시트가 뜬다 | 좁게 줄인 창의 마우스 사용자에게 시트가 뜬다 |
| **코드로 교정** | 불가능하다 | 임계값을 옮긴다 |
| **확인 방법** | 해당 기기를 확보해야 한다 | 창을 줄인다 |

**폭으로 판정할 때 감수하는 것**은 터치 노트북과 태블릿 가로가 `wide`로 판정되어 팝오버가 뜨는 것, 좁게 줄인 데스크탑 창이 `compact`로 판정되어 시트가 뜨는 것입니다. **두 경우 모두 양쪽 표현이 사용 가능한 상태로 끝납니다.** 오판의 대가가 이 수준에 머무른다는 점이 폭을 축으로 두는 근거이며, 최소 터치 타겟을 표현과 무관하게 지키면 손가락으로도 조작할 수 있습니다.

## 3. 뷰포트 판정 로직의 캡슐화와 주입 함수

```ts
// shared/lib/adaptive/viewport-class.ts
export function injectViewportClass(): Signal<'wide' | 'compact'> {
  const isBrowser = isPlatformBrowser(inject(PLATFORM_ID));
  const observer = inject(BreakpointObserver);
  const state = toSignal(observer.observe(WIDE), { initialValue: null });

  return computed(() => {
    if (!isBrowser) return 'wide';
    return state()?.matches ? 'wide' : 'compact';
  });
}
```

컴포넌트가 미디어 쿼리 문자열을 직접 갖지 않고 이 의미 신호(`injectViewportClass`)만 씁니다. **규칙의 핵심은 구현 수단이 아니라 래퍼의 존재입니다** — 판정 기준이 바뀌면 이 파일 하나만 고칩니다.

구현에는 CDK의 `BreakpointObserver`를 씁니다. Spartan brain이 CDK를 요구하므로 이미 의존성에 있고, 리스너 정리와 중복 구독 처리를 직접 만들 이유가 없습니다.

**이름이 판정 대상을 그대로 드러내야 합니다.** 반환값이 `'pointer' | 'touch'`이면 입력 장치를 판정한 것으로 오인해 엉뚱한 분기가 붙습니다.

### 비브라우저 환경의 기본값 처리

서버에는 뷰포트가 없으므로 판정은 항상 `wide`입니다. **이 값은 코드가 명시적으로 반환하는 것이지 미디어 쿼리 결과가 아닙니다.**

그대로 쓰면 반대가 됩니다. CDK는 비브라우저 환경에서 `MediaMatcher`를 `noopMatchMedia`로 대체하며, 이 구현은 모든 쿼리에 `matches: false`를 담아 구독 즉시 방출합니다. `(min-width: 48rem)`도 false가 되어 판정이 `compact`로 떨어지고 넓은 화면의 첫 페인트가 시트가 됩니다. 그래서 비브라우저 분기를 먼저 두어 `wide`를 고정합니다.

어느 쪽을 기본값으로 골라도 반대쪽은 깜빡입니다. **프리렌더되는 경로에서 적응형 컴포넌트를 쓰지 않는 이유가 그것이며, 이 위반은 예외로 드러나지 않고 화면으로만 나타납니다.**

## 4. 적응형 컴포넌트 구현 패턴

위에서부터 순서대로 판정하고 먼저 해당하는 항목에서 멈춥니다.

```text
0. 그 자체로 하나의 일인가?          → 주소(쿼리)를 먼저 준다. 그 뒤에 A~C 로 표현을 정한다
1. 표시 위치만 다른가?              → A: 오버레이 위치 전략 교체
2. 상호작용 모델 자체가 다른가?       → B: 표현 컴포넌트 교체
3. B 인데 번들 측정에서 문제가 나왔나? → C: B 에 지연 로딩 추가
```

**0번이 가르는 것은 주소를 갖는가입니다.** 그 자체로 하나의 일인 것(세우기 · 상세)은 목적지이며 열림 상태를 주소의 쿼리에 둡니다. 값 하나를 고르고 끝나는 것(거르개 · 정렬 · 고르개)은 일시적이며 주소를 갖지 않습니다. 일시적인 것에 주소를 주면 뒤로가기가 조작한 횟수만큼 멈추며, 이는 필터에 히스토리를 쌓지 않는 규칙과 같은 이유입니다.

**경로가 아니라 쿼리에 둡니다.** 경로를 바꾸면 그 화면이 언마운트되어 뒤에 남아야 할 것이 사라지고, 셸이 경로 변경에 베일을 씌워 덮을 화면을 먼저 가립니다. 쿼리만 바뀌면 화면이 그대로 서 있고 베일도 서지 않습니다.

네이티브 위임(터치에서 OS 기본 UI를 쓰는 것)은 채택하지 않습니다. OS와 브라우저마다 외형이 달라져 화면 통제를 잃기 때문입니다. 그 결과 날짜 선택기 같은 컴포넌트를 직접 만들게 되며, 접근성 부담은 brain이 제공하는 프리미티브가 흡수합니다.

### 패턴 A: 오버레이 위치 전략 교체

드롭다운과 바텀시트의 차이가 표시 위치뿐인 경우입니다. 콘텐츠 DOM을 유지하므로 컴포넌트를 두 벌 만들지 않습니다.

```ts
const positionStrategy = computed(() =>
  viewport() === 'compact' ? positionBuilder.global().bottom('0').centerHorizontally() : null,
);
```

**다만 오리진이 붙어 있는 동안에는 이 입력이 읽히지 않습니다.** `BrnPopover`의 위치 전략 계산이 오리진 유무를 먼저 보고, 붙어 있으면 그 요소에 연결한 전략을 만들어 돌려줍니다. 오리진은 트리거 디렉티브가 클릭 시점에 자기 호스트로 설정합니다. **입력이 조용히 무시되고 팝오버가 그대로 뜨므로 증상이 화면으로만 드러납니다.**

해소는 오리진을 비우는 것입니다.

```ts
effect(() => {
  popover().setOrigin(viewport() === 'compact' ? null : button().nativeElement);
});
```

**표면 클래스도 함께 바꿉니다.** 위치만 옮기고 클래스를 그대로 두면 트리거 옆에 맞춰진 폭의 상자가 화면 하단에 뜹니다. 폭에 따라 바꾸려면 정적 속성이 아니라 바인딩이어야 하므로, 클래스를 고정하는 helm 표면 디렉티브 대신 컴포넌트가 표면 요소를 직접 갖습니다.

남는 한계는 바텀시트 고유 제스처(드래그로 닫기, 스냅 포인트)입니다. 그 수준이 필요하면 패턴 B로 올립니다.

### 패턴 B: 전용 표현 컴포넌트 교체

```text
shared/ui/navigation/
├── navigation.ts              공개 API. 항목과 현재 위치만 소유한다
├── navigation-sidebar.ts      wide 표현
├── navigation-bottom-tabs.ts  compact 표현
└── index.ts                   navigation 만 내보낸다
```

**표현 컴포넌트를 공개 API로 내보내지 않습니다.** 외부는 하나만 알며 어느 표현이 뜨는지 신경 쓰지 않습니다. 두 표현은 **같은 입출력 계약**을 가져야 하며, 계약이 다르면 상위 컴포넌트가 분기를 알게 되어 캡슐화가 무너집니다.

### 패턴 C: 적응형 컴포넌트 지연 로딩

두 표현이 모두 번들에 들어가는 것이 **측정으로 확인된 경우에만** 적용합니다. 얻는 것은 번들 감소이고 잃는 것은 첫 열기 지연입니다. 지연 대상은 배럴이 아니라 그 컴포넌트의 진입점을 직접 임포트해야 합니다.

## 5. 레이아웃 골격과 표면 구조

레이아웃은 `app` 계층이 소유합니다. `pages` 슬라이스는 자신이 어느 레이아웃 안에 놓이는지 알지 못합니다.

| 레이아웃 | 용도 | 골격 축 |
| :--- | :--- | :---: |
| **랜딩** | 공개 소개 화면 | 없음 |
| **인증** | 로그인 · 가입 | 없음 |
| **앱셸** | 인증 후 업무 화면 | 있음 |
| **문서형** | 문서 · 도움말 | 있음 |

랜딩과 인증은 네비게이션 구조가 없거나 최소이므로 골격 축을 갖지 않습니다 — "인증 화면의 골격은 무엇인가"라는 질문이 성립하지 않습니다.

### 레이아웃 골격별 스크롤 컨테이너 위치 구조

| 골격 | 구조 | 스크롤 컨테이너 |
| :--- | :--- | :--- |
| `topbar` | 헤더가 전폭, 그 아래 네비게이션과 본문 | 문서 전체. 스크롤바가 뷰포트 오른쪽 끝 |
| `sidebar` | 사이드바가 전고, 헤더는 콘텐츠 열 안 | 콘텐츠 박스. 스크롤바가 안쪽 |

시각적 배치가 아니라 **이 차이가 골격을 둘로 나누는 근거입니다.** 표면(`bordered` · `inset`)은 콘텐츠와 네비게이션을 경계선으로 나눌지 여백으로 나눌지이며, `topbar`는 `bordered`로 고정합니다 — 문서 전체가 스크롤되는 구조에서 여백을 쓰면 콘텐츠 둘레의 배경이 스크롤과 함께 움직여 표면 경계가 스크롤 영역과 어긋납니다.

### 구조적 템플릿 분기와 페인트 CSS 분기

```text
스크롤 컨테이너의 위치가 달라지는가?
  예   → 구조. 템플릿 분기
  아니오 → 색 · 경계 · 여백만 달라지는가?
            예 → 페인트. 루트 data 속성 + CSS 변수
```

스크롤 containment는 어느 요소가 `overflow`를 갖는가의 문제이므로 CSS 변수로 전환할 수 없습니다. 반대로 색과 경계는 마크업을 바꾸지 않고 전환하는 편이 저렴합니다. **분기하는 것은 골격이지 내용물이 아닙니다** — 네비게이션 항목, 헤더 컨트롤, 본문 슬롯은 두 템플릿이 공유합니다.

## 6. 레이아웃 소유권과 골격 캡슐화

라우트는 레이아웃 컴포넌트 하나만 참조하며 그것이 어느 골격으로 그려지는지 알지 못합니다.

```text
app/layout/
├── app-shell.ts            공개. 골격을 판정해 분기한다
├── app-shell-topbar.ts     비공개
└── app-shell-sidebar.ts    비공개
```

**패턴 B와 같은 구조입니다.** 두 자리가 같은 원리를 공유하므로 규칙을 따로 익힐 필요가 없습니다.

이 원칙이 여러 곳에서 되풀이됩니다.

- **화면에 고정되는 조작**: 플로팅 요소의 위치는 그것을 소유한 프레임이 정합니다. 셸이 경로를 보고 직접 그리면 셸이 특정 화면의 세부를 알게 됩니다.
- **오른쪽 aside 슬롯**: 셸이 슬롯을 소유하고 내용은 화면이 냅니다. 셸은 슬롯이 찼는지만 알고 무엇이 들었는지는 모릅니다. 반대로 화면이 자기 자리와 폭을 정하면 레이아웃 소유가 흩어집니다.
- **베일의 자리**: 셸과 프레임이 겹치면 안쪽이 자리를 가져가고 셸은 물러납니다. 이때도 셸은 경로가 아니라 "안쪽이 자리를 가져갔는가"만 묻습니다.

### Aside 슬롯 템플릿 전달 메커니즘과 반응형 전환

전달 수단은 템플릿입니다. 화면이 `<ng-template>`을 슬롯 서비스에 등록하고 셸이 그것을 그립니다. 셸은 `app`이고 화면은 `pages`라 둘이 함께 참조할 수 있는 자리가 `shared`뿐이므로 서비스를 거기 둡니다. 템플릿으로 주고받으므로 **내용의 인젝터는 선언 위치인 화면이며 라우트가 제공한 프로바이더가 그대로 닿습니다.**

**aside는 전고를 차지하며 헤더까지 함께 밀어냅니다. 겹치지 않습니다.** 헤더를 aside 밖에 두면 상단 바만 전폭으로 남아 aside가 화면의 일부만 가른 것처럼 보이므로, 헤더와 본문을 한 열에 담고 그 열 전체가 좁아지게 합니다. 좁은 화면에서는 나란히 놓을 폭이 없어 그 열을 통째로 감추고 aside가 화면을 덮습니다. **헤더도 함께 사라지므로 aside 안에 닫는 수단을 반드시 둡니다.** DOM이 같고 레이아웃만 바뀌므로 이것은 반응형이며 런타임 판정을 쓰지 않습니다.

등장과 퇴장에 화면 밖 위치를 쓰면 셸에서 **가로만** 잘라 냅니다. 요소가 화면 밖에 서는 동안 그 상자가 뷰포트를 넘어 가로 스크롤이 생기고, 가로 스크롤바가 서면 세로가 그만큼 부족해져 세로 스크롤까지 따라옵니다. `overflow-x: clip`을 쓰며 `hidden`은 스크롤 컨테이너를 만들어 그 안의 sticky가 뷰포트 대신 그 요소를 기준으로 삼게 하므로 쓰지 않습니다. 세로는 자르지 않습니다 — `topbar` 골격은 문서 전체가 스크롤 컨테이너라 세로까지 자르면 화면이 스크롤되지 않습니다.

## 7. 골격별 스크롤 격리와 라우터 연동 제약

**골격이 스크롤 컨테이너를 정하므로 스크롤에 얽힌 문제도 골격을 따라갑니다.**

`position: sticky`는 가장 가까운 스크롤 컨테이너를 기준으로 동작합니다. 같은 컴포넌트가 `topbar`에서는 고정되고 `sidebar`에서는 고정되지 않는 상황이 그래서 생깁니다.

라우터의 스크롤 위치 복원도 **문서 스크롤만 대상으로 합니다.** `sidebar`처럼 내부 박스가 스크롤되는 구조에서는 동작하지 않아, 목록을 스크롤해 상세로 들어갔다 돌아오면 맨 위로 올라갑니다. 내부 스크롤을 선택한 레이아웃은 저장과 복원을 직접 구현해야 하며 **이 비용은 골격 선택의 대가입니다.**

sticky 헤더가 있으면 뷰포트 스크롤러의 오프셋을 함께 지정합니다. 라우터의 앵커 이동은 `scroll-margin-top`을 따르지 않습니다 — 좌표를 계산해 스크롤하는 경로라 CSS가 닿지 않습니다. 지정하지 않으면 앵커로 이동했을 때 대상 제목이 헤더에 가립니다.

### 오버레이 스크롤 잠금 정책과 라우팅 충돌 방지

오버레이가 열릴 때 배경 스크롤을 막되 CDK의 전략을 씁니다. 직접 문서를 고정하면 스크롤바가 사라지며 레이아웃이 흔들리고, 오버레이가 중첩될 때 복원 시점이 어긋나 스크롤이 잠긴 채 남습니다.

**같은 어긋남은 직접 잠그지 않아도 재현됩니다.** 잠금 전략은 문서를 고정할 때 위치를 저장하고 닫을 때 되돌리므로, 오버레이 안의 링크로 다른 화면에 가면 라우터가 상단으로 보낸 뒤 오버레이가 닫히면서 이전 위치로 복원되어 새 화면이 중간부터 보입니다. 해제 시점을 앞지르려는 시도는 취약합니다 — 오버레이가 닫힘 애니메이션을 마친 뒤 정리되므로 지연을 얼마로 잡아도 경쟁이 남습니다. **이동 수단을 품는 오버레이는 잠금 자체를 두지 않습니다.** 배경이 스크롤되는 대가를 받아들이는 것이며 화면 대부분을 덮는 시트에서는 체감이 작습니다.

## 8. 시스템 오류 및 상태 화면 배치 정책

**401 · 403 · 404 · 500 은 전체 화면 에러로 통일하고 셸의 네비게이션을 유지하지 않습니다.**

상황마다 판정하지 않는 이유는 **판정할 수 없는 경우가 있기 때문**입니다. 세션 만료나 부트스트랩 실패에서는 네비게이션 항목을 조회할 수단 자체가 없습니다. 유지 가능한 경우와 불가능한 경우를 나누면 에러마다 판정이 들어가고, 판정이 들어가는 규칙은 배치 예측 가능성을 떨어뜨립니다.

전체 화면 에러는 상황 설명 · 복구 액션 · 추적 식별자를 갖습니다. **복구 액션이 없으면 사용자에게 남는 수단은 브라우저 뒤로가기뿐이며, 셸을 유지하지 않기로 한 결정은 화면 안에 복구 경로를 두는 것을 전제로 성립합니다.**

화면을 대체하지 않는 것도 있습니다. 네트워크 끊김, 세션 곧 만료, 점검 예정 공지는 기존 내용이 여전히 유효하므로 배너로 표시합니다. 배너는 고정 슬롯을 차지하며 콘텐츠를 밀어냅니다 — 겹치면 하단 내용이 가려집니다.

**빈 상태는 에러가 아닙니다.** 정상 응답이며 콘텐츠 영역 안에 표시하고, 다음 행동은 데이터를 만드는 동작 안내입니다.

**점검 화면은 애플리케이션 라우트로 만들지 않습니다.** 애플리케이션이 뜨지 않는 상태이므로 정적 HTML로 제공하며 인프라 계층이 응답합니다. 라우트로 두면 정작 배포되지 않은 상황에서 그 화면을 보여줄 수 없습니다.

## 9. 인쇄 미디어 대응과 전용 스타일 정책

업무 시스템은 화면을 지면으로 출력하는 요구가 생깁니다. 화면 골격을 그대로 인쇄하면 네비게이션이 지면을 차지하고 내부 스크롤 영역이 잘립니다.

크롬을 숨기고, **내부 스크롤 컨테이너의 `overflow`와 높이 제한을 해제하며**(해제하지 않으면 첫 화면 분량만 인쇄됩니다), 표의 행이나 카드가 잘리지 않게 하고, 배경색으로만 의미를 전달하지 않습니다. 배경은 기본적으로 인쇄되지 않습니다.

인쇄 스타일은 레이아웃 컴포넌트가 소유합니다. 개별 화면이 각자 정의하면 규칙이 흩어집니다.
