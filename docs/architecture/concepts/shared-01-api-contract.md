# 공통 01. API 계약과 명세 전달 체계

프론트엔드와 백엔드가 주고받는 HTTP API 계약의 구조와, 해당 계약이 서버에서 클라이언트로 전달되는 처리 메커니즘을 서술합니다. 이 문서는 두 영역에 동시에 적용되는 공통 규격입니다.

**계약의 소유권은 서버에 있습니다.** 계약의 정의와 변경은 서버가 주도하며, 클라이언트는 계약의 소비자로서 생성된 명세를 참조합니다.

## 1. 경로 규약

```text
/api/v1/tasks
/api/v1/tasks/{taskId}
```

| 규약 | 내용 |
| :--- | :--- |
| 접두사 | `/api` 로 시작합니다. 정적 자원과 섞이지 않습니다 |
| 버전 | 경로에 둡니다 |
| 자원 이름 | 복수형 명사입니다 |
| 동사 | 쓰지 않습니다. 행위는 메서드가 나타냅니다 |
| 식별자 | 경로 변수이며 이름은 `<자원>Id` 입니다 |

버전을 헤더가 아닌 URI 경로에 배치하는 이유는 가시성 확보입니다. 주소창, 서버 로그, API 문서에서 호출 대상 버전이 명확히 드러나며, 클라이언트가 헤더를 누락하여 기본 버전으로 폴백되는 문제를 방지합니다. **대가는 URL 이 길어지는 것과 판이 갈릴 때 경로가 두 벌이 되는 것입니다.**

### 상태 변경 요청 경로

동사 대신 **변경 대상 상태를 하위 자원으로 표현**합니다.

```text
PATCH /api/v1/tasks/{taskId}/completion     완료 여부
PATCH /api/v1/tasks/{taskId}/importance     중요 표시
```

명령 형태의 경로는 자원이 아닌 동작을 나타내므로, 토글이나 되돌리는 조작마다 새로운 엔드포인트가 증식합니다. 상태를 하위 자원으로 두면 활성화와 비활성화가 동일 경로에 대한 단일 상태 값 변경으로 처리됩니다.

## 2. HTTP 메서드와 상태 코드

| 상황 | 메서드 | 성공 코드 | 본문 |
| :--- | :--- | :--- | :--- |
| 목록 | `GET` | 200 | 배열 |
| 하나 | `GET` | 200 | 객체 |
| 생성 | `POST` | 201 + `Location` | 없음 |
| 전체 교체 | `PUT` | 204 | 없음 |
| 부분 변경 | `PATCH` | 204 | 없음 |
| 삭제 | `DELETE` | 204 | 없음 |

**상태 변경 요청의 성공 응답에는 본문을 싣지 않습니다.** 클라이언트가 변경 후 연관 조회를 재실행하여 화면을 동기화하므로 변경 응답 본문을 읽는 곳이 없으며, **읽지 않는 것이 계약에 남으면 명세와 생성 타입과 테스트가 계속 그것을 부양합니다.**

생성된 리소스의 식별자는 `Location` 헤더로 전달합니다. 생성 직후 해당 리소스의 상세 화면을 노출해야 하는 경우 `Location` 헤더에 명시된 경로로 단건 조회를 수행합니다.

## 3. 데이터 표현 형식과 필드 규격

**응답 본문에 공통 래퍼(Envelope) 구조를 두지 않고 리소스 데이터를 최상위에 직접 직렬화합니다.** 요청의 성공과 실패는 HTTP 상태 코드로 구분되며, 래퍼 구조는 전송 계층의 상태 정보를 본문에 중복 표현하는 형태가 되기 때문입니다.

| 값 | 형식 |
| :--- | :--- |
| 식별자 | UUID 문자열 |
| 날짜 | `YYYY-MM-DD` |
| 지역 시각 | `YYYY-MM-DDTHH:mm` — 시간대 지정자를 붙이지 않습니다 |
| 절대 시각 | ISO 8601 UTC |
| 정하지 않은 값 | `null`. 키를 빼지 않습니다 |

**지역 시각과 절대 시각을 형식으로 구분합니다.** 사용자가 지정한 달력 시각과 시스템에서 발생한 절대 순간을 동일한 형식으로 취급하면 소비 측에서 시간대(Timezone) 처리 방식을 결정할 수 없습니다. 이 구분은 저장 계층의 컬럼 타입 결정 기준과 일치합니다.

값이 지정되지 않은 필드는 키를 생략하지 않고 `null`로 유지합니다. 속성 키를 유지하는 이유는 **값이 없음과 해당 필드 정의가 존재하지 않음을 명확히 구분하기 위함**입니다. **키가 사라지면 오타와 미구현이 같은 모양이 됩니다.**

## 4. 목록 반환 정책과 페이징 기준

현재는 **전량을 반환하고 필터와 정렬을 클라이언트가 수행합니다.** 단일 사용자가 소유한 데이터 규모가 화면에서 직접 처리 가능한 범위에 있으며, 사용자 관점별 다양한 필터링 조건을 네트워크 요청 없이 즉각 처리하기 위함입니다.

**페이징을 도입하는 조건은 목록 응답이 클라이언트가 처리하기에 과도한 크기가 되는 시점입니다.** 해당 시점에 필터링 조건을 조회 포트로 위임하고 계약에 페이징 규약을 추가합니다. **쓰지 않는 파라미터가 계약에 남으면 그것도 유지 대상이 되므로** 미리 넣지 않습니다.

## 5. API 계약 전달과 타입 동기화 체계

```text
서버 코드 ──▶ OpenAPI 명세 ──▶ 타입 생성 ──▶ 클라이언트 코드
```

OpenAPI 명세는 서버가 런타임에 제공하고 클라이언트는 이를 바탕으로 TypeScript 정적 타입을 생성합니다. **두 컴포넌트 간의 유일한 연결점이며 컴파일 오류를 통해 계약 불일치를 조기에 감지합니다.**

| 축 | 하는 일 |
| :--- | :--- |
| 서버 | 엔드포인트와 DTO 를 정의하고 명세를 내보낸다 |
| 클라이언트 | 명세로 타입을 생성해 커밋하고, 손으로 고치지 않는다 |

타입 생성 절차와 산출물의 취급 정책은 프론트엔드 데이터 흐름 문서에 따릅니다. 서버가 응답 타입이나 필드를 변경하면 타입 생성을 다시 실행해야 하며, **재생성 결과와 그것을 사용하는 클라이언트 코드를 같은 커밋에 담습니다.** 나누면 중간 커밋이 컴파일되지 않습니다.

OpenAPI 명세를 제공하지 않는 백엔드와 연동해야 하는 경우 **명세 발행을 먼저 요청합니다.** 요청이 수용되지 않아 타입을 수동으로 작성해야 한다면 그 프로젝트는 이 표준에서 이탈한 것이므로 결정 기록에 사유와 범위를 남깁니다. **표준 문서를 조건부로 완화하지 않습니다.**
