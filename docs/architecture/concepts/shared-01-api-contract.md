# 공통 01. API 계약과 명세 전달 체계

프론트엔드와 백엔드가 주고받는 HTTP API 계약의 구조와, 해당 계약이 서버에서 클라이언트로 전달되는 처리 메커니즘을 서술한다. 이 문서는 두 영역에 동시에 적용되는 공통 규격이다.

**계약의 소유권은 서버에 있다.** 계약의 정의와 변경은 서버가 주도하며, 클라이언트는 계약의 소비자로서 생성된 명세를 참조한다.

## 1. 경로 규약

```text
/api/v1/tasks
/api/v1/tasks/{taskId}
```

| 규약 | 내용 |
| :--- | :--- |
| 접두사 | `/api`로 시작한다. 정적 자원 경로와 분리한다 |
| 버전 | 경로에 명시한다 |
| 자원 이름 | 복수형 명사를 사용한다 |
| 동사 | 경로에 동사를 사용하지 않는다. 행위는 HTTP 메서드로 표현한다 |
| 식별자 | 경로 변수이며 명명은 `<자원>Id`이다 |

버전을 HTTP 헤더가 아닌 URI 경로에 배치하는 이유는 가시성 확보이다. 브라우저 주소창, 웹 서버 접근 로그, API 명세 문서에서 호출 대상 버전이 명확히 식별되며, 클라이언트의 헤더 누락으로 인한 기본 버전 폴백 오류를 방지하기 위함이다.

### 상태 변경 요청 경로

동사 대신 **변경 대상 상태를 하위 자원으로 표현한다.**

```text
PATCH /api/v1/tasks/{taskId}/completion     완료 여부
PATCH /api/v1/tasks/{taskId}/importance     중요 표시
```

명령 형태의 경로는 자원이 아닌 행위를 표현하므로, 상태 변경 유형마다 엔드포인트가 무분별하게 증가한다. 상태를 하위 자원으로 설계하면 활성화와 비활성화가 동일 엔드포인트에 대한 단일 상태 값 변경으로 일관되게 처리된다.

## 2. HTTP 메서드와 상태 코드

| 상황 | 메서드 | 성공 코드 | 본문 |
| :--- | :--- | :--- | :--- |
| 목록 | `GET` | 200 | 배열 |
| 단건 | `GET` | 200 | 객체 |
| 생성 | `POST` | 201 + `Location` | 없음 |
| 전체 교체 | `PUT` | 204 | 없음 |
| 부분 변경 | `PATCH` | 204 | 없음 |
| 삭제 | `DELETE` | 204 | 없음 |

**상태 변경 요청의 성공 응답에는 본문(Body)을 포함하지 않는다.** 클라이언트는 상태 변경 후 연관 조회를 재실행하여 화면을 동기화하므로 변경 응답 본문을 소비하지 않기 때문이다. 소비하지 않는 응답 모델을 계약에 남기면 불필요한 DTO 유지보수와 테스트 비용이 지속적으로 발생한다.

생성된 리소스의 식별자는 `Location` 응답 헤더로 전달한다. 생성 직후 해당 리소스의 상세 화면으로 이동해야 하는 경우 `Location` 헤더의 경로로 단건 조회를 수행한다.

## 3. 데이터 표현 형식과 필드 규격

**응답 본문에 공통 래퍼(Envelope) 구조를 두지 않고 리소스 데이터를 최상위에 직접 직렬화한다.** 요청의 성공과 실패는 HTTP 상태 코드로 구분되며, 공통 래퍼 구조는 HTTP 전송 계층의 상태 정보를 응답 본문에 중복 표현하는 불필요한 결합을 유발하기 때문이다.

| 값 | 형식 |
| :--- | :--- |
| 식별자 | UUID 문자열 |
| 날짜 | `YYYY-MM-DD` |
| 로컬 시각 | `YYYY-MM-DDTHH:mm` — 시간대 지정자를 표기하지 않는다 |
| 절대 시각 | ISO 8601 UTC |
| 미지정 값 | `null`. 키를 생략하지 않는다 |

**로컬 시각과 절대 시각을 형식으로 구분한다.** 사용자가 지정한 달력 시각과 시스템에서 발생한 절대 순간(Instant)을 동일한 형식으로 취급하면 소비 측에서 시간대(Timezone) 변환 기준을 확정할 수 없다. 이 구분은 데이터베이스 저장 계층의 컬럼 타입 결정 기준과 일치한다.

**서버가 비즈니스 일자를 계산하는 기준 시간대는 `Asia/Seoul`로 고정한다.** '오늘의 할일'처럼 서버가 일자를 계산하여 기록하는 기준과 사용자의 로컬 일자가 다르면 시차로 인해 데이터 불일치가 발생하기 때문이다. 시스템 절대 시각(UTC Instant)은 이 설정의 영향을 받지 않는다.

값이 존재하지 않는 필드는 JSON 객체에서 키를 생략하지 않고 `null` 값을 명시한다. 필드 부재(키 없음)와 값 부재(`null`)를 명확히 구분하여 스키마 계약의 무결성을 유지하기 위함이다.

## 4. 목록 반환 정책과 페이징 기준

**현재는 목록 데이터를 전량 반환하고 필터와 정렬은 클라이언트에서 수행한다.** 단일 사용자 범위의 데이터 규모가 클라이언트 메모리에서 즉각 처리 가능한 수준이며, 다채로운 필터링과 정렬 인터랙션을 추가 네트워크 왕복 없이 처리하기 위함이다.

**페이징은 목록 응답 데이터 크기가 성능 한계를 초과하는 시점에 선별 도입한다.** 해당 시점에 영속성 계층에 페이징 쿼리를 위임하고 API 계약에 페이징 파라미터를 추가한다. 사용하지 않는 매개변수를 사전에 계약에 추가하지 않는다.

## 5. API 계약 전달과 타입 동기화 체계

```text
서버 코드 ──▶ OpenAPI 명세 ──▶ 타입 생성 ──▶ 클라이언트 코드
```

OpenAPI 명세는 서버가 런타임에 노출하고 클라이언트는 이를 바탕으로 TypeScript 정적 타입을 생성한다. 두 영역 간의 단일 계약 원본이며, 컴파일 시점에 계약 불일치를 조기에 검출한다.

| 축 | 역할 |
| :--- | :--- |
| 서버 | 엔드포인트와 DTO를 정의하고 OpenAPI 명세를 발행한다 |
| 클라이언트 | 발행된 명세로부터 타입을 자동 생성하여 커밋하며, 수동 수정하지 않는다 |

타입 생성 절차와 산출물 관리 정책은 [프론트엔드 03. 데이터 흐름과 상태 동기화](./frontend-03-data-flow.md)를 따른다. 서버 계약 변경 시 타입 생성을 재실행하고, **생성된 타입 산출물과 이를 참조하는 클라이언트 코드를 단일 커밋으로 원자적 반영한다.** 분리 커밋 시 중간 상태에서 빌드가 깨지기 때문이다.

OpenAPI 명세를 제공하지 않는 외부 백엔드와 연동해야 하는 경우 명세 발행을 우선 요구한다. 불가피하게 수동 타입을 정의해야 한다면 아키텍처 결정 기록(ADR)에 예외 사유와 영향 범위를 기록한다. 예외 상황을 이유로 표준 아키텍처 문서를 임의 완화하지 않는다.
