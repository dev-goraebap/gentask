# 유스케이스 작성 지침

유스케이스 서술서 작성 규칙이다. 백로그와 슬라이스 운영은 [결정-0007](../architecture/decisions/0007-shared-software-process.md)을 따른다.

기준 문헌은 이바 야콥슨(Ivar Jacobson), 이언 스펜스(Ian Spence), 키스 데 멘돈카(Keith de Mendonca)의 **Use-Case 3.0** (*The Guide to Succeeding with Use Cases – Refreshed*, May 2024)이며, 쪽수는 [Use-Case_3.0_2024.pdf](./Use-Case_3.0_2024.pdf)를 따른다. 문장 규칙은 앨리스터 코번(Alistair Cockburn)의 《Writing Effective Use Cases》를 참고한다.

- 원문 eBook: [Ivar Jacobson International](https://www.ivarjacobson.com/publications/books/use-case-30-ebook)
- 실무 요약: Simon Martinelli의 [Use-Case 3.0 해설](https://martinelli.ch/use-case-3-0-the-refreshed-guide-to-driving-development-with-use-cases/)

## 1. 유스케이스 식별

유스케이스 1개는 **주 액터의 단일 목표**를 나타내며, 해당 목표에 이르는 모든 경로(성공 · 예외 · 실패)를 포괄한다. (p.4, p.6)

식별 필수 요소: (p.6)

- **관심 시스템 (System of Interest)** — 시스템의 내부와 외부 경계
- **주 액터 (Primary Actor)** — 목표를 갖고 유스케이스를 개시하는 역할
- **목표 (Goal)** — 성공 시 주 액터가 얻는 실질적 가치

액터 규칙:

- 유스케이스를 시작하는 주체를 **주 액터**, 시스템이 호출하는 외부 주체를 **지원 액터**로 정의한다. (p.6)
- 액터는 직책이나 인물이 아닌 역할 단위로 정의하며, 상호작용 방식과 목표가 같으면 하나로 통합한다. (p.7)

유스케이스 제외 항목:

- 동일 목표에 이르는 다른 경로는 별도 유스케이스가 아니라 **대체 흐름**으로 정의한다. (p.9, p.17)
- **슬라이스**는 흐름을 조합한 구현 및 검증 단위이며 자체 식별자를 갖지 않는다. 서술서에 기술하지 않고 백로그 스토리가 이를 관리한다. (p.6, p.27)
- **인수 조건**은 서술서에 기술하지 않고 백로그 스토리에서 관리한다. 서술서에는 흐름만 기술한다.

초기 시점에 모든 유스케이스를 일괄 도출할 필요 없이, 가치를 제공하는 항목부터 우선 식별하고 점진적으로 확장한다. (p.37)

## 2. 서술서 작성

기본 흐름과 대체 흐름을 분리하여 작성한다. 초기에는 간결하고 정확한 개요로 시작한 뒤 필요한 시점에 구체화하며, 상세한 분량보다 정확성을 우선한다. (p.9, p.17)

```text
# [ID] [유스케이스 이름]

- 목표: 성공했을 때 액터가 얻는 실질적 가치
- 주 액터: 개시하는 역할 (단수형)
- 지원 액터: 호출되는 외부 시스템이나 역할 (없으면 '없음')
- 트리거: 유스케이스가 시작되는 계기나 조건

## 기본 흐름 (Basic Flow)
1. 액터가 …한다.
2. 시스템이 …한다.

## 대체 흐름 (Alternate Flows)
- [조건 이름]
- [조건 이름]
```

### 목표와 트리거

- **목표**는 유스케이스 이름을 동사형으로 단순 반복하지 않고, 작성 이유와 액터가 얻는 실질적 가치를 기술한다. (p.6) (예: `작업 추가`의 목표를 `작업을 적어둔다`가 아닌 `할 일을 등록하여 기억에 의존하지 않고 체계적으로 관리한다`로 기술)
- **트리거**는 절차의 단계가 아니라 시작 조건이다. (*"The use case starts when …"*, p.10) 예를 들어 `할 일이 발생했다`는 트리거이고, 1단계는 액터가 시스템과 첫 상호작용을 개시하는 행위로 기술한다.

### 기본 흐름

- 목표에 이르는 가장 단순하고 대표적인 성공 경로 **하나**만 기술한다. (p.9, p.16)
- 각 단계는 액터 또는 시스템의 명확한 행위 단위로 기술한다. (p.9)
- 작성 중 도출되는 예외와 대안은 대체 흐름에 **조건 이름만** 기록하고 기본 흐름에 집중한다. (p.17)

### 대체 흐름

> "A list of all the special cases, alternative paths, optional steps, and errors that need to be handled." (p.9)

- 오류뿐 아니라 **선택적 단계 · 특수 사례 · 또 다른 성공 경로 · 실패 상황**을 단일 목록에서 다룬다. (p.9)
- 초안에서는 세부 절차 없이 조건 이름만 나열한다. (예: `제목이 비어 있다`, `기한을 설정한다`, `작성을 취소한다`) (p.17)
- 세부 절차는 해당 흐름을 포함하는 슬라이스에 착수할 때 작성한다. (p.19)
- **선택적 단계의 조합은 새 대체 흐름이 아니다.** `기한을 설정한다`와 `미리 알림을 설정한다`는 각각 독립된 항목이고, 둘을 함께 거치는 것은 **실행 경로**다. (p.28–29) 조합마다 항목을 만들면 선택 항목이 증가할 때 조합의 수가 기하급수적으로 늘어난다.
- 한쪽이 다른 쪽에 의존하는 경우에만 해당 흐름 안에 전제로 기술한다. (예: 알림 설정이 기한 없이 성립하면 기한을 전제로 두지 않음)
- 세부 절차를 기술할 때는 종료 형태(기본 흐름 복귀 단계, 다른 성공으로 종료, 실패로 종료 중 하나)를 명시한다. 조건 이름만 나열하는 초안에서는 생략한다.

## 3. 분할

### 분할 단위

**조작 단위로 분할한다.** 추가 · 조회 · 편집 · 삭제 · 완료가 각각 독립된 문서다. 데이터 조작 단위 분할을 지양하는 견해도 있으나, 화면과 API가 해당 단위로 분리되고 판정 비용이 들지 않으므로 채택한다.

이에 따라 동일한 성격의 선택적 단계가 복수 문서에 나타날 수 있다. 예를 들어 `기한 설정`(추가)과 `기한 수정`(편집)은 절차와 복귀 지점이 달라 독립된 흐름으로 취급한다.

**조회는 독립적인 목표일 때만 별도 문서로 분리한다.**

- 목록을 확인하고 다음 작업을 선정하는 경우: 독립 분리 (`작업 조회`)
- 프로필 화면에 진입하여 정보를 수정하는 경우: 관리의 선행 단계 (`프로필 관리`)
- 작업 상세 화면에 진입하여 수정하는 경우: 편집의 선행 단계 (`작업 편집`)

읽기 전용 화면(공유 링크, 타인 프로필, 활동 이력)이 추가되면 독립 문서로 분리한다.

### 분할 시 유의 사항

- **화면 및 위젯 단위** (상세 패널 열기, 저장하기) — UI 변경 시 문서 구조가 함께 영향받으므로 지양한다.
- **조회 조건 단위** (오늘 보기, 완료 보기, 전체 보기) — 단일 조회 목표에 속하는 대체 흐름으로 통합한다.
- **필드 단위** (제목 수정, 메모 수정, 기한 수정) — 유스케이스가 아닌 필드 명세서 단위로 파편화되지 않도록 단일 편집 유스케이스로 통합한다.

이름이 데이터 조작 동사와 같아도 목표 문장이 단일하면 유스케이스로 성립한다.

## 체크리스트

**식별**

- [ ] 주 액터와 목표가 한 문장으로 표현되는가
- [ ] 성공 경로와 실패 · 예외 경로가 같은 목표 아래 묶여 있는가
- [ ] 화면이나 기능 목록이 아니라 액터의 목표 단위인가

**서술**

- [ ] 목표에 단순 기능명이 아니라 액터가 얻는 가치가 기술되어 있는가
- [ ] 기본 흐름의 각 단계가 액터 또는 시스템의 명확한 행위로 기술되어 있는가
- [ ] 대체 흐름에 오류뿐 아니라 선택 · 특수 사례가 조건 이름으로 정의되어 있는가
- [ ] 아직 구현하지 않는 대체 흐름을 불필요하게 미리 상세화하지 않았는가

**흐름**

- [ ] 구체화된 대체 흐름의 종료 형태(복귀 · 다른 성공 · 실패)가 명시되어 있는가
