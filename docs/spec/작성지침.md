# 유스케이스 작성 지침

유스케이스 서술서 작성 규칙입니다. 백로그와 슬라이스 운영은 [결정-0007](../architecture/decisions/0007-shared-software-process.md)을 따릅니다.

기준 문헌은 이바 야콥슨(Ivar Jacobson), 이언 스펜스(Ian Spence), 키스 데 멘돈카(Keith de Mendonca)의 **Use-Case 3.0** (*The Guide to Succeeding with Use Cases – Refreshed*, May 2024)이며, 쪽수는 [Use-Case_3.0_2024.pdf](./Use-Case_3.0_2024.pdf)를 따릅니다. 문장 규칙은 앨리스터 코번(Alistair Cockburn)의 《Writing Effective Use Cases》를 참고합니다.

- 원문 eBook: [Ivar Jacobson International](https://www.ivarjacobson.com/publications/books/use-case-30-ebook)
- 실무 요약: Simon Martinelli 의 [Use-Case 3.0 해설](https://martinelli.ch/use-case-3-0-the-refreshed-guide-to-driving-development-with-use-cases/)

## 1. 유스케이스 식별

유스케이스 1개는 **주 액터의 단일 목표**를 나타내며, 해당 목표에 이르는 모든 경로(성공 · 난관 · 실패)를 포괄합니다. (p.4, p.6)

식별 필수 요소: (p.6)

- **관심 시스템 (System of Interest)** — 시스템의 내부와 외부 경계
- **주 액터 (Primary Actor)** — 목표를 갖고 유스케이스를 개시하는 역할
- **목표 (Goal)** — 성공 시 주 액터가 얻는 실질적 가치

액터 규칙:

- 유스케이스를 시작하는 주체를 **주 액터**, 시스템이 호출하는 외부 주체를 **지원 액터**로 정의합니다. (p.6)
- 액터는 직책이나 인물이 아닌 역할 단위로 정의하며, 상호작용 방식과 목표가 같으면 하나로 묶습니다. (p.7)

유스케이스 제외 항목:

- 동일 목표에 이르는 다른 경로는 별도 유스케이스가 아니라 **대체 흐름**으로 정의합니다. (p.9, p.17)
- **슬라이스**는 흐름을 조합한 구현 및 검증 단위이며 자체 식별자를 갖지 않습니다. 서술서에 적지 않고 백로그의 Story 가 그 자리를 갖습니다. (p.6, p.27)
- **인수 조건**은 서술서에 적지 않고 Story 파일이 갖습니다. 서술서가 갖는 것은 흐름입니다.

초기 시점에 모든 유스케이스를 일괄 도출할 필요 없이, 가치를 제공하는 항목부터 우선 식별하고 점진적으로 확장합니다. (p.37)

## 2. 서술서 작성

기본 흐름과 대체 흐름을 분리하여 작성합니다. 초기에는 간결하고 정확한 개요로 시작한 뒤 필요한 시점에 구체화하며, 상세한 분량보다 정확성을 우선합니다. (p.9, p.17)

```text
# [ID] [유스케이스 이름]

- 목표: 성공했을 때 액터가 얻는 실질적 가치
- 주 액터: 개시하는 역할 (단수형)
- 지원 액터: 호출되는 외부 시스템이나 역할 (없으면 '없음')
- 트리거: 유스케이스가 시작되는 계기나 조건

## 기본 흐름 (Basic Flow)
1. 액터가 …한다.
2. 시스템이 …한다.

## 대체 흐름 (Alternate Flows)
- [조건 이름]
- [조건 이름]
```

### 목표와 트리거

- **목표**는 유스케이스 이름을 동사형으로 단순 반복하지 않고, 작성 이유와 얻는 실질적 가치를 기술합니다. (p.6) (예: `작업 추가`의 목표를 `작업을 적어둔다`가 아닌 `떠오른 일을 목록에 남겨, 기억에 의존하지 않는다`로 기술)
- **트리거**는 절차의 단계가 아니라 시작 조건입니다. (*"The use case starts when …"*, p.10) 예를 들어 `할 일이 떠올랐다`는 트리거이고, 1단계는 액터가 시스템과 첫 상호작용을 개시하는 행위로 기술합니다.

### 기본 흐름

- 목표에 이르는 가장 단순하고 대표적인 성공 경로 **하나**만 기술합니다. (p.9, p.16)
- 각 단계는 액터 또는 시스템의 명확한 행위 단위로 기술합니다. (p.9)
- 작성 중 도출되는 예외와 대안은 대체 흐름에 **조건 이름만** 기록하고 기본 흐름에 집중합니다. (p.17)

### 대체 흐름

> "A list of all the special cases, alternative paths, optional steps, and errors that need to be handled." (p.9)

- 오류뿐 아니라 **선택적 단계 · 특수 사례 · 또 다른 성공 경로 · 실패 상황**을 단일 목록에서 다룹니다. (p.9)
- 초안에서는 세부 절차 없이 조건 이름만 나열합니다. (예: `제목이 비어 있다`, `기한을 지정한다`, `작성을 취소한다`) (p.17)
- 세부 절차는 해당 흐름을 포함하는 슬라이스에 착수할 때 작성합니다. (p.19)
- **선택적 단계의 조합은 새 대체 흐름이 아닙니다.** `기한을 지정한다`와 `미리 알림을 설정한다`는 각각 독립된 항목이고, 둘을 함께 거치는 것은 **실행 경로**입니다. (p.28–29) 조합마다 항목을 만들면 선택 항목이 늘 때 조합의 수가 기하급수로 증가합니다.
- 한쪽이 다른 쪽에 의존한다고 정한 경우에만 해당 흐름 안에 전제로 기술합니다. (예: 알림 설정이 기한 없이 성립하면 기한을 전제로 두지 않음)
- 세부 절차를 기술할 때는 종료 형태(기본 흐름 복귀 단계, 다른 성공으로 종료, 실패로 중단 중 하나)를 명시합니다. 조건 이름만 나열하는 초안에서는 적지 않습니다.

## 3. 분할

### 자르는 단위

**조작 단위로 자릅니다.** 추가 · 보기 · 편집 · 삭제 · 완료가 각각 문서 하나입니다. 데이터 조작 단위로 나누는 것을 안티패턴으로 보는 견해가 있으나, 화면과 API 가 실제로 그 단위로 갈리고 판정 비용이 들지 않으므로 채택합니다.

대가는 같은 선택적 단계가 두 문서에 나타나는 것입니다. `기한을 붙인다`(추가)와 `기한을 편집한다`(편집)가 그 예이며, 절차와 복귀 지점이 서로 달라 실제로는 다른 흐름입니다.

**조회는 그 자체로 끝나는 목표일 때만 독립 문서입니다.**

- 목록을 훑고 다음에 할 일을 고르면 끝난다 → 독립 (`작업 보기`)
- 프로필을 열면 반드시 뭔가 고치러 온 것이다 → 관리의 첫 단계 (`프로필 관리`)
- 작업 상세를 열면 고치러 온 것이다 → 편집의 첫 단계 (`작업 편집`)

읽기 전용 화면(공유 링크, 남의 프로필, 활동 이력)이 생기면 그때 독립시킵니다.

### 여전히 유의할 것

**금지가 아니라 다시 볼 신호이며, 더 나은 이름이 없으면 그대로 씁니다.**

- **화면 및 위젯 단위** (상세 패널 열기, 저장하기) — UI 변경 시 문서 구조가 함께 영향을 받습니다.
- **조회 조건 단위** (오늘 보기, 완료 보기, 전체 보기) — 단일 조회 목표에 속하는 대체 흐름입니다.
- **필드 단위** (제목 수정, 메모 수정, 기한 수정) — 유스케이스가 아닌 필드 명세서 단위로 분할된 상태입니다.

이름이 데이터 조작 동사와 같아도 목표 문장이 단일하면 유스케이스로 성립합니다.

## 체크리스트

**식별**

- [ ] 주 액터와 목표가 한 문장으로 표현되는가
- [ ] 성공 경로와 실패 · 예외 경로가 같은 목표 아래 묶여 있는가
- [ ] 화면이나 기능 목록이 아니라 액터의 목표 단위인가

**서술**

- [ ] 목표에 기능명이 아니라 액터가 얻는 가치가 적혀 있는가
- [ ] 기본 흐름의 각 단계가 누가 무엇을 하는지로 적혀 있는가
- [ ] 대체 흐름에 오류뿐 아니라 선택 · 특수 사례가 조건 이름으로 있는가
- [ ] 아직 구현하지 않는 대체 흐름을 미리 상세화하지 않았는가

**흐름**

- [ ] 풀어 쓴 대체 흐름의 끝이 복귀 · 다른 성공 · 실패 중 하나로 밝혀져 있는가
