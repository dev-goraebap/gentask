# 개발 프로세스

본 문서는 이 저장소가 기능을 발견하고 구현해 검증하기까지의 절차를 정의합니다. Use-Case 3.0 의 유스케이스와 슬라이스를 1인 개발 흐름에 맞게 줄인 것입니다.

## 전제

제품은 두 축으로 이루어집니다. 이 프로세스는 요구사항 축만 다룹니다.

| 축 | 위치 | 성격 |
| :--- | :--- | :--- |
| **요구사항 축** | `docs/` | 무엇을 만드는가. 프로젝트마다 새로 발견됩니다. |
| **참조 아키텍처** | `web/docs/` | 어떻게 만드는가의 기준. 프로젝트를 넘나들며 축적되며 프로젝트 시작 전에 준비되어 있어야 합니다. 진입점은 [web/docs/architecture/index.md](../web/docs/architecture/index.md)입니다. |

1인 규모와 UI 선행 방식에서 따라오는 구조가 있습니다. 백엔드는 모놀리식이고 프론트와 백엔드는 분리됩니다. 이것은 별도의 아키텍처 결정이 아니라 프로세스의 귀결입니다.

## 산출물의 자리

| 폴더 | 산출물 | 원본인 것 |
| :--- | :--- | :--- |
| **`docs/1.analysis/`** | 유스케이스 모델과 서술서 | 모델은 배경, 액터, 유스케이스, 범위 밖을 갖습니다. 서술서는 기본 흐름과 대체 흐름을 갖습니다. |
| **GitHub Issues** | 슬라이스 | 이슈 하나가 슬라이스 하나이자 작업 항목 하나입니다. 성공 조건, 프론트 · 백엔드의 구현 판단, 확인 절차, 진행 상태를 갖습니다. 마일스톤과 프로젝트는 쓰지 않습니다. |
| **`docs/2.design/`** | 전체 아키텍처 | 프론트와 백엔드를 아우르는 구조. 백엔드가 생긴 뒤 작성합니다. |

유스케이스 작성 규칙은 [1.analysis/작성지침.md](1.analysis/작성지침.md)가 갖습니다. 이 문서는 단계와 경계만 정의합니다.

### 슬라이스와 이슈

슬라이스 하나가 이슈 하나입니다. 유스케이스는 서술서로만 있고 이슈 · 마일스톤으로 만들지 않습니다. 원문은 슬라이스를 서술서 안의 표로 추적하고 그 아래에 작업 항목을 여럿 두지만, 1인 개발에서는 둘 다 이슈로 합칩니다. 서술서에는 슬라이스를 적지 않고, 이슈 본문의 프론트 · 백엔드 절이 작업 항목을 대신합니다. 슬라이스 하나는 한 번 앉아 끝내고 확인하는 분량이며, 같은 자리에서 갈라지는 흐름은 한 슬라이스로 묶습니다. 자르는 기준은 작성지침이 갖습니다.

경계는 **흐름은 서술서, 슬라이스는 이슈**입니다.

| 항목 | 자리 | 사유 |
| :--- | :--- | :--- |
| **기본 흐름 · 대체 흐름** | 서술서 | 요구사항의 원본이며 git 이 개정 이력을 갖습니다. |
| **성공 조건 · 지나는 흐름** | 이슈 본문 | 슬라이스의 정의입니다. 저장소 안의 사본은 그 경로를 지나는 테스트의 이름이 맡습니다. |
| **구현 판단** | 이슈의 프론트 · 백엔드 절 | 아키텍처를 바꾸지 않는 요구사항별 기술 판단의 자리입니다. 같은 판단이 두 번째 이슈에 나타나면 참조 문서나 결정 기록으로 올립니다. |
| **상태** | 이슈의 open · closed | 흐름과 무관하게 바뀌는 값입니다. |
| **서술서 → 슬라이스** | 이슈 제목의 `TK-00N` 검색 | 표를 따로 두면 이슈와 서술서가 서로를 가리키는 중복이 됩니다. |

흐름을 개정하면 그 ID 로 검색해 해당 흐름을 적은 이슈의 성공 조건을 맞춥니다. 이 탐색이 트래커 밖에서는 되지 않는다는 것이 이 구조의 대가입니다.

## 단계

### 0. 경계 정하기

별도의 기획 문서를 두지 않습니다. Use-Case 3.0 에서 시스템의 경계와 범위를 정하는 것은 유스케이스 모델의 첫 활동이므로, [유스케이스 모델](1.analysis/유스케이스-모델.md)의 배경 · 액터 · 범위 밖 절이 기획의 자리입니다.

- **배경**: 왜 만드는지와 요구사항의 기준점을 적습니다.
- **액터**: 주 액터와 지원 액터를 적고, 아직 올리지 않은 후보는 올리는 조건과 함께 남깁니다.
- **범위 밖**: 기준점에 있지만 올리지 않은 것을 이유와 올리는 조건과 함께 적습니다. 의도한 생략을 남기는 자리입니다.

기획이 이 세 절을 넘어 두꺼워지면(릴리스 계획, 이해관계자) 그때 `docs/0.planning/` 을 열고 배경 절을 옮깁니다.

### 1. 분석 — 유스케이스 초안

모델에 등록한 유스케이스마다 서술서를 초안으로 만듭니다.

- 기본 흐름은 단계까지 쓰고, 대체 흐름은 **조건 이름만** 나열합니다.
- 흐름에서 슬라이스를 잘라 이슈를 엽니다. 제목에 슬라이스 ID 와 이름을, 본문에 지나는 흐름과 성공 조건을 적습니다. 아직 결정이 안 난 흐름은 자르지 않습니다.
- 대체 흐름의 상세 절차는 이 단계에서 쓰지 않습니다. 그 흐름을 지나는 슬라이스에 착수할 때 씁니다.

### 2. 슬라이스 착수

착수할 이슈를 고르면 다음 둘을 합니다.

1. **흐름 구체화**: 슬라이스가 지나는 대체 흐름의 시작 조건과 처리 절차, 종결을 서술서에 씁니다. 기본 흐름만 지나면 건너뜁니다.
2. **이슈 확정**: 성공 조건이 흐름과 맞는지 확인하고, 프론트 · 백엔드에서 하기로 한 것과 확인 절차를 적습니다.

성공 조건이 한 문장으로 적히지 않는 슬라이스는 아직 착수할 수 없습니다.

### 3. 구현 — UI 선행

목 계층 뒤에서 UI 를 먼저 만들고, 백엔드가 생기면 DI 교체로 잇습니다.

- UI 는 서비스 인터페이스 뒤의 목 구현을 통해서만 데이터에 접근합니다. 이 인터페이스의 타입이 백엔드 API 계약의 입력입니다.
- 커밋은 이슈 번호를 가리킵니다 (`Refs #12`). 소스 주석에는 채번하지 않습니다.
- 테스트의 추적 키는 **슬라이스 ID** 입니다. 이슈 번호가 아닌 이유는 원본이 서술서이고 이슈는 그것의 진행 상태이기 때문입니다.
- 슬라이스 ID 는 **그 슬라이스의 경로를 처음부터 끝까지 지나는 테스트**에만 붙입니다. 화면 테스트(목 계층 위)와 종단 테스트가 해당하며, 이름은 성공 조건 문장을 그대로 씁니다. 예를 들어 `describe('TK-001 S1: 제목을 적으면 목록에 그 할일이 있다')` 입니다. 도구가 태그를 지원하면(Playwright) 이름 대신 태그로 답니다.
- 단위 테스트에는 붙이지 않습니다. 함수 하나의 테스트가 성공 조건을 이름으로 가지면 경로가 닫혔다는 거짓 주장이 됩니다. 단위 테스트는 그 단위가 보장하는 것을 이름으로 갖습니다.
- 목 위의 화면 테스트가 통과한 것은 프론트 경로까지 참이라는 뜻입니다. 백엔드가 붙으면 같은 이름의 종단 테스트가 그 자리를 잇습니다.
- 구현 중 흐름이 바뀌면 서술서를 먼저 고칩니다. 문구 · 색 · 간격 같은 표면 변경은 문서를 거치지 않습니다.

### 4. 검증

완료의 정의는 코드가 돌아가는 것이 아니라 **성공 조건이 참임이 확인된 것**입니다.

- 성공 조건 문장을 따라 그 슬라이스가 지나는 경로만 확인합니다. 처음에는 수동으로, 같은 경로를 반복 확인하게 되면 종단 테스트가 같은 문장을 확인합니다.
- 프론트와 백엔드가 나뉘면 둘을 붙여 확인합니다. 단위 테스트만으로 검증됨이 되지 않습니다.
- 이슈의 확인 절차를 밟고 닫습니다. 이슈가 닫힌 것이 슬라이스가 검증됨의 표시입니다.

## 전역 규칙

| 규칙 | 내용 |
| :--- | :--- |
| **문서 우선 변경** | 동작과 흐름이 바뀌면 서술서를 먼저 고치고 코드가 따라옵니다. 표면 변경은 예외입니다. |
| **번호 불변** | 유스케이스 ID(`TK-001`), 대체 흐름 번호(`A1`), 슬라이스 ID(`S1`)는 부여 뒤 바꾸지 않습니다. 삭제는 결번으로 사유를 남기고, 추가는 말번입니다. AI 로 문서를 재생성한 뒤에는 번호가 유지됐는지 확인합니다. |
| **판단은 문서, 강제는 훅** | 기계가 판정할 수 있는 것은 린터 · 테스트 · 빌드로 내려보냅니다. 문서에는 판단이 필요한 규약만 남깁니다. |

## 흐름 요약

```text
0  경계 정하기     → 유스케이스 모델: 배경, 액터(후보 포함), 범위 밖
1  분석            → 서술서 초안 (기본 흐름 단계, 대체 흐름은 이름만)
                     + 슬라이스마다 이슈 (흐름, 성공 조건)
2  슬라이스 착수   → 지나는 대체 흐름 구체화 + 이슈의 성공 조건 · 구현 판단 · 확인 절차
3  구현 (UI 선행)  → 목 인터페이스 뒤에서 만들고 커밋은 이슈 번호, 경로를 지나는 테스트는 슬라이스 ID
4  검증            → 성공 조건 문장대로 그 경로를 확인하고 이슈를 닫음

[경계] 흐름은 서술서, 슬라이스는 이슈 (유스케이스는 이슈로 만들지 않음)
[전역] 문서 우선 변경 · 번호 불변 · 판단은 문서, 강제는 훅
```
