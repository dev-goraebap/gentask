# 웹앱 프로토타입 First 프로세스

본 문서는 이 저장소가 기능을 발견하고 구현해 검증하기까지의 절차를 정의합니다.

## 정의와 전제

이 프로세스는 **스펙 주도 개발(SDD)을 개인 개발 흐름에 맞게 테일러링한 것**입니다.

핵심 전제는 제품을 이루는 두 축 중 하나가 사전에 준비되어 있어야 한다는 것입니다.

- **요구사항 축 (What)** — 무엇을 만들 것인가. 이 프로세스가 다루는 대상이며 프로젝트마다 새로 발견되고 작성됩니다.
- **참조 아키텍처 (How의 기준)** — 어떻게 만들 것인가의 기준. 테일러링된 프레임워크 소스코드, 폴더 구조, 상태관리·접근성·반응형 규칙, 코딩 컨벤션, 디자인 토큰 등입니다. **이 축은 프로젝트 시작 전에 준비되어 있어야 하며 그 준비도가 제품의 완성도를 좌우합니다.** 요구사항 축이 프로젝트마다 새로 발견되는 것이라면, **참조 아키텍처는 프로젝트를 넘나들며 축적되는 자산**입니다.

참조 아키텍처가 구체적으로 무엇인지는 이 문서에서 다루지 않습니다. 필요한 전제는 자신만의 아키텍처 자산이 준비되어 있다는 것뿐입니다. 이 문서에서 그 산출물을 통칭해 **steering**이라 부릅니다.

이 저장소의 프론트엔드 steering 진입점은 [`web/docs/architecture/index.md`](../web/docs/architecture/index.md)입니다. 시각 언어는 아키텍처 밖의 [`web/docs/design/DESIGN.md`](../web/docs/design/DESIGN.md)가 소유합니다.

이 방식 자체가 1인 개발에 테일러링된 것이므로, 프로세스의 성격에서 자연스럽게 따라오는 구조가 있습니다.

- 1인 규모이므로 마이크로서비스는 기각되고 백엔드는 **모놀리식**으로 갑니다.
- 프로토타입을 만들 때 이미 준비된 프론트엔드 메타 프레임워크로 시각적인 부분을 먼저 만들어 내는 방식이므로, 자연스럽게 **디커플드 아키텍처**(프론트와 백엔드 분리)를 차용하게 됩니다.
- 즉 이것들은 별도의 아키텍처 결정이 아니라 **프로세스의 귀결**입니다.
- 모노레포와 멀티레포 여부는 이 프로세스에서 다루지 않습니다. 개인 프로젝트는 주로 모노레포를 씁니다.

## 전역 규칙

프로세스 전체에 적용되며 단계별 규칙보다 우선합니다.

- **문서 우선 변경**: 요구사항이 바뀌면 코드가 아니라 requirements.md를 먼저 수정하고 코드가 문서를 따라옵니다. 이 순서가 무너지면 스펙은 죽은 문서가 됩니다. 단, **표면 변경(문구·색·간격)은 문서를 거치지 않습니다.** 동작과 플로우 변경만 문서를 거칩니다. 이 예외가 없으면 프로토타입 루프가 죽습니다.
- **이층 번호 불변**: 번호의 계층을 변동성의 계층과 맞춥니다.
  - **스토리 수준 번호**(요구사항 1, 2, 3)는 초안 생성 시점부터 불변입니다. 삭제는 결번 처리하고 사유를 기록하며, 추가는 말번으로 합니다.
  - **수용 기준 번호**(1.1, 1.2)는 requirements 확정 시점부터 불변입니다. 확정 전 초안 구간에는 부여하지 않습니다. 변동이 심한 층위에 불변 번호를 주면 결번이 쌓여 번호가 소음이 됩니다.
  - AI로 문서를 재생성한 뒤에는 번호가 유지됐는지 확인합니다.
- **문서는 판단, 강제는 훅**: 절대 어기면 안 되는 규칙(린트, 레이어 위반, 커밋 형식)은 훅과 린터로 강제합니다. 문서(steering)에는 판단이 필요한 규약만 남깁니다.

## 1. 요구사항 탐색 + 초안 생성

사전에 준비된 요구사항 관련 문서 또는 즉흥적인 인터뷰를 통해, AI에게 만들고자 하는 프로젝트의 기능들을 설명합니다.

- AI에게는 "구현하지 말고, 애매한 부분·엣지 케이스·빠진 시나리오를 질문으로 찾아내라"고 지시합니다. 인터뷰를 백로그로 바꾸는 단계입니다.
- 인터뷰가 끝나면 착수할 기능에 대해 **requirements.md를 초안(Draft) 상태로 생성**합니다.
  - **스토리 수준까지만** 작성합니다. 요구사항 1, 2, 3과 각 한두 줄 설명입니다. 스토리 층위는 만들기 전에도 안정적이므로("댓글 작성 기능이 있다") 이 번호는 처음부터 불변 규칙을 적용합니다.
  - 수용 기준(1.1, 1.2)은 아직 쓰지 않습니다. "어떻게 동작하는가"의 디테일은 프로토타입에서 발견될 것이기 때문입니다.
  - 문서 상단에 상태를 표기합니다: `상태: Draft`
- 이렇게 하면 프로토타입 커밋부터 요구사항 번호 채번이 가능하고, "화면 수정 → 관련 요구사항부터 본다"는 동선이 **프로젝트 전 구간에서 동일**해집니다. 규율이 하나여야 유지됩니다. 구간마다 규율이 다르면 반드시 느슨한 쪽으로 무너집니다.

## 2. UI 프로토타입 (진화형)

준비된 프레임워크와 문서를 에이전트 컨텍스트에 올려 UI를 먼저 만들고, 백엔드를 연결하기 전까지 반복 개선합니다.

### 규칙

- **목 계층은 교체 가능하게 둡니다.** UI는 서비스 인터페이스 뒤의 Mock 구현(`MockXxxService`)을 통해서만 데이터에 접근합니다. 컴포넌트에 목데이터를 직접 박지 않습니다.
  - 이 인터페이스의 **타입 정의가 이후 백엔드 스펙의 API 계약 입력**이 됩니다. 2번과 3번을 잇는 다리입니다.
  - 백엔드 연결은 대공사가 아니라 DI 프로바이더 교체와 계약 검증으로 축소됩니다.
- **정지 조건을 미리 정합니다.** "핵심 시나리오 N개가 목데이터로 시연 가능하면 이 단계를 종료한다"는 형태이며, 기능 착수 시 N개 시나리오를 명시해 무한 다듬기를 방지합니다.
- 프레임워크의 아키텍처·디자인 토큰 규약(steering)은 프로토타입에도 그대로 적용됩니다. 진화형이므로 이 코드가 곧 최종 코드입니다.
- **초안 문서와의 상호작용**은 다음과 같습니다.
  - 프로토타입 커밋은 스토리 수준 번호로 채번합니다 (`Requirements: 1`).
  - 다듬으면서 발견한 것들(동작 변경, 새 시나리오, 화면 밖 요구사항)은 초안 문서에 자유롭게 메모합니다. 단, 수용 기준 번호는 아직 박지 않습니다.
  - 스토리 자체가 추가되거나 폐기되면 초안에서도 말번 추가와 결번 처리를 합니다.

## 2.5. requirements 확정 게이트

프로토타입 정지 조건에 도달하면 **초안(Draft)을 확정(Confirmed)으로 승격**합니다. 새 문서를 만드는 것이 아니라 기존 초안을 완성하는 작업입니다.

- **수용 기준 기입**: 프로토타입으로 확정된 동작들을 "사용자가 X하면 Y가 된다" 형태로 각 스토리 아래 수용 기준(1.1, 1.2)으로 번호 매겨 기입합니다. 이 시점부터 수용 기준 번호도 불변 규칙에 들어갑니다.
- **기각 목록 부록**: 시도했다가 버린 대안과 기각 이유를 부록으로 붙입니다. 예를 들어 "무한스크롤 시도 → X 때문에 페이징으로 회귀" 형태입니다. 없으면 나중에 기각했던 안을 다시 시도하게 됩니다.
- **화면 밖 요구사항 반영**: 다듬는 중 발견했지만 화면으로 검증하지 못한 것들(권한, 오류 케이스, 데이터 제약, 동시성)을 수용 기준 또는 미해결 항목으로 기입합니다. 미해결 항목은 3번 스펙 작성 시 AI 인터뷰의 집중 대상이 됩니다.
- **상태 변경**: `상태: Draft → Confirmed`. 이 게이트를 통과해야 백엔드 착수가 가능합니다.

## 3. 스펙 심화 (백엔드 착수 직전)

백엔드를 연결할 때가 되면 확정된 requirements.md를 입력으로 스펙을 심화합니다. 프로토타입으로 검증하지 못한 영역(권한, 오류, 데이터 제약, 동시성 — 2.5의 미해결 항목)을 중심으로 AI 인터뷰를 돌려 수용 기준을 보강합니다. 화면으로 발견한 것과 논리로 발견할 것의 분업입니다.

### 기능의 단위

- 각 기능은 **에픽 1개 단위, 또는 유스케이스 2~5개** 수준입니다.
- 절단 기준은 "한 번의 스펙 → 구현 → 검증 루프로 완결해서, 그 자체로 동작하는 가치를 배포할 수 있는가"입니다.
- 스토리가 5~7개를 넘으면 쪼갭니다. 쪼갠 조각이 단독으로 검증할 것이 없으면 너무 잘게 자른 것입니다.
- 데이터 중심("Comment 스펙")이 아니라 **동작 중심**("대화 나누기")으로 이름 짓고 자릅니다.

### requirements.md

초안(1번)부터 확정·심화(2.5, 3번)까지 전 구간에 적용되는 서술 원칙입니다. **문서 형식은 [`docs/templates/requirements.template.md`](templates/requirements.template.md)를 따릅니다.** 에이전트에게 형식을 매번 설명하지 않고 CLAUDE.md에서 템플릿을 참조시킵니다. 형식 표준이 하나가 아니라서 템플릿 없이는 세션마다 문체가 달라지고, Draft/Confirmed와 이층 번호 같은 고유 규칙은 에이전트가 스스로 맞출 수 없습니다. 작성 규칙을 템플릿 안의 주석 블록에 두면 문서를 열 때마다 규칙이 컨텍스트에 실려, CLAUDE.md가 압축돼도 살아남는 이중 안전장치가 됩니다.

- **사용자가 보고 느끼는 기능 관점**에서 서술합니다.
- 포함과 제외 기준은 '화면이냐 아니냐'가 아니라 **'동작이냐 그림이냐'**입니다.
  - **포함**: 관찰 가능한 모든 동작 — 도메인 규칙과 UI 동작 둘 다입니다. "삭제 시 확인 단계를 거친다"는 화면 얘기지만 동작이므로 포함합니다.
  - **제외**: 구현 수단(steering과 design의 몫)과 미적 세부입니다. 색·간격·레이아웃은 디자인 토큰 또는 스크린샷 첨부로 대체합니다.
- **표기 형식을 하나로 고정합니다.** 수용 기준은 EARS 형식을 권장합니다 — "WHEN [조건] THEN 시스템은 [동작]을 SHALL 한다". 정하지 않으면 스펙마다 문체가 달라집니다.
- **넘버링**은 계층 번호(요구사항 1 → 수용 기준 1.1, 1.2)를 쓰며 전역 규칙의 이층 번호 불변 원칙을 따릅니다.

### design.md (조건부)

**문서 형식은 [`docs/templates/design.template.md`](templates/design.template.md)를 따릅니다.**

- 요구사항이 **일반적인 패턴이 아닐 때만** 해당 요구사항에 대응하는 design.md를 작성합니다.
- 내용은 "표준 패턴을 따르되 여기는 이런 이유로 다르게 간다"는 **편차와 그 근거**만 담습니다. 기존 패턴의 반복 서술을 금지합니다.
- **승격 규칙**: 같은 패턴이 다시 발현되면 전체 아키텍처 문서(steering)로 승격합니다.
- **승격 후 뒷정리**: 승격 시 원본 design.md의 해당 내용은 아키텍처 문서 참조로 대체하거나 삭제합니다. 같은 내용이 두 곳에 존재하면 반드시 어긋납니다.
- 승격 대상이 갈림길 결정이면 **결정 기록도 함께 발행합니다.** 편차는 정의상 "표준을 벗어난 이유"를 담으므로 검토한 대안과 트레이드오프가 이미 있는 경우가 많습니다. 근거를 steering 본문으로 흡수하면 "규칙은 steering, 근거는 결정 기록"이라는 분리가 깨집니다.

## 4. 구현

실제 코드 기능 구현을 진행합니다. 백엔드 스펙 작성 시 2번에서 확보한 목 서비스 인터페이스를 API 계약으로 입력합니다.

### 채번 규칙

- **커밋 푸터**에 `Spec: <기능명>` 과 `Requirements: <번호>` 를 포함합니다. `git log --grep` 으로 요구사항별 구현 이력을 추적할 수 있습니다.
- **테스트 코드**의 테스트명 또는 describe 블록에 요구사항 번호를 포함합니다. 예를 들어 `describe('1.2: 내용이 1000자 초과 시 저장 거부')` 형태입니다.
- 소스 주석 채번은 하지 않습니다. 코드가 여러 요구사항에 걸치기 시작하면 관리가 불가능해집니다.
- 빠뜨린 커밋을 소급 수정하는 완결성 집착은 하지 않습니다. 편하게 적되 빠뜨려도 스트레스받지 않는 수준으로 둡니다.

## 5. 검증 게이트

구현 완료의 정의는 "코드가 돌아감"이 아니라 **"수용 기준이 충족됨이 확인됨"**입니다.

- requirements.md의 수용 기준을 하나씩 짚으며 각각 어디서 어떻게 충족되는지 확인합니다.
- 테스트가 없는 수용 기준에는 테스트를 추가합니다. EARS 문장은 그대로 테스트 케이스로 번역됩니다.
- 이 게이트를 통과해야 기능이 완료된 것입니다.
