# 결정-0012: 인증 후 CSR 영역은 라우트 리졸버 + 임계 시간 오버레이로 로딩을 처리한다

- 상태: 승인됨
- 날짜: 2026-07-26

## 맥락

[결정-0011](결정-0011-렌더링-모드-경계.md)로 `app/**`가 CSR이 되면서, 그 영역의 로딩 UI를
정해야 했다. 두 전략은 전제가 다르다.

| | fetch-on-render (스켈레톤/스피너) | fetch-then-render (리졸버) |
|---|---|---|
| 컴포넌트 마운트 | 데이터 없이 먼저 | 데이터 준비 후 |
| 로딩을 아는 주체 | 컴포넌트 | 라우터 |
| 레이아웃 시프트 | 빈 상태→채워진 상태 구간에서 발생 | 그 구간이 페이지 안에 없음 |

### 사실 확인 (2026-07 리서치)

"Angular가 리졸버에서 멀어지는가"를 확인했다. **아니다.**

- deprecated된 것은 **클래스 기반** 리졸버(`Resolve` 인터페이스·`InjectionToken`)이며 v15.2에
  함수형 `ResolveFn`으로 대체됐다. 개념이 아니라 작성 방식이 바뀐 것이다
- [공식 가이드](https://angular.dev/guide/routing/data-resolvers)가 v22 문서에 현행으로 유지되고,
  `withComponentInputBinding()`으로 결과를 컴포넌트 input에 받는 방식을 권장한다
- 공식 문서가 드는 이점이 우리 동기와 같다: "빈 상태 방지", "중요 데이터에 대해 로딩 상태 불필요"
- 동시에 경고한다: 네비게이션 지연, **로딩 인디케이터 제공 필수**, 가벼운 구현 유지, 캐싱 고려
- Angular 22가 signal-first인 것은 맞지만(`resource`·`rxResource`·`httpResource` stable, `chain()` 추가),
  이는 **다른 축**이다 — 리졸버는 "언제 가져오는가"(라우팅), resource는 "비동기 상태를 어떻게
  모델링하는가"(상태). 둘의 문서가 나란히 현행인 것이 그 증거다

## 검토한 대안

- **fetch-on-render (스켈레톤)**: 기각. 스켈레톤은 치수를 실제 콘텐츠와 일치시켜야만 제 역할을
  하는데, 콘텐츠가 바뀔 때 함께 고치는 것을 잊으면 **스켈레톤 자체가 레이아웃 시프트를 만든다.**
  이 부채가 페이지 수만큼 쌓인다. 또한 로딩/에러/빈/완료 4상태 분기를 페이지마다 반복해야 한다
- **fetch-then-render (선택)**: 컴포넌트에 로딩 분기가 없다. 추가 비용(오버레이·캐시·에러 라우팅)은
  `shared`에 한 번 구현하는 **일회성**이며 페이지 수에 비례하지 않는다
- **signal/resource로 전부 대체**: 축이 다르므로 대체 관계가 아니다. 화면 안 갱신에는 오히려 우수하여
  아래 결정에서 역할을 나눠 채택했다

판단 근거를 세 관점으로 정리하면 — **UI 완성도**: 빈→채워짐 전환 구간이 없어 CLS 유발원이 차단된다.
**사용자 경험**: 인증 후 영역은 사용자가 이미 앱 안에 있고 API가 대체로 빠르므로 오버레이가
뜨는 일 자체가 드물다. 반면 스켈레톤은 오래 떠 있으면 "있는 척하다 사라지는" 불쾌감을 주고,
실제로 빈 목록이었을 때 특히 나쁘다. **코드 복잡도**: 일회성 인프라 대 페이지마다 반복.

## 결정

1. **라우트 진입 데이터는 함수형 `ResolveFn`**으로 확보하고, `withComponentInputBinding()`으로
   컴포넌트 `input()`에 바인딩한다.
2. **필수 데이터만 리졸버에 넣는다.** 부가 데이터는 화면 안에서 가져온다.
3. **전환 오버레이에 임계 시간 게이트(기본 150ms)를 둔다.** 그 안에 끝나는 전환에는 오버레이를
   띄우지 않는다. 게이트가 없으면 빠른 전환에서 깜빡이며, 페이드 아웃 때문에 더 도드라진다.
4. **캐시로 재방문을 즉시 처리한다(SWR).** 백그라운드 갱신 중에는 콘텐츠 영역을 비우지 않고
   얇은 상단 진행바로만 알린다.
5. **화면 안의 갱신은 `httpResource`**로 처리한다. 리스트·검색처럼 필터가 자주 바뀌는 화면은
   **진입만 리졸버, 이후 필터 변경은 `httpResource`** 로 하고 `runGuardsAndResolvers`를 확인한다.
   모달·버튼 클릭 요청도 로컬 로딩 UI를 쓴다.
6. **에러는 유형별로 분기한다.** 리졸버 에러가 네비게이션을 조용히 취소하게 두지 않는다 —
   사용자가 "클릭했는데 아무 일도 안 일어남"을 겪는다.
   - 401 → 로그인으로 리다이렉트(원래 경로 보존) / 403 → 권한 없음 / 404 → 전용 에러 페이지
   - 5xx·오프라인·rate limit → **같은 URL에 머물며** 재시도·안내 UI (URL은 유효하므로)
   - validation → 라우트 전환과 무관, 폼 인라인
7. 빈 상태는 최초 진입·검색 결과 없음·삭제 후 세 케이스를 구분한다.

규칙 전문은 [설계/웹.md](../설계/웹.md) §6.

## 재검토 조건

- Angular가 리졸버를 실제로 비권장하거나 동등한 대체 API를 내놓으면 재평가한다
- 실제 사용에서 오버레이가 자주 뜨면(느린 API) 리졸버 범위를 더 좁히거나 해당 화면만 fetch-on-render를 혼용한다
- 성능 예산·레이아웃 안정성(CWV 목표치, `scrollbar-gutter`, 폰트 fallback)은 실제 화면이 생긴 뒤 별도로 정한다

## 결과

- 페이지 컴포넌트에서 로딩 분기·undefined 처리가 사라진다
- 감수하는 것: 전환 오버레이·캐시·에러 라우팅 인프라를 `shared`에 먼저 만들어야 한다.
  느린 API가 있으면 진입이 지연되므로 "필수만 리졸버" 원칙이 실질적 방어선이다
