# 결정-0022: 소셜 제공자 토큰을 보관하지 않는다 — 스키마에서 칸을 없앤다

- 상태: 승인됨
- 날짜: 2026-07-29

## 맥락

당시 전제: Spring Boot 4.1, PostgreSQL, 소셜 제공자 2종(구글·카카오, AUTH-04 네이버는 폐기).
베이스라인 태그(v0.1) 이전이며 `V2__auth_schema.sql`이 배포된 적이 없다.

`accounts` 테이블은 처음부터 `access_token`·`refresh_token`·`token_expires_at` 세 칸을 갖고 있었다.
제공자(구글·카카오)가 발급한 토큰을 담기 위한 자리다 — 우리 세션 토큰이 아니다. 액세스 토큰은
수명이 짧고(구글 약 1시간, 카카오 약 6시간), 리프레시 토큰은 **사용자가 화면 앞에 없을 때** 새
액세스 토큰을 받기 위한 것이다. 즉 이 세 칸의 존재 이유는 하나뿐이다: **사용자를 대신해 그
제공자의 API를 호출하는 것.**

AUTH-02·03 구현 시점에 토큰을 저장하지 않기로 이미 판단했다(요구사항/인증.md, 2026-07-29). 쓸 데가
없고, 쓰지 않을 자격증명은 유출 시 피해만 키우기 때문이다. 다만 **칸은 스키마에 남겼다** — "채우면
되니 자리는 두자"는 판단이었다.

그 결과 지금 코드는 이렇게 생겼다. `SocialLoginSuccessHandler`가 `new SocialIdentity(provider,
name, null, null, null)`로 세 자리에 `null`을 넣고, 그 `null`이 `SocialIdentity` → `Account.social()`
→ `JooqAccountRepository`를 지나 DB의 빈 칸에 도달한다. **다섯 곳을 통과하는 값이 항상 `null`이다.**
승인자가 스키마를 읽다가 "이 값이 왜 필요한 건지"를 물었고, 그것이 이 결정의 계기다.

## 검토한 대안

- **칸을 남기고 주석으로 의도를 박는다**: 마이그레이션 SQL에 "제공자 API 위임 호출용 예약"을 적는다.
  나중에 필요해지면 마이그레이션 없이 채울 수 있다. 단점 — 죽은 칸이 계속 남고, `null`만 흐르는
  파라미터 세 개가 도메인·저장소·핸들러의 시그니처를 계속 부풀린다. 무엇보다 **"칸이 있으니 채우자"는
  유혹이 남는다.** 그때 평문 저장이 되면 우리 DB 유출이 남의 서비스 침해로 번진다.
- **칸을 남기고 지금 암호화 저장까지 구현한다**: 기각 — 쓰지 않는 값을 위해 키 관리·회전 설계를
  먼저 하는 셈이다. 순서가 거꾸로다.
- **칸을 지운다(채택)**: 스키마·도메인·저장소에서 함께 없앤다.

## 결정

**`accounts`에서 `access_token`·`refresh_token`·`token_expires_at` 세 칸을 제거한다.**
`SocialIdentity`·`Account`에서도 대응 필드를 없앤다.

**`V2__auth_schema.sql`을 직접 수정한다** — 새 마이그레이션을 추가하지 않는다. 이 마이그레이션은
아직 어디에도 배포되지 않았고 베이스라인 태그 전이다. 배포 이력이 없는 마이그레이션에 `drop column`
마이그레이션을 얹으면, 파생 프로젝트가 "만들었다 지우는" 이력을 그대로 물려받는다.

**이 결정은 [결정-0015](결정-0015-이메일-소유-증명.md)의 연장선이다.** 제공자에게서 받은 것을
필요 이상으로 들고 있지 않는다는 같은 원칙이다 — 이메일을 신뢰하지 않고 타입에서 없앴듯이,
토큰도 담을 자리 자체를 없앤다. **없는 칸은 잘못 채워질 수 없다.**

**[결정-0014](결정-0014-세션-방식.md) §결과의 마지막 항목**("`account` 테이블의 `accessToken`·
`refreshToken` 필드는 이 결정과 무관하게 그대로 유지된다")**을 이 결정이 대체한다.** 결정-0014의
본 결정(불투명 세션 토큰 + DB 조회)은 유효하며 영향받지 않는다 — 그 필드는 애초에 우리 세션과
무관한 제3자 토큰이었으므로, 그것을 없애는 것이 세션 방식을 건드리지 않는다.

## 결과

- **로그인 경로에서 `null` 세 개가 사라진다.** `SocialIdentity`는 제공자와 신원 식별자 둘만 남아
  "제공자가 증명하는 것은 신원 하나뿐"이라는 사실을 타입이 그대로 말한다.
- **"토큰을 보관하지 않는다"를 테스트로 지킬 필요가 없어진다.** 담을 자리가 없으므로 컴파일러가
  지킨다. 기존의 `assertThat(account.accessToken()).isNull()` 단언은 함께 제거했다.
- 감수하는 것: **제공자 API 위임 호출이 필요해지면 마이그레이션이 하나 더 든다.** 그때는 칸을
  되살리는 것으로 끝나지 않는다 — 저장 시 암호화와 키 회전을 함께 결정해야 하고, 그건 새 결정기록의
  몫이다. 칸이 남아 있었다면 그 결정 없이 채워질 수 있었다는 점에서, 이 비용은 대가가 아니라 안전장치다.
- 로컬 개발 DB는 Flyway 체크섬이 어긋난다 — 스키마를 지우고 다시 만들어야 한다(`flyway clean` 또는
  로컬 DB 재생성). 배포된 환경이 없으므로 운영 영향은 없다.

## 재검토 조건

- **PROF-04(소셜 연동 관리)처럼 제공자 API를 사용자 대신 호출하는 요구사항이 생길 때.** 그때
  이 결정을 대체하는 새 결정기록을 쓰되, 저장 시 암호화·키 회전·토큰 폐기 시점을 함께 정한다.
- 파생 프로젝트가 제공자 API 연동(캘린더·연락처 가져오기 등)을 핵심 기능으로 삼는 경우 — 키트
  단계에서 미리 넣지 않고, 그 프로젝트에서 위 조건에 따라 추가한다.
