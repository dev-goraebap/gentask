# 결정-0019: 1차 컴포넌트는 직접 만들고 헤드리스 라이브러리 선택은 2차로 미룬다

- 상태: 승인됨
- 날짜: 2026-07-27

## 맥락

디자인 시스템 컴포넌트를 만들 때 접근성·키보드·포커스·위치 지정 로직을 직접
떠안을지, 유지되는 헤드리스 라이브러리에서 조달할지 정해야 했다.

당시 전제: Angular 22, M1 인증 화면이 첫 소비자, 이후 M2 프로필·M3 파일업로드·
M4 알림이 이어진다.

**1차 컴포넌트와 2차 컴포넌트의 성질이 다르다는 것이 판단의 출발점이었다.**

| | 1차 | 2차 |
|---|---|---|
| 예 | Button · Input · Field · OtpInput · Card · Alert · Link · Spinner | Dialog · Sheet · Select · Dropdown · Tooltip · Tabs · Combobox |
| 어려운 동작 | **없음** | 포커스 트랩 · 위치 지정 · 리스트 키보드 내비 · 스크롤 잠금 · 인접 레이어 관리 |
| 직접 만들 때 위험 | 낮음 | 높음 — 접근성 결함이 눈에 보이지 않는다 |

1차에는 조달할 어려운 동작이 없다. 필요한 접근성은 네이티브 요소가 이미 갖고
있거나(버튼·입력의 키보드·폼 연동) 속성 배선 문제다(`label[for]`,
`aria-describedby`, `aria-invalid`).

## 검토한 대안

- **대안 A — 지금 라이브러리를 고르고 1차부터 그 위에 얹는다**
  - 장점: 2차에서 갈아타는 비용이 없다. 처음부터 일관된 기반.
  - 단점: **1차가 그 라이브러리를 실제로 쓰지 않는다.** 쓰지 않는 채로 선택을
    굳히면 무엇이 좋은 선택인지 판단할 근거가 없는 상태로 결정을 확정한다.
    Angular 생태계에서 후보(Angular CDK · Spartan · Ark UI Angular)의 유지보수
    상태와 적합성은 실제로 어려운 위젯을 만들 때 드러난다.
- **대안 B — 1차는 직접 만들고 2차 시작 시점에 고른다 (선택)**
  - 장점: 결정을 필요한 시점으로 미룬다. 2차를 시작할 때는 우리 토큰·컴포넌트
    계약이 이미 있어서 후보를 실제 요구에 대조할 수 있다.
  - 단점: 1차와 2차의 구현 방식이 달라질 수 있다. 다만 1차는 네이티브 요소 위의
    스타일·속성 배선이라 어떤 라이브러리를 골라도 그 위에 얹히지 않는다.
- **대안 C — 의견 키트(Material · PrimeNG · ng-zorro)**: 동작 + 표현 + **그들의
  디자인 의견**을 함께 들고 와 결정-0017에서 설계한 토큰을 덮는다. 톤 & 매너를
  직접 정하는 것이 이 키트의 목적이므로 방향이 반대다. **기각.**

## 결정

1. **1차 컴포넌트는 직접 만든다.** 헤드리스 라이브러리를 도입하지 않는다.
2. **네이티브 요소 위에 속성 선택자로 얹는다.** `button[ui-button]`,
   `input[ui-input]`. 래퍼 요소를 만들지 않으므로 폼 연동·네이티브 의미가 그대로
   살고 flex 레이아웃에서도 예상대로 동작한다. `<div>`에 역할을 붙여 컨트롤을
   만들지 않는다.
3. **접근성 배선은 컴포넌트가 가져간다.** `label[for]`↔`id`,
   `aria-describedby`, `aria-invalid`는 호출부에서 손으로 하면 반드시 빠뜨린다.
   `UiField`가 투영된 컨트롤을 `contentChild`로 찾아 밀어 넣는다.
4. **시각 표현을 접근성 속성에 묶는다.** 입력의 오류 테두리는 `aria-invalid`
   선택자로 걸린다 — 접근성 속성을 붙이는 것이 곧 시각 표현이므로 한쪽만 하는
   실수가 구조적으로 불가능해진다.
5. **2차를 시작할 때 헤드리스 라이브러리를 결정하고 새 결정기록을 남긴다.**
   그 시점에 후보의 최신 릴리스·이슈 건강도·Angular 버전 호환성을 검증한다
   (메모리에 의존하지 않는다).
6. **직접 만드는 경우에도 어려운 부분은 조각 유틸리티에 기댄다.** 포커스 트랩·
   위치 지정·리스트 키보드 내비를 손으로 쓰지 않는다.

## 재검토 조건

- **2차 컴포넌트를 시작할 때** — 이 결정이 예고한 시점이다. 그때 위젯 프리미티브를
  고르고 1차를 그 위로 옮길 필요가 있는지 함께 판단한다.
- **1차에 어려운 동작이 필요해질 때**(예: Input에 자동완성 드롭다운) — 그 컴포넌트가
  사실 2차라는 신호다. 미루지 않고 그 시점에 결정한다.
- **접근성 검토에서 직접 구현의 결함이 발견될 때** — 조달로 전환한다.

## 결과

- 쓰지 않는 라이브러리에 선택을 굳히지 않는다
- 1차 컴포넌트가 네이티브 요소 위에 얹히므로 어떤 라이브러리를 골라도 버려지지
  않는다 — 2차 결정이 1차를 무효화하지 않는다
- 의존성이 늘지 않아 파생 프로젝트가 물려받는 부채가 작다
- 감수하는 것
  - 1차의 접근성을 우리가 책임진다. 검증을 문서가 아니라 **확인 가능한 형태**로
    남겨야 한다 — 현재는 워크벤치에서 브라우저로 속성을 확인했고, 자동 검사는
    2차 시작 시 Vitest 애드온으로 붙인다
  - 1차와 2차의 구현 방식이 달라 보일 수 있다. 계약(`디자인시스템.md` §8)이
    같으므로 호출부에서는 차이가 드러나지 않는다
