# 결정-0015: 이메일 소유 증명은 제공자 주장이 아니라 자체 OTP로 한다

- 상태: 승인됨
- 날짜: 2026-07-27

## 맥락

[결정-0014](결정-0014-세션-방식.md)로 세션 방식을 정한 뒤, 남은 미결은 **소셜 제공자가 알려주는
이메일 검증 여부를 어떻게 다루느냐**였다. AUTH-05(이메일 키 통합)의 원래 설계는 제공자가 준
이메일을 통합 키로 쓰고, 제공자가 "이 이메일을 검증했다"고 알려줄 때만 자동 연결하는 것이었다.
그 전제에서 **네이버가 검증 여부를 제공하는지 확인되지 않은 상태**였고, 확인 결과에 따라
AUTH-05의 동작이 제공자별로 갈릴 예정이었다.

당시 전제: 제공자 3종(구글·카카오·네이버), 4테이블 구조(`user`/`session`/`account`/`verification`),
`user.email`이 계정 전체에서 유일, same-origin 배포, 향후 모바일 앱 추가 가능.
그리고 **[계획](../계획.md)의 비범위에 있는 결제를 나중에 편입할 가능성**이 논의의 무게를 바꿨다.

### 확인한 사실

**제공자별 이메일 검증 신호**

| 제공자 | 검증 신호 | 비고 |
|---|---|---|
| 구글 | `email_verified` (OIDC 표준) | 있음 |
| 카카오 | `is_email_verified` | 있음. 별도로 `is_email_valid`("다른 카카오계정에 사용돼 만료")도 제공 |
| 네이버 | **없음** | 프로필 응답은 `id`·`age`·`birthday`·`birthyear`·`email`·`gender`·`mobile`·`name`·`nickname`·`profile_image` |

네이버만의 문제가 아니다. Facebook·Twitter·Twitch·Spotify·WindowsLive·WorkOS도 명시적 검증
플래그가 없다. 즉 **제공자 이메일을 신뢰하는 설계는 제공자를 추가할 때마다 인증 로직을
재검토해야 하는 부채**다. 키트는 파생 프로젝트가 제공자를 추가할 것을 전제하므로 이 부채가 크다.

카카오 문서는 두 가지를 직접 경고한다 — "유효 여부와 인증 여부를 항상 확인하고 사용해야 한다",
그리고 **"이메일을 ID나 유일성 기준으로 쓰지 말 것"**(사용자가 변경할 수 있기 때문). AUTH-05의
원래 설계가 정면으로 걸리는 지점이다.

**pre-hijacking 실측 결과**

[Pre-hijacked accounts (USENIX Security 2022)](https://www.usenix.org/conference/usenixsecurity22/presentation/sudhodanan)는
인기 사이트 75개 중 **최소 35개**가 취약함을 실측했다(Instagram·LinkedIn·Dropbox·Zoom·WordPress.com 포함).
5가지 변종 중 둘이 이 결정과 직결된다.

- **Classic-Federated Merge**: 공격자가 피해자 이메일로 비밀번호 가입 → 미검증 계정이 함정으로 잠들어
  있다가 → 피해자가 나중에 같은 이메일로 소셜 로그인 → 병합되면 공격자의 비밀번호가 피해자 계정에 남는다.
  공격자는 검증을 통과할 필요가 없다. **검증은 피해자가 소셜 로그인으로 대신 해준다.**
- **Non-Verifying IdP**: 위의 거울상 — 검증하지 않는 제공자로 공격자가 먼저 가입한다.

논문이 지목한 근본 원인은 하나다: *서비스가 계정 기능을 허용하기 전에 사용자가 그 식별자를 실제로
소유하는지 검증하지 않는다.* 권고도 그대로다 — *strict identifier verification before enabling any
account features.*

**"보편적 관행"은 두 층으로 갈린다**

- 일반 웹앱용 라이브러리(Better Auth 등): 자동 병합이 기본값이지만 **제공자가 검증을 확인했거나
  신뢰 목록에 있을 때만**. 아니면 거절한다. 신뢰 목록에는 "계정 탈취 위험을 높인다"는 경고가 붙어 있다.
- IdP 제품(Auth0): 검증된 이메일이어도 자동 연결하지 않는다. 근거는 "검증된 이메일은 사용자가
  **지금** 두 계정 모두에 인증할 수 있다는 증거가 못 된다"는 것. 두 계정 모두에 로그인시킨 뒤 연결한다.

즉 다수 관행이 곧 안전은 아니다 — 그 다수의 절반이 실제로 취약했다.

### 결제를 붙일 계획이 이 결정의 무게를 바꾼다

1. **탈취의 값이 올라간다.** 저장된 결제수단·활성 구독이 들어 있는 계정은 탈취 시 정상 구매 이력
   때문에 기본 사기 탐지를 통과하고, 가맹점은 상품과 차지백으로 두 번 손해를 본다. 구독은 차지백이
   도착하기까지 몇 달간 이행이 계속되어 더 나쁘다.
2. **중복 계정이 돈 문제가 된다.** 소셜로 구독한 사용자가 나중에 비밀번호로 로그인하면 구독이 보이지
   않는다. 결과는 문의·이중 결제·카드사 분쟁이며, 권한 판정이 `user` 단위인데 `user`가 쪼개지면
   판정 자체가 틀린다.
3. **사후 병합이 사실상 불가능하다.** 결제 전이면 계정 병합은 행 몇 개 옮기는 일이다. 결제 후에는
   Stripe Customer·구독·인보이스·결제수단·세금 기록이 각 `user`에 붙어 있고 **Stripe는 구독을
   Customer 간에 이관해주지 않는다** — 취소·재생성해야 하며 청구 주기와 인보이스 이력이 깨진다.

따라서 **`user` 정체성은 결제를 붙이기 전에 확정해야 한다.** 지금 느슨하게 두고 나중에 조이는 선택은
존재하지 않는다.

## 검토한 대안

### 이메일 소유를 무엇으로 증명할 것인가

- **대안 A — 제공자 이메일을 신뢰하고, 검증된 경우에만 자동 병합** (Better Auth 기본값, 주류)
  - 장점: 소셜 가입이 1단계로 끝난다. 구현이 가장 적다.
  - 단점: 네이버는 신호가 없어 제공자별로 동작이 갈린다. 제공자를 추가할 때마다 신호 유무를
    재조사해야 한다. 카카오 문서가 경고하는 "이메일을 유일성 기준으로 쓰기"를 그대로 한다.
- **대안 B — 연동 시 두 계정 모두에 인증 요구** (Auth0 권고)
  - 장점: 가장 보수적이며 "지금 접근 가능함"을 증명한다.
  - 단점: 임의의 IdP를 상대하는 제품의 기준이다. 제공자가 3종으로 고정된 우리 상황에는 과하고,
    소셜 로그인마다 추가 인증이 붙어 UX 비용이 크다.
- **대안 C — 사용자가 직접 입력한 이메일을 자체 OTP로 증명 (선택)**
  - 장점: 제공자의 검증 신호에 의존하지 않으므로 **제공자를 추가해도 인증 로직을 건드릴 필요가
    없다**(키트 성격상 결정적). 신뢰 근원이 우리 쪽에 있어 제공자별 분기가 사라진다.
    소유 증명을 가입 선행 조건으로 두면 pre-hijacking 5종 중 3종이 전제부터 성립하지 않는다.
  - 단점: 소셜 최초 로그인이 2단계가 된다. OTP 인프라(발급·검증·rate limit)를 직접 책임진다.

### 증명 수단: OTP vs 매직링크

| 축 | OTP(6자리) | 매직링크 |
|---|---|---|
| 컨텍스트 유지 | 원래 탭에 머문다 | 새 탭·인앱 브라우저에서 열려 컨텍스트가 끊긴다 |
| 메일 스캐너 프리페치 | 해당 없음 | 안티피싱 프록시가 사용자보다 먼저 토큰을 소진한다 |
| 추측 저항 | 10⁶ — 시도 제한 필수 | 128비트 — 원천 안전 |
| 향후 모바일 앱 | 코드 입력으로 끝 | Universal Links·App Links 설정 필요 |
| 발송 채널 교체 | 채널 무관(메일→SMS 자유) | 메일 + 도메인 설정에 묶인다 |

매직링크가 우세한 축은 엔트로피 하나이며 표준 방어책으로 메울 수 있다. 반면 우리는 **소셜 최초
로그인 중간에 이메일 증명을 끼워넣기로** 했으므로 컨텍스트 유지가 결정적이다 — 매직링크는 제공자
인증을 마친 브라우저와 링크가 열리는 브라우저가 달라 중간 상태를 서버측에서 이어붙여야 한다.

## 결정

**대안 C를 택하고, 증명 수단은 OTP로 한다.**

1. **이메일은 사용자가 직접 입력하고 자체 OTP로 소유를 증명한다.** 소유 증명 없이는 계정이 생기지
   않는다 — 이것이 이 결정의 핵심이며, AUTH-01의 "가입 후 검증" 정책을 "증명 선행"으로 바꾼다.
2. **소셜 제공자가 준 이메일은 신뢰하지 않는다.** 이메일 scope를 요구하지 않으며, 받더라도 입력칸
   기본값(편의) 이상으로 쓰지 않는다. 제공자는 신원만 증명한다.
3. **OTP 파라미터**
   - 6자리, CSPRNG(`SecureRandom`), 앞자리 0 허용(zero-pad)
   - 만료 10분, 1회용(사용 즉시 폐기)
   - **시도 5회 실패 시 코드 폐기** 후 재발송 요구
   - 저장은 **앱 시크릿을 키로 하는 HMAC-SHA256**. 평문 금지. 단순 해시는 10⁶ 전수라 DB 유출 시
     즉시 복원되고, bcrypt는 불필요하게 느려 rate limit과 겹치면 DoS 지점이 된다
   - 발송 rate limit은 **비대칭**으로 둔다 — IP별을 촘촘히, 이메일별은 넉넉히. 이메일별만 조이면
     공격자가 한도를 소진시켜 정상 가입을 막는 서비스 거부가 된다
   - 메일 본문에 "요청하지 않았다면 이 코드를 누구에게도 알려주지 마세요"를 넣는다
4. **계정 생성 시점과 대기 레코드** — 이 항목이 지켜지지 않으면 위 결정이 무의미해진다
   - **코드 발급 단계에서 `user` 행을 만들지 않는다.** 대기 중인 가입 시도는 `verification`에만 둔다.
     편의상 "pending user"를 미리 만들면 없앤 함정이 되살아난다
   - **이메일 유일성 제약은 `user`에만 걸고 대기 레코드에는 걸지 않는다.** 대기 시도가 이메일을
     예약하면 공격자가 코드 발급만 반복해 선점할 수 있다. 같은 이메일에 여러 대기 시도가 동시에
     존재할 수 있고, 먼저 코드를 맞힌 쪽이 계정을 얻는다
   - **OTP 검증은 `(이메일, 코드)`가 아니라 대기 레코드 식별자로 조회한다.** 시작 시점에 발급한
     식별자를 클라이언트가 들고 있어야 한다. 이메일과 코드만으로 찾으면, 공격자가 피해자 이메일로
     시작한 대기 레코드(공격자의 소셜 신원이 붙어 있다)를 피해자가 자기 화면에서 완성시켜버리는
     공격이 성립한다
   - 소셜 최초 로그인의 검증된 제공자 신원은 대기 레코드에 함께 담긴다. `account.userId`가
     NOT NULL이므로 `user` 없이 `account`에 둘 수 없다
   - **OTP 통과 후 세션 토큰을 새로 발급한다.** 대기 단계의 토큰을 승격시키면 세션 고정이 된다
5. **이메일 동일성 판정**
   - 소문자화 + 앞뒤 공백 제거는 한다
   - **점 제거·플러스 태그 제거는 하지 않는다.** Gmail은 같은 함으로 취급하지만 다른 제공자는 다른
     주소로 취급하므로, 제거하면 그쪽에서 남의 주소로 가입되는 사고가 난다
   - 원문을 저장하고 유일성 제약은 정규화된 값에 건다
6. **AUTH-05 연동 규칙은 기존 방침을 유지한다.** 이메일 입력 단계에서 기존 계정이 발견되면 OTP를
   보내지 않고 "로그인 후 연동" 경로로 안내한다. 연동 경로에 OTP가 들어가지 않으므로 훔칠 코드가
   없고, 기존 계정에 로그인하는 것 자체가 대안 B가 요구하는 "양쪽 인증"을 충족한다.
   추가 분기를 두지 않는다.
7. **`account`의 키는 `(provider, providerAccountId)`이며 유니크다.** 제공자의 subject id(구글 `sub`,
   카카오 numeric id, 네이버 `id`)로 잡는다. 이메일을 제공자 식별 키로 쓰지 않는다.
8. **`verification`은 다목적이므로 용도(`purpose`) 컬럼을 두고 조회에서 항상 필터한다.** 가입·이메일
   변경·비밀번호 재설정·로그인 복구가 같은 테이블을 쓴다. 이메일 변경용 코드가 비밀번호 재설정에
   통과하면 그것만으로 계정 탈취다.
9. **메일 발송은 트랜잭션 커밋 이후에 한다.** 트랜잭션 안에서 발송하면 롤백 시 유령 코드가 나간다.
   발송 실패는 재발송으로 복구한다([결정-0016](결정-0016-메일-발송-인프라.md)).
10. **이메일이 계정의 최상위 신뢰 근원이 된다는 사실을 명시한다.** 메일함을 장악한 사람은 계정을
    장악한다. 비밀번호 재설정이 있는 거의 모든 서비스가 이미 그런 구조이므로 새로 생기는 약점은
    아니지만, 민감한 도메인의 파생 프로젝트는 여기에 2단계 인증을 얹어야 한다는 신호로 삼는다.

스키마의 컬럼·인덱스 수준 상세는 `docs/설계/데이터베이스.md`에서 정한다.

## 재검토 조건

- **제공자가 우리보다 강한 신원 보증을 주는 경우** — 예를 들어 기업 SSO(OIDC `email_verified` +
  도메인 소유 증명)를 편입할 때. 그때는 그 제공자에 한해 OTP를 생략하는 예외를 결정기록으로 남긴다.
- **OTP 발송 비용·도달률이 문제가 되는 경우** — 발송 채널을 바꾸는 것으로 대응한다. OTP는 채널에
  무관하므로 이 결정 자체는 유지된다.
- **가입 이탈률이 실제로 측정되어 문제로 확인되는 경우** — 소셜 2단계를 완화하는 방안(대안 A로의
  부분 회귀)을 그때 검토한다. 다만 결제가 이미 붙어 있으면 되돌리는 비용이 크다.

## 결과

- pre-hijacking 5종 중 **Classic-Federated Merge · Non-Verifying IdP · Trojan Identifier가 전제부터
  성립하지 않는다.** 함정 계정이 만들어질 수 없기 때문이다. 남은 둘은 세션 무효화(AUTH-07)와
  이메일 변경 정책(PROF-05)이 담당한다
- 이메일 스쿼팅(남의 이메일 선점으로 정상 가입 차단)이 불가능해진다
- **제공자를 추가해도 인증 로직을 재검토할 필요가 없다.** 파생 프로젝트가 애플·깃허브 등을 붙일 때
  검증 신호 유무를 조사하지 않아도 된다 — 키트로서 가장 큰 이득
- `user` 정체성이 결제를 붙이기 전에 확정되므로, 사후 병합의 불가능성을 피한다
- 감수하는 것
  - **소셜 최초 로그인이 2단계가 된다.** 제공자 인증 후 이메일 입력·OTP를 거친다
  - OTP 발급·검증·rate limit·재발송을 직접 책임진다. 매직링크보다 방어 항목이 많다
  - 플러스 태그를 허용하므로 한 사람이 계정을 여럿 만들 수 있다. 결제 편입 시 무료 체험 남용
    경로가 되며, 인증 계층이 아니라 남용 방지 계층에서 다룬다
  - 가입·연동 흐름은 계정 존재 여부를 완전히 숨길 수 없다. 화면에는 "입력하신 주소로 안내 메일을
    보냈습니다"만 노출하고 실제 분기를 메일 내용으로 가르는 완화책을 설계에서 검토한다
