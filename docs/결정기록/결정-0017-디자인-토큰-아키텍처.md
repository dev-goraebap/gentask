# 결정-0017: 디자인 토큰은 3계층 CSS 변수로 두고 DTCG 빌드는 도입하지 않는다

- 상태: 대체됨(→ [결정-0024](결정-0024-디자인-시스템-krill-채택.md))
- 날짜: 2026-07-27

> 2026-08-03에 디자인 시스템을 Krill로 교체하며 이 결정을 대체했다. 3계층 구조·`light-dark()`
> 전환·역할 기반 반경 이름은 더 이상 유효하지 않다. **대비 검증을 테스트로 강제한다(§8)는
> 판단은 살아남았고** 결정-0024가 Krill의 계약에 맞게 다시 썼다.

## 맥락

M1 인증 화면을 만들기 전에 디자인 시스템 기반이 필요했다. 톤 & 매너의 출처는
구매한 상용 팩(Halo, 다크 전용)이며 그 원본은 저장소 밖의 추적되지 않는 위치에
둔다.

당시 전제: Angular 22 + Tailwind 4, 대상 플랫폼은 웹 하나, 라이트·다크 양쪽 지원
필요(사람 결정), 파생 프로젝트마다 톤 & 매너가 달라진다는 키트 특성.

핵심 제약이 둘이었다.

1. **파생 프로젝트가 각자 다른 테마를 쓴다.** 컴포넌트에 한 브랜드의 팔레트가
   박히면 파생 프로젝트가 매번 컴포넌트를 뜯어야 한다.
2. **출처 팩이 다크 전용이다.** 라이트 단계와 신호색의 어두운 변형이 없어서
   우리가 설계해야 했고, 단순 반전으로는 되지 않았다 — 팩의 라임을 흰 배경에
   얹으면 1.6:1이고 액센트에 흰 텍스트를 얹으면 4.21:1로 AA에 미달한다.

## 검토한 대안

### 토큰을 어디에 두는가

- **대안 A — DTCG JSON + Style Dictionary 빌드**: `foundation` 스킬이 권하는
  구성이다. 토큰을 `$value`/`$type` JSON으로 두고 빌드 단계가 CSS 변수·Tailwind
  테마·TS 상수를 생성한다.
  - 장점: 여러 플랫폼(웹·iOS·Android·Figma)으로 같은 토큰을 내보낼 수 있다.
    도구 생태계가 있다.
  - 단점: **Tailwind 4의 `@theme`이 이미 토큰 계층이다.** 빌드 단계를 얹으면
    Tailwind가 이미 소비하는 것을 생성하기 위해 파이프라인을 하나 더 유지한다.
    대상 플랫폼이 웹 하나라 다중 내보내기의 값이 실현되지 않는다.
- **대안 B — CSS 커스텀 프로퍼티 3계층 (선택)**: 프리미티브 → 시맨틱(Tailwind
  `@theme`) → 컴포넌트.
  - 장점: 빌드 단계가 없다. 값의 정본이 CSS 한 곳이고, 브라우저가 직접 읽는
    것과 우리가 쓰는 것이 같은 파일이라 어긋날 여지가 없다.
  - 단점: 다중 플랫폼 내보내기가 안 된다. 토큰 문서를 손으로 유지한다.

### 라이트/다크를 어떻게 전환하는가

- **모드별 블록을 따로 둔다**: `:root`에 라이트, `@media (prefers-color-scheme:
  dark)`와 `[data-theme='dark']`에 다크. 견고하지만 **같은 목록을 두세 번 쓴다**.
  한쪽만 고치는 실수가 반드시 생긴다.
- **`light-dark()` (선택)**: 두 값을 한 줄에 선언하고 `color-scheme`이 고른다.
  중복이 없어 구조적으로 어긋날 수 없다. 대가는 지원 범위 — Tailwind 4가 이미
  요구하는 것보다 약간 새롭다(Safari 17.5+).

## 결정

1. **토큰은 3계층 CSS 커스텀 프로퍼티로 둔다.** DTCG + 빌드 도구는 도입하지 않는다.
   - 프리미티브 `--prim-*` — 원시 값. `themes/*.css`. 교체 단위
   - 시맨틱 `--color-*`·`--text-*`·`--radius-*` — 역할 이름. Tailwind `@theme`에
     선언해 유틸리티가 함께 생성된다
   - 컴포넌트 — **시맨틱만 읽는다.** 프리미티브를 직접 읽지 않는다
2. **프리미티브 이름은 색조가 아니라 팔레트 위치로 부른다**(`--prim-accent-500`).
   초록 액센트 팔레트가 들어와도 이름이 거짓말이 되지 않는다. **숫자는 항상
   밝기이며 작을수록 밝다** — 이 규칙 덕에 라이트·다크가 같은 이름에서 서로 다른
   단계를 골라 쓸 수 있다.
3. **새 팔레트는 `--prim-*` 목록을 전부 정의해야 한다.** 그 목록이 팔레트와
   시맨틱 계층 사이의 계약이며, 교체는 파일 한 줄 바꾸기다.
4. **색상 모드는 `light-dark()`로 전환한다.** 기본은 OS 선호(`color-scheme:
   light dark`), 명시적 전환은 `[data-theme]`이며 `:root`에 한정하지 않아 하위
   트리에도 걸린다.
5. **그림자는 모드별 블록으로 덮는다.** `light-dark()`의 구현 지원이 색상 값에
   집중되어 있어 색이 아닌 값에는 쓰지 않는다. 값이 셋뿐이라 중복 비용이 작다.
6. **간격 토큰을 만들지 않는다.** 출처 팩의 간격 스케일이 Tailwind 기본 스케일과
   같아서 `p-6` = 24px가 이미 성립한다.
7. **반경·타입은 크기가 아니라 역할로 이름 붙인다**(`rounded-control`,
   `text-headline-lg`). 타입 토큰에는 굵기·행간·자간을 함께 담아 호출부가 네 값을
   매번 고르지 않게 한다.
8. **대비 검증을 테스트로 강제한다.** `contrast.spec.ts`가 실제 CSS를 파싱해
   WCAG 대비를 계산한다. 문서에만 적어두면 다음 사람이 다시 돌리지 않는다.
   본문·보조 텍스트는 AA 4.5:1, 비활성·경계선·채움은 UI 3:1.
9. **채움과 잉크를 분리한다**(`accent`/`accent-ink`, `danger-fill`/`danger`).
   채움은 그 위의 흰 텍스트가 AA를 넘어야 하고 잉크는 캔버스 위에서 AA를 넘어야
   해서 한 값으로 두 조건을 만족할 수 없다.
10. **원칙은 `docs/설계/디자인시스템.md`에 자족적으로 쓴다.** 출처 팩 문서는
    저장소 밖에 있어 사라질 수 있으므로, 그것 없이도 판단할 수 있어야 한다.

## 재검토 조건

- **네이티브 앱이나 Figma 동기화가 필요해질 때** — 그때 DTCG + Style Dictionary를
  도입한다. 시맨틱 이름을 이미 역할 기반으로 잡아 뒀으므로 JSON으로 옮기는
  작업이며 재설계가 아니다.
- **`light-dark()`를 못 쓰는 브라우저를 지원해야 할 때** — 모드별 블록으로
  전환한다. 시맨틱 이름은 그대로이므로 컴포넌트는 바뀌지 않는다.
- **토큰이 손으로 유지하기 어려운 규모가 될 때**(팔레트 여러 벌, 브랜드 여러 개)
  — 생성 도구를 검토한다.

## 결과

- 테마 교체가 프리미티브 파일 하나 교체다. 컴포넌트·문서·워크벤치는 그대로 간다
- 빌드 단계가 없어 클론 직후 동작한다(결정-0013과 같은 기준)
- 라이트·다크가 한 줄에 함께 선언되어 한쪽만 고치는 실수가 불가능하다
- 대비가 회귀하면 테스트가 그 자리에서 실패한다. 값을 일부러 깨서 확인했다
- 감수하는 것
  - **다중 플랫폼 내보내기가 안 된다.** 웹 하나인 동안은 손실이 없다
  - 토큰 문서(`디자인시스템.md`)를 손으로 유지한다. 값이 바뀌면 표를 함께 고쳐야
    하며, 이것이 어긋날 여지가 남는 유일한 지점이다
  - `light-dark()`는 Safari 17.5+를 요구한다. Tailwind 4의 하한(16.4)보다 높다
  - 하위 트리 모드 전환을 허용한 대가로 **`color` 상속 함정**이 생긴다. 경계에서
    전경색을 다시 선언하지 않으면 바깥 모드의 계산값이 내려온다. `@layer base`의
    `[data-theme] { color: ... }`로 막았다
