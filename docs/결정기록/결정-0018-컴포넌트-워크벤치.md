# 결정-0018: 컴포넌트 워크벤치는 Storybook(angular-vite)으로 한다

- 상태: 승인됨
- 날짜: 2026-07-27

## 맥락

디자인 시스템 컴포넌트를 앱 화면 없이 격리해서 보고 검토할 곳이 필요했다.
라이트·다크 양쪽을 지원하기로 했으므로(결정-0017) **두 모드를 함께 볼 수 있는지**가
특히 중요했다 — 한 모드만 보면 다른 쪽이 깨진 것을 늦게 발견한다.

당시 전제: Angular 22, `@angular/build`(Vite 기반), **zoneless**(`angular.json`에
polyfills 없음), TypeScript 6, Tailwind 4, Vitest 4 이미 설치됨, SSR 사용.

키트 특성이 판단에 걸렸다. **워크벤치 설정은 파생 프로젝트가 물려받아 유지해야
하는 부채다.** 결정-0013에서 "클론 직후 Docker 없이 빌드"를 기준으로 삼은 것과
같은 종류의 고민이었다.

## 검토한 대안

- **대안 A — Storybook (`@storybook/angular-vite`) (선택)**
  - 장점: 사실상 표준. 애드온 생태계(a11y 검사, 뷰포트, 상호작용 테스트). 스토리
    포맷이 널리 알려져 있어 파생 프로젝트가 이해하기 쉽다. 링크로 공유 가능.
  - 단점: preview 상태(문서가 "APIs and defaults may change"라고 밝힌다).
    `@analogjs/vite-plugin-angular`(서드파티) 의존. Vite 버전이 둘로 갈린다
    (Angular 22는 7.x, Storybook은 8.x를 요구).
- **대안 B — Storybook (webpack, `@storybook/angular`)**: stable이지만 레거시
  `@angular-devkit/build-angular`를 peer로 요구한다. 우리는 `@angular/build`를
  쓰므로 빌드 툴체인이 둘이 된다. **기각.**
- **대안 C — 자체 워크벤치 라우트 + Vitest**: `/dev/ui`에 컴포넌트 갤러리를 두고
  자동 검증은 이미 있는 Vitest가 맡는다. 의존성 0, 버전 리스크 0. 잃는 것은 격리
  렌더링과 애드온이며, a11y 자동 검사를 재현하려면 결국 직접 만들게 된다.
  **Storybook이 동작함을 확인해 채택하지 않았다.**
- **대안 D — 정적 빌드 + 서빙**: `storybook build` 결과를 서빙한다. HMR이 없어
  값 하나 바꿀 때마다 10~20초 전체 재빌드를 수동으로 돌려야 한다. 디자인 시스템
  작업은 "바꾸고 눈으로 확인"의 반복이라 이 비용이 크다. **기각.**

## 검증한 것

Storybook을 고르기 전에 **실제로 도는지 확인했다.** 문서만으로는 우리 조합
(Angular 22 + `@angular/build` + zoneless + SSR)에서의 동작을 알 수 없었다.

시그널로 갱신되는 컴포넌트를 워크벤치에 올려 브라우저에서 클릭했다. 정적
컴포넌트는 변경 감지가 깨져 있어도 렌더링되므로 검증이 되지 않는다.

- dev 서버·정적 빌드 **양쪽에서** 클릭 수만큼 DOM이 갱신됐다
- `window.Zone === undefined` — **zone.js 없이 동작한다.** peer로 선언되어 있지만
  실제로 설치되지 않으며, 앱의 zoneless 구성을 워크벤치가 깨지 않는다

이것이 가장 걱정했던 지점이었다. 워크벤치만 zone.js를 되살리면 한쪽에서만
재현되는 변경 감지 버그가 생긴다. 그 위험은 실재하지 않았다.

## 결정

1. **`@storybook/angular-vite`를 쓴다.** `@angular/build`와 같은 Vite 계열이고
   Vitest 애드온으로 상호작용 테스트를 붙일 수 있다.
2. **`.storybook/tsconfig.json`을 반드시 둔다.** 프리셋이 Angular 변환 플러그인에
   이 경로를 넘긴다. 없으면 TypeScript 타입과 `@Component` 데코레이터가 변환되지
   않은 채 브라우저로 나가 프리뷰가 `SyntaxError`로 멈춘다. **그 에러는 화면에
   표시되지 않고 "스토리 준비 중" 상태로 보이므로 원인을 찾기 어렵다.**
3. **`preview.ts`에 애플리케이션 프로바이더를 추가하지 않는다.** 워크벤치가 앱과
   다른 변경 감지 설정을 쓰면 한쪽에서만 재현되는 버그가 생긴다. 전역 스타일만
   앱과 공유한다.
4. **모든 컴포넌트 스토리는 라이트·다크를 나란히 띄운다.** `[data-theme]`을 하위
   트리에 걸 수 있게 만들어 둔 덕에 한 화면에 둘을 넣을 수 있다.
5. **`format:check`가 `.storybook`도 검사한다.** 설정 파일이 포맷 게이트 밖에
   있으면 반드시 어긋난다.

## 재검토 조건

- **`@storybook/angular-vite`가 stable에서 벗어나 깨지는 경우** — 대안 C(자체
  워크벤치 + Vitest)로 전환한다. 스토리는 컴포넌트를 참조하는 얇은 파일이므로
  전환 비용이 스토리 재작성에 한정된다.
- **Angular 메이저 업그레이드에서 Storybook이 따라오지 못하는 경우** — 같다.
  업그레이드를 Storybook에 묶어 미루지 않는다.
- **디자이너와 협업하거나 팀이 커지는 경우** — 애드온(a11y 자동 검사, 디자인
  리뷰 링크 공유)의 값이 올라간다. 이 결정이 그 방향에 유리하다.

## 결과

- 컴포넌트를 앱 화면 없이 격리해서 보고, 두 모드를 동시에 비교할 수 있다
- HMR이 있어 값을 바꾸고 바로 확인하는 반복이 빠르다
- zoneless 구성이 워크벤치 때문에 흐트러지지 않는다
- 감수하는 것
  - preview 상태 도구를 키트 기본값으로 둔다. 파생 프로젝트가 물려받는 부채다
  - Vite 버전이 트리에 둘 존재한다(Angular 7.x / Storybook 8.x). 현재 문제를
    일으키지 않지만 플러그인 동작이 갈릴 여지가 있다
  - `@analogjs/vite-plugin-angular`(서드파티)에 간접 의존한다

## 메모 — 로컬 환경

이 저장소의 로컬 폴더명에 `&`가 들어 있어 Windows cmd 셔임이 깨지고
`npm run storybook`이 동작하지 않는다. 바이너리를 직접 호출해 우회한다.

```bash
cd web && node ./node_modules/storybook/dist/bin/dispatcher.js dev -p 6006
```

파생 프로젝트의 정상 경로에서는 스크립트가 그대로 동작하므로 키트 결함이 아니다.
