# 결정-0003: git 전략 — 가벼운 GitHub Flow (이슈 → 브랜치 → PR → squash 머지)

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

M0에서 코드 변경 작업(린트 구성)이 시작되면서 브랜치·커밋·머지 규칙이 필요해졌다.
운영 주체는 1인(devgo) + AI 에이전트이며, 형상관리 요건(SP 3.2 — main은 항상
베이스라인 가능한 상태 유지)과 1인 체제의 낮은 프로세스 비용을 동시에 만족해야 한다.

당시 전제: GitHub 단일 원격 저장소(webapp-devkit), CI는 아직 미구성(#4 예정),
QA 페르소나 에이전트 미구성(#3 예정).

## 검토한 대안

- **trunk-based (main 직접 커밋)**: 가장 가볍지만, CI 게이트가 사후에 작동해 main이 깨진 상태로 남을 수 있고, 에이전트 QA 검토가 붙을 절차적 지점이 없음
- **git-flow (develop/release 브랜치)**: 1인 프로젝트에 과함. 유지 비용이 실익을 초과
- **가벼운 GitHub Flow**: 코드 변경만 PR을 거치고, 문서 소규모 수정은 직커밋 허용

## 결정

1. 기본 브랜치는 `main`, 항상 베이스라인(태그) 가능한 상태를 유지한다
2. **코드·설정 변경**: 이슈 등록 → 브랜치 `feat/<이슈번호>-<설명>` → PR → CI 게이트 → **squash 머지**(사람 승인)
3. **문서만의 소규모 수정**(오타·문구·결정기록 추가): main 직커밋 허용
4. 커밋 메시지는 Conventional Commits, 요구사항 관련 작업은 본문에 ID 참조

혼자인데도 PR을 쓰는 근거:

- **CI 게이트가 머지 전에 작동** — main이 깨진 상태가 되는 것을 구조적으로 차단 (SP 3.2.2 형상 통제)
- **QA 페르소나 에이전트가 붙을 절차적 지점** — PR이라는 검토 단위가 있어야 에이전트 리뷰가 프로세스가 됨 (SP 3.1)
- **추적성이 공짜** — 이슈 ↔ PR ↔ 커밋이 GitHub에서 자동으로 엮여 요구사항 ID → 코드 추적이 검색만으로 완성 (SP 2.1.3)

문서 소규모 수정을 예외로 두는 근거: 모든 변경에 PR을 강제하면 1인 체제에서
비용이 규율을 이겨 프로세스 전체가 형해화된다. 예외의 경계는 "코드·설정을 건드리는가"이다.

squash를 택한 근거: PR 하나 = main의 커밋 하나가 되어 히스토리가 이슈 단위로 읽히고,
에이전트가 만드는 중간 커밋(시행착오 포함)이 main을 오염시키지 않는다.

## 결과

- main 히스토리가 "이슈 단위의 완결된 변경" 목록이 되어 CHANGELOG 작성·형상감사가 쉬워진다
- 감수하는 것: 작업마다 이슈·브랜치·PR 생성 비용. 대부분 에이전트가 수행하므로 실질 부담은 낮다
- 규칙의 원본은 AGENTS.md의 "git 전략" 절이며, 이 문서는 그 근거를 보존한다
