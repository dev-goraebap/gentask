# 결정-0014: 인증 세션은 DB 세션 + 이중 전달(쿠키·Bearer)로 한다

- 상태: 승인됨
- 날짜: 2026-07-26

## 맥락

M1 인증 구현 전에 세션 방식을 정해야 했다. 설계 문서에 "세션 방식(쿠키 vs 토큰)은 M1에서 결정"이라는
예고만 있었고 결정은 없었다 — 그마저 문서 재편(#16) 과정에서 유실되어, 미결 항목이라는 표시조차
사라진 상태였다.

당시 전제: Spring Boot 4.1 모듈러 모놀리스, PostgreSQL, same-origin 배포([설계/인프라.md](../설계/인프라.md) §2),
인증 후 화면은 CSR([결정-0011](결정-0011-렌더링-모드-경계.md)). **API 서버는 웹 전용이 아니며 향후 모바일 앱이
클라이언트로 추가될 수 있다** — 이 전제가 논의의 중심이었다.

### 논의에서 확인한 사실

- **액세스+리프레시 구조는 OAuth 2.0의 제3자 위임을 위해 만들어졌다.** 리소스 서버가 클라이언트를
  신뢰하지 않고, 리소스 서버와 인가 서버가 분리되어 매 요청 조회가 불가능한 상황을 전제한다.
  "내 프론트가 내 백엔드를 호출한다"를 위한 설계가 아니다.
- SPA 붐(2015~2020) 시기에 자기 서비스 로그인에도 복사됐고, 그 배경에는 실질적 이유가 있었다 —
  프론트와 API의 도메인 분리, 모바일 쿠키 처리의 번거로움, 무상태 확장 요구.
- **2023~2026 표준 권고는 브라우저 앱에 대해 세션 쿠키로 되돌아왔다.** IETF의
  [OAuth 2.0 for Browser-Based Applications](https://datatracker.ietf.org/doc/draft-ietf-oauth-browser-based-apps/23/)는
  BFF 패턴을 권고한다 — 토큰은 서버가 들고 브라우저에는 HttpOnly 세션 쿠키만 내려준다.
- **세션 저장 방식과 토큰 전달 방식은 직교한다.** 불투명 세션 토큰도 `Authorization: Bearer`로 보낼 수 있다.
  모바일이 요구하는 것은 Bearer 전달이지 JWT가 아니다.

## 검토한 대안

- **JWT 액세스 토큰 + 불투명 리프레시 토큰(DB 저장)**: 팀에서 오래 운용해온 구성이며 정석적이다.
  액세스 토큰 수명 동안 DB 조회를 아낀다(요청 100회 → 조회 1회). 기각 사유는 아래 "얻는 것과 잃는 것" 참조
- **JWT를 쿠키에 담기**: XSS 방어는 얻지만 즉시 무효화 불가는 그대로다 — 그것은 전달 방식이 아니라
  JWT의 본질이다
- **DB 세션 + 이중 전달 (선택)**

핵심은 **DB에 불투명 토큰을 두는 것은 세 안이 모두 같다**는 점이다. 차이는 그 위에 JWT 액세스
레이어를 얹느냐 하나뿐이다.

| 액세스 레이어가 필요한 조건 | 우리 상황 |
|---|---|
| 리소스 서버가 여러 개, 각자 독립 검증 | 아니다 — 모듈러 모놀리스 |
| 제3자에게 API 개방 | 아직 아니다 |
| 프론트와 API가 다른 도메인 | 아니다 — same-origin 전제 |
| DB 조회가 병목이 될 트래픽 | 아직 아니다 — 인덱스 조회 1회, 캐시 가능 |

반면 **즉시 무효화가 필요한 요구사항이 이미 셋** 있다: 비밀번호 변경 시 다른 세션 정리(PROF-03),
로그아웃, 기기 관리.

## 결정

1. **세션은 `session` 테이블에 저장한다.** 토큰은 불투명한 난수이며 그 자체에 정보를 담지 않는다.
2. **전달은 두 경로를 지원한다.**
   - 웹: `HttpOnly` `Secure` `SameSite` 쿠키 — JS가 접근할 수 없어 XSS로 탈취되지 않는다
   - 모바일·외부 클라이언트: `Authorization: Bearer <token>`
   - **세션 테이블은 하나다.** 전달 방식만 다르다.
3. **쿠키 경로에는 CSRF 방어를 둔다.** Bearer 경로는 해당 없다.
4. 세션은 사용 시 만료를 연장(슬라이딩)하고, 무효화는 행 삭제로 즉시 반영한다.
5. `session` 테이블에 `ipAddress`·`userAgent`를 두어 기기 목록·개별 로그아웃의 기반으로 삼는다.

## 재검토 조건

- **서비스를 여러 개로 분리**하거나 **외부 개발자에게 API를 개방**할 때 — 그때 이 세션 테이블 위에
  JWT 액세스 레이어를 얹는다. 우리 세션 토큰이 곧 리프레시 토큰 역할을 하므로 **재작성이 아니라 추가**다.
- 세션 조회가 실제 병목으로 측정되면 캐시를 앞에 두고, 그래도 부족하면 위 전환을 검토한다.
- 인증 후 화면을 SSR로 전환하려는 경우 — 쿠키 방식은 그대로 동작하므로 이 결정이 제약이 되지 않는다.

## 결과

- 로그아웃·비밀번호 변경·기기 관리가 즉시 반영된다
- 클라이언트가 토큰 1개만 다루면 된다 — 401 인터셉터·재발급·중복 갱신 방지가 필요 없다
- 감수하는 것: 요청마다 세션 조회 1회. 액세스 토큰 레이어가 아끼는 몫을 포기한다
- **`account` 테이블의 `accessToken`·`refreshToken` 필드는 이 결정과 무관하게 그대로 유지된다** —
  그것은 소셜 제공자의 API를 호출하기 위한 토큰이며 브라우저로 나가지 않는다
