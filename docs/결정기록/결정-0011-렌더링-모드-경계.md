# 결정-0011: 렌더링 모드 경계를 URL 접두사로 긋는다

- 상태: 승인됨
- 날짜: 2026-07-26

## 맥락

Angular 19부터 라우트별 렌더링 모드(하이브리드 렌더링)가 정식 기능이고, 우리 스캐폴드에도
`app.routes.server.ts` + `provideServerRendering(withRoutes(...))`가 이미 배선되어 있다
(현재 전부 `Prerender`).

키트의 화면은 성격이 둘로 갈린다 — 공개 페이지(랜딩·로그인·가입)는 SEO와 초기 로딩이 중요하고,
인증 이후 화면은 SEO가 무의미하며 인터랙티브하다. 어떤 기준으로 나눌지 정해야 했다.

당시 전제: Angular 22, `@angular/ssr`, 인증은 M1에서 구현 예정.

## 검토한 대안

- **전부 SSR**: 인증 후 화면까지 서버가 렌더링하려면 서버가 사용자 인증 상태를 알아야 한다 —
  쿠키 전달, `REQUEST` 토큰 주입, 플랫폼별 서비스 분리 같은 복잡도가 급증하는데 얻는 것은 없다(SEO 무관)
- **전부 CSR**: 공개 페이지의 SEO·초기 로딩을 포기하게 된다
- **라우트마다 모드 명시**: 앱 라우트와 서버 라우트를 이중 관리하게 되어 화면을 추가할 때마다
  두 곳을 고쳐야 하고, 어느 순간 반드시 어긋난다
- **URL 접두사로 경계 (선택)**: 인증 경계 = URL 경계 = 렌더링 경계를 일치시킨다

## 결정

| 영역 | 모드 | 대상 |
|---|---|---|
| 공개 | `RenderMode.Prerender` | `/`, `/login`, `/signup` |
| 인증 이후 | `RenderMode.Client` | `app/**` |
| 그 외 | `RenderMode.Server` | fallback |

- **인증 후 화면을 추가할 때 `app.routes.server.ts`를 건드리지 않는다.** `app/` 아래에 라우트만
  넣으면 모드가 따라온다.
- Prerender는 빌드 시점 값이 구워지므로, 런타임 설정에 의존하는 공개 페이지는 그 값을 API로 받거나
  `RenderMode.Server`로 전환한다.

## 결과

- 화면 추가 시 서버 라우트 설정을 유지보수하지 않는다
- **리졸버가 브라우저에서만 돈다** — 인증 후 영역이 CSR이므로 [결정-0012](결정-0012-CSR-데이터-로딩-전략.md)의
  로딩 전략이 SSR 인증 복잡도와 얽히지 않는다. 두 결정이 서로를 단순하게 만든다
- 감수하는 것: 인증 후 화면은 초기 렌더가 브라우저 몫이다. 앱 셸 HTML은 서버가 내려주므로 빈 화면 문제는 없다
