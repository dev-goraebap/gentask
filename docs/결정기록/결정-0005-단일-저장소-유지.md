# 결정-0005: web/server를 하나의 저장소로 관리 (모노레포 유지)

- 상태: 승인됨
- 날짜: 2026-07-24

## 맥락

이 저장소는 Angular(`web/`)와 Spring Boot(`server/`)라는 서로 다른 프레임워크를
한 저장소에 담고 있다. 외부 개발자로부터 "프레임워크별로 저장소를 나누는 게 좋지 않냐"는
의견을 받아, 유지 여부를 명시적으로 결정했다.

당시 전제: 1인(devgo) + AI 에이전트 운영, GitHub Template Repository로 파생,
태그 = 베이스라인 정책(AGENTS.md), CI는 web/server 독립 잡으로 분리 구성(#4).

## 검토한 대안

- **저장소 분리(polyrepo)**: 저장소별 권한·릴리스 주기 분리가 가능. 그러나 web/server 버전
  조합을 추적할 제3의 장치가 필요해지고, 가로지르는 자산(docs, AGENTS.md, 요구사항, API 계약)의
  귀속이 애매해지며, 파생 시 저장소 2개를 복제·연결해야 한다
- **단일 저장소 유지(선택)**: 아래 근거

## 결정

단일 저장소를 유지한다. 근거:

1. **베이스라인이 조합을 동결한다** — 태그 하나가 "이 web + 이 server + 이 문서 + 이 API 계약"의
   스냅샷. 저장소를 나누면 버전 조합 관리라는 새 문제가 생기는데, 모노레포는 이를 공짜로 해결한다
2. **핵심 자산이 web/server를 가로지른다** — 요구사항 ID(예: AUTH-01)는 화면과 API를 동시에
   규정한다. 프로세스 문서 체계가 단일 형상 안에 있어야 추적성이 성립한다
3. **파생이 한 번에 된다** — Template Repository 복제 한 번으로 전체 키트가 넘어간다
4. **1인 체제라 분리의 이점(팀별 권한, 독립 릴리스 주기)이 발생하지 않는다**

모노레포의 알려진 비용에 대한 대응:

- 커밋 구분 → Conventional Commits scope(`feat(web):`, `chore(server):`) + `git log -- web/`
- CI 낭비 → web/server 독립 잡(이미 분리). 빌드가 무거워지면 경로 필터로 스킵 추가
- 배포 분리 → 배포 단위는 저장소가 아니라 워크플로가 정한다. 필요 시 경로·태그 트리거의
  별도 워크플로(deploy-web.yml, deploy-server.yml)로 각자 배포

## 재검토 조건

다음 신호가 오면 분리를 재검토한다 (이 문서를 대체하는 새 결정기록 작성):

- 협업자가 생겨 web/server 접근 권한을 나눠야 할 때
- 한쪽을 다른 프로젝트가 독립적으로 의존하게 될 때
- 저장소 크기로 clone·CI가 실질적으로 느려질 때

분리가 필요해지면 `git filter-repo`로 히스토리를 보존한 채 분리할 수 있으므로,
현재 결정이 미래를 잠그지 않는다.

## 결과

- 형상관리(태그=베이스라인)와 추적성 체계가 단순하게 유지된다
- 감수하는 것: 저장소가 커질수록 CI 경로 필터 등 관리 장치가 점진적으로 필요해짐
