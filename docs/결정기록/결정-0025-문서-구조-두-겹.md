# 결정-0025: 아키텍처 문서를 시스템과 애플리케이션 두 겹으로 나눈다

- 상태: 승인됨
- 날짜: 2026-08-05

## 맥락

문서가 전부 저장소 루트 `docs/설계/`에 평평하게 있었다. `인프라.md`(시스템 전체) ·
`서버.md`(백엔드) · `웹.md`(프런트엔드) · `데이터베이스.md` · `디자인시스템.md` 다섯이 같은 층에
놓여 있었고, 두 가지가 불편했다.

**첫째, `서버.md` 하나가 열 가지 주제를 담고 있었다.** API 계약 · 모듈 경계 · 내부 구조 · 의존
방향 · 조회와 명령 · 저장소 · 예외 · 보안 · 테스트 · ArchUnit이 §1~§10에 눌려 있었다. 그래서 코드
주석이 `설계/서버.md §5.3` 같은 **절 번호**로 문서를 가리켰고, 문서를 손볼 때마다 번호가 흔들릴
위험을 안고 있었다.

**둘째, 백엔드 코드를 보는 사람이 문서를 찾으려면 저장소 루트로 올라가야 했다.** 코드와 그것을
규정하는 문서가 다른 나무에 있었다.

devgo가 다른 프로젝트(safety-solution)에서 arc42 골격 + `references/` + `decisions/` 구조를 시험하고
있었고, 그 방식을 이 저장소에 적용하기로 했다.

## 검토한 대안

- **현행 유지 (평평한 `docs/설계/`)**: 옮기는 비용이 0이다. 그러나 문서 하나가 열 주제를 담는 문제와
  코드-문서 거리 문제가 그대로 남는다.
- **주제별로 쪼개되 루트에 둔다**: 절 번호 문제는 풀리지만 코드와 문서가 여전히 떨어져 있고,
  루트 `docs/설계/`에 파일이 열 개 넘게 쌓인다.
- **두 겹으로 나눈다 (선택)**: 시스템 전체는 루트가, 각 애플리케이션은 자기 프로젝트 폴더가
  소유한다. 애플리케이션 문서는 arc42 골격의 `아키텍처.md` 하나와 주제별 `references/`로 나눈다.

## 결정

**아키텍처 문서를 두 겹으로 나눈다.**

| 겹 | 위치 | 담는 것 |
|---|---|---|
| 시스템 | `docs/설계/아키텍처.md` | 구성, 배포 전제, 오리진, 외부 의존, 형상 단위 |
| 애플리케이션 | `<프로젝트>/docs/아키텍처.md` | 그 애플리케이션의 내부 구조 (arc42 12절) |

1. **애플리케이션 문서는 골격과 규칙을 나눈다.** `아키텍처.md`는 **왜 그렇게 나누었는가**를 쓰고,
   같은 폴더의 `references/*.md`가 **무엇을 지켜야 하는가**를 주제별로 소유한다. 본문 상단에 주제와
   참조 문서를 잇는 색인 표를 둔다.
2. **코드 주석은 절 번호가 아니라 파일을 가리킨다.** 주제별로 쪼개졌으므로 번호가 필요 없어졌고,
   문서를 고쳐도 참조가 흔들리지 않는다.
3. **ADR 번호는 저장소 전역으로 채번하되 위치는 소관을 따른다.** 서버 코드만 바꾸는 결정은
   `server/docs/decisions/`에, 시스템·프로세스·웹에 걸친 결정은 `docs/결정기록/`에 둔다. 번호가
   겹치지 않으므로 `결정-0007` 하나로 어느 문서인지 특정된다.
4. **`인프라.md`는 `설계/아키텍처.md`로 흡수하고 삭제한다.** 둘 다 시스템 전체를 다루므로 남겨 두면
   원본이 두 벌이 된다.
5. **프런트엔드는 뒤로 미룬다.** `web/docs/`를 만들 때 `설계/웹.md`를 같은 형태로 옮기고 삭제한다.
   그때까지 `설계/웹.md`를 지우지 않는다 — 지우면 코드가 따르는 규칙이 저장소에서 사라진다.

## 결과

- 백엔드 코드를 보는 사람이 같은 나무 안에서 규칙 문서를 찾는다.
- 주제 하나를 고칠 때 그 주제 파일만 열면 되고, **절 번호가 흔들려 코드 주석이 어긋나는 경로가
  사라졌다.**
- arc42 골격 덕에 "이 항목을 어디에 쓸 것인가"를 매번 새로 정하지 않는다.
- 감수하는 것
  - **참조 경로가 65건 바뀌었다.** 소스 주석 27건과 문서 38건이며, 옮기면서 한 번에 고쳤다.
    앞으로도 문서를 옮길 때마다 같은 비용이 든다.
  - **문서를 찾는 곳이 둘로 늘었다.** 어느 겹에 속하는지 애매한 주제(예: 배포 전제)는 판단이
    필요하다. 기준은 "한 애플리케이션만의 이야기인가"이다.
  - **ADR이 두 폴더로 갈렸다.** 소관이 애매한 것(인증 계약처럼 서버가 소유하지만 웹이 소비하는
    결정)은 루트에 남겼다. 이 판단은 사례가 쌓이면 다시 볼 수 있다.
  - 이동한 ADR 8건의 **본문 링크를 손봤다.** 결정 내용은 건드리지 않았으며 경로만 고쳤다 —
    ADR 불변 원칙이 금지하는 것은 결정의 사후 수정이지 링크 유지보수가 아니다.
