# 결정-0021: 남용 방지는 엣지·애플리케이션·사람 증명 3층으로 나눈다

- 상태: 제안
- 날짜: 2026-07-28

## 맥락

AUTH-01 구현(#28) 과정에서 시도 제한을 auth 모듈 안에 인메모리로 만들었다. 보안 검토가
IP·이메일 축의 비대칭 방향, 로그인 경로의 제한 부재, 프록시 뒤에서의 클라이언트 IP 위조를
지적해 반영했지만, 그 과정에서 **더 위의 질문 둘이 남았다.**

1. **시도 제한은 이 요구사항 한정인가, 전역이어야 하는가.** 지금은 auth 모듈이 소유하고
   인증 흐름에만 걸려 있다.
2. **한도에 닿았을 때 차단이 맞는가.** 차단은 정상 사용자를 잠그고, 공격자가 남의 계정을
   반복해 잠그는 수단이 된다(검토 신규-C, 성공 시 카운터 초기화로 부분 완화).

당시 전제: **아직 배포 전이고 단일 인스턴스다.** 계획.md의 범위에 Cloudflare R2가 파일
저장소로 이미 들어 있어 **Cloudflare 의존이 이미 존재한다.** 키트는 파생 프로젝트가 복제해
쓰는 것을 전제하며(결정-0002), 발송 인프라를 고를 때도 "되돌리기 쉬운 결정은 가장 빨리
시작할 수 있는 쪽으로 정한다"는 기준을 적용했다(결정-0016).

### 확인한 사실

**시도 제한에는 성격이 다른 두 종류가 있다.**

| 종류 | 판단 기준 | 어디서 가능한가 |
|---|---|---|
| 요청량 제한 | 이 IP가 단위 시간에 몇 번 두드렸나 | 엣지·프록시·앱 어디서나 |
| 의미 기반 제한 | 이 **이메일**로 코드를 몇 번 받아갔나, 이 **계정**에 몇 번 로그인 시도했나 | 앱만 |

**엣지는 요청 본문을 열어 "어느 계정에 대한 시도인지" 판단하지 않는다.** 따라서 공격자가 IP를
분산하면 계정 하나를 노린 공격은 엣지 규칙에 걸리지 않는다. 반대로 앱에서만 막으면 모든 요청이
서버까지 도달해 커넥션·스레드·CPU를 소비한 뒤에 거부된다. **둘은 서로를 대체하지 못한다.**

**캡챠는 차단 장치가 아니라 비용 장치다.** 사람을 고용해 푸는 우회 시장이 실재하므로, 캡챠를
넣더라도 훨씬 느슨한 상한은 남겨야 한다.

**Cloudflare 무료 플랜의 제약**(2026-07 확인): 요청률 규칙 **1개**, 측정 기간은 10초 또는
1분만 선택 가능, 챌린지 액션 사용 시 지속 시간을 지정할 수 없고 스로틀링으로 동작한다.
규칙을 세밀하게 쪼갤 수 없으므로 **가장 넓은 그물 하나**로 써야 한다.

**Turnstile은 R2와 같은 계정에서 발급된다** — 새 외부 의존이 아니라 이미 있는 의존의 활용이다.
이 사실이 "키트에 외부 서비스를 하나 더 요구한다"는 반대 근거를 없앤다.

## 검토한 대안

### 어디서 막을 것인가

- **앱에서만 (현행)**: 의미 기반 판단이 가능하고 외부 의존이 없다. 그러나 모든 요청이 서버까지
  도달하며, 정적 경로·존재하지 않는 경로에 대한 폭주는 전혀 다루지 못한다.
- **엣지에서만**: 서버에 도달조차 하지 않아 가장 싸다. 그러나 계정·이메일 단위 방어가 불가능해
  결정-0015가 요구한 OTP 발급 제한(이메일별)을 구현할 수 없다.
- **3층으로 나눔 (선택)**: 각 층이 자기가 판단할 수 있는 것만 맡는다.

### 한도에 닿으면 무엇을 할 것인가

- **차단 (현행)**: 구현이 가장 단순하다. 그러나 비밀번호를 잊은 정상 사용자가 잠기고, 공격자가
  피해자 이메일로 오답을 반복해 그 계정을 무기한 잠글 수 있다.
- **지연(백오프)**: 사용자 체감은 덜 나쁘다. 그러나 공격자는 요청을 병렬로 던지므로 지연이
  방어가 되지 않는다.
- **사람 증명 요구 (선택)**: 차단이 아니라 "사람이면 계속"이다. 정상 사용자는 몇 초를 더 쓰고
  넘어가고, 자동화된 반복은 비용이 급등한다. 표적 계정 잠금이 원천적으로 사라진다.

## 결정

**3층으로 나누고, 각 층은 자기가 판단할 수 있는 것만 맡는다.**

| 층 | 담당 | 판단 근거 | 비용 |
|---|---|---|---|
| 1. 엣지 (Cloudflare) | IP당 요청률, 봇 트래픽 | 요청 메타데이터 | 설정만, 코드 0줄 |
| 2. 애플리케이션 | 이메일별·계정별·용도별 시도 | 도메인 지식 | 이미 구현됨 |
| 3. 사람 증명 (Turnstile) | 자동화된 반복 시도 | 챌린지 통과 여부 | 서버 + 프론트 |

1. **엣지는 Cloudflare가 담당한다.** 무료 플랜의 규칙 1개 제약에 맞춰 `/api/v1/*`에 넓은
   그물 하나만 건다. 세밀한 판단은 2층에 맡긴다.
2. **2층은 현행 구조를 유지한다.** 포트(`AttemptRateLimiter`)는 auth 모듈이 소유하고,
   **두 번째 소비자 모듈이 실제로 생길 때** 공용으로 승격한다(서버.md §3 — 미리 만들지 않는다).
3. **인메모리 구현은 단일 인스턴스 전제다.** 다중 인스턴스로 배포하면 카운터가 인스턴스마다
   갈려 한도가 사실상 배수가 되고 재배포마다 초기화된다. 그 시점에 공유 저장소(Redis 등)
   어댑터로 교체한다 — 포트 뒤에 있으므로 구현체 교체로 끝난다.
4. **사람 증명은 Turnstile로 하고, 로그인·OTP 확인 경로에서 N회 실패 후 요구한다.**
   챌린지를 통과하면 시도를 계속할 수 있다. **2층의 상한은 없애지 않고 느슨하게 남긴다** —
   캡챠는 비용 장치이지 차단 장치가 아니다.
5. **캡챠 검증은 비밀번호 해시 계산보다 먼저 한다.** bcrypt는 의도적으로 느리므로, 검증을
   뒤에 두면 캡챠가 오히려 CPU 고갈의 증폭기가 된다(AUTH-01에서 rate limit에 적용한 것과 같은 이유).
6. **키가 없으면 캡챠는 꺼진 채 동작한다.** 키트를 복제한 사람이 Cloudflare 설정 없이도 즉시
   실행할 수 있어야 한다(결정-0016과 같은 기준). 키를 넣는 순간 켜진다.
7. **캡챠도 포트 뒤에 둔다.** 파생 프로젝트가 hCaptcha·reCAPTCHA로 바꾸면 어댑터만 교체한다.
8. **신뢰 프록시 목록에 Cloudflare 대역을 넣는다.** Cloudflare의 서버 IP 대역은 공개되어
   있으므로, 짐작으로 채우던 `TRUSTED_PROXIES`를 공식 문서 값으로 확정할 수 있다.
9. **파생 프로젝트가 엣지를 쓰지 않으면 1층이 비어 있음을 문서로 경고한다.** 앱에 전역 IP
   스로틀을 안전망으로 넣지 않는다 — 지금 실익이 없고, 필요해지면 "엣지 없는 환경에서 켜는
   옵션"으로 추가하는 편이 구조가 깔끔하다.

### 미결 — 승인자 정보 대기

다음은 Cloudflare 계정·도메인 구성을 확인한 뒤 이 문서에 채운다.

- 엣지 규칙의 구체 수치(경로·기간·임계·액션)
- 캡챠 발동 임계 횟수 — 3회는 오타 두 번이면 바로 걸려 UX 부담이 있고, 5회는 방어가 늦다
- 캡챠를 로그인에만 걸지, OTP 확인에도 걸지

## 재검토 조건

- **다중 인스턴스로 배포할 때** — 2층 어댑터를 공유 저장소로 교체한다. 이 결정 자체는 유지된다.
- **캡챠 우회가 실제로 측정될 때** — 임계를 조이거나 위험 신호 기반 판단(디바이스·행동)을 검토한다.
- **Cloudflare를 쓰지 않게 될 때** — 1층이 비므로 앱 전역 스로틀 도입을 그때 결정기록으로 남긴다.
- **두 번째 모듈이 시도 제한을 필요로 할 때** — 포트를 공용으로 승격한다(결정 2).

## 결과

- 각 층이 자기가 판단할 수 있는 것만 맡아, 엣지가 못 하는 계정 단위 방어와 앱이 하기 비싼
  요청량 방어가 각각 제자리를 찾는다
- **정상 사용자가 잠기지 않는다.** 비밀번호를 잊어 여러 번 틀려도 사람임을 증명하면 계속할 수 있다
- **표적 계정 잠금이 사라진다.** 공격자가 남의 계정에 오답을 넣어도 그 계정 주인이 막히지 않는다
- 비밀번호 검증 앞에 사람 증명이 서므로, 느린 해시 계산 자체를 노린 자원 고갈이 막힌다
- 감수하는 것
  - **프론트 작업이 따라온다** — 로그인 화면에 위젯을 띄우고 토큰을 함께 보내야 한다
  - **캡챠 서비스 장애가 로그인 장애가 된다.** 장애 시 정책(열 것인가 닫을 것인가)을 구현
    시점에 정해야 한다
  - 접근성 부담 — 스크린리더·저시력 사용자에게 캡챠는 진입 장벽이다. Turnstile은 대부분
    상호작용 없이 통과하지만 0은 아니다
  - 1층이 Cloudflare에 묶인다. 다만 R2로 이미 묶여 있어 새로 생기는 종속은 아니다
