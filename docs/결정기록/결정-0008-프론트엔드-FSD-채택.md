# 결정-0008: 프론트엔드 구조로 Feature-Sliced Design(v2.1) 채택, 최소 레이어로 시작

- 상태: 승인됨
- 날짜: 2026-07-24

## 맥락

`web/`은 현재 Angular CLI 스캐폴드 상태(`app/` 아래 컴포넌트 몇 개)다. 인증 화면을 만들기 전에
어떤 기준으로 폴더를 나눌지 정해야 했다. 서버 쪽은 모듈 경계를 명문화하기로 했으므로
([결정-0007](결정-0007-서버-모듈-구조.md)), 프론트만 관행에 맡기면 한쪽 경계만 지켜진다.

당시 전제: Angular 22(standalone + SSR), Tailwind, 1인 + AI 에이전트 운영,
파생 프로젝트가 이 구조를 물려받음. FSD 공식 스킬이 저장소 자산으로 이미 설치되어 있음.

## 검토한 대안

- **Angular 관행 구조 (core/shared/features)**: 기각 — 널리 쓰이지만 `core`·`shared`의 경계가 모호해 시간이 지나면 둘 다 쓰레기장이 된다. 무엇보다 강제 장치가 없어 규칙이 문서에만 남는다
- **기능별 폴더만 (structure by feature)**: 기각 — 시작은 단순하나 재사용 코드의 자리가 정해지지 않아 결국 임의의 `common/`이 생긴다
- **FSD v2.1 채택**: 선택. 레이어별 import 방향과 슬라이스 공개 API가 명시적이고, **공식 린터(Steiger)가 있어 강제 가능**하다. 서버의 ArchUnit과 같은 구도를 프론트에도 세울 수 있다

## 결정

1. **FSD v2.1을 채택**한다. 레이어 import는 아래 방향으로만, 같은 레이어 슬라이스 간 교차 import 금지, 슬라이스 외부에서는 `index.ts`만 참조.
2. **최소 레이어(`app` + `pages` + `shared`)로 시작**하고 `widgets`·`features`·`entities`는 만들지 않는다. 추출 조건은 셋 다 충족할 때다 — 지금 실제로 2곳 이상에서 쓰이고 있고, 사용처들이 항상 함께 변경되지는 않으며, 경계 책임이 좁을 것.
3. **"키트니까 레이어를 미리 갖춰 보여준다"를 명시적으로 기각**한다. 빈 레이어는 파생 프로젝트에 잘못된 신호를 주어, 쓰지도 않을 추상을 채우게 만든다. FSD의 "단순하게 시작하고 필요할 때 추출한다"가 키트에도 그대로 적용된다.
4. 인증 토큰·세션은 `entities/user`가 아니라 **`shared/auth`**에 둔다(FSD 권고). CRUD 성격의 API 호출은 `shared/api`에 둔다.
5. **Steiger 린터를 CI 게이트에 포함**한다.
6. FSD 자체의 상세 규칙은 저장소의 FSD 스킬이 정본이며, 우리 프로젝트가 내린 선택만 [설계/웹.md](../설계/웹.md)에 기록한다 — 방법론 문서를 우리 저장소에 복제하지 않는다.

## 재검토 조건

- Angular 생태계에 동등한 강제력을 가진 다른 구조 표준이 자리잡으면 재평가한다
- Steiger가 Angular 프로젝트에서 실효를 내지 못하면(오탐·미지원) 강제 장치를 다시 고른다

## 결과

- 프론트·백 양쪽 모두 "공개 경계를 명시하고 강제 장치로 지킨다"는 같은 원칙 위에 선다
- 감수하는 것: FSD 학습 비용, Angular 예제가 React 중심 자료보다 적음
- 최소 레이어로 시작하므로 초기에는 거의 모든 코드가 `pages/`에 놓인다 — 의도된 상태다
