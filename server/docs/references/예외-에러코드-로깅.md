# 예외 · 에러 코드 · 로깅

본 문서는 오류를 표현하고 바깥으로 내보내는 방식을 정의합니다.
HTTP 응답 형식 자체는 [API 설계](API-설계.md) §3이 소유합니다.

## 1. 예외

- 비즈니스 오류는 항상 예외로 던지고(`BusinessException(ErrorCode)` 류), 컨트롤러에서
  `ResponseEntity`를 직접 조립하지 않습니다. 전역 예외 핸들러가 RFC 7807 응답으로 변환합니다.
- 예외 배치는 **불변식 위반은 `domain`에, 흐름·정책 실패는 해당 피쳐에** 둡니다
  ([패키지 배치와 참조 규칙](패키지-배치와-참조-규칙.md) §2).

## 2. 에러 코드

- 모듈별 enum으로 정의하고, 코드 문자열은 `<모듈>_<사유>` 형태를 따릅니다.
- 하이픈은 요구사항 ID, 언더스코어는 에러 코드로 구분을 강제합니다 — 추적성 검색이 오염되지
  않도록 하기 위함입니다.
- 사유를 구분하되 **열거 가능성을 만들지 않습니다.** 존재하지 않는 대기 레코드와 틀린 코드는 같은
  `AUTH_OTP_INVALID`입니다.

## 3. 로깅

- 요청 추적은 `traceId`(MDC)와 응답 헤더 `X-Trace-Id`로 합니다.

> **주의: 비밀번호·토큰·개인정보 원문은 로그에 남기지 않습니다**
> 메일 발송 실패처럼 수신자를 남겨야 하는 경우에도 주소를 마스킹합니다 — SMTP 장애 시 가입자
> 목록이 로그로 새는 경로가 되기 때문입니다.

## 4. 서블릿 필터에서 나는 오류

`@RestControllerAdvice`는 필터 단계의 오류를 잡지 못합니다. 필터에서 실패를 내보내야 하면 RFC 7807
본문을 직접 쓰는 전용 컴포넌트를 통합니다(`ProblemResponseWriter`). 그러지 않으면 컨테이너 기본
에러 페이지가 나가 형식이 갈립니다(보안 검토 F7).
