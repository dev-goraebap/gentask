# API 설계

본 문서는 `server`가 바깥에 제공하는 HTTP 계약의 규약을 정의합니다.

개별 엔드포인트의 요청·응답 스키마는 이 문서가 소유하지 않습니다. 그것은 코드에서 생성되는
OpenAPI 문서의 몫이며, 무엇을 만들 것인가는 요구사항 문서의 인수조건이 담당합니다.

## 1. REST 준수 범위

지키는 것은 HTTP 메서드 구분(GET/POST/PUT/PATCH/DELETE), `/리소스` 또는 `/리소스/{id}` 계층,
리소스명 복수형입니다.

지키지 않는 것은 HATEOAS입니다. 응답에 링크를 담아 발견 가능하게 할 실익이 없습니다 — web은
OpenAPI 문서로 이미 서버와 연결되어 있습니다.

## 2. 경로와 버저닝

- 모든 API는 `/api/v1` 아래에 둡니다. 파생 프로젝트가 키트 API를 유지한 채 자기 API를 얹을 수
  있어야 하므로, 버전 세그먼트를 처음부터 둡니다.
- 리소스명은 영문 전체 단어의 복수형을 씁니다: `/api/v1/sessions`, `/api/v1/users/{id}`,
  `/api/v1/attachments`.
- 하위 리소스는 상위 id 아래에 중첩합니다: `/api/v1/users/{id}/social-accounts`.

## 3. 에러 응답 — RFC 7807 단일 형식

에러는 전 구간 `application/problem+json`(Spring의 `ProblemDetail`) 하나로 응답합니다. 성공 응답을
감싸는 공통 봉투(envelope)는 쓰지 않습니다 — HTTP 상태 코드가 이미 그 역할을 합니다.

```json
{
  "type": "about:blank",
  "title": "인증 정보가 올바르지 않습니다",
  "status": 401,
  "detail": "이메일 또는 비밀번호를 확인해 주세요",
  "instance": "/api/v1/sessions",
  "code": "AUTH_INVALID_CREDENTIALS",
  "traceId": "..."
}
```

- `code`는 클라이언트가 분기 판단에 쓰는 **안정적인 식별자**입니다. 문구(`title`·`detail`)는 바뀔
  수 있지만 `code`는 계약입니다.
- `traceId`는 서버 로그와 대조하기 위한 추적 키입니다. 응답 헤더 `X-Trace-Id`로도 함께 나갑니다.

## 4. 에러 코드 명명 — 요구사항 ID와 구분한다

에러 코드는 `<모듈>_<사유>` 형태의 SCREAMING_SNAKE_CASE로 씁니다: `AUTH_INVALID_CREDENTIALS`,
`FILE_UPLOAD_EXPIRED`.

요구사항 ID(`AUTH-01`)와 형태가 겹치면 추적성 검색이 오염되므로, **하이픈은 요구사항 ID,
언더스코어는 에러 코드**로 구분을 강제합니다.

## 5. 인증 계약

클라이언트가 인증을 어떻게 수행하는지는 공개 계약의 일부입니다 — 웹과 모바일이 서로 다른 경로를
쓰기 때문입니다. 근거는 [결정-0014](../../../docs/결정기록/결정-0014-세션-방식.md), 선택의 배경과
대안 비교는 [참고 자료](../../../docs/참고/결정-0014-보충-세션-방식.md)에 있습니다.

| 클라이언트 | 세션 토큰 전달 | 함께 필요한 것 |
|---|---|---|
| 웹 | `HttpOnly` `Secure` `SameSite` 쿠키 | CSRF 방어 |
| 모바일·외부 | `Authorization: Bearer <token>` | 없음 |

- 토큰은 **불투명한 난수**입니다. 자체 검증되는 JWT가 아니며 `session` 테이블 조회로 검증합니다.
- **세션 테이블은 하나입니다.** 두 전달 경로가 같은 세션을 가리킵니다.
- 무효화(로그아웃·비밀번호 변경·비밀번호 재설정·기기 정리)는 즉시 반영됩니다.
- 소셜 제공자가 발급한 액세스·리프레시 토큰은 받지도 보관하지도 않습니다
  ([결정-0022](../decisions/결정-0022-소셜-제공자-토큰-미보관.md)).

## 6. 이메일 소유 증명 계약

이메일 소유 증명(OTP)도 공개 계약의 일부입니다 — 클라이언트가 **대기 레코드 식별자를 들고
다녀야** 하기 때문입니다. 근거는 [결정-0015](../../../docs/결정기록/결정-0015-이메일-소유-증명.md).

- 증명 흐름은 두 번의 호출입니다: **발급**(이메일 → 대기 레코드 식별자) → **검증**(식별자 + 코드).
- **검증은 `(이메일, 코드)`가 아니라 대기 레코드 식별자로 조회합니다.** 이메일과 코드만으로 찾으면
  타인이 시작한 대기 레코드를 피해자가 자기 화면에서 완성시키는 공격이 성립합니다.
- 대기 레코드는 아직 `user`가 아닙니다. 식별자는 **인증 자격이 아니며** 세션으로 승격되지 않습니다.
  검증 통과 시 세션 토큰을 새로 발급합니다.
- 소셜 최초 로그인은 2단계이며, 제공자 인증 결과는 대기 레코드에 담깁니다 — `user` 없이 `account`를
  만들지 않습니다.
- **제공자 인증과 이메일 입력 사이를 잇는 중간 표는 `HttpOnly` 쿠키로만 전달합니다.** URL 쿼리에
  실으면 액세스 로그·`Location` 헤더·브라우저 히스토리·`Referer`에 남고, 표를 주운 사람이 자기
  이메일로 소유 증명을 통과해 남의 제공자 신원을 영구 선점할 수 있습니다(보안 검토 F1). 표는 한 번
  쓰면 쿠키에서 지웁니다.
- 발급 응답은 계정 존재 여부를 노출하지 않습니다. 기존 계정이 발견되면 코드를 보내지 않고 안내
  메일을 보내되, 응답 형태는 동일합니다.
- 오류 코드는 사유를 구분하되 열거 가능성을 만들지 않습니다: `AUTH_OTP_EXPIRED`,
  `AUTH_OTP_ATTEMPTS_EXCEEDED`, `AUTH_OTP_INVALID`.

### 6.1 기기 목록의 표시 값은 화면이 이스케이프해야 한다

> **주의: 이 값은 공격자가 통제합니다**
> `GET /api/v1/sessions`는 `userAgent`·`ipAddress`를 **원문 그대로** 내려줍니다. 사용자가 자기 로그인
> 요청에 임의의 User-Agent를 넣을 수 있기 때문입니다. 서버는 이 값을 인증 판단에 쓰지 않고 길이도
> 자르므로 서버 결함은 아니지만, **프런트가 이스케이프 없이 렌더하면 자기 화면 한정 XSS**가 됩니다
> (검토 #32-5). Angular는 보간과 속성 바인딩을 기본으로 이스케이프하므로 그대로 쓰면 안전하며,
> `innerHTML`·`bypassSecurityTrustHtml`을 이 값에 쓰지 않습니다.

## 7. API 문서는 손으로 쓰지 않는다

서버 코드에서 springdoc-openapi가 OpenAPI 스펙을 생성하고, 그것이 API 문서의 정본입니다.
엔드포인트 목록·요청·응답 스키마를 마크다운으로 옮겨 적지 않습니다 — 코드와 어긋나는 순간
마이너스 문서가 됩니다.

**springdoc은 아직 도입하지 않았습니다.** 도입 전까지 개별 엔드포인트의 계약을 기록하는 곳은
요구사항 문서의 인수조건과 컨트롤러 코드뿐이며, 그 사이를 메우려고 마크다운 API 명세를 만들지
않습니다 — 이 절이 금지하는 바로 그것이기 때문입니다.
