# 결정-0010: 조회 경로는 QueryService + 조회 포트 + 어댑터로 분리한다

- 상태: 승인됨
- 날짜: 2026-07-24

## 맥락

[결정-0007](결정-0007-서버-모듈-구조.md)로 모듈 구조를 정했지만, **조회(경량 CQRS의 읽기 경로)가
어느 자리에 놓이는가**는 비어 있었다. 조회는 도메인을 거치지 않으므로 레이어 규칙을
그대로 적용하기 어렵고, 잘못 두면 두 방향의 사고가 난다 — 컨트롤러가 데이터 접근을 직접
알게 되거나, 반대로 명령 경로가 도메인을 우회하게 된다.

당시 전제: Spring Boot 4.1 / jOOQ / PostgreSQL, 조회 서비스는 단위 테스트하지 않고
통합 테스트로 검증한다는 방침([테스트](../references/테스트.md) §1).

## 검토한 대안

### A. QueryService가 SQL을 직접 보유 (application에 `DSLContext` 주입) — 기각

처음 검토한 안이다. 조회에는 보호할 도메인 규칙이 없으니 격리 장치도 불필요하고,
포트를 둬도 단위 테스트에서 소비할 곳이 없다는 논거였다. 다음 반박으로 기각했다.

- **기술 종속적이다.** 이 구조는 jOOQ가 임베디드 DSL이라서만 성립한다. MyBatis라면 SQL이
  XML에 있으므로 QueryService는 Mapper 인터페이스를 호출할 수밖에 없고, 구조 자체가 달라진다.
  키트의 정체성은 "스택은 바뀔 수 있고 설계가 자산"([결정-0002](../../../docs/결정기록/결정-0002-프로젝트-정체성과-이름.md))인데,
  아키텍처가 특정 라이브러리의 형태에 의존하면 스택 교체가 아키텍처 재작성이 된다.
- **이미 있는 규칙과 불일치했다.** 패키지 배치 규칙은 `OAuthClient`·`MailSender` 같은 포트를 피쳐에 선언하고
  구현을 infrastructure에 두게 하고 있었다. 조회만 예외로 둘 이유가 없었다.
- 이 안을 유지하려면 "application에서 jOOQ 직접 사용은 QueryService만 허용"이라는 ArchUnit
  예외 규칙이 필요했다. **없어도 될 예외를 만들고 그 예외를 지킬 장치를 덧붙이는 구조**였다.

### B. 피쳐 서비스 하나로 병합 (명령·조회를 한 클래스에, 주석으로 구분) — 기각

QueryService가 대부분 싱크홀이 되므로 클래스를 늘리지 말자는 안이다. 병합이 아끼는 것은
**피쳐당 클래스 1개**뿐이며(포트·어댑터는 어느 쪽이든 필요), 잃는 것이 더 컸다.

- **테스트 정책이 기계 판정 불가능해진다.** 분리하면 "`~QueryService`는 단위 테스트 제외"가
  클래스 이름으로 판정된다. 병합하면 "조회 메서드는 제외"가 되어 주석과 사람의 판단에 의존한다 —
  구현자가 에이전트인 우리 체제에서 특히 취약하고, "강제 장치 없는 규칙은 부패한다"는 원칙에 어긋난다.
- **트랜잭션 기본값이 어긋날 수 있다.** 분리하면 `readOnly`와 쓰기가 각자 클래스 기본값이다.
  병합하면 명령 메서드의 override를 빠뜨렸을 때 쓰기가 조용히 실패한다.
- **의존 목록이 흐려진다.** 명령 경로에 조회 포트가 주입되어 있으면 도메인 우회의 지름길이 열린다.

### C. 승격 기준 — 하나로 시작하고 조회가 늘면 분리 — **보류(검토 필요)**

모듈 계층 승격 기준·FSD 추출 조건과 형식이 같아 일관성이 있다. 다만 다음 약점이 있어
이번에는 채택하지 않았고, **폐기가 아니라 보류**로 둔다.

- 승격 전 구간에서는 B의 약점(테스트 정책 흐림, 트랜잭션 사고)이 그대로 노출된다.
- 계층 승격은 미뤄도 폴더가 평평할 뿐이지만, 이 승격은 미루는 동안 실제 사고가 발생할 수 있어
  성격이 다르다.
- 기준이 있는 규칙은 "아직 기준 미달"로 미뤄지다 끝내 분리되지 않는 경향이 있다.

향후 실제 코드가 쌓인 뒤 재검토한다 — 작은 피쳐에서 분리가 형식으로만 느껴지는지,
승격 시점을 기계적으로 판정할 방법이 있는지가 판단 재료다.

## 결정

**처음부터 분리한다.**

| 자리 | 클래스 | 역할 |
|---|---|---|
| `application/<피쳐>/` | `XxxQueryService` | 조회 유스케이스. `@Transactional(readOnly = true)` |
| `application/<피쳐>/` | `XxxQueries` | 조회 포트(인터페이스). 피쳐가 소유 |
| `infrastructure/query/` | `JooqXxxQueries` | 어댑터. 기술은 여기서만 |

- 포트 이름은 제공하는 것으로 짓는다. `QueryRepository`는 DDD의 Repository와 충돌하므로 쓰지 않는다.
- 기본은 포트가 화면 DTO를 직접 반환한다. 도메인 보강이 필요할 때만 중간 타입을 둔다.
- 조회는 애그리거트를 조립하지 않되, **도메인 규칙을 순수 판정 함수로 재사용하는 것은 허용**한다 —
  규칙이 SQL에 복제되어 두 곳에 존재하는 것을 막기 위함이다.
- 명령 서비스는 조회 포트를 주입받지 않는다(ArchUnit 규칙 7).

## 재검토 조건

- 대안 C(승격 기준)를 다시 평가한다 — M1~M2의 실제 피쳐가 쌓인 뒤
- 조회 로직이 복잡해지거나 조회 전용 저장소(검색엔진 등)가 생기면 포트의 값이 커지므로 이 결정이 더 강해진다
- 반대로 모든 피쳐에서 QueryService가 순수 통과이기만 하다면 C를 다시 검토할 근거가 된다

## 결과

- 영속성 기술이 바뀌어도 application은 무변경 — 키트의 스택 교체 시나리오에 부합한다
- ArchUnit 예외 규칙이 불필요해져 규칙 집합이 오히려 단순해졌다
- 감수하는 것: 조회 대부분이 QueryService에서 포트를 그대로 통과시키는 싱크홀이 된다.
  대가로 얻는 것은 기술 중립성, 도메인 보강 지점, 기계 판정 가능한 테스트 정책이다
