# 결정-0007: 서버 모듈 구조 — Modulith 경계 규약 + 내부 레시피 + ArchUnit 강제

- 상태: 승인됨
- 날짜: 2026-07-24

## 맥락

M1에서 인증을 구현하기 전에 서버 패키지 구조를 정해야 했다. 구조 없이 인증부터 만들면
폴더 배치·의존 방향·모듈 경계를 인증 코드 안에서 즉석 결정하게 되고, 근거 없이 굳는다.

참고한 선례는 둘이다. 하나는 팀 프로젝트(safety-solution)의 백엔드 아키텍처 문서 —
`module.<bc>` 중간 겹과 `contract` 패키지(OHS/PL)로 컨텍스트 경계를 표현한다. 다른 하나는
TodoGen 플랫폼의 ADR-0013 — Spring Modulith 규약을 차용해 모듈 루트를 공개 API로 삼는다.

리서치의 결론은 "반박 불가능한 폴더 구조는 존재하지 않는다"였다. 폴더 구조는 상충하는
힘들(피쳐 응집 vs 계층 재사용)의 타협이고, 어느 쪽을 골라도 반대편의 비판이 유효하다.
다만 논쟁이 수렴한 지점은 구조가 아니라 **규칙**이다: 최상위 분할은 비즈니스 능력 기준,
공개 API와 internal의 구분, 도메인은 바깥을 모른다, 그리고 **강제 장치 없는 구조는 반드시
부패한다.** 따라서 "반박 불가능성"은 구조 선택이 아니라 규칙의 명문화와 자동 강제에서 온다.

당시 전제: Spring Boot 4.1 / Java 21 / jOOQ / PostgreSQL, 모듈 4개 규모(auth·mail·storage·notification),
1인 + AI 에이전트 운영, 파생 프로젝트가 이 구조를 물려받음.

## 검토한 대안

- **package by layer (controller/service/repository 최상위)**: 기각 — 구현 세부를 추상보다 앞세우는 역방향. 피쳐 하나 수정에 전 계층을 열게 되고 모듈 분리가 어렵다
- **순수 vertical slice (계층 없이 피쳐 폴더만)**: 기각 — 불변식·도메인 규칙이 슬라이스에 흩어진다. `domain` 계층을 유지해 "공유는 domain으로 내린다"는 탈출구를 확보하는 하이브리드를 택함
- **`module.<bc>` + `contract` 패키지 (safety-solution 방식)**: 기각 — `module.` 겹은 모든 것이 그 아래 있어 구분 기능이 없다. `contract` 패키지 + OHS/PL 격식은 컨텍스트가 여럿인 대형 도메인에는 맞지만 모듈 4개 규모에는 무겁다. 핵심 아이디어(도메인 엔티티를 노출하지 않고 전용 공개 타입을 쓴다)는 아래 결정에 흡수했다
- **Spring Modulith 라이브러리 도입**: 보류 — 경계 검증·문서 생성·모듈 이벤트를 주지만 런타임 의존성이다. 이 규모에서는 ArchUnit(테스트 전용, 런타임 영향 없음)으로 충분하다. 모듈 간 이벤트 통신이 필요해지면 재검토한다
- **모듈 레벨 `x/shared`**: 기각 — 사실상 네 번째 레이어가 되어 별도 의존 규칙이 필요해지고, "어느 레이어 것인가"라는 방어 질문을 생략하게 만들어 쓰레기장이 된다

## 결정

1. **패키지 루트는 `dev.goraebap.devkit`.** 스프링 이니셜라이저 기본값 `com.example.demo`를 걷어낸다. 파생 프로젝트는 부트스트랩에서 이 루트를 치환한다.
2. **모듈 = 루트의 직계 하위 패키지**, 모듈 루트 직계 클래스 = 공개 API, 하위 패키지 = internal (Spring Modulith 규약).
3. **모듈 경계는 애그리거트 소유를 기준으로 긋는다.** 요구사항 묶음이 아니다 — 프로필(PROF-*)이 별도 모듈이 아니라 `auth`의 피쳐인 이유가 이것이다.
4. **승격 기준**: 애그리거트 2개 이상 또는 피쳐 3개 이상이면 `application`/`domain`/`infrastructure` 계층 도입, 그 전에는 플랫 유지.
5. **의존 방향과 중복 처방**을 명문화하고, **ArchUnit 6개 규칙으로 강제**한다. 위반은 빌드 실패.

상세 구조와 규칙 표는 [패키지 배치와 참조 규칙](../references/패키지-배치와-참조-규칙.md)에 둔다. 이 결정기록은 근거를 보존하고,
참조 문서는 현재의 규칙을 서술한다.

## 결과

- 구조 논쟁이 취향 다툼이 아니라 "이 결정기록의 개정 제안"이 된다
- 인증 구현이 정해진 자리에서 시작되고, 배치 판단을 매번 다시 하지 않는다
- 감수하는 것: ArchUnit 테스트 의존성 추가, 규칙 위반 시 우회가 아니라 문서 개정을 거쳐야 하는 마찰
- jOOQ 채택 덕에 "도메인은 프레임워크를 모른다"가 타협 없이 성립한다 — JPA였다면 애노테이션 부착을 허용하는 예외가 필요했다
