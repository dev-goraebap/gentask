# 01. 개발 환경

본 문서는 빌드 구성과 로컬 실행 절차, 그리고 규칙이 강제되는 지점을 정의합니다.

## 1. 구성 파일의 역할

| 파일 | 역할 |
| :--- | :--- |
| `build.gradle` | 의존성, 코드 생성, 정적 분석 설정 |
| `gradle/gradle-daemon-jvm.properties` | Gradle 데몬이 쓸 JVM 판 |
| `compose.yaml` | 로컬 개발용 데이터베이스 |
| `src/main/resources/application.properties` | 접속 정보와 마이그레이션 위치 |
| `lombok.config` | 접근자 형태와 금지 기능 |
| `config/checkstyle/` | 컨벤션 규칙과 예외 목록 |
| `config/spotbugs/exclude.xml` | 결함 탐지 오탐 제외 목록 |

**규칙의 원본은 설정 파일입니다.** 본 문서가 규칙을 옮겨 적지 않고 파일을 참조합니다. 두 벌이 되면 한쪽이 낡습니다.

## 2. JVM

컴파일 대상은 Java 21 이며, **Gradle 데몬도 21 이상이어야 합니다.**

`build.gradle` 의 toolchain 은 컴파일에만 적용되고 플러그인은 Gradle 자신의 JVM 에서 로드됩니다. jOOQ 코드 생성 플러그인이 JVM 21 을 요구하므로 로컬 기본 JDK 가 그보다 낮으면 **설정 단계에서 실패합니다.** `gradle/gradle-daemon-jvm.properties` 가 그 요구를 저장소에 고정하며, 조건에 맞는 JDK 가 없으면 Gradle 이 내려받습니다.

## 3. 로컬 실행

```bash
./gradlew bootRun
```

`spring-boot-docker-compose` 가 `compose.yaml` 의 컨테이너를 함께 띄우고 종료 시 내립니다. **데이터베이스를 따로 준비하는 절차가 없습니다.** 이 의존성은 `developmentOnly` 이므로 배포 산출물에 들어가지 않습니다.

접속 정보의 기본값은 `compose.yaml` 과 맞춰 두었고, 그 밖의 환경은 `DB_URL` · `DB_USERNAME` · `DB_PASSWORD` 로 주입합니다. **자격증명을 저장소에 평문으로 두지 않습니다.**

**호스트 포트는 기본값(5432)을 쓰지 않습니다.** 개발 기계에 다른 PostgreSQL 이 떠 있으면 그것이 5432 를 잡고 있어 컨테이너가 뜨지 않습니다. 데이터베이스 도구로 붙을 때는 아래 값을 씁니다.

| 항목 | 값 |
| :--- | :--- |
| 호스트 · 포트 | `localhost:5434` |
| 데이터베이스 · 사용자 · 비밀번호 | `refarch` |

## 4. 빌드가 하는 일

```bash
./gradlew build
```

| 단계 | 하는 일 | 실패 조건 |
| :--- | :--- | :--- |
| **`jooqCodegen`** | 마이그레이션 SQL 에서 테이블 클래스를 생성합니다 | SQL 을 파서가 해석하지 못할 때 |
| **`compileJava`** | 생성물을 소스 경로에 포함해 컴파일합니다 | 없는 컬럼을 참조할 때 |
| **`spotlessCheck`** | 포맷이 규격과 다른지 봅니다 | 다를 때. `spotlessApply` 로 고칩니다 |
| **`checkstyleMain`** | 명명과 금지 패턴을 봅니다 | 위반이 하나라도 있을 때 |
| **`spotbugsMain`** | 바이트코드에서 결함 패턴을 찾습니다 | 제외 목록에 없는 탐지가 있을 때 |
| **`test`** | 단위 테스트와 통합 테스트, ArchUnit 규칙 | 하나라도 실패할 때 |

**코드 생성이 컴파일보다 먼저입니다.** 스키마와 코드가 어긋난 상태가 빌드 시점에 드러나며, 기동 시점이나 배포 이후로 미뤄지지 않습니다.

## 5. 정적 분석의 분담

도구 셋이 **겹치지 않게** 나눠 맡습니다.

| 도구 | 맡는 것 | 성격 |
| :--- | :--- | :--- |
| **Spotless** | 포맷 | 기계가 재작성합니다. 개발자가 관리하지 않습니다 |
| **Checkstyle** | 명명 규칙과 금지 패턴 | 빌드 오류로 처리합니다 |
| **SpotBugs** | 결함 패턴 | 바이트코드를 분석합니다 |
| **ArchUnit** | 구조 규칙 | 테스트로 실행합니다. [02. 패키지 배치와 참조 규칙](02-package-structure.md) 5절 |

**Checkstyle 에 포맷 규칙을 넣지 않습니다.** 두 도구가 같은 항목을 다루면 한쪽은 고쳐 주고 다른 쪽은 실패시키는 상태가 됩니다. 포맷은 협의 대상이 아니라 기계가 정하는 것이라는 전제가 이 분담의 근거입니다.

**생성 코드는 넷 모두에서 제외합니다.** 우리가 쓰지 않은 코드에 우리 표준을 적용할 이유가 없습니다.

정당한 예외는 억제 목록에 **사유 주석과 함께** 등록합니다. 그 목록이 표준을 벗어난 위치와 사유의 등록부 역할을 합니다.

## 6. 테스트 실행 요건

**통합 테스트는 Docker 를 요구합니다.** 컨테이너로 실제 PostgreSQL 을 띄워 마이그레이션을 적용하기 때문입니다. Docker 가 없으면 그 테스트만 실패하며, 단위 테스트와 ArchUnit 은 영향을 받지 않습니다.

테스트용 컨테이너는 `compose.yaml` 의 로컬 데이터베이스와 분리합니다. 테스트가 개발 중인 데이터베이스를 쓰면 남아 있던 데이터에 따라 결과가 갈리고, 테스트가 그것을 지우면 개발하던 상태가 사라집니다.

**두 곳의 이미지 태그를 같은 값으로 유지합니다.** 다르면 로컬에서 통과한 마이그레이션이 테스트에서 실패하는 일이 생기는데, 원인이 스키마가 아니라 판 차이라 찾기 어렵습니다.
