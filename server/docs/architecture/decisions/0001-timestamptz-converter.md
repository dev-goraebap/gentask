# 결정-0001: 시각 변환만 코드 생성에 내린다

- 상태: 승인됨
- 날짜: 2026-08-23
- 관련 문서: [06. 데이터 접근](../references/06-data-access.md)

## 맥락 (Context)

도메인은 절대 순간을 `Instant` 로 갖고 jOOQ 생성물은 `timestamptz` 컬럼을 `OffsetDateTime` 으로 냅니다. 두 타입 사이를 저장소 구현이 손으로 이었습니다.

`task` 모듈 하나만 있는 시점에 이미 반복이 셋 나왔습니다.

| 반복 | 규모 |
| :--- | :--- |
| `toInstant(OffsetDateTime)` | `JooqTaskRepository` 와 `JooqTaskQuery` 에 글자 그대로 두 벌 |
| `save()` 의 `set` 구문 | insert 10 줄 · update 8 줄, 그중 8 줄이 완전 중복 |
| 값 객체 껍질 | `.value()` 와 `new TaskTitle(...)` 이 컬럼마다 |

두 번째 모듈이 서기 전에 무엇을 공용으로 내리고 무엇을 손에 남길지 정해야 했습니다.

## 검토한 대안 (Options)

### 대안 1: 그대로 둔다

| 구분 | 내용 |
| :--- | :--- |
| **장점** | 조립 경로가 전부 한 파일 안에 보입니다 |
| **단점** | 모듈마다 같은 변환 메서드가 두 벌씩 늘어납니다 |
| **기각 사유** | 이 반복은 모듈 수에 비례해 늘고, 내용이 매번 같아 판단이 개입할 자리가 없습니다 |

### 대안 2: `shared` 에 리플렉션 매퍼를 자작한다

| 구분 | 내용 |
| :--- | :--- |
| **장점** | `toDomain` 이 모듈마다 반복되지 않습니다 |
| **단점** | `Task.restore` 를 우회하는 세 번째 조립 경로가 생깁니다 |
| **기각 사유** | 필드가 늘면 손 매핑은 생성자 인자 개수가 맞지 않아 컴파일에서 걸리지만, 리플렉션은 조용히 `null` 을 둡니다. 검증하는 `of` 와 검증하지 않는 정규 생성자를 나눈 것도 무의미해집니다 |

### 대안 3: 값 객체까지 `forcedTypes` 로 내린다

| 구분 | 내용 |
| :--- | :--- |
| **장점** | 매핑이 가장 짧아집니다. `TITLE` 컬럼이 곧 `TaskTitle` 입니다 |
| **단점** | 생성된 `jooq` 패키지가 `module.task.domain` 을 import 합니다 |
| **기각 사유** | 모듈이 늘면 생성물 하나가 모든 모듈의 도메인을 알게 됩니다. 인프라 생성물이 도메인에 의존하는 방향이라 [04. 계층](../references/04-layers.md)의 의존 방향과 어긋납니다 |

### 대안 4: 시각 변환만 Converter 로 내린다 (채택)

`timestamptz` 컬럼에 `forcedType` 을 걸어 생성물이 처음부터 `Instant` 를 내게 합니다. 애그리거트 조립은 손에 남습니다.

## 결정 (Decision)

**타입 대 타입의 기계적 변환만 코드 생성에 내리고, 어느 컬럼이 어느 필드인지는 손에 남깁니다.**

가르는 기준은 판단의 유무입니다. `OffsetDateTime` → `Instant` 에는 고를 것이 없어 한 번 적으면 모든 모듈에 같게 적용됩니다. 컬럼과 필드의 대응에는 매번 고를 것이 있고, 손에 두면 컴파일러가 그 대응을 검사합니다.

## 결과 (Consequences)

- 두 파일에 복제되어 있던 `toInstant` 와 `toOffsetDateTime` 이 사라집니다. `task` 모듈에서 4 개 메서드가 0 개가 되었고, 새 모듈은 처음부터 이 반복을 갖지 않습니다.
- 시간대 없는 `timestamp` 는 걸리지 않습니다. `remind_at` 은 `LocalDateTime` 으로 남아, 절대 순간이 아닌 값이 실수로 순간이 되는 일을 타입이 막습니다.
- 감수하는 것
  - `save()` 의 `set` 8 줄 중복과 값 객체 껍질 벗기기는 그대로 남습니다. 컬럼이 하나 늘면 insert 와 update 두 자리를 고쳐야 합니다.
  - 규칙이 `build.gradle` 의 정규식으로 표현되며, 매칭 실패는 빌드를 세우지 않고 경고만 냅니다. 생성물의 타입을 눈으로 확인해야 적용 여부를 압니다.
- 명시적으로 기각한 것: 영속성 매핑을 위한 리플렉션 장치. 애그리거트 조립의 유일한 입구를 `restore` 로 두는 한 재론하지 않습니다.

## 재검토 조건

- 모듈이 셋을 넘고 `toDomain` 의 모양이 실제로 같은 것으로 확인될 때. 지금은 반복되는 것이 모양이고 내용은 매번 다르며, 공용 매퍼를 만들어도 컬럼과 필드의 대응은 애노테이션이나 설정으로 자리를 옮길 뿐 사라지지 않습니다. 옮긴 자리는 컴파일러가 검사하지 못합니다.
- 값 객체가 열을 넘어 껍질 벗기기가 조립의 대부분을 차지할 때. 대안 3 의 의존 방향 문제를 모듈별 생성 설정으로 나눌 수 있는지가 그때의 쟁점입니다.
