# 프론트엔드 참조 아키텍처

본 문서는 이 저장소의 프론트엔드 규칙이 어디에 있는지를 가리키는 진입점입니다. 규칙 본문은 담지 않고, 무엇이 어느 자리에 있으며 어떤 순서로 필요해지는지만 정의합니다.

분류는 arc42 섹션 체계를 차용합니다. 필요한 섹션만 사용하며, §1(소개와 목표)·§3(컨텍스트와 범위)·§6(런타임 뷰)·§11(위험과 기술 부채)은 도메인이 있어야 성립하므로 참조 아키텍처에는 두지 않습니다. 특정 프로젝트의 상위 아키텍처 문서가 생기면 그쪽이 그 섹션들을 갖고 이 문서를 참조합니다.

## 에이전트 지침

- 현재 작업에 해당하는 문서만 읽습니다. 전부 싣지 않습니다.
- 규칙을 바꾸려면 먼저 §9의 결정 기록을 확인합니다. 사정을 모르고 되돌리면 같은 논의를 반복하게 됩니다.
- 새 참조 문서를 만들면 이 문서에 등록하는 것까지가 생성 작업입니다.
- 아직 없는 문서는 파일명만 적고 `(작성 예정)`으로 표시합니다. 작성한 뒤 링크로 바꿉니다.
- UI 코드를 납품하기 전에 [13. 접근성](references/13-accessibility.md)의 기준을 통과시킵니다.

## 파일명과 번호

참조 문서는 `references/NN-이름.md` 형식이며 `NN`은 **도입 순서**입니다. 읽는 순서가 아니라 **작성하거나 이식할 때 몰라서 막히는 순서**이고, 기준은 "나중에 바꿀 때 이미 쓴 코드를 얼마나 건드리는가"입니다.

| 구간 | 번호 | 시점 |
| :--- | :--- | :--- |
| **기반** | 01~04 | 첫 코드를 쓰기 전에 확정되어 있어야 합니다 |
| **화면** | 05~13 | UI 프로토타입 구간에서 필요해집니다 |
| **연결** | 14~16 | 백엔드를 붙일 때 필요해집니다 |
| **검증** | 17~19 | 검증 게이트 이후에 필요해집니다 |

프로세스 단계와의 대응은 [프로세스 문서](../../../docs/process.md)가 원본입니다.

## §2 제약조건 (Constraints)

바꿀 수 없는 전제입니다. 아래 모든 규칙이 이것을 근거로 삼습니다.

| 제약 | 내용 |
| :--- | :--- |
| **개발 규모** | 1인. 운영 복잡도가 늘면 기능 개발 생산성이 그만큼 떨어집니다 |
| **대상 플랫폼** | 웹 하나. 네이티브와 디자인 도구 동기화는 대상이 아닙니다 |
| **프레임워크** | Angular 22, Tailwind CSS 4, TypeScript 6 |
| **색상 모드** | 라이트와 다크 양쪽을 지원합니다 |
| **배포 구조** | 프론트엔드와 백엔드를 분리하고 백엔드는 모놀리식으로 둡니다 |

마지막 항목은 별도의 아키텍처 결정이 아니라 **프로세스의 귀결**입니다. 근거는 [프로세스 문서](../../../docs/process.md)의 정의와 전제 절에 있습니다.

## §4 해법 전략 (Solution Strategy)

위 제약 아래에서 고른 상위 방침입니다. 상세 규칙은 각 참조 문서가, 선택의 근거와 기각한 대안은 §9의 결정 기록이 소유합니다.

- **배치의 일의성을 최우선으로 둡니다.** 같은 코드를 둘 자리가 여럿이 되는 순간부터 규칙이 있어도 구조를 읽을 수 없게 되므로, 배치 규칙이 첫 자리이고 도구가 빌드에서 강제합니다.
- **접근성과 상호작용 로직을 직접 만들지 않습니다.** 헤드리스 프리미티브가 포커스·키보드·ARIA를 소유하고, 우리는 그 위의 시각 층만 소유합니다.
- **시각 언어를 아키텍처 밖에 둡니다.** 아키텍처는 토큰의 이름 집합과 하한을, [DESIGN.md](../design/DESIGN.md)가 그 안을 채우는 값을 소유합니다.
- **UI는 서비스 인터페이스 뒤에서만 데이터에 접근합니다.** 프로토타입 구간의 Mock 구현과 이후의 Http 구현이 같은 인터페이스를 갖고, 그 타입 정의가 백엔드 API 계약의 입력이 됩니다.
- **판단이 필요한 것만 문서에 둡니다.** 기계가 판정할 수 있는 것은 린터·테스트·빌드로 내려보내고, 문서에는 그 강제 수단이 무엇인지를 함께 적습니다.
