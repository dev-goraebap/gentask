# 09. 서버 상태와 클라이언트 상태

본 문서는 화면이 다루는 데이터를 종류별로 나누고, 각각을 어느 계층이 소유하며 어떻게 갱신하고 무효화하는지를 정의합니다.

## 1. 상태의 세 종류

상태는 **원본이 어디에 있는가**로 구분합니다. 이 구분이 저장 위치와 갱신 방식을 결정합니다.

| 종류 | 원본 | 화면이 가진 것 | 저장 위치 |
| :--- | :--- | :--- | :--- |
| **서버 상태** | 서버 | 사본. 언제든 낡을 수 있습니다 | 조회 지점의 `api` 세그먼트 |
| **클라이언트 상태** | 화면 | 원본 | 해당 슬라이스의 `model` 세그먼트 |
| **URL 상태** | 브라우저 히스토리 | 원본 | Angular Router |

서버 상태를 클라이언트 상태처럼 다루는 것이 가장 흔한 오류입니다. 조회 결과를 `signal` 에 담아 두고 그것을 원본처럼 수정하면, 서버와 화면이 어긋난 사실을 아무도 알 수 없게 됩니다.

| 구분 | 준수 지침 (Do) | 금지 지침 (Don't) |
| :--- | :--- | :--- |
| **서버 상태 갱신** | 서버에 변경을 요청하고 조회를 다시 실행합니다 | 응답 사본을 직접 수정해 화면만 바꿉니다 |
| **파생 값** | `computed` 로 계산합니다 | 별도 `signal` 에 복사해 둡니다 |
| **필터 · 정렬 · 페이지** | URL 쿼리 파라미터에 둡니다 | 컴포넌트 `signal` 에 둡니다 |

### 1.1 신선도를 맞추는 단계

사본을 원본과 맞추는 수단에는 단계가 있습니다. **아래에서 시작하고, 위로 올라가는 것은 필요가 측정으로 확인된 뒤입니다.**

| 단계 | 수단 | 올라가서 얻는 것 |
| :--- | :--- | :--- |
| **1** | 화면 진입마다 조회 | — |
| **2** | 1 + 변경 뒤 조회 | 내가 바꾼 것이 화면에 반영됩니다 |
| **3** | 캐시를 두고 키로 무효화 | 같은 데이터의 중복 요청이 사라집니다 |
| **4** | 낡은 사본을 먼저 보이고 뒤에서 갱신 | 화면 전환에 대기가 없습니다 |
| **5** | 서버가 변경을 밀어 줍니다 | 다른 사용자의 변경이 곧바로 보입니다 |

**본 저장소는 2단계입니다.** 조회는 라우트 스코프의 `httpResource` 가 갖고(3.1절), 변경이 성공하면 명령을 부른 쪽이 `reload()` 로 같은 조회를 다시 일으킵니다(4.1절).

**3단계부터 캐시가 생기므로 낡은 사본을 보여 주는 것을 감수합니다.** 1·2단계는 들고 있는 사본이 없어 낡은 것을 보여 줄 수 없습니다 — 가장 단순한 단계가 가장 정확하며, 위로 올라가며 사는 것은 속도이고 파는 것은 정확성입니다.

4단계는 갱신 시점의 판정을 도구에 넘기므로 그 판정이 옳은지를 검토로 확인할 수 없게 됩니다. 5단계는 연결이 끊긴 동안의 처리를 새로 정해야 합니다.

3단계 이상의 도입 조건은 6절이 갖습니다.

## 2. 데이터 접근의 형태

**컴포넌트는 Mock 데이터를 하드코딩하거나 HTTP 호출을 직접 구현하지 않습니다.** 데이터 접근은 `api` 세그먼트의 서비스가 갖습니다.

구간마다 형태가 다릅니다.

| 구간 | 조회 | 명령 |
| :--- | :--- | :--- |
| **프로토타입** | 인젝션 토큰 뒤의 Mock 구현 | 같은 Mock 구현 |
| **연동 이후** | `httpResource` 를 든 서비스(3.1절) | 같은 서비스의 `HttpClient` 메서드(4.1절) |

프로토타입 구간의 인터페이스는 [프로세스](../../../../docs/process.md) 2단계의 요구사항입니다. Mock 구현이 인터페이스를 구현하고, 그 타입 정의가 백엔드 API 계약의 입력이 됩니다. 백엔드가 붙으면 생성 타입이 그 자리를 대체하며 **인터페이스와 Mock 은 전환과 함께 걷힙니다.** 절차와 근거는 [14. API 계약 소비](14-api-contract.md) 4절이 원본입니다.

## 3. 서버 상태 조회

### 3.1 조회의 수단

조회는 `httpResource` 로 통일합니다. **화면 진입에 필수인 데이터도 같습니다.** 진입 필수인가는 수단이 아니라 **누가 드는가**(3.2절)와 **대기를 어디에 표현하는가**를 정합니다.

| 조회 | 소유 | 대기 표현 |
| :--- | :--- | :--- |
| **화면 진입에 필수** | 라우트 스코프의 조회 상자 (3.2절) | 최초 조회(`loading`)에 화면이 베일을 배치 |
| **필수가 아님** | 쓰는 화면의 `api` 세그먼트 | 해당 영역 안에서 표시 |

리졸버(`ResolveFn`)를 조회 수단으로 쓰지 않습니다. 대기와 실패가 라우터 뒤로 들어가 화면이 볼 신호가 없고, 재조회 수단이 네비게이션뿐이라 변경 뒤 갱신(4.1절)마다 라우터를 거쳐야 합니다. `httpResource` 는 대기·실패가 `status` 신호로 오고 `loading` 과 `reloading` 의 구분(3.3절)이 프레임워크에서 나옵니다.

리졸버가 사는 것은 "데이터를 받은 뒤 화면을 그리므로 반쯤 채워진 화면이 원천 차단된다"입니다. 그 성질은 포기하지 않습니다. 조회가 끝나기 전에는 빈 안내를 내지 않고 최초 조회를 베일이 덮으므로, 같은 결과를 화면 층에서 얻습니다. 세부 규칙과 층별 적용 경계는 [10. 로딩 전략](10-loading.md)이 원본입니다.

```ts
// entities/task/api/task-list.ts — 화면 진입에 필수. 라우트 providers 에 등록합니다
@Injectable()
export class TaskList {
  private readonly resource = httpResource<readonly Task[]>(() => ENDPOINTS.tasks);

  readonly tasks = computed(() => (this.resource.hasValue() ? this.resource.value() : []));
  readonly status = this.resource.status;

  reload(): void {
    this.resource.reload();
  }
}
```

```ts
// pages/task-detail/api/comments.ts — 접힌 패널을 펼칠 때 조회
export function injectComments(id: Signal<string>) {
  return httpResource<CommentListResponse>(() => `/api/tasks/${id()}/comments`);
}
```

외부 상태 라이브러리 도입은 6절의 조건을 충족할 때만 검토합니다.

### 3.2 소유와 수명

진입 필수 조회는 **그 구역을 감싸는 라우트 정의의 `providers` 에 등록한 서비스**가 듭니다. `providedIn: 'root'` 를 쓰지 않습니다. 근거는 [02. 패키지 배치](02-package-structure.md) 7.5절에 있습니다.

라우트 깊이가 곧 수명입니다. 구역을 떠나면 서비스가 파괴되어 낡은 사본이 남지 않고, 하위 화면들이 한 인스턴스를 공유하므로 같은 데이터를 화면마다 다시 요청하지 않습니다.

**정적 생성 경로에서는 요청을 보내지 않습니다.** `httpResource` 는 서버 렌더 중에도 돌고, 정적 생성은 백엔드 없이 도는 빌드 단계라 요청을 보내면 프리렌더가 응답을 기다리다 끊깁니다. 요청 계산식이 `isPlatformServer` 판정으로 `undefined` 를 돌려주면 그 요청은 나가지 않습니다.

### 3.3 httpResource 의 상태 해석

`ResourceStatus` 는 여섯 값을 가집니다.

| 값 | 의미 | 화면 처리 |
| :--- | :--- | :--- |
| `idle` | 요청이 아직 시작되지 않음 | 아무것도 표시하지 않습니다 |
| `loading` | 최초 조회 또는 요청 파라미터 변경 | 진입 필수 조회면 베일, 보조 조회면 해당 영역에 인디케이터 |
| `reloading` | `reload()` 호출로 재조회 중 | **이전 값을 유지한 채** 갱신 표시만 겹칩니다. 베일 비대상 |
| `resolved` | 조회 완료 | 값을 표시합니다 |
| `error` | 조회 실패 | 에러 표시. 규칙은 [15. 예외 · 에러 표시 · 로깅](15-error-handling.md) |
| `local` | 로컬에서 값을 설정함 | |

`loading` 과 `reloading` 을 구분해서 다루어야 합니다. 둘을 같은 분기로 처리하면 재조회 때마다 영역이 비었다가 다시 그려집니다.

**스켈레톤을 사용하지 않습니다.** 근거는 [10. 로딩 전략](10-loading.md) 1절에 있습니다.

### 3.4 조회의 소유 위치

조회 함수의 배치는 [02. 패키지 배치](02-package-structure.md) 3절의 판정 트리를 따릅니다. 결과만 옮기면 다음과 같습니다.

| 조회의 성격 | 위치 |
| :--- | :--- |
| 라우트 스코프의 진입 필수 조회 | `entities/<도메인>/api/`. 목록과 상세가 같은 상자를 봅니다 |
| 한 화면에서만 쓰는 보조 조회 | `pages/<화면>/api/` |
| 도메인 무관 CRUD 헬퍼 | `shared/api/` |

라우트 스코프 서비스는 `app/app.routes.ts` 가 즉시 임포트하므로 초기 번들에 들어갑니다. **HTTP 호출만 담고 변환 로직을 넣지 않으며**, 배럴이 아니라 전용 진입점으로 내보냅니다. 배럴을 즉시 임포트와 지연 임포트가 함께 쓰면 지연이 무효가 되기 때문이며, 근거는 [01. 개발 환경](01-dev-environment.md) 7절에 있습니다.

같은 화면 안의 컴포넌트 둘이 같은 데이터를 필요로 하면 **각각 조회하지 않습니다.** 라우트 스코프의 한 인스턴스를 보거나 입력으로 전달받습니다. `httpResource` 는 요청 중복 제거를 제공하지 않으므로 인스턴스 두 개는 요청 두 번을 뜻합니다.

## 4. 명령과 무효화

### 4.1 명령

데이터를 변경하는 요청은 `httpResource` 를 쓰지 않습니다. `httpResource` 는 읽기 전용이며 요청이 바뀔 때 진행 중인 작업을 중단하므로, 변경 요청에 사용하면 중도 취소될 수 있습니다.

변경은 `HttpClient` 를 직접 사용하고 완료 후 관련 조회를 무효화합니다.

**명령은 그 조회를 든 서비스가 함께 갖습니다.** 조회 하나와 그것을 무효화하는 명령들이 한 클래스에 있으며, 명령은 성공한 뒤 자기 리소스의 `reload()` 를 부릅니다. 무효화가 클래스 안에서 끝나므로 호출부가 재조회를 기억하지 않습니다. 실패하면 예외가 호출부로 나가고 재조회는 일어나지 않습니다.

```ts
async setCompleted(id: string, completed: boolean): Promise<void> {
  await this.patch(ENDPOINTS.taskCompletion(id), { completed });
  this.resource.reload();
}
```

**조회 없이 명령만 쓰는 호출부가 생기면 그 명령을 별도 서비스로 떼어냅니다.** `httpResource` 는 인스턴스 생성 시점에 요청을 내므로, 합친 서비스를 명령 때문에 주입하면 필요 없는 조회가 함께 나갑니다. 로그인·가입 화면이 인증 명령만 쓰고 `/me` 조회는 쓰지 않는 것이 이 경우이며, 그래서 인증 명령은 분리된 서비스에 있습니다.

떼어낼 조건은 **호출부의 존재**이지 성격의 차이가 아닙니다. "명령은 상태가 없으니 다른 상자" 는 배치 근거가 되지 않습니다. 나누면 주입이 둘로 늘고 무효화를 호출부가 조율해야 하는데, 그 대가를 지불할 이유가 실제 호출부로 확인될 때만 나눕니다.

계층이 갈려 조회를 직접 부를 수 없을 때는 4.2절의 신호를 씁니다.

```ts
// features/task-complete/api/complete.ts
export async function completeTask(id: string): Promise<void> {
  await lastValueFrom(inject(HttpClient).post<void>(`/api/tasks/${id}/complete`, {}));
  inject(InvalidationBus).emit('task');
}
```

### 4.2 무효화 신호

변경을 수행하는 곳(`features`)과 조회를 소유하는 곳(`pages`)은 계층이 달라 서로를 임포트할 수 없습니다. `features` 가 `pages` 를 참조하는 것은 상위 계층 참조이므로 금지입니다.

이를 해소하기 위해 **무효화 신호를 `shared` 에 둡니다.** 신호는 문자열 키이므로 계층 참조가 발생하지 않습니다.

```ts
// shared/api/invalidation.ts
@Injectable({ providedIn: 'root' })
export class InvalidationBus {
  private readonly ticks = signal(new Map<string, number>());

  emit(key: string): void {
    this.ticks.update((m) => new Map(m).set(key, (m.get(key) ?? 0) + 1));
  }

  tick(key: string): Signal<number> {
    return computed(() => this.ticks().get(key) ?? 0);
  }
}
```

조회 측은 이 신호를 요청 계산식에 포함시켜 구독합니다.

```ts
const tick = inject(InvalidationBus).tick('task');
const list = httpResource<TaskListResponse>(() => {
  tick();                                    // 신호가 바뀌면 재요청합니다
  return `/api/tasks?page=${page()}`;
});
```

무효화 키는 도메인 단위로 정의하고 `shared/api/invalidation-keys.ts` 에 상수로 모읍니다. 문자열을 호출부에 흩뿌리면 오타를 검출할 수 없습니다.

### 4.3 낙관적 업데이트

기본적으로 **사용하지 않습니다.** 서버 응답을 기다린 뒤 조회를 무효화하는 것이 기본 흐름입니다.

낙관적 업데이트는 실패 시 되돌리는 경로와 그 사이에 발생한 다른 변경을 조정하는 경로를 함께 만들어야 합니다. 그 복잡도를 감수할 근거가 측정으로 확인된 화면에서만 적용하며, 적용 시 결정 기록으로 사유를 남깁니다.

## 5. 클라이언트 상태와 URL 상태

### 5.1 클라이언트 상태

화면에서만 의미를 갖는 값입니다. 선택된 탭, 열린 아코디언, 편집 중인 임시 입력값이 해당합니다.

**그 값을 사용하는 최소 범위가 소유합니다.** 컴포넌트 하나만 쓰면 그 컴포넌트의 `signal` 이고, 슬라이스 여러 컴포넌트가 쓰면 슬라이스의 `model` 세그먼트입니다. 전역 스토어에 올리는 것을 금지합니다.

### 5.2 URL 상태

다음은 **반드시** URL 쿼리 파라미터에 둡니다.

- 목록의 필터 조건
- 정렬 기준과 방향
- 페이지 번호와 크기
- 탭이나 단계 중 현재 위치가 공유·북마크되어야 하는 것

새로고침·뒤로가기·링크 공유가 별도 구현 없이 동작하며 상태 복원 코드를 작성할 필요가 없습니다.

세부 규칙은 [08. 라우팅과 네비게이션](08-routing.md)이 원본입니다.

## 6. 외부 상태 라이브러리 도입 조건

캐시와 무효화는 1.1절의 3단계이며 그것을 손으로 짜지 않습니다. TanStack Query 등 서버 상태 라이브러리는 다음이 **측정으로 확인된 뒤에만** 검토합니다.

| 조건 | 확인 방법 |
| :--- | :--- |
| 동일 데이터의 중복 요청이 실제로 발생함 | 네트워크 탭에서 같은 요청이 반복되는지 확인 |
| 화면 전환 시 재조회 지연이 사용자에게 체감됨 | 목록에서 상세로 갔다 돌아올 때의 지연 측정 |
| 무효화 대상이 도메인 키로 표현하기 어려울 만큼 복잡해짐 | 무효화 키가 열 개를 넘고 상호 의존이 생김 |

도입을 결정하면 결정 기록으로 남깁니다. Angular 용 패키지가 실험 단계이면 마이너·패치에서도 파괴적 변경이 예고되므로 **패치 수준까지 버전을 고정합니다.**

## 7. 금지 사항

| 금지 | 사유 |
| :--- | :--- |
| 컴포넌트가 Mock 데이터나 HTTP 호출 직접 보유 | 백엔드 연동 시 광범위한 코드 수정이 필요해집니다 |
| 조회 결과를 `signal` 에 복사해 직접 수정 | 서버와 화면의 불일치를 검출할 수 없습니다 |
| `httpResource` 로 변경 요청 수행 | 읽기 전용이며 진행 중 요청을 중단합니다 |
| 같은 화면에서 같은 데이터를 두 번 조회 | 요청 중복 제거가 없어 그대로 두 번 나갑니다 |
| 조회가 끝나기 전에 빈 안내 노출 | 없는 것과 아직 모르는 것이 같은 화면이 됩니다 |
| 조회를 쓰지 않는 호출부가 있는데 명령을 합쳐 둠 | 명령만 필요한 곳에서 조회 요청이 함께 나갑니다 |
| 라우트 스코프 조회 서비스에 변환 로직 포함 | 초기 번들에 계산 로직이 포함됩니다 |
| 무효화 키 문자열을 호출부에 직접 기재 | 오타를 검출할 수 없습니다 |
| 필터·페이지 상태를 컴포넌트 `signal` 에 보관 | 새로고침과 뒤로가기에서 소실됩니다 |
| 전역 스토어에 화면 전용 상태 보관 | 화면을 떠나도 상태가 남습니다 |
