# 결정-0001: 시각 언어를 아키텍처 문서 밖에 두고 DESIGN.md 가 소유한다

- 상태: 승인됨
- 날짜: 2026-08-17
- 관련 문서: [참조 아키텍처 진입점](../index.md), [DESIGN.md](../../design/DESIGN.md)

## 맥락

이 저장소는 프로젝트를 넘나들며 축적되는 참조 아키텍처를 만드는 것이 목적입니다. 파생 프로젝트마다 시각 언어가 달라지지만 구조와 규약은 그대로 물려받습니다.

선행 저장소는 디자인 시스템 문서 하나가 두 가지를 함께 담았습니다. 헤드리스 층과 시각 층의 분리, 토큰의 원본 위치, 임의 색상값 금지 같은 **기술 규약**과, 팔레트·곡률·표면 처리 같은 **시각 언어**가 같은 문서에 있었습니다.

그 구성에서 문제가 두 번 드러났습니다. 첫째, 시각 언어를 교체할 때마다 아키텍처 문서를 고치게 되어 규약과 취향의 변경 이력이 섞였습니다. 둘째, 참조 아키텍처가 특정 취향을 갖게 되어 파생 프로젝트가 그것을 물려받을지 판단할 근거가 없었습니다.

동시에 분리가 실제로 가능하다는 증거도 나왔습니다. 선행 저장소가 팔레트를 통째로 교체하면서 컴포넌트 코드를 한 줄도 수정하지 않았습니다.

또 하나의 전제가 생겼습니다. DESIGN.md 는 Google Labs 가 발행한 공개 규격이며, YAML 프런트매터에 기계 판독 토큰을, 마크다운 본문에 사람 판독 근거를 담습니다. 규격은 "토큰이 규범적 값이고 산문은 그것을 적용하는 맥락을 제공한다"고 정의합니다.

## 검토한 대안

### 대안 1: 아키텍처 문서 하나가 전부 소유

| 구분 | 내용 |
| :--- | :--- |
| **장점** | 문서가 하나여서 찾을 자리가 명확합니다. 규약과 값이 붙어 있어 맥락이 끊기지 않습니다 |
| **단점** | 시각 언어를 바꿀 때마다 아키텍처 문서를 고치게 되어 변경 이력이 섞입니다. 파생 프로젝트가 취향까지 물려받습니다 |
| **기각 사유** | 참조 아키텍처의 목적과 충돌합니다. 프로젝트마다 다시 정할 것과 넘나들며 유지될 것을 한 문서에 두면 그 경계가 사라집니다 |

### 대안 2: DESIGN.md 를 값의 유일한 원본으로 두고 CSS 를 생성물로 취급

| 구분 | 내용 |
| :--- | :--- |
| **장점** | 단일 원본이 명확합니다. 규격의 정의에 정확히 맞고 외부 도구가 그대로 소비할 수 있습니다 |
| **단점** | 생성 파이프라인을 하나 더 유지합니다. 색 하나를 바꿀 때도 문서를 먼저 고쳐야 하므로 프로토타입 루프가 느려집니다 |
| **기각 사유** | 프로세스의 전역 규칙이 "표면 변경(문구·색·간격)은 문서를 거치지 않는다"를 명시하고 있으며, 그 예외가 없으면 프로토타입 루프가 죽는다고 적혀 있습니다. 대상 플랫폼이 웹 하나여서 다중 내보내기의 값도 실현되지 않습니다 |

### 대안 3: 그릇과 하한은 아키텍처, 값과 근거는 DESIGN.md (채택)

## 결정

**시각 언어를 아키텍처 문서 밖으로 분리하고 `web/docs/design/DESIGN.md` 가 소유합니다.**

경계는 "값이냐 규칙이냐"가 아니라 **"프로젝트마다 다시 정하는가"** 로 긋습니다.

| 아키텍처가 소유 | DESIGN.md 가 소유 |
| :--- | :--- |
| 헤드리스 층과 시각 층의 분리, 컴포넌트 사본 정책 | — |
| 토큰의 원본 위치, 이름 집합, 등록 방법, 추가 절차 | 각 이름에 담기는 값 |
| 임의 색상값 금지, 클래스 사용 범위, 쌓임 순서 관리 | — |
| 대비 4.5:1, 터치 타겟 44×44, 입력 글자 16px 하한 | — |
| — | 팔레트, 곡률, 표면 처리, 타이포, 모션 성격 |

**토큰 이름 집합이 둘 사이의 계약입니다.** DESIGN.md 는 아키텍처가 고정한 이름을 전부 채워야 하며, 빠진 이름은 그 자리에서 드러납니다.

**값의 원본은 CSS 이고 DESIGN.md 는 규칙과 근거의 원본입니다.** 규격이 프런트매터를 규범적 값으로 정의하지만, 본 저장소는 프로토타입 루프를 지키기 위해 그 방향을 뒤집습니다. 프런트매터는 현재 값의 스냅숏이며 어긋나면 CSS 가 이깁니다.

**`components` 키를 비우고 `omitted` 에 사유를 남깁니다.** Atlassian 이 이 규격을 실측한 결과 DESIGN.md 가 기존 컴포넌트를 가져다 쓰는 대신 다시 그리는 경향이 확인되었습니다. 본 저장소는 컴포넌트 사본을 소유하는 구조여서 그 문제에 정면으로 노출됩니다. 컴포넌트의 시각 규칙은 본문 서술로만 담습니다.

**하한은 테스트가 강제합니다.** 대비 검증은 아키텍처가 소유하고 기준을 걸며, 파싱 대상은 DESIGN.md 가 채운 CSS 입니다. 디자인은 하한 위에서 자유롭고 아래로는 내려갈 수 없습니다.

## 결과

- 시각 언어 교체가 파일 한 장과 토큰 값 교체로 끝납니다. 아키텍처 문서와 컴포넌트 코드는 그대로입니다.
- 참조 아키텍처가 특정 취향을 갖지 않게 되어 파생 프로젝트가 자기 시각 언어를 갖습니다.
- 감수하는 것
  - **"값만 갈아끼운다"가 항상 성립하지 않습니다.** 기준 반경 변경은 파생 체계 전체를 움직이고, 초타원 곡률은 CSS 속성 추가이며, 종이 질감은 층위 결정을 포함하고, 반투명 표면은 새 토큰을 요구합니다. DESIGN.md 가 구조 변경을 요청하는 경로가 필요하며 그 요청이 승인되면 아키텍처 쪽이 함께 바뀝니다.
  - **프런트매터와 CSS 가 어긋날 수 있습니다.** 값이 두 곳에 존재하며 이것이 본 결정이 남기는 유일한 중복입니다. CSS 를 원본으로 못박아 판정 기준은 남겨 두지만, 동기화는 사람이 합니다.
  - **규격의 정의와 반대 방향을 택했습니다.** 규격을 그대로 소비하는 외부 도구에 이 저장소의 DESIGN.md 를 넣으면 최신이 아닐 수 있습니다.
- 명시적으로 기각한 것: 아키텍처 문서가 팔레트 값을 갖는 구성. 재론하지 않습니다.

## 재검토 조건

- **네이티브 앱이나 디자인 도구 동기화가 필요해질 때** — 다중 내보내기의 값이 실현되므로 대안 2를 다시 검토합니다. 토큰 이름을 이미 역할 기반으로 고정해 두었으므로 옮기는 작업이며 재설계가 아닙니다.
- **프런트매터와 CSS 의 어긋남이 실제로 문제를 일으켰을 때** — 생성 또는 검증 단계를 도입합니다.
- **DESIGN.md 규격이 alpha 를 벗어날 때** — 키 구성이 바뀌면 프런트매터를 맞춥니다.
